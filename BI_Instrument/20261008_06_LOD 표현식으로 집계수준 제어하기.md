# **1. LOD를 이해하려면 먼저 계산 수준을 알아야 한다**

> ## **1-1) 같은 Measure라도 View에 따라 결과가 달라진다**

Tableau의 기본 집계는 **현재 View에 어떤 Dimension이 포함되어 있는지**에 따라 계산 수준이 달라진다.

예를 들어 축구 GPS 데이터가 다음과 같다고 가정한다.

```text
player_id   position      match_id   hsr_distance_m
P001        Winger        M001            1,100
P001        Winger        M002              900
P002        Winger        M001              800
P003        Midfielder    M001              650
```

원본 데이터의 한 행은

```text
선수 × 경기
```

수준이다.

하지만 View에 `position`만 배치하고

```text
SUM([HSR Distance M])
```

을 사용하면 Tableau는 포지션 수준으로 집계한다.

[ Result ]

```text
Winger
= 1,100 + 900 + 800
= 2,800m

Midfielder
= 650m
```

반면 View에

```text
position
+
player_id
```

를 배치하면 집계 수준이 달라진다.

[ Result ]

```text
Winger

P001 → 2,000m
P002 →   800m

Midfielder

P003 →   650m
```

즉 같은 `SUM([HSR Distance M])`이라도 **View의 Dimension 조합이 바뀌면 계산 수준도 바뀐다.**

<br>

> ## **1-2) Level of Detail (LOD)이란?**

Level of Detail은 데이터를 **어떤 Dimension 조합을 기준으로 나누어 계산하는가**를 의미한다.

예를 들어 다음처럼 생각할 수 있다.

```text
View = Position
→ 포지션 수준

View = Position + Player
→ 포지션 × 선수 수준

View = Match + Player
→ 경기 × 선수 수준

View = Season + Match + Player
→ 시즌 × 경기 × 선수 수준
```

Dimension이 많이 추가될수록 일반적으로 더 세부적인 수준이 된다.

```text
Season
    ↓
Season + Match
    ↓
Season + Match + Player

Coarse
→
Fine
```

<br>

> ## **1-3) Granularity와 LOD의 관계**

`Granularity`와 `LOD`는 비슷한 의미로 사용되지만 문맥을 구분해서 이해하면 좋다.

| 개념 | 의미 |
| --- | --- |
| 원본 Data Grain | 원본 데이터 한 행이 나타내는 단위 |
| View LOD | 현재 View의 Dimension이 만드는 집계 단위 |
| LOD Expression | 계산에 사용할 Dimension 수준을 명시적으로 제어 |

예를 들어 GPS 원본 데이터의 Grain이

```text
Player × Match
```

라고 해도 View에서는

```text
Position
```

수준으로 집계할 수 있다.

LOD Expression을 사용하면 View가 `Position` 수준이어도 계산 자체는

```text
Player
```

수준으로 수행할 수 있다.

# **2. 왜 LOD Expression이 필요한가?**

> ## **2-1) View와 실제 계산 수준이 다를 수 있다**

다음 질문을 생각해보자.

```text
포지션별로
선수 1명당 평균 HSR은 얼마인가?
```

View에서 보고 싶은 수준은

```text
Position
```

이다.

하지만 계산 과정에서는 먼저

```text
Player
```

수준의 총 HSR이 필요하다.

예를 들어 Winger가 다음과 같다고 하자.

```text
P001

M001 → 1,100
M002 →   900

선수 총 HSR
= 2,000m


P002

M001 → 800

선수 총 HSR
= 800m
```

그다음 Winger 선수 평균을 계산해야 한다.

```text
2,000 + 800
─────────────
      2

= 1,400m
```

즉 계산 흐름은

```text
원본
Player × Match
    ↓
Player 수준 집계
    ↓
Position 수준 평균
```

이다.

현재 View만 이용한 단순 `AVG([HSR Distance M])`와는 의미가 다르다.

이처럼 **View 수준과 필요한 계산 수준이 다를 때 LOD Expression이 필요하다.**


<br><br>

# **3. LOD Expression의 기본 문법**

> ## **3-1) 기본 구조**

Tableau LOD Expression의 대표적인 문법은 다음과 같다.

```text
{
    FIXED | INCLUDE | EXCLUDE
    [Dimension]
    :
    Aggregate Expression
}
```

예:

```text
{ FIXED [Player ID] : SUM([HSR Distance M]) }
```

구조를 나누면

```text
FIXED
→ 계산 수준을 어떻게 정의할지

[Player ID]
→ 계산에 사용할 Dimension

:

SUM([HSR Distance M])
→ 해당 수준에서 수행할 집계
```

이다.

<br>

> ## **3-2) 여러 Dimension도 지정할 수 있다**

예를 들어 선수별 시즌 총 이동거리가 필요하다면

```text
{
    FIXED
    [Season],
    [Player ID]
    :
    SUM([Total Distance M])
}
```

처럼 여러 Dimension을 사용할 수 있다.

계산 수준은

```text
Season × Player
```

가 된다.

<br>

> ## **3-3) 세 가지 LOD**

Tableau에서 대표적으로 사용하는 LOD는 다음과 같다.

| LOD | 핵심 개념 |
| --- | --- |
| `FIXED` | 지정한 Dimension을 기준으로 계산 |
| `INCLUDE` | 현재 View에 Dimension을 추가하여 더 세부적으로 계산 |
| `EXCLUDE` | 현재 View의 Dimension을 계산 수준에서 제거 |

간단히 기억하면

```text
계산 수준 직접 지정
→ FIXED

현재보다 더 세부적으로
→ INCLUDE

현재보다 덜 세부적으로
→ EXCLUDE
```

이다.

# **4. FIXED - 계산 기준을 명시적으로 지정하기**

> ## **4-1) FIXED의 핵심**

`FIXED`는 **View에 존재하는 다른 Dimension을 기준으로 계산 수준을 정하지 않고, 식에 명시한 Dimension을 기준으로 계산**한다.

예를 들어

```text
{ FIXED [Player ID] : SUM([HSR Distance M]) }
```

은 View에

```text
Position
Match
Season
```

등이 존재하더라도 `[Player ID]`를 기준으로 총 HSR을 계산한다.

이를

```text
Player Total HSR
```

이라고 하자.

<br>

> ## **4-2) 축구 선수별 총 HSR**

원본:

```text
Player   Match   HSR

P001     M001    1100
P001     M002     900
P002     M001     800
P002     M002    1000
```

[ Tableau : code ] "선수별 총 고강도 주행거리 고정"

```text
{ FIXED [Player ID] :
    SUM([HSR Distance M])
}
```

[ Result ]

```text
P001
= 1,100 + 900
= 2,000m

P002
= 800 + 1,000
= 1,800m
```

이 계산 결과는

```text
Player
```

수준이다.

<br>

> ## **4-3) View가 Match 수준이어도 결과는 Player 수준**

View:

```text
Player
+
Match
```

라고 해도 FIXED 값은

```text
P001 M001 → 2,000
P001 M002 → 2,000

P002 M001 → 1,800
P002 M002 → 1,800
```

처럼 반복해서 보일 수 있다.

왜냐하면 계산 자체가

```text
Player
```

수준에서 이미 끝났기 때문이다.

즉,

```text
FIXED 계산 수준
<
View의 세부 수준
```

이면 동일한 FIXED 결과가 여러 Mark에 반복되어 나타날 수 있다.

# **5. FIXED 실무 예제 - 최초 기록과 기준값 만들기**

> ## **5-1) 선수별 최초 경기일**

선수별로 가장 처음 출전한 날짜를 구하고 싶다고 하자.

[ Tableau : code ] "선수별 최초 경기일"

```text
{ FIXED [Player ID] :
    MIN([Match Date])
}
```

데이터:

```text
P001   2026-03-01
P001   2026-03-15
P001   2026-04-02

P002   2026-02-20
P002   2026-03-10
```

[ Result ]

```text
P001 → 2026-03-01
P002 → 2026-02-20
```

이 값은

```text
선수별 최초 출전일
```

이라는 안정적인 기준값으로 사용할 수 있다.

<br>

> ## **5-2) 선수별 최고 스프린트 속도**

[ Tableau : code ] "선수별 시즌 최고속도"

```text
{ FIXED [Player ID] :
    MAX([Max Speed Kmh])
}
```

[ Result ]

```text
P001 → 34.8 km/h
P002 → 33.2 km/h
P003 → 35.1 km/h
```

이후 현재 경기 속도와 비교할 수도 있다.

```text
[Match Max Speed]
/
[Player Career Max Speed]
* 100
```

# **6. FIXED를 이용한 전체 대비 비율**

> ## **6-1) 전체 값을 기준으로 비교하고 싶을 때**

축구팀 전체 HSR 대비 각 포지션의 HSR 비율을 구한다고 하자.

전체 HSR은 View에 Position이 있더라도 변하지 않는 하나의 기준값이어야 한다.

[ Tableau : code ] "전체 팀 HSR"

```text
{ FIXED :
    SUM([HSR Distance M])
}
```

Dimension을 지정하지 않은 FIXED는 전체 데이터 수준의 집계를 계산할 수 있다.

예를 들어

```text
Winger HSR      = 3,000
Midfielder HSR  = 2,000
Defender HSR    = 1,000
```

이면

```text
Team HSR
= 6,000m
```

이다.

<br>

> ## **6-2) 전체 대비 포지션 비율**

[ Tableau : code ] "전체 팀 HSR 대비 포지션 HSR 비율"

```text
SUM([HSR Distance M])
/
ATTR(
    { FIXED :
        SUM([HSR Distance M])
    }
)
```

Winger의 경우

```text
3,000
─────
6,000

= 50%
```

[ Result ]

```text
Winger       50.0%
Midfielder   33.3%
Defender     16.7%
```

`FIXED`로 전체 기준값을 만든 뒤 현재 View 수준의 값을 비교하는 대표적인 활용이다.

# **7. INCLUDE - View보다 더 세부적인 수준에서 먼저 계산**

> ## **7-1) INCLUDE의 핵심**

`INCLUDE`는 **현재 View에 없는 Dimension을 계산 수준에 추가**한다.

즉

```text
현재 View LOD
+
지정한 Dimension
```

수준에서 먼저 계산한다.

그 계산 결과를 View 수준에서 다시 집계할 수 있다.

대표적인 사용 상황은

```text
현재 화면
→ Position

필요한 중간 계산
→ Position × Player
```

이다.

<br>

> ## **7-2) 포지션별 선수 평균 HSR**

View에는

```text
Position
```

만 있다고 하자.

하지만 선수별 HSR을 먼저 계산해야 한다.

[ Tableau : code ] "현재 View에 선수 수준을 추가한 총 HSR"

```text
{ INCLUDE [Player ID] :
    SUM([HSR Distance M])
}
```

원본:

```text
Position   Player   Match   HSR

Winger     P001     M001    1100
Winger     P001     M002     900
Winger     P002     M001     800
```

INCLUDE 내부 계산:

```text
Winger × P001
→ 2,000

Winger × P002
→ 800
```

이 Field를 View에서

```text
AVG()
```

로 집계하면

```text
2,000 + 800
─────────────
      2

= 1,400m
```

[ Result ]

```text
Winger 평균 선수 HSR
= 1,400m
```

즉 INCLUDE의 핵심 흐름은

```text
View LOD
    ↓
Dimension 추가
    ↓
더 세부적인 수준에서 계산
    ↓
View 수준으로 다시 Aggregate
```

이다.


<br><br>

# **8. INCLUDE는 View에 따라 결과가 변할 수 있다**

> ## **8-1) INCLUDE는 View Context를 사용한다**

다음 계산을 생각하자.

```text
{ INCLUDE [Player ID] :
    SUM([HSR Distance M])
}
```

View가

```text
Position
```

이라면 내부 계산 수준은

```text
Position × Player
```

이다.

하지만 View가

```text
Position + Match
```

라면 계산 수준은

```text
Position × Match × Player
```

가 된다.

즉 INCLUDE는 FIXED와 달리 **현재 View의 Dimension을 함께 사용한다.**

따라서 View의 구조가 달라지면 INCLUDE 결과도 달라질 수 있다.

<br>

> ## **8-2) FIXED와 INCLUDE 차이**

| 항목 | FIXED | INCLUDE |
| --- | --- | --- |
| View Dimension 참조 | 기본적으로 계산 수준 결정에 사용하지 않음 | 사용 |
| 지정 Dimension | 계산 수준 자체를 지정 | View LOD에 추가 |
| View 변경 영향 | 상대적으로 적음 | 큼 |
| 대표 활용 | 고정 기준값 | 세부 수준 계산 후 재집계 |

```text
FIXED
→ 계산 기준을 직접 정한다.

INCLUDE
→ 현재 View에 계산 기준을 더한다.
```


<br><br>

# **9. EXCLUDE - View에서 특정 Dimension을 제거**

> ## **9-1) EXCLUDE의 핵심**

`EXCLUDE`는 현재 View의 Level of Detail에서 지정한 Dimension을 제거한다.

예를 들어 View가

```text
Position + Match
```

라고 하자.

현재 기본 계산:

```text
SUM([Player Load])
```

는

```text
Position × Match
```

수준에서 계산된다.

그런데 Match를 제외하고 Position 전체 기준값이 필요하다면

```text
{ EXCLUDE [Match ID] :
    SUM([Player Load])
}
```

를 사용할 수 있다.

<br>

> ## **9-2) 포지션 총 부하를 경기별 행에 표시**

데이터:

```text
Position   Match   Load

Winger     M001     620
Winger     M002     680
Winger     M003     600
```

현재 View:

```text
Position + Match
```

기본 `SUM([Load])`:

```text
M001 → 620
M002 → 680
M003 → 600
```

[ Tableau : code ] "경기 Dimension을 제외한 포지션 전체 Load"

```text
{ EXCLUDE [Match ID] :
    SUM([Player Load])
}
```

[ Result ]

```text
Winger 전체

620 + 680 + 600
= 1,900
```

View에는

```text
M001 → 1,900
M002 → 1,900
M003 → 1,900
```

처럼 표시될 수 있다.

즉 각 경기 값을 **포지션 전체 기준값과 비교**할 수 있다.


<br><br>

# **10. EXCLUDE를 이용한 기준 대비 비교**

> ## **10-1) 경기 Load가 포지션 평균에서 얼마나 벗어났는가?**

View가

```text
Position
+
Match
```

일 때 경기별 Load와 Position 전체 평균을 비교하고 싶다고 하자.

먼저 Position 수준 평균을 만든다.

[ Tableau : code ] "Match 수준을 제외한 Position 평균 Load"

```text
{ EXCLUDE [Match ID] :
    AVG([Player Load])
}
```

그다음

[ Tableau : code ] "포지션 기준 대비 현재 경기 부하 차이"

```text
AVG([Player Load])
-
AVG([Position Baseline Load])
```

처럼 비교할 수 있다.

예:

```text
현재 경기 Load
= 720

Position 평균
= 640
```

[ Result ]

```text
720 - 640
= +80
```

즉

```text
현재 경기에서
포지션 평균보다 80 높은 Load
```

로 해석할 수 있다.

# **11. FIXED / INCLUDE / EXCLUDE 한 번에 비교**

> ## **11-1) 현재 View가 Position이라고 가정**

```text
현재 View
→ Position
```

이라고 하자.

| Expression | 계산 수준 |
| --- | --- |
| `{ FIXED [Player ID] : SUM([HSR]) }` | Player |
| `{ INCLUDE [Player ID] : SUM([HSR]) }` | Position × Player |
| `{ EXCLUDE [Position] : SUM([HSR]) }` | Position을 제외한 상위 수준 |

가장 중요한 차이는

```text
FIXED
→ View를 기준으로 더하거나 빼는 개념이 아님

INCLUDE
→ View + Dimension

EXCLUDE
→ View - Dimension
```

이다.

<br>

> ## **11-2) 선택 기준**

```text
View와 관계없이
선수별 값을 고정하고 싶다.
→ FIXED
```

```text
현재 View보다
더 세부적으로 계산한 뒤
다시 평균 등을 내고 싶다.
→ INCLUDE
```

```text
현재 View에서
특정 Dimension을 무시한
더 큰 기준값이 필요하다.
→ EXCLUDE
```


> ## **12-3) 야구**

# **13. LOD와 Filter의 Order of Operations**

> ## **13-1) 왜 Filter를 했는데 FIXED 값이 안 바뀔까?**

LOD를 사용할 때 가장 자주 혼동하는 부분이다.

예를 들어 선수별 최초 경기일을 다음과 같이 계산했다고 하자.

```text
{ FIXED [Player ID] :
    MIN([Match Date])
}
```

P001의 경기 기록:

```text
2025-11-20
2026-02-01
2026-03-15
```

선수 최초 경기일은

```text
2025-11-20
```

이다.

그런데 View에서

```text
Year = 2026
```

이라는 일반 Dimension Filter를 적용했다고 하자.

View에는

```text
2026-02-01
2026-03-15
```

만 보인다.

그럼에도 FIXED 결과는

```text
2025-11-20
```

일 수 있다.

이는 FIXED LOD가 일반 Dimension Filter보다 먼저 평가되기 때문이다.

# **14. LOD 중심으로 보는 Tableau 실행 순서**

> ## **14-1) 핵심 실행 순서**

Tableau의 전체 Order of Operations에는 더 많은 단계가 존재하지만 LOD 학습에서는 다음 흐름이 중요하다.

```text
Extract Filter
        ↓
Data Source Filter
        ↓
Context Filter
        ↓
FIXED LOD
        ↓
Dimension Filter
        ↓
INCLUDE / EXCLUDE LOD
        ↓
Measure Filter
        ↓
Table Calculation Filter
```

즉

```text
FIXED
→ 일반 Dimension Filter보다 먼저

INCLUDE / EXCLUDE
→ 일반 Dimension Filter보다 뒤
```

에서 평가된다.

<br>

> ## **14-2) 중요 비교**

| Filter / Calculation | 일반적인 상대 순서 |
| --- | --- |
| Extract Filter | 먼저 |
| Data Source Filter | 먼저 |
| Context Filter | FIXED보다 먼저 |
| FIXED LOD | Dimension Filter보다 먼저 |
| Dimension Filter | INCLUDE / EXCLUDE보다 먼저 |
| INCLUDE / EXCLUDE | Dimension Filter 후 |
| Measure Filter | 이후 |
| Table Calculation Filter | 매우 후반 |

따라서 단순히

```text
Filter를 걸었다.
```

라고 해서 모든 계산식이 동일한 방식으로 영향을 받는 것은 아니다.

```text
하지만
```

# **16. Context Filter - FIXED의 계산 범위를 바꾸기**

> ## **16-1) 2026년 안에서 최초 경기일을 계산하려면?**

분석 질문이

```text
선수의 생애 최초 경기일
```

이 아니라

```text
2026년에 출전한 경기 중
가장 첫 경기일
```

이라면 결과가 달라져야 한다.

Year Filter를 Context Filter로 설정하면

```text
Year = 2026
        ↓
Context Filter
        ↓
FIXED
```

순서가 된다.

처리 흐름:

```text
전체 데이터
        ↓
Context Filter

2026년만 유지
        ↓
FIXED

MIN(Match Date)
```

P001 데이터:

```text
2026-02-01
2026-03-15
```

[ Result ]

```text
2026-02-01
```

<br>

> ## **16-2) Context Filter는 단순히 FIXED용 기능이 아니다**

Context Filter는 Tableau의 Filter 실행 순서에서 Context를 만드는 기능이다.

LOD에서는 특히

```text
일반 Dimension Filter
→ FIXED보다 늦음

Context Filter
→ FIXED보다 빠름
```

이라는 차이가 중요하다.

따라서

```text
FIXED가 Filter를 무조건 무시한다.
```

라고 외우는 것보다

```text
어떤 Filter가 FIXED보다
먼저 실행되는가?
```

를 이해하는 것이 정확하다.

# **17. INCLUDE / EXCLUDE와 Filter**

> ## **17-1) 일반 Dimension Filter의 영향을 받는다**

INCLUDE와 EXCLUDE는 일반 Dimension Filter보다 뒤에서 평가된다.

따라서 예를 들어

```text
Season = 2026
```

이라는 Dimension Filter가 있다면

```text
{ INCLUDE [Player ID] :
    SUM([HSR Distance M])
}
```

는 일반적으로 2026년으로 필터링된 범위에서 계산된다.

흐름:

```text
전체 데이터
    ↓
Dimension Filter
2026년
    ↓
INCLUDE
Player 수준 계산
```

<br>

> ## **17-2) FIXED와 비교**

```text
일반 Dimension Filter
        ↓
FIXED

X
```

FIXED가 먼저 계산된다.

반면

```text
Dimension Filter
        ↓
INCLUDE / EXCLUDE

O
```

이다.

이 차이가 LOD 분석에서 매우 중요하다.

# **18. 실무형 종합 예제 - 축구 선수 시즌 Load 분석**

> ## **18-1) 분석 질문**

퍼포먼스 코치가 다음 내용을 요청했다고 가정한다.

```text
1. 선수별 시즌 총 HSR은?

2. 포지션별 선수 평균 HSR은?

3. 경기별 HSR이 포지션 전체 기준에서
   어느 정도 차이가 나는가?

4. 특정 시즌만 선택하면
   모든 계산 기준도 해당 시즌으로 바뀌어야 하는가?
```

각 질문은 서로 다른 LOD가 필요할 수 있다.

<br>

> ## **18-2) 선수별 시즌 총 HSR**

[ Tableau : code ] "선수별 시즌 총 HSR"

```text
{ FIXED [Season], [Player ID] :
    SUM([HSR Distance M])
}
```

```text
Season 2026

P001 → 18,400m
P002 → 15,900m
P003 → 16,750m
```

<br>

> ## **18-3) 포지션별 선수 평균 HSR**

View:

```text
Position
```

계산:

[ Tableau : code ] "Position View에 선수 수준을 포함"

```text
{ INCLUDE [Player ID] :
    SUM([HSR Distance M])
}
```

View에서 Aggregation:

```text
AVG()
```

예를 들어 Winger:

```text
P001 → 18,400
P002 → 15,600
P003 → 17,000
```

계산:

```text
18,400 + 15,600 + 17,000
─────────────────────────
             3
```

[ Result ]

```text
17,000m
```

<br>

> ## **18-4) 경기별 Load를 포지션 전체 기준과 비교**

View:

```text
Position
+
Match
```

Position 수준 HSR:

[ Tableau : code ] "Match Dimension을 제외한 Position HSR"

```text
{ EXCLUDE [Match ID] :
    SUM([HSR Distance M])
}
```

이 값을 활용해 경기 비중 등을 계산할 수 있다.

```text
현재 경기 HSR
──────────────
포지션 전체 HSR
```

<br>

> ## **18-5) 시즌 Filter가 FIXED에 반영되어야 한다면**

만약

```text
[Season] = 2026
```

가 FIXED 계산에 반드시 먼저 반영되어야 하는데 LOD 내부에 `[Season]`을 명시하지 않았다면, 필요에 따라 시즌 Filter를 Context로 설정하는 방법을 고려할 수 있다.

하지만 무조건 Context Filter로 바꾸는 것이 아니라

```text
계산 자체를

{ FIXED [Season], [Player ID] : ... }

로 설계할 수 있는가?
```

도 먼저 검토해야 한다.

LOD 설계와 Filter 설계는 서로 연결되어 있다.

# **21. Table-Scoped LOD**

> ## **21-1) Dimension 없이 전체 기준을 계산할 수도 있다**

LOD Expression에는 `FIXED / INCLUDE / EXCLUDE`를 쓰지 않는 Table-Scoped 형태도 존재한다.

예:


이는 개념적으로


와 같은 전체 Table 수준의 값을 만들 수 있다.

예를 들어 Dataset 전체의 최초 경기일을 계산하면

```text
{ MIN([Match Date]) }
```

을 사용할 수 있다.

Dimension을 지정하지 않은 전체 기준값을 만들 때 이해해두면 좋다.

# **22. LOD 결과가 View에 표시될 때 다시 집계될 수 있다**

> ## **22-1) LOD 하나로 모든 계산이 끝나는 것은 아니다**

LOD Expression이 반환한 값이 View보다 더 세부적인 Grain을 가지고 있다면 Tableau는 그 결과를 View 수준에서 다시 Aggregate해야 할 수 있다.

예를 들어

```text
View
→ Position
```

인데

```text
{ FIXED [Player ID] :
    SUM([HSR Distance M])
}
```

은 Player 수준이다.

한 Position에 여러 Player가 있으므로 Tableau는

```text
SUM
AVG
MIN
MAX
```

등 어떤 방식으로 Player 수준 결과를 Position 수준으로 다시 집계할지 결정해야 한다.

예:

```text
AVG(
    { FIXED [Player ID] :
        SUM([HSR Distance M])
    }
)
```

즉 LOD를 사용할 때는 두 단계로 생각해야 한다.

```text
1. LOD 내부에서 어느 수준으로 계산하는가?

2. 그 결과를 현재 View에서 어떻게 다시 집계하는가?
```

# **23. FIXED / INCLUDE / EXCLUDE의 결과 특성**

> ## **23-1) FIXED 결과의 성격**

FIXED는 지정한 Dimension에 따라 계산되므로 View 구조가 변해도 해당 LOD 자체의 계산 기준은 유지된다.

다만

```text
Filter

Data 범위

LOD 결과의 View 재집계
```

등의 영향은 별도로 고려해야 한다.

<br>

> ## **23-2) INCLUDE / EXCLUDE 결과의 성격**

INCLUDE와 EXCLUDE는 현재 View Level of Detail을 기반으로 작동한다.

따라서 View에서 Dimension을 추가하거나 제거하면 계산 결과도 달라질 수 있다.

```text
FIXED
→ 지정 Dimension 중심

INCLUDE / EXCLUDE
→ View Context 중심
```

이라고 이해하면 좋다.


<br><br>

# **24. LOD와 Table Calculation을 혼동하지 않는다**

> ## **24-1) 계산 시점 자체가 다르다**

LOD Expression과 Table Calculation은 둘 다 집계 결과를 다루지만 동작 시점이 다르다.

| 구분 | LOD | Table Calculation |
| --- | --- | --- |
| 계산 기준 | Data / View Grain | View에 표시된 결과 |
| 대표 예 | 선수별 총매출 고정 | 누적합, 순위 |
| 실행 시점 | Query 단계 | View 결과 이후 |
| 대표 함수 | FIXED / INCLUDE / EXCLUDE | RUNNING_SUM / RANK |

예를 들어

```text
{ FIXED [Player ID] :
    SUM([Player Load])
}
```

는 선수 단위 집계 수준을 제어한다.

반면

```text
RUNNING_SUM(SUM([Player Load]))
```

는 View에 만들어진 집계 결과를 이용해 누적 계산한다.

```text
LOD
→ "어떤 Grain에서 계산?"

Table Calculation
→ "표시된 결과를 어떻게 다시 계산?"
```

으로 구분하면 이해하기 쉽다.


<br><br>

# **25. LOD를 사용하기 전에 먼저 기본 집계로 해결 가능한지 확인**

> ## **25-1) 모든 계산에 LOD가 필요한 것은 아니다**

다음 질문은 단순 집계로 충분하다.

```text
포지션별 총 HSR
```

View:

```text
Position
```

Measure:

```text
SUM([HSR Distance M])
```

이면 된다.

굳이

```text
{ FIXED [Position] :
    SUM([HSR Distance M])
}
```

을 사용할 필요가 없는 경우가 많다.

LOD는 특히

```text
View의 Grain
≠
필요한 계산 Grain
```

일 때 의미가 있다.

따라서

```text
기본 Aggregation
    ↓
해결 가능한가?
    │
    ├─ YES → 기본 집계
    │
    └─ NO
         ↓
     LOD 검토
```

순서가 좋다.

# **26. 자주 발생하는 LOD 실수**

> ## **26-1) FIXED를 View에서 보이는 값 그대로 고정한다고 생각한다**

FIXED는

```text
현재 화면에 표시된 숫자를 고정
```

하는 기능이 아니다.

정확하게는

```text
지정한 Dimension 수준에서
Aggregate Expression을 계산
```

한다.

<br>

> ## **26-2) INCLUDE는 단순히 Dimension을 추가하는 것에서 끝난다고 생각한다**

INCLUDE의 중요한 목적은

```text
더 세부적 Grain에서 계산
        ↓
현재 View Grain으로 재집계
```

이다.

예를 들어 고객별 매출을 먼저 계산한 뒤 지역별 고객 평균을 계산하는 형태이다.

<br>

> ## **26-3) EXCLUDE를 Filter라고 생각한다**

```text
{ EXCLUDE [Match ID] : ... }
```

은 Match 데이터를 삭제하는 것이 아니다.

현재 계산 Level of Detail에서

```text
Match ID Dimension의 영향을 제외
```

하는 것이다.

<br>

> ## **26-4) FIXED가 모든 Filter를 무시한다고 생각한다**

부정확한 기억:

```text
FIXED는 Filter를 무조건 무시한다.
```

정확한 이해:

```text
일반 Dimension Filter
→ FIXED 이후

Context Filter
→ FIXED 이전

Data Source / Extract Filter
→ FIXED 이전
```

이다.

<br>

> ## **26-5) Filter 문제를 모두 Context로 해결한다**

Context Filter는 유용하지만 무조건적인 해결책은 아니다.

먼저

```text
LOD 자체의 Dimension 설계가 올바른가?

현재 질문이 전체 기간 기준인가?

필터된 기간 기준인가?

FIXED 대신 INCLUDE / EXCLUDE가 적절한가?
```

를 검토해야 한다.

<br>

> ## **26-6) LOD 결과를 다시 어떻게 Aggregate하는지 확인하지 않는다**

LOD가 더 세부적인 수준을 반환한다면 View에서

```text
SUM
AVG
MIN
MAX
```

중 무엇으로 다시 Aggregate하는지에 따라 결과가 달라진다.

이 부분을 확인하지 않으면 계산 자체는 맞지만 최종 KPI가 잘못될 수 있다.

# **27. LOD 문제를 푸는 사고 순서**

> ## **27-1) 5단계로 생각하기**

LOD 문제를 만나면 다음 질문부터 한다.

```text
1. 원본 Data Grain은 무엇인가?

2. 현재 View LOD는 무엇인가?

3. 실제 계산해야 하는 Grain은 무엇인가?

4. 계산 Grain이 View보다
   독립적 / 세부적 / 상위 수준 중 무엇인가?

5. Filter가 계산보다
   먼저 적용되어야 하는가?
```

그다음 선택한다.

```text
독립적인 Dimension 기준
→ FIXED

View + 세부 Dimension
→ INCLUDE

View - 특정 Dimension
→ EXCLUDE
```

<br>

> ## **27-2) 흐름도**

```text
분석 질문
    ↓
현재 View LOD 확인
    ↓
필요 계산 LOD 확인
    ↓
두 수준이 같은가?
    │
    ├─ YES
    │    ↓
    │ 기본 Aggregation
    │
    └─ NO
         ↓
계산 수준을 독립적으로 지정?
         │
         ├─ YES → FIXED
         │
         └─ NO
              ↓
View보다 세부적?
         │
         ├─ YES → INCLUDE
         │
         └─ NO
              ↓
View Dimension 일부 제거?
         │
         └─ YES → EXCLUDE
              ↓
Filter Order 확인
              ↓
LOD 결과 재집계 확인
              ↓
Sample 검증
```

# **28. LOD 계산 결과 검증 방법**

> ## **28-1) 작은 데이터로 직접 검산한다**

LOD는 계산 수준 때문에 결과를 직관적으로 확인하기 어려울 수 있다.

따라서 작은 Sample로 검증하는 것이 좋다.

예:

```text
Player   Match   HSR

P001     M1      100
P001     M2      200
P002     M1      400
```

계산:

```text
{ FIXED [Player] :
    SUM([HSR])
}
```

수작업:

```text
P001
= 100 + 200
= 300

P002
= 400
```

[ Result ]

```text
P001 → 300
P002 → 400
```

이후 Position 평균이라면

```text
300 + 400
─────────
    2

= 350
```

처럼 한 단계씩 확인한다.

<br>

> ## **28-2) 검증 체크리스트**

```text
원본 Grain은 무엇인가?

View Dimension은 무엇인가?

LOD Dimension은 무엇인가?

LOD 안의 Aggregation은 무엇인가?

LOD 결과가 View에서 다시 집계되는가?

어떤 Filter가 존재하는가?

Filter는 FIXED보다 먼저인가?

Dimension Filter인가 Context Filter인가?

View Dimension을 바꾸면 결과가 예상대로 변하는가?
```

# **29. Advanced 추가 학습**

> ## **29-1) Nested LOD**

LOD Expression 안에서 다른 LOD 결과를 활용하는 복합 계산도 가능하다.

예를 들어

```text
경기별 총 Load
        ↓
그 경기별 값들의 시즌 평균
```

처럼 여러 단계의 Grain 제어가 필요할 수 있다.

다만 Nested LOD는 계산 흐름이 복잡해지므로

```text
각 단계 Grain
```

을 명확하게 적어두는 것이 중요하다.

<br>

> ## **29-2) LOD와 Relationship**

Relationship을 사용하는 Data Model에서는 서로 다른 Logical Table이 서로 다른 Grain을 가질 수 있다.

따라서 LOD를 작성할 때도

```text
Field가 어느 Logical Table에 존재하는가?

Relationship의 Grain은 무엇인가?

현재 분석에 어떤 Table이 사용되는가?
```

를 함께 확인하는 습관이 중요하다.

<br>

> ## **29-3) LOD와 Table Calculation 결합**

실무에서는

```text
LOD
→ 기준 Grain 계산

Table Calculation
→ 순위 / 누적 / 이동평균
```

처럼 두 계산을 연결할 수도 있다.

예를 들어

```text
선수별 시즌 Load
→ FIXED

시즌 Load Ranking
→ RANK
```

처럼 사용할 수 있다.

# **30. 핵심정리**

1. Level of Detail은 **어떤 Dimension 조합을 기준으로 데이터를 나누고 집계하는가**를 의미한다.

2. Tableau의 기본 Aggregate는 현재 View에 포함된 Dimension에 따라 계산 수준이 달라진다.

```text
Position
→ Position Level

Position + Player
→ Position × Player Level
```

3. 따라서 같은

```text
SUM([HSR Distance M])
```

이라도 View의 Dimension 구성이 달라지면 결과가 달라질 수 있다.

4. LOD Expression은 **현재 View와 별도로 계산에 사용할 집계 수준을 제어**하기 위한 기능이다.

5. 대표적인 LOD Expression은 다음 세 가지이다.

```text
FIXED

INCLUDE

EXCLUDE
```

6. LOD의 기본 구조는 다음과 같다.

```text
{
    LOD Type
    [Dimension]
    :
    Aggregate Expression
}
```

7. `FIXED`는 View의 다른 Dimension을 계산 수준 결정에 사용하지 않고 **명시된 Dimension을 기준으로 계산**한다.

8. 예를 들어

```text
{ FIXED [Player ID] :
    SUM([HSR Distance M])
}
```

은 선수 수준에서 총 HSR을 계산한다.

9. 여러 Dimension을 함께 FIXED할 수도 있다.

```text
{ FIXED [Season], [Player ID] :
    SUM([Player Load])
}
```

10. Dimension을 지정하지 않은 FIXED를 이용하면 전체 Data 수준의 기준값을 만들 수 있다.

```text
{ FIXED :
    SUM([HSR Distance M])
}
```

11. 전체 대비 비율이나 선수별 Baseline처럼 **View가 바뀌어도 유지할 기준 수준**이 필요할 때 FIXED가 유용하다.

12. `INCLUDE`는 현재 View의 Dimension에 지정한 Dimension을 추가하여 **더 세부적인 Grain에서 먼저 계산**한다.

13. INCLUDE의 중요한 목적은 다음 두 단계이다.

```text
세부 Grain에서 계산
        ↓
현재 View Grain으로 재집계
```

14. 예를 들어 Position View에서 선수별 총 HSR을 먼저 계산한 뒤 평균을 구하려면

```text
{ INCLUDE [Player ID] :
    SUM([HSR Distance M])
}
```

을 사용하고 그 결과를 `AVG`로 다시 집계할 수 있다.

15. INCLUDE는 View의 Dimension을 계산 Context로 사용하므로 View 구조가 변경되면 결과도 달라질 수 있다.

16. `EXCLUDE`는 현재 View에 존재하는 특정 Dimension을 **계산 Level of Detail에서 제거**한다.

17. 예를 들어

```text
View
→ Position + Match

{ EXCLUDE [Match ID] :
    SUM([Player Load])
}
```

은 Match 수준을 제거한 Position 기준 값을 만들 수 있다.

18. EXCLUDE는 데이터를 제거하는 Filter가 아니라 **계산 Grain에서 Dimension의 영향을 제거하는 기능**이다.

19. 세 가지 LOD는 다음처럼 구분할 수 있다.

| LOD | 핵심 |
| --- | --- |
| FIXED | 계산 Grain 직접 지정 |
| INCLUDE | View Grain에 Dimension 추가 |
| EXCLUDE | View Grain에서 Dimension 제거 |

20. LOD 계산에서는 **LOD 내부 계산 수준뿐 아니라 View에서 그 결과를 다시 어떻게 Aggregate하는지**도 확인해야 한다.

21. 예를 들어 Player 수준 FIXED 값을 Position View에 사용하면 여러 Player 결과를 다시

```text
AVG
SUM
MIN
MAX
```

중 하나로 집계해야 할 수 있다.

22. LOD와 Filter를 함께 사용할 때는 Tableau의 Order of Operations가 중요하다.

23. LOD와 관련된 핵심 실행 순서는 다음처럼 이해할 수 있다.

```text
Extract Filter
        ↓
Data Source Filter
        ↓
Context Filter
        ↓
FIXED LOD
        ↓
Dimension Filter
        ↓
INCLUDE / EXCLUDE LOD
        ↓
Measure Filter
        ↓
Table Calculation Filter
```

24. FIXED LOD는 일반적인 Dimension Filter보다 먼저 평가된다.

25. 따라서 일반 Dimension Filter로 데이터를 숨겨도 FIXED 계산의 기준값이 그대로 남을 수 있다.

26. FIXED보다 먼저 Filter를 적용해야 한다면 **Context Filter**를 사용하는 방법을 고려할 수 있다.

27. 하지만 모든 Filter를 Context로 바꾸는 것이 정답은 아니며, 먼저 LOD 자체의 Dimension 설계가 맞는지 확인해야 한다.

28. INCLUDE와 EXCLUDE는 일반 Dimension Filter보다 뒤에서 평가되므로 일반적으로 Dimension Filter가 적용된 데이터 범위에서 계산된다.

29. 다음 문장은 부정확하다.

```text
FIXED는 모든 Filter를 무시한다.
```

더 정확하게는

```text
FIXED는 일반 Dimension Filter보다 먼저 계산되지만

Context Filter,
Data Source Filter,
Extract Filter 등

더 앞에서 처리되는 Filter의 영향을 받을 수 있다.
```

30. LOD와 Table Calculation은 목적이 다르다.

```text
LOD
→ 어떤 Grain에서 계산할 것인가?

Table Calculation
→ View에 표시된 결과를 어떻게 다시 계산할 것인가?
```

31. 다음과 같은 문제에는 LOD가 유용하다.

```text
선수별 시즌 총 HSR

선수별 개인 최고 기록

선수별 최초 경기일

피험자별 평균 후 집단 평균

전체 대비 비율

현재 경기와 장기 Baseline 비교
```

32. 하지만 현재 View 수준에서 단순 `SUM`, `AVG`만으로 해결할 수 있는 문제라면 불필요하게 LOD를 사용할 필요는 없다.

33. LOD 문제는 다음 세 수준을 구분하면 훨씬 쉽게 이해할 수 있다.

```text
원본 Data Grain

현재 View LOD

실제로 필요한 Calculation LOD
```

34. LOD를 선택하는 가장 중요한 기준은 다음과 같다.

```text
View와 독립된 기준?
→ FIXED

View보다 더 세부적인 계산?
→ INCLUDE

View보다 덜 세부적인 계산?
→ EXCLUDE
```

35. 운동역학처럼 반복 측정이 존재하는 데이터에서는 다음처럼 LOD를 이용하여 분석 단위를 통제할 수 있다.

```text
Trial
    ↓
Subject Mean
    ↓
Group Mean
```

36. 이것은 Trial 수가 많은 피험자에게 불필요하게 큰 가중치가 주어지는 문제를 피하기 위한 분석 설계에도 활용할 수 있다.

37. 수영에서는

```text
Athlete × Event
```

수준의 개인 최고 기록을 FIXED로 만든 뒤 각 경기 기록과 비교할 수 있다.

38. 축구 GPS에서는

```text
Player × Season
```

수준의 Load를 FIXED로 만들거나, Position View에서 Player 수준을 INCLUDE하여 선수 평균을 계산할 수 있다.

39. LOD 계산이 복잡해질수록 작은 Sample Data로 직접 계산하여 Tableau 결과와 비교해야 한다.

40. LOD 분석의 전체 사고 흐름은 다음과 같다.

```text
Analysis Question
        ↓
Raw Data Grain
        ↓
Current View LOD
        ↓
Required Calculation LOD
        ↓
세 수준 비교
        ↓
기본 Aggregate로 가능한가?
        │
        ├─ YES
        │   ↓
        │ 기본 Aggregate
        │
        └─ NO
            ↓
FIXED / INCLUDE / EXCLUDE
            ↓
LOD 내부 Aggregate 확인
            ↓
View에서 재집계 확인
            ↓
Filter 확인
            ↓
Order of Operations 확인
            ↓
Sample Data로 검증
            ↓
Visualization
            ↓
Interpretation
```

41. 결국 LOD의 핵심은 문법을 외우는 것이 아니라 다음 질문에 정확히 답하는 것이다.

```text
"현재 화면은 어떤 Grain인가?"

"내가 실제로 계산해야 하는 Grain은 무엇인가?"

"그 두 Grain 사이의 차이를
FIXED / INCLUDE / EXCLUDE 중
어떤 방식으로 제어해야 하는가?"

"Filter는 이 계산보다
먼저 적용되어야 하는가,
나중에 적용되어야 하는가?"
```
