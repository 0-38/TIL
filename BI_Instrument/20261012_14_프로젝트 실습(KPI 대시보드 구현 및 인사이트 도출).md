# **1. 프로젝트 개요 - 배드민턴 경기분석 + 웨어러블 + 운동역학 데이터**

> ## **1-1) 실무 문제 정의**

이번 프로젝트에서는 프로 배드민턴 선수의 **경기 후반 Performance 저하 원인**을 분석한다고 가정한다.

코칭스태프는 최근 다음 현상을 확인했다.

```text
1게임 승률
→ 비교적 안정적

2게임 이후
→ 공격 성공률 감소

3게임까지 진행된 경기
→ 결정구간 실점 증가

후반부
→ 이동 속도 감소
→ 착지 충격 증가
```

코칭스태프의 초기 가설은 다음과 같다.

```text
"후반 경기력 저하는
기술 문제라기보다
누적 이동 부하와 피로 때문이 아닐까?"
```

하지만 이는 아직 검증되지 않은 가설이다.

가능한 원인은 여러 가지다.

```text
가능성 1
후반 공격 정확도가 감소

가능성 2
상대가 전술적으로 적응

가능성 3
고강도 이동량 증가

가능성 4
반복 런지 후 착지 비대칭 증가

가능성 5
심박수와 Player Load 증가

가능성 6
경기 후반 Rally Length 증가
```

따라서 Dashboard에서는

```text
기술

경기 상황

외부 부하

내부 부하

운동역학
```

을 함께 확인해야 한다.

<br>

> ## **1-2) 프로젝트 핵심 질문**

```text
경기 후반에 실제 경기력이 감소하는가?

        ↓

어떤 기술 지표가 가장 크게 변하는가?

        ↓

이동 부하와 고강도 움직임은 증가하는가?

        ↓

심박수와 내부 부하는 어떻게 변하는가?

        ↓

착지 비대칭과 충격 지표도 변하는가?

        ↓

문제가 특정 선수에게 집중되는가?

        ↓

추가 훈련 또는 분석이 필요한 선수는 누구인가?
```

# **3. 데이터 연결 전에 KPI Grain부터 확인하기**

> ## **3-1) 왜 Grain이 중요한가?**

예를 들어 한 Game에 Rally Event 데이터가 40행 존재하고 Wearable Game Summary가 1행 있다고 하자.

이를 단순 Join하면

```text
Wearable Player Load
= 420
```

이 40회 반복될 수 있다.

```text
420
420
420
...
40행
```

이 상태에서

```text
SUM([player_load_au])
```

를 사용하면

[ Result ]

```text
420 × 40
= 16,800
```

이라는 잘못된 값이 발생한다.

따라서 KPI를 구현하기 전에

```text
각 Table의 한 행이 무엇인지

KPI는 어느 Grain에서 계산해야 하는지
```

를 확인해야 한다.

<br>

> ## **3-2) 이번 프로젝트 권장 구조**

논리적 관계:

```text
Athlete Master
      │
      │ athlete_id
      ↓
Match Performance
      │
      │ athlete_id + match_id + game_no
      ↓
Wearable Summary
      │
      │ athlete_id + match_id + game_no
      ↓
Biomechanics Summary
```

같은 Grain의 Summary Table이라면 Join도 가능하지만, 원본 Event-level 데이터를 함께 사용할 경우 Relationship 또는 사전 집계를 우선 검토한다.

# **6. KPI 2 - Attack Winner Rate**

> ## **6-1) 단순 공격 Winner 수보다 비율이 중요한 이유**

선수 A:

```text
Attack Winner
→ 18

Attack Attempts
→ 45
```

선수 B:

```text
Attack Winner
→ 14

Attack Attempts
→ 28
```

Winner 수만 보면 A가 높지만 공격 효율은 다르다.

<br>

> ## **6-2) 계산**

[ Tableau : code ] "공격 시도 대비 Winner 비율"

```text
SUM([attack_winners])
/
SUM([attack_attempts])
```

[ Result ]

선수 A:

```math
\frac{18}{45}
=
40.0\%
```

선수 B:

```math
\frac{14}{28}
=
50.0\%
```

따라서

```text
Winner Count
```

과

```text
Winner Rate
```

는 서로 다른 정보를 제공한다.

# **11. KPI 7 - Landing Asymmetry**

> ## **11-1) 좌우 착지 힘 비대칭**

좌·우 Peak vGRF를 이용해 비대칭을 계산할 수 있다.

예시 공식:

```math
\text{Asymmetry}
=
\frac{|L-R|}
{\max(L,R)}
\times 100
```

<br>

> ## **11-2) Tableau 계산**

[ Tableau : code ] "좌우 Peak vGRF 비대칭"

```text
ABS(
    AVG([left_peak_vgrf_n])
    -
    AVG([right_peak_vgrf_n])
)
/
MAX(
    AVG([left_peak_vgrf_n]),
    AVG([right_peak_vgrf_n])
)
* 100
```

Field:

```text
Peak vGRF Asymmetry %
```

예:

```text
Left
→ 2,150 N

Right
→ 2,430 N
```

[ Result ]

```math
\frac{|2150-2430|}
{2430}
\times100
=
11.5\%
```

<br>

> ## **11-3) 해석 주의**

비대칭 값만으로

```text
부상 위험

병리

재활 필요
```

를 단정해서는 안 된다.

사용 목적은

```text
선수 개인의 평소 값과 비교

경기 전후 변화 비교

반복 측정 변화 확인
```

에 두는 것이 적절하다.

# **12. KPI 8 - Game 1 대비 후반 Performance Drop**

> ## **12-1) LOD로 Game 1 기준값 만들기**

선수·경기마다 Game 1의 Attack Winner Rate를 기준값으로 사용한다고 가정한다.

먼저 Game 단위 공격 효율을 만든다.

[ Tableau : code ] "행 수준 Game 공격 성공률"

```text
[attack_winners]
/
[attack_attempts]
```

Field:

```text
Game Attack Rate
```

<br>

> ## **12-2) Game 1 Baseline**

[ Tableau : code ] "경기별 Game 1 공격 성공률"

```text
{ FIXED [athlete_id], [match_id] :
    AVG(
        IF [game_no] = 1 THEN [Game Attack Rate] END
    )
}
```

Field:

```text
Game 1 Attack Baseline
```

<br>

> ## **12-3) Drop 계산**

[ Tableau : code ] "Game 1 대비 공격 성공률 변화"

```text
AVG([Game Attack Rate])
-
AVG([Game 1 Attack Baseline])
```

예:

```text
Game 1
→ 48%

Game 3
→ 37%
```

[ Result ]

```text
37% - 48%
= -11%p
```

이렇게 하면 경기별 초기 Performance를 기준으로 후반 저하 정도를 비교할 수 있다.

# **29. SQL로 Game 단위 Summary 검증하기**

> ## **29-1) 실무형 집계 예제**

[ SQL : code ] "선수-경기-게임 단위 경기분석 요약"

```sql
SELECT
    athlete_id,
    match_id,
    game_no,
    SUM(attack_winners) AS attack_winners,
    SUM(attack_attempts) AS attack_attempts,
    SUM(unforced_errors) AS unforced_errors,
    SUM(rally_count) AS rallies,
    AVG(player_load_au) AS avg_player_load,
    SUM(high_intensity_distance_m) AS high_intensity_distance_m,
    AVG(avg_heart_rate_bpm) AS avg_hr_bpm,
    AVG(landing_asymmetry_pct) AS landing_asymmetry_pct
FROM badminton_performance
GROUP BY
    athlete_id,
    match_id,
    game_no;
```

# **31. 핵심정리**

1. KPI Dashboard 구현은 Chart 제작보다 먼저 **데이터 Grain 확인**에서 시작해야 한다.

2. 경기분석, Wearable, 운동역학 데이터는 서로 다른 측정 구조를 가지므로 Key와 집계 수준을 확인해야 한다.

3. 이번 프로젝트에서는 다음 Grain을 사용했다.

```text
Athlete

Athlete × Match × Game
```

4. Event-level 데이터와 Game Summary를 잘못 Join하면 Measure가 반복되어 중복 집계될 수 있다.

5. 핵심 KPI는 비즈니스 또는 퍼포먼스 문제와 직접 연결되어야 한다.

6. 이번 프로젝트의 주요 KPI는 다음과 같다.

```text
Game Win Rate

Attack Winner Rate

Error Rate

Player Load

High-Intensity Distance

Internal Load

Landing Asymmetry

Late-Game Performance Drop
```

7. 기술 Performance와 신체 부하는 서로 다른 의미를 가지므로 함께 보되 혼동하지 않아야 한다.

8. Attack Winner Rate는 다음과 같이 계산한다.

```math
\frac{\text{Attack Winners}}
{\text{Attack Attempts}}
```

9. Error Rate는 단순 Error 수보다 Rally 수를 고려한 비율이 비교에 적합할 수 있다.

10. Wearable 부하는 Sensor Algorithm과 단위 정의를 확인해야 한다.

11. 서로 다른 Device에서 계산된 `Player Load AU`는 직접 비교하기 전에 측정 조건을 확인해야 한다.

12. Heart Rate는 대표적인 Internal Load 지표로 사용할 수 있다.

13. External Load와 Internal Load는 같은 개념이 아니다.

14. Landing Asymmetry는 좌우 차이를 정량화할 수 있지만 임상적 위험을 직접 의미하지 않는다.

15. 운동역학 데이터는 선수 개인 Baseline과 반복 측정 변화가 중요하다.

16. LOD를 사용하면 경기별 초기 Baseline을 고정할 수 있다.

17. 예:

```text
Game 1 Attack Baseline
```

을 만든 뒤 Game 3와 비교할 수 있다.

18. KPI는 계산식이 실행되는지만 확인해서는 안 된다.

19. 작은 Sample Data를 사용하여 직접 검산하는 것이 중요하다.

20. Dashboard 상단에는 핵심 KPI를 배치하고 상세 Sensor 데이터는 아래 단계에서 탐색하도록 구성할 수 있다.

21. 서로 다른 단위의 Measure를 무리하게 Dual Axis에 겹치지 않는 것이 좋다.

22. Technical, External Load, Internal Load, Biomechanics Panel을 분리하면 해석이 쉽다.

23. Filter와 Parameter는 서로 다른 목적을 가진다.

24. Filter는 분석 범위를 제한한다.

25. Parameter는 사용자가 분석 기준을 변경하도록 한다.

26. Action은 선수 선택 후 상세 Chart를 연결할 때 활용할 수 있다.

27. Filter Action은 선택한 선수의 Detail을 볼 때 적합하다.

28. Highlight Action은 전체 선수 Context를 유지하면서 선택 선수를 비교할 때 적합하다.

29. Dashboard에서 확인한 상관 패턴만으로 인과관계를 단정하면 안 된다.

30. 다음과 같은 결과가 동시에 나타나더라도

```text
Player Load 증가

Landing Asymmetry 증가

Attack Performance 감소
```

이 세 변수 사이의 직접적인 인과관계가 자동으로 증명되는 것은 아니다.

31. 인사이트는 다음 순서로 작성하는 것이 좋다.

```text

        ↓
```

```text

```

35. 전체 평균에서 보이지 않는 문제가 특정 선수에게 집중될 수 있다.

36. Segment 분석에서는 선수, 상대 수준, Tournament Round, 경기시간 등을 고려할 수 있다.

37. 경기분석의 결과는 상대와 경기 상황의 영향을 함께 받는다.

38. Sensor 데이터는 Synchronization이 중요하다.

39. Video와 Sensor 시간이 맞지 않으면 Shot Event와 Movement 데이터를 잘못 연결할 수 있다.

40. Missing Sensor 값과 실제 0값을 구분해야 한다.

41. Sampling Rate가 다른 Sensor의 Peak 값은 직접 비교하기 어려울 수 있다.

42. Dashboard KPI 검증 시 원본 데이터와 SQL Summary를 함께 비교하면 신뢰성을 높일 수 있다.
