# **1. 효과적인 BI 대시보드는 무엇을 해결해야 하는가?**

> ## **1-1) 이번 장에서 사용할 양궁 성과 데이터**

이번 장에서는 기존 축구 GPS 데이터가 아니라 **양궁 국가대표 훈련·대회 성과 데이터**를 사용한다.

한 행은 기본적으로

```text
한 선수
×
한 세트 또는 Round
```

수준의 기록이라고 가정한다.

예시 데이터 구조는 다음과 같다.

| Field | 의미 | 예시 |
| --- | --- | --- |
| `athlete_id` | 선수 ID | A001 |
| `athlete_name` | 선수명 | Archer 01 |
| `session_date` | 훈련·경기 날짜 | 2026-09-18 |
| `event_type` | 훈련·예선·본선 구분 | Qualification |
| `distance_m` | 사거리 | 70 |
| `round_no` | Round 번호 | 1 |
| `arrow_count` | 발사 화살 수 | 36 |
| `total_score` | 총점 | 348 |
| `ten_count` | 10점 개수 | 24 |
| `x_count` | X 개수 | 11 |
| `group_size_cm` | 화살 군집 크기 | 12.8 |
| `wind_speed_ms` | 평균 풍속 | 2.4 |
| `heart_rate_avg_bpm` | 평균 심박수 | 112 |
| `target_score` | 목표 점수 | 345 |
| `world_standard_score` | 비교 기준 점수 | 350 |

실무에서는 이 데이터를 이용해 다음 질문을 해결할 수 있다.

```text
현재 팀 성과는 목표 수준에 도달했는가?

        ↓

어떤 선수의 성과가 안정적인가?

        ↓

누가 평균 점수는 높지만
일관성이 떨어지는가?

        ↓

최근 점수 추세는 상승하고 있는가?

        ↓

바람이 강한 환경에서
성과가 크게 떨어지는 선수는 누구인가?

        ↓

어떤 선수를 추가 분석해야 하는가?
```

좋은 Dashboard는 이 모든 숫자를 그냥 보여주는 것이 아니라 **의사결정 순서에 맞게 정리**해야 한다.

```text
상태 확인
    ↓
문제 발견
    ↓
원인 탐색
    ↓
선수 비교
    ↓
추가 조치
```

<br>

> ## **1-2) BI Dashboard의 핵심 목적**

Dashboard의 목적은

```text
많은 Chart를 보여주는 것
```

이 아니다.

핵심은

```text
사용자가
현재 상황을 빠르게 이해하고

문제가 있는 영역을 찾고

그 다음 행동을 결정하도록
지원하는 것
```

이다.

예를 들어 양궁 퍼포먼스 디렉터가 확인해야 하는 질문은 다음처럼 정리할 수 있다.

| 분석 단계 | 질문 | 필요한 정보 |
| --- | --- | --- |
| 상태 확인 | 팀 평균 점수는 목표 이상인가? | 평균 점수, 목표 달성률 |
| 추세 확인 | 최근 기록은 좋아지고 있는가? | 날짜별 평균 점수 |
| 비교 | 어떤 선수의 성과가 높은가? | 선수별 평균 점수 |
| 안정성 | 누가 기록 변동이 큰가? | 표준편차, 군집 크기 |
| 원인 탐색 | 환경에 따라 성과가 달라지는가? | 풍속, 점수 |
| 행동 | 누구를 추가 분석할 것인가? | KPI + 상세 데이터 |

따라서 Dashboard 설계는 다음 순서로 시작해야 한다.

```text
사용자 정의

        ↓

의사결정 정의

        ↓

필요한 질문 정의

        ↓

KPI 정의

        ↓

Chart 선정

        ↓

레이아웃 설계
```

# **2. Dashboard의 KPI를 먼저 정의한다**

> ## **2-1) 양궁 Dashboard 핵심 KPI**

이번 예제에서는 다음 KPI를 사용한다.

```text
평균 화살 점수

평균 Round 점수

10점 비율

X 비율

목표 달성률

평균 Group Size
```

각 KPI는 서로 다른 의미를 가진다.

| KPI | 의미 |
| --- | --- |
| 평균 화살 점수 | 전체적인 득점 효율 |
| 평균 Round 점수 | Round 수준 경기력 |
| 10점 비율 | 높은 점수 획득 빈도 |
| X 비율 | 중심부 명중 능력 |
| 목표 달성률 | 목표 점수 이상 기록한 비율 |
| Group Size | 화살 분산 정도 |

<br>

> ## **2-2) 평균 화살 점수 계산**

[ Tableau : code ] "화살 1발당 평균 점수"

```text
SUM([total_score]) / SUM([arrow_count])
```

예를 들어

```text
총점
= 1,392

화살 수
= 144
```

이면

[ Result ]

```text
1,392
─────
 144

= 9.67점
```

이 값은 단순한 총점보다 선수·세션 간 비교에 유리하다.

<br>

> ## **2-3) 10점 비율**

[ Tableau : code ] "전체 화살 중 10점 획득 비율"

```text
SUM([ten_count]) / SUM([arrow_count])
```

예:

```text
10점
= 96발

전체
= 144발
```

[ Result ]

```text
96
───
144

= 66.7%
```

<br>

> ## **2-4) X 비율**

[ Tableau : code ] "전체 화살 중 X 비율"

```text
SUM([x_count]) / SUM([arrow_count])
```

예:

```text
X
= 41

전체
= 144
```

[ Result ]

```text
28.5%
```

<br>

> ## **2-5) 목표 달성 여부**

[ Tableau : code ] "Round 목표 점수 달성 여부"

```text
IF [total_score] >= [target_score] THEN "Target Achieved"
ELSE
    "Below Target"
END
```

데이터:

```text
Round Score
→ 348

Target
→ 345
```

[ Result ]

```text
Target Achieved
```

<br>

> ## **2-6) 목표 달성률**

[ Tableau : code ] "목표 이상 Round의 비율"

```text
SUM(IIF([total_score] >= [target_score], 1, 0))
/
COUNT([total_score])
```

예:

```text
전체 Round
→ 20

목표 달성
→ 14
```

[ Result ]

```text
14
──
20

= 70%
```

여기서 `COUNT([total_score])`은 Null이 아닌 `total_score`의 개수를 계산한다.

# **3. 시각적 위계 - 사용자가 어디부터 보게 할 것인가?**

> ## **3-1) 나쁜 Dashboard 구조**

다음처럼 구성되었다고 생각해보자.

```text
┌───────────────────────────────┐
│ 선수별 X 개수 │ 풍속별 점수    │
├────────────────┬──────────────┤
│ Round별 점수    │ Group Size   │
├────────────────┴──────────────┤
│ 선수별 화살 수                  │
├───────────────────────────────┤
│ 목표 달성률 │ 평균 점수         │
└───────────────────────────────┘
```

퍼포먼스 디렉터가 가장 먼저 알고 싶은 것은

```text
현재 성과가 목표를 달성했는가?
```

인데 핵심 KPI가 화면 하단에 있다.

따라서 사용자가 먼저

```text
세부 정보
```

를 해석해야 한다.

<br>

> ## **3-2) 개선된 구조**

다음처럼 배치한다.

```text
┌─────────────────────────────────────┐
│ 평균 점수 │ 목표 달성률 │ 10점 비율 │
├─────────────────────────────────────┤
│ 주간 평균 점수 추세                  │
├──────────────────┬──────────────────┤
│ 선수별 성과      │ 점수 vs 안정성    │
├──────────────────┴──────────────────┤
│ 환경 조건별 상세 분석                │
└─────────────────────────────────────┘
```

사용자의 시선은 다음 흐름으로 이동한다.

```text
현재 성과
    ↓
최근 변화
    ↓
선수 비교
    ↓
원인 탐색
```

<br>

> ## **3-3) 정보 우선순위**

| 우선순위 | 정보 | 목적 |
| --- | --- | --- |
| 1 | KPI | 현재 상태 판단 |
| 2 | Trend | 변화 확인 |
| 3 | Athlete Comparison | 성과 차이 확인 |
| 4 | Diagnostic Chart | 원인 탐색 |
| 5 | Detail | 세부 검증 |

Dashboard의 모든 요소를 같은 크기로 만들면

```text
모든 정보가 중요
```

하게 보이므로 실제로는

```text
어떤 정보도 중요하지 않게
```

느껴질 수 있다.

# **4. 양궁 BI Dashboard의 의사결정 흐름**

> ## **4-1) Dashboard에서 해결할 실제 질문**

퍼포먼스 코치가 다음 순서로 판단한다고 가정한다.

```text
팀 평균 점수가 목표 수준인가?

        ↓

최근 점수가 상승하고 있는가?

        ↓

목표 미달 선수가 누구인가?

        ↓

그 선수는 점수는 낮지만 안정적인가?

        ↓

바람이 강한 조건에서만 문제가 있는가?

        ↓

기술 또는 환경 적응 훈련이 필요한가?
```

Dashboard도 이 순서를 따라가는 것이 좋다.

<br>

> ## **4-2) 분석 화면 구조**

```text
[1]
Team KPI

        ↓

[2]
Score Trend

        ↓

[3]
Athlete Comparison

        ↓

[4]
Consistency Analysis

        ↓

[5]
Environment Analysis

        ↓

[6]
Athlete Detail
```

사용자가 Dashboard를 볼 때

```text
무엇을 클릭해야 할지
추측해야 하는 화면
```

보다

```text
질문의 순서가
화면 구조에 반영된 화면
```

이 더 이해하기 쉽다.

# **5. 인지부하를 줄이는 Dashboard 설계**

> ## **5-1) Cognitive Load(인지부하)**

**인지부하**는 Dashboard를 이해하기 위해 사용자가 사용하는 정신적 노력이다.

예를 들어 선수별 평균 점수를 비교하는 Chart가 다음과 같다고 하자.

```text
Archer 01 → 빨강
Archer 02 → 노랑
Archer 03 → 초록
Archer 04 → 파랑
Archer 05 → 보라
Archer 06 → 주황

+ 그림자
+ 3D
+ 진한 Grid Line
+ 모든 값 Label
```

선수마다 다른 색상이 분석적으로 특별한 의미가 없다면 사용자는

```text
색상 구분
+
막대 길이
+
숫자
+
범례
```

를 동시에 처리해야 한다.

<br>

> ## **5-2) 개선**

```text
Athlete 01    █████████  9.72
Athlete 02    ████████   9.61
Athlete 03    ████████   9.59
Athlete 04    ███████    9.44
Athlete 05    ███████    9.40
```

원칙:

```text
정렬

일관된 색상

불필요한 Grid 제거

필요한 Label만 유지

문제가 있는 Athlete만 강조
```

분석 목표가

```text
누가 기준 이하인가?
```

라면 기준 이하 Athlete만 강조할 수 있다.

<br>

> ## **5-3) 필요한 정보는 제거하지 않는다**

인지부하를 줄인다고 해서 무조건

```text
축 제거

Label 제거

Grid 제거

Tooltip 제거
```

를 하는 것은 아니다.

정확한 값 비교에 필요한 요소라면 유지해야 한다.

핵심은

```text
정보를 줄이는 것
```

이 아니라

```text
정보를 이해하는 데
불필요한 요소를 줄이는 것
```

이다.

# **6. Data-Ink Ratio(데이터-잉크 비율) 적용**
데이터 시각화에서 실제 데이터를 표현하는 요소의 비중을 높여야 시각화가 효율적으로 이루어진다.

이것을 **Data-Ink Ratio(데이터-잉크 비율)** 라고 하며, 차트에서 데이터를 이해하는 데 필요하지 않은 장식적인 요소를 줄이는 것이다. 

> ## **6-1) 데이터보다 장식이 눈에 띄면 안 된다**

다음 요소는 정보 전달에 직접 필요하지 않을 수 있다.

```text
두꺼운 Border

강한 Background

3D Effect

Shadow

Gradient

과도한 Grid

불필요한 Icon
```

예를 들어 선수별 평균 점수는 단순 Bar만으로도 충분하다.

```text
Athlete A    █████████
Athlete B    ████████
Athlete C    ███████
```

굳이

```text
3D Bar

Shadow

Gradient

Pattern
```

을 사용할 필요는 없다.

<br>

> ## **6-2) Before / After**

| 요소 | Before | After |
| --- | --- | --- |
| 배경 | 강한 Gradient | 단순 배경 |
| Grid | 모든 축에 진한 선 | 필요한 선만 |
| Border | 모든 Chart에 테두리 | Section 구분만 |
| Color | 모든 Athlete 다른 색 | 기본색 + 강조색 |
| Label | 모든 Measure 표시 | 핵심 값만 |
| Legend | 여러 개 반복 | 필요 최소화 |

목표는

```text
장식 ↓

Data 표현 ↑
```

# **7. Preattentive Attributes(전주의적 속성)을 활용해 문제를 빠르게 발견하기**

> ## **7-1) 목표 미달 선수 강조**

선수별 평균 Round Score:

```text
Archer 01    348.5
Archer 02    346.8
Archer 03    341.4
Archer 04    347.2
Archer 05    339.8
```

Target:

```text
345
```

사용자가 직접 모든 숫자를 읽게 하지 않는다.

[ Tableau : code ] "목표 점수 기준 선수 상태"

```text
IF AVG([total_score]) >= AVG([target_score]) THEN "On Target"
ELSE
    "Below Target"
END
```

[ Result ]

```text
Archer 01 → On Target
Archer 02 → On Target
Archer 03 → Below Target
Archer 04 → On Target
Archer 05 → Below Target
```

이 Field를 Color에 배치하면 주의가 필요한 선수를 빠르게 확인할 수 있다.

<br>

> ## **7-2) 색상은 분석 의미가 있어야 한다**

좋지 않은 사용:

```text
선수마다 임의의 색상
```

좋은 사용:

```text
Normal
→ 기본색

Target Miss
→ 강조색
```

색상을

```text
구분
```

이 아니라

```text
의미
```

전달에 사용한다.

<br>

> ## **7-3) 색상에만 의존하지 않는다**

예:

```text
Below Target
```

을 색상뿐 아니라

```text
Label

Tooltip

Shape

Status Text
```

등으로 함께 제공할 수 있다.

특정 색을 구분하기 어려운 사용자도 정보를 이해할 수 있도록 만드는 것이 좋다.

# **8. Sequential / Diverging / Categorical Color**

> ## **8-1) Categorical**

서로 다른 범주를 구분할 때 사용한다.

예:

```text
Training
Qualification
Final
```

이들은 순서가 아니라 서로 다른 Category이다.

<br>

> ## **8-2) Sequential**

값의 크기를 표현할 때 사용한다.

예:

```text
Wind Speed

낮음
→
높음
```

또는

```text
Score

낮음
→
높음
```

Heatmap에서 사용할 수 있다.

<br>

> ## **8-3) Diverging**

중심 기준을 기준으로 양수·음수를 표현할 때 적합하다.

예:

```text
Score vs Target
```

계산:

[ Tableau : code ] "목표 대비 점수 차이"

```text
AVG([total_score])
-
AVG([target_score])
```

예:

```text
Athlete 01
348 - 345
= +3

Athlete 03
341 - 345
= -4
```

[ Result ]

```text
+3
→ 목표 초과

0
→ 기준

-4
→ 목표 미달
```

이 경우 발산형 색상으로 기준을 중심으로 차이를 보여줄 수 있다.

# **9. Gestalt 원리로 Dashboard를 그룹화한다**

사람은 화면의 요소를 개별적으로만 인식하지 않고, 위치나 형태 등의 공통점에 따라 하나의 그룹으로 받아들이기도 한다. 

이러한  시각적 지각 특성을 설명하는 것이 **Gastalt(게슈탈트)** 원리이다.


> ## **9-1) Proximity(근접성) - 가까이 있는 정보는 같은 그룹으로 인식된다**

다음 KPI는 서로 연관성이 높다.

```text
Average Arrow Score

10 Rate

X Rate

Target Achievement Rate
```

따라서 하나의 KPI 영역에 배치한다.

```text
┌──────────────────────────────────┐
│ Avg Score │ 10 Rate │ X Rate │ Target │
└──────────────────────────────────┘
```

반대로 환경 데이터는 다른 영역에 배치한다.

```text
Wind Speed

Group Size

Heart Rate
```

<br>

> ## **9-2) Similarity(유사성) - 같은 의미는 같은 형태로 표현한다**

예:

```text
성과 KPI
→ 같은 Card Style

환경 변수
→ 동일한 Axis/Style

경고 상태
→ 동일한 강조 방식
```

Chart마다 디자인이 다르면 사용자는 각 Chart의 의미를 다시 학습해야 한다.

<br>

> ## **9-3) Continuity(연속성) - 시각적으로 연결되거나 연속된 요소를 하나의 흐름으로 인식한다.**

Chart와 KPI를 일정한 기준선으로 정렬한다.

```text
KPI  KPI  KPI  KPI

Trend────────────

Player────│Stability───
```

정렬이 맞지 않으면 Dashboard가 복잡해 보이고 Section 관계도 이해하기 어렵다.  


따라서 관련 차트와 지표를 일정한 방향으로 배치하여 분석의 흐름을 유도해야한다.  
  
  
<br><br>

# **10. 잘못된 차트 선택 - Pie Chart 남용**

```text
Athlete 03    13%
Athlete 04    12%

Athlete 06    12%
```

Pie Chart에서는

```text

12%

14%
```

의 차이를 정확하게 비교하기 어렵다.


# **11. 잘린 축이 만드는 왜곡**

> ## **11-1) 실제 점수 차이**

선수 평균 Round Score:

```text
Athlete A
→ 348

Athlete B
→ 342
```

차이는

```text
6점
```

이다.

<br>

> ## **11-2) 축을 340부터 시작한다면**

시각적으로는

```text
Athlete A    ████████

Athlete B    ██
```

처럼 매우 큰 차이로 느껴질 수 있다.

하지만 전체 360점 Scale을 기준으로 보면

```text
6점 차이
```

이다.

<br>

> ## **11-3) Bar Chart는 일반적으로 0부터**

Bar의 길이가 값 자체를 표현하므로 일반적으로 0을 기준으로 하는 것이 안전하다.

```text
Score

0
|
|──────────────────────── 348
|───────────────────────  342
```

<br>

> ## **11-4) 하지만 Line Chart는 다르다**

Line Chart는 주로

```text
값의 위치와 변화
```

를 확인한다.

예:

```text
Day 1
→ 345

Day 2
→ 347

Day 3
→ 343

Day 4
→ 349
```

변화를 자세히 확인하기 위해

```text
340~350
```

범위를 사용할 수도 있다.

다만 축 범위를 명확하게 보여줘야 한다.

# **24. 실무 진단 사례**


등을 사용하는 것이 적절할 수 있다.

```text
많은 Gauge
```

```text
숫자는 많지만

```


사용자 경험:

```text
상태 확인
    ↓
문제 Athlete 발견
    ↓
원인 탐색
    ↓
추가 분석
```

이것이 BI Dashboard 설계의 핵심이다.

# **26. Advanced 추가 학습**

> ## **26-1) Small Multiples**

여러 Athlete의 점수 추세를 동일한 Scale로 나누어 배치하면 서로 다른 선이 겹치는 복잡한 Line Chart보다 비교하기 쉬울 수 있다.

```text
Athlete A Trend

Athlete B Trend

Athlete C Trend
```

<br>

> ## **26-2) Reference Line**

다음 기준을 Chart에 직접 표시할 수 있다.

```text
Target Score

Team Average

World Standard
```

단순히 평균값만 보여주는 것보다 기준과의 차이를 빠르게 판단할 수 있다.

<br>

> ## **26-3) Control Chart 관점**

장기간 Performance 데이터를 분석한다면 단순 평균뿐 아니라 변동 범위를 이용해

```text
평소 범위를 벗어난 기록
```

을 탐지하는 관리도적 접근도 학습할 수 있다.

# **27. 핵심정리**

1. 효과적인 BI Dashboard의 목적은 많은 Chart를 보여주는 것이 아니라 **사용자의 의사결정을 지원하는 것**이다.

2. Dashboard 설계는 다음 질문에서 시작한다.

```text
누가 사용하는가?

무슨 질문에 답하는가?

어떤 결정을 내려야 하는가?
```

3. KPI는 Dashboard의 목적과 직접 연결되어야 한다.

4. 양궁 Performance Dashboard에서는 다음과 같은 KPI를 사용할 수 있다.

```text
평균 화살 점수

평균 Round 점수

10점 비율

X 비율

목표 달성률

Group Size
```

5. 동일한 데이터라도 정보 배치 순서에 따라 Dashboard의 이해도가 달라진다.

6. 일반적으로 다음과 같은 정보 흐름이 효과적일 수 있다.

```text
Summary
    ↓
Trend
    ↓
Comparison
    ↓
Diagnostic
    ↓
Detail
```

7. Visual Hierarchy는 중요한 정보를 상대적으로 더 쉽게 발견하도록 하는 설계 원칙이다.

8. Visual Hierarchy에는 다음 요소를 사용할 수 있다.

```text
위치

크기

색상

여백

그룹화
```

9. 모든 요소를 강조하면 실제로 중요한 정보가 무엇인지 구분하기 어려워진다.

10. Cognitive Load는 사용자가 Dashboard를 이해하기 위해 사용하는 정신적 노력이다.

11. 좋은 Dashboard는 정보를 무조건 줄이는 것이 아니라 **불필요한 해석 비용을 줄인다.**

12. Data-Ink 원칙에서는 Data 이해에 기여하지 않는 장식 요소를 최소화한다.

13. 대표적으로 다음 요소를 검토한다.

```text
3D

Shadow

Gradient

과도한 Grid

불필요한 Border

중복 Label
```

14. 색상은 장식이 아니라 정보 전달 수단으로 사용해야 한다.

15. 특별한 의미가 없다면 모든 Category를 서로 다른 강한 색상으로 표시할 필요는 없다.

16. Sequential Palette는 값의 크기 표현에 적합하다.

17. Categorical Palette는 서로 다른 범주 구분에 적합하다.

18. Diverging Palette는 기준값을 중심으로 양수와 음수를 비교할 때 적합하다.

19. Preattentive Attribute를 사용하면 중요한 문제를 빠르게 발견하도록 도울 수 있다.

20. 다만 강조할 대상은 먼저 분석적으로 정의되어야 한다.

21. Gestalt의 Proximity 원리를 이용하면 관련 KPI와 Chart를 가까이 배치할 수 있다.

22. Similarity를 이용하면 같은 의미의 정보를 일관된 스타일로 표현할 수 있다.

23. Alignment는 Dashboard 구조를 이해하기 쉽게 만든다.

24. Pie Chart는 Category가 많거나 값이 비슷한 경우 정확한 비교에 불리할 수 있다.

25. 정확한 비교가 중요하면 정렬된 Bar Chart가 더 적합한 경우가 많다.

26. 3D Chart는 원근감 때문에 실제 값의 크기를 왜곡할 수 있다.

27. 막대그래프는 막대 길이가 값의 크기를 나타내므로 일반적으로 0 기준 축을 사용하는 것이 중요하다.

28. Line Chart는 변화 분석을 위해 좁은 축 범위를 사용할 수 있지만 축 범위를 명확하게 보여줘야 한다.

29. Dual Axis는 서로 다른 Measure를 함께 표현할 수 있지만 Scale을 조절하면 두 지표의 관계를 오해하게 만들 수 있다.

30. 서로 다른 단위의 관계를 분석하려면 Scatter Plot이 더 적절할 수 있다.

31. Gauge와 Donut은 모든 KPI에 사용할 필요가 없다.

32. KPI Card는 작은 공간에서 다음 정보를 효율적으로 전달할 수 있다.

```text
현재값

기준값

증감
```

33. 평균만으로 Performance를 평가하면 변동성을 놓칠 수 있다.

34. 같은 평균을 가진 Athlete라도 표준편차는 크게 다를 수 있다.

35. 따라서 Performance Dashboard에서는 상황에 따라

```text
Average

STDEV

Distribution

Group Size
```

를 함께 고려할 수 있다.

36. 환경 변수와 Performance의 관계를 관찰하더라도 곧바로 인과관계라고 판단하면 안 된다.

37. Dashboard 진단은 개인적 취향이 아니라 일정한 설계 기준으로 수행해야 한다.

38. 핵심 진단 영역은 다음과 같다.

```text
목적

시각적 위계

차트 적합성

색상·잉크

정직성
```

39. 목적 점검에서는 Dashboard가 어떤 의사결정을 지원하는지 확인한다.

40. 시각적 위계 점검에서는 핵심 KPI가 먼저 발견되는지 확인한다.

41. 차트 적합성 점검에서는 분석 질문에 적절한 Chart를 사용했는지 확인한다.

42. 색상·잉크 점검에서는 시각적 요소에 실제 의미가 있는지 확인한다.

43. 정직성 점검에서는 축·집계·단위가 실제 데이터의 의미를 왜곡하지 않는지 확인한다.

44. Dashboard 문제는 다음 구조로 설명하는 것이 좋다.

```text
문제

        ↓

왜 문제인가?

        ↓

관련 설계 원칙

        ↓

개선 방법
```

45. 양궁 Dashboard의 예를 적용하면 다음과 같이 진단할 수 있다.

```text
Goal KPI가 화면 하단
→ Visual Hierarchy 문제
→ 상단 Summary 영역으로 이동

8명의 점수를 Pie로 표현
→ 정확한 비교 어려움
→ Sorted Bar

Score Bar가 330부터 시작
→ 차이 과장
→ 일반적으로 0축 사용

Athlete마다 무지개 색상
→ 인지부하 증가
→ 기본색 + 의미 있는 강조색

Score와 HR을 임의 Dual Axis
→ 관계 오해 가능
→ Scatter 또는 분리 Chart
```

46. 효과적인 Dashboard의 핵심은 화려함이 아니다.

47. 최종적으로 좋은 BI Dashboard는 다음 흐름을 지원해야 한다.

```text
현재 상태를 빠르게 이해

        ↓

중요한 문제 발견

        ↓

관련 비교 수행

        ↓

원인 후보 탐색

        ↓

상세 데이터 확인

        ↓

의사결정
```

48. 따라서 이번 장에서 가장 중요한 원칙은 다음과 같다.

```text
"Dashboard는 데이터를 많이 보여주는 화면이 아니라,

사용자가 어떤 정보를 먼저 보고,
무엇을 문제로 판단하며,
어떤 추가 분석으로 이동해야 하는지를

시각적으로 안내하는 의사결정 도구이다."
```
