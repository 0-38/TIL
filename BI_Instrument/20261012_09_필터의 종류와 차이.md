# **[Tableau] : <br> 필터의 종류와 차이**

<br>


# **1. Tableau Filter는 단순히 데이터를 숨기는 기능이 아니다**

> ## **1-1) Filter의 핵심 역할**

Tableau의 Filter는 분석에 사용할 데이터의 범위를 제한한다.

예를 들어 축구 GPS Dashboard에서 다음과 같은 조건을 선택할 수 있다.

```text
Season
→ 2026

Position
→ Winger

Competition
→ League

Player
→ P001 / P002 / P003
```

사용자가

```text
Season = 2026
Position = Winger
```

를 선택하면 해당 조건에 맞는 데이터만 이용해 View가 구성된다.

하지만 Filter에서 중요한 것은 단순히

```text
어떤 데이터를 보여줄 것인가?
```

만이 아니다.

다음 질문도 함께 생각해야 한다.

```text
Filter가 언제 실행되는가?

Filter 이후 어떤 계산이 수행되는가?

Top N의 모집단이 바뀌는가?

LOD의 계산 범위가 바뀌는가?

다른 Worksheet에도 적용되는가?
```

즉 Tableau Filter는

```text
Data 범위
+
계산 순서
+
Dashboard 적용 범위
```

를 함께 이해해야 한다.

<br>

> ## **1-2) 같은 Filter라도 결과가 달라질 수 있다**

예를 들어 선수 HSR 상위 5명을 분석한다고 하자.

전체 선수 기준 Top 5:

```text
P001
P004
P007
P009
P012
```

그 이후

```text
Position = Winger
```

Filter를 적용했다고 하자.

사용자가 원하는 것이

```text
Winger 중 HSR Top 5
```

라면 Winger 데이터를 먼저 남긴 뒤 순위를 계산해야 한다.

하지만 실행 순서가 다르면

```text
전체 선수 Top 5
        ↓
그중 Winger만 표시
```

가 될 수 있다.

따라서

```text
Top N
+
Dimension Filter
```

를 함께 사용할 때는 **Order of Operations**를 이해해야 한다.

# **2. Order of Operations — Tableau의 계산 실행 순서**

> ## **2-1) 모든 Filter가 동시에 실행되는 것은 아니다**

Tableau는 Filter와 계산을 정해진 순서에 따라 처리한다.

이를

```text
Order of Operations
```

또는

```text
Query Pipeline
```

이라고 한다.

이번 과정에서 중요한 흐름을 단순화하면 다음과 같다.

```text
Extract Filter
        ↓
Data Source Filter
        ↓
Context Filter
        ↓
FIXED LOD
        ↓
Dimension Filter
Top / Conditional Filter
        ↓
INCLUDE / EXCLUDE LOD
        ↓
Measure Filter
        ↓
Table Calculation
        ↓
Table Calculation Filter
```

실제 Tableau에는 이 밖에도 Set, Forecast, Trend Line 등의 단계가 존재할 수 있다.

중요한 것은

```text
위에서 실행된 결과가
아래 단계의 계산 범위를 결정할 수 있다.
```

는 점이다.

<br>

> ## **2-2) 실행 순서가 중요한 이유**

다음 두 분석은 서로 다르다.

```text
전체 선수에서 Top 5를 계산
        ↓
Winger만 표시
```

와

```text
Winger만 먼저 선택
        ↓
Winger 중 Top 5 계산
```

결과가 같을 수도 있지만 대부분의 실제 데이터에서는 다를 수 있다.

따라서 Filter를 사용할 때는

```text
무엇을 Filter하는가?
```

뿐 아니라

```text
언제 Filter하는가?
```

도 중요하다.

# **3. Extract Filter**

> ## **3-1) Extract에 저장할 데이터 자체를 제한한다**

Extract Filter는 Tableau Extract에 포함될 데이터 범위를 제한한다.

예를 들어 GPS 원본 Database에

```text
2021
2022
2023
2024
2025
2026
```

데이터가 있지만 Dashboard에서는 최근 3시즌만 사용한다고 하자.

```text
Extract Filter

Season >= 2024
```

로 제한할 수 있다.

개념적으로

```text
원본 Database
        ↓
Extract Filter
2024~2026
        ↓
Tableau Extract
        ↓
분석
```

이 된다.

<br>

> ## **3-2) 일반 Worksheet Filter와 차이**

```text
Worksheet Dimension Filter
→ 분석 중 특정 데이터를 표시하지 않음
```

과 달리

```text
Extract Filter
→ Extract에 포함할 데이터 자체를 제한
```

한다.

따라서 Extract가 생성된 이후 분석에 사용할 수 있는 데이터 범위 자체가 달라진다.

| 구분 | Extract Filter | Dimension Filter |
| --- | --- | --- |
| 적용 위치 | Extract 생성 단계 | Worksheet 분석 단계 |
| 목적 | Extract Data 범위 제한 | View Data 제한 |
| 실행 순서 | 매우 앞 | 이후 |
| 예 | 최근 3시즌만 저장 | 2026시즌만 표시 |


<br><br>

# **4. Data Source Filter**

> ## **4-1) Data Source 수준의 범위를 제한한다**

Data Source Filter는 해당 Tableau Data Source에서 사용할 데이터의 범위를 제한한다.

예를 들어 구단별 Published Data Source를 운영한다고 하자.

```text
전체 League Data

Team A
Team B
Team C
Team D
```

Team A 분석용 Data Source에서

```text
Team = "A"
```

로 제한할 수 있다.

```text
전체 데이터
    ↓
Data Source Filter
    ↓
Team A 데이터
    ↓
Workbook 분석
```

<br>

> ## **4-2) Worksheet마다 반복하지 않아도 된다**

Data Source 수준에서 제한되기 때문에 해당 Data Source를 사용하는 분석의 기반 범위 자체에 영향을 준다.

대표적인 활용은

```text
특정 국가만 제공

특정 조직 데이터만 제공

분석에 필요 없는 과거 기간 제외
```

등이다.

다만

```text
Data Source Filter
= 보안 기능 전체
```

라고 단순하게 이해하면 안 된다.

실제 데이터 접근 제어는 조직의 권한·게시 설정·Row Level Security 설계까지 함께 고려해야 한다.


<br><br>

# **5. Dimension Filter**

> ## **5-1) 범주형 기준으로 데이터 선택**

Dimension Filter는 다음처럼 Category를 기준으로 데이터를 제한할 때 사용한다.

```text
Position
Team
Player
Event
Competition
Season
```

예를 들어

```text
Position = Winger
```

를 선택하면 Winger에 해당하는 데이터만 View에 포함된다.

<br>

> ## **5-2) 축구 GPS 예제**

데이터:

```text
Player   Position      HSR

P001     Winger       1200
P002     Winger        950
P003     Defender      700
P004     Midfielder   1050
```

Filter:

```text
Position = Winger
```

[ Result ]

```text
P001    1200
P002     950
```

Dimension Filter는 실무 Dashboard에서 가장 일반적으로 사용되는 Filter 중 하나이다.

<br>

> ## **5-3) Dimension Filter는 View 계산 전에 영향을 줄 수 있다**

예를 들어 Percent of Total Table Calculation이 있다면 일반 Dimension Filter가 먼저 데이터를 제한하고 이후 Table Calculation이 계산될 수 있다.

따라서 Category를 Filter했을 때

```text
전체 기준 비율
```

이 아니라

```text
남은 데이터 기준 비율
```

로 다시 계산될 수 있다.

이 부분은 LOD와 Table Calculation을 사용할 때 특히 중요하다.


<br><br>

---

# **6. Measure Filter**

> ## **6-1) 집계된 Measure 결과를 기준으로 Filter**

Measure Filter는 일반적으로 집계된 Measure를 기준으로 데이터를 제한한다.

예를 들어 선수별 총 HSR이 다음과 같다고 하자.

```text
P001    12,500m
P002     8,900m
P003    14,200m
P004     6,800m
```

조건:

```text
SUM([HSR Distance M])
>= 10,000
```

[ Result ]

```text
P001    12,500
P003    14,200
```

<br>

> ## **6-2) Dimension Filter와 차이**

```text
Position = Winger
```

는 Dimension 값 자체를 제한한다.

반면

```text
SUM(HSR) >= 10,000
```

은 Aggregate 결과를 평가한다.

| 구분 | Dimension Filter | Measure Filter |
| --- | --- | --- |
| 기준 | Dimension Member | 집계된 Measure |
| 예 | Winger | HSR ≥ 10,000 |
| 실행 | 상대적으로 앞 | Dimension Filter 이후 |
| 질문 | 어떤 Category? | 어느 정도 이상의 값? |


<br><br>

# **7. Context Filter — 후속 분석의 기준 범위를 먼저 만든다**

> ## **7-1) Context Filter란?**

Context Filter는 일반 Dimension Filter보다 먼저 적용되어 **다른 Filter와 계산이 사용할 기준 데이터 범위**를 만든다.

예를 들어

```text
Position = Winger
```

를 Context Filter로 설정한다면

```text
전체 선수
    ↓
Winger만 남김
    ↓
이 범위를 Context로 설정
    ↓
Top N 등 후속 Filter 계산
```

이 된다.

<br>

> ## **7-2) Tableau에서 설정**

기존 Dimension Filter를

```text
Add to Context
```

하면 Context Filter로 변경할 수 있다.

Context Filter는 Filters Shelf에서 일반 Filter와 구분되는 형태로 표시된다.

<br>

> ## **7-3) Context Filter의 핵심은 성능이 아니라 계산 범위**

Context Filter를 다음처럼 이해하면 부정확하다.

```text
Context Filter
→ Dashboard를 빠르게 만드는 Filter
```

더 중요한 목적은

```text
다른 Filter가 계산할
기준 모집단을 먼저 정하는 것
```

이다.

성능 개선이 발생하는 상황도 있지만 모든 경우 성능이 좋아지는 것은 아니다.


<br><br>

# **8. Top N과 Context Filter**

> ## **8-1) 전체 Top 5와 Position Top 5는 다르다**

데이터:

```text
Player   Position      HSR

P001     Winger       1500
P002     Winger       1200
P003     Winger       1100
P004     Winger        950
P005     Winger        900
P006     Defender     1700
P007     Defender     1600
P008     Midfielder   1550
P009     Midfielder   1400
P010     Defender     1300
```

전체 Top 5:

```text
P006    1700
P007    1600
P008    1550
P001    1500
P009    1400
```

그 후 Winger Filter를 적용하면 남는 선수는

```text
P001
```

뿐이다.

하지만 사용자의 질문이

```text
Winger 중 HSR Top 5
```

라면 기대 결과는

```text
P001    1500
P002    1200
P003    1100
P004     950
P005     900
```

이다.

<br>

> ## **8-2) Context 적용**

```text
Position = Winger
        ↓
Add to Context
        ↓
Winger만 데이터 범위에 남김
        ↓
HSR 기준 Top 5
```

[ Result ]

```text
P001    1500
P002    1200
P003    1100
P004     950
P005     900
```

즉 Context Filter는 **Top N의 모집단을 먼저 정의하는 역할**을 한다.


<br><br>

# **9. Top N을 설계할 때 반드시 정해야 하는 모집단**

> ## **9-1) "Top 5"만으로는 지표 정의가 부족하다**

다음은 모두 다른 분석이다.

```text
League 전체 선수 Top 5

Team 내부 Top 5

Position 내부 Top 5

2026 시즌 Top 5

최근 5경기 기준 Top 5
```

따라서 Top N을 만들기 전에 다음을 명확히 해야 한다.

```text
Top N을
어떤 데이터 범위에서 계산할 것인가?
```

<br>

> ## **9-2) 실무 설계 흐름**

```text
분석 질문
    ↓
Top N Measure 정의
    ↓
Top N 모집단 정의
    ↓
모집단 Filter가
Top N보다 먼저 적용되어야 하는가?
    ↓
Context 필요 여부 결정
```

예:

```text
질문
→ Winger 중 Sprint Count Top 10

모집단
→ Winger

평가 Measure
→ SUM(Sprint Count)

따라서
→ Position Context
→ Player Top 10
```

# **10. Context Filter와 FIXED LOD**

> ## **10-1) FIXED는 일반 Dimension Filter보다 먼저 계산된다**

선수별 시즌 최고속도를 다음처럼 계산했다고 하자.

[ Tableau : code ] "선수별 전체 기간 최고속도"

```text
{ FIXED [Player ID] :
    MAX([Max Speed Kmh])
}
```

선수 P001:

```text
2025    34.8
2026    33.9
```

FIXED 결과:

```text
34.8
```

이후 일반 Dimension Filter에서

```text
Season = 2026
```

을 선택해도 FIXED가 이미 계산된 상태라면

[ Result ]

```text
34.8 km/h
```

가 유지될 수 있다.

<br>

> ## **10-2) 2026 안에서 최고속도를 계산하고 싶다면**

질문이

```text
선수의 전체 기간 최고속도
```

가 아니라

```text
2026 시즌 안에서 최고속도
```

라면 Season Filter가 FIXED보다 먼저 적용되어야 한다.

한 가지 방법은 Season Filter를 Context에 추가하는 것이다.

```text
Season = 2026
    ↓
Context
    ↓
FIXED
    ↓
P001 최고속도
= 33.9
```

[ Result ]

```text
33.9 km/h
```

<br>

> ## **10-3) LOD 자체 설계도 먼저 검토한다**

하지만 Context만이 정답은 아니다.

계산 목적이 원래부터

```text
Season × Player
```

수준이라면 다음처럼 작성하는 것이 더 명확할 수도 있다.

```text
{ FIXED [Season], [Player ID] :
    MAX([Max Speed Kmh])
}
```

따라서

```text
Filter로 해결할 것인가?

LOD Grain 자체를 수정할 것인가?
```

를 함께 판단해야 한다.


<br><br>

# **11. Table Calculation Filter**

> ## **11-1) 계산 후 Mark를 제한하는 Filter**

Table Calculation은 View의 집계 결과에서 계산된다.

따라서 Table Calculation 결과에 Filter를 적용하면 **계산이 끝난 후 표시할 Mark를 제한하는 형태**가 될 수 있다.

예를 들어 선수별 HSR Rank를 만든다.

[ Tableau : code ] "선수별 HSR 순위"

```text
RANK(
    SUM([HSR Distance M])
)
```

Filter용 계산:

[ Tableau : code ] "상위 5위 선수만 표시"

```text
RANK(
    SUM([HSR Distance M])
)
<= 5
```

[ Result ]

```text
Rank 1 → True
Rank 2 → True
Rank 3 → True
Rank 4 → True
Rank 5 → True
Rank 6 → False
```

<br>

> ## **11-2) 일반 Dimension Filter와 차이**

Dimension Filter:

```text
계산 전에 Data 범위 제한
```

Table Calculation Filter:

```text
View 계산
    ↓
Table Calculation
    ↓
계산 결과에 따라 Mark 표시 제한
```

따라서 Rank Top N을 구현할 때

```text
Dimension Top Filter
```

와

```text
RANK Table Calculation Filter
```

는 화면이 비슷해 보여도 실행 단계가 다르다.


<br><br>

# **12. Top Filter와 RANK Filter 비교**

> ## **12-1) 두 방식은 같은 기능이 아니다**

| 항목 | Dimension Top N | RANK Table Calculation |
| --- | --- | --- |
| 계산 단계 | Dimension Filter 단계 | Table Calculation 단계 |
| View 의존성 | 상대적으로 낮음 | 높음 |
| Compute Using | 사용하지 않음 | 중요 |
| Addressing/Partitioning | 없음 | 중요 |
| 대표 활용 | 일반 Top N | View Context 기반 Rank |

예를 들어

```text
각 Position 내부에서 선수 Rank
```

처럼 Partition이 중요한 경우에는 `RANK()` Table Calculation이 더 자연스러운 경우도 있다.

<br>

> ## **12-2) RANK 방식 예제**

View:

```text
Position
Player
HSR
```

계산:

```text
RANK(SUM([HSR Distance M]))
```

Compute Using:

```text
Player
→ Addressing

Position
→ Partitioning
```

그러면 Rank가 Position마다 다시 시작된다.

```text
Winger

P001 → Rank 1
P002 → Rank 2


Defender

P006 → Rank 1
P010 → Rank 2
```

# **13. Interactive Filter — 과거의 Quick Filter**

> ## **13-1) Quick Filter는 별도 실행 단계가 아니다**

과거에는 화면에 표시되는 Filter Control을 흔히 `Quick Filter`라고 불렀다.

현재 Tableau에서는

```text
Show Filter
```

를 통해 표시되는 Interactive Filter 또는 Filter Card로 이해하는 것이 더 정확하다.

중요한 것은

```text
Quick Filter
```

라는 별도의 Order of Operations 단계가 존재하는 것이 아니라는 점이다.

Filter Card는 사용자가 Filter 조건을 직접 변경할 수 있게 하는 UI이다.

<br>

> ## **13-2) Filter Card 유형**

Dimension 특성에 따라 다음과 같이 표현할 수 있다.

```text
Single Value List

Single Value Dropdown

Multiple Values List

Multiple Values Dropdown
```

숫자나 날짜에서는 Range 등의 형태도 활용할 수 있다.

예:

```text
Season
→ Single Value Dropdown

Player
→ Multiple Values Dropdown

Match Date
→ Date Range
```

<br>

> ## **13-3) Dashboard에서 Filter가 너무 많으면 안 되는 이유**

Filter를 많이 표시하면 사용자는 선택해야 할 것이 지나치게 많아질 수 있다.

또한 Interactive Filter 각각의 값 목록을 구성하기 위한 Query 부담도 발생할 수 있다.

따라서

```text
분석에 꼭 필요한 Filter만 제공

관련 Filter는 그룹화

사용자에게 의미 있는 순서로 배치
```

하는 것이 좋다.


<br><br>

# **14. Only Relevant Values**

> ## **14-1) 앞선 Filter 선택에 맞는 값만 보여주기**

예를 들어

```text

Player
```

두 Filter가 있다고 하자.

Team A를 선택한 뒤 Player Filter에

```text

```

보이게 만들고 싶을 수 있다.

이때 Filter Card의

```text

```

를 사용할 수 있다.

```text

    ↓

    ↓

```

다만 Filter 간 의존성이 많아지면 Dashboard Query 부담도 증가할 수 있으므로 무분별하게 사용할 필요는 없다.

# **15. Apply to Worksheets**

> ## **15-1) Filter는 기본적으로 현재 Worksheet에만 적용된다**

Filter를 새로 만들면 기본적으로 현재 Worksheet의 View에 적용된다.

예를 들어 Dashboard가 다음 Sheet로 구성되었다고 하자.

```text
Sheet 1
선수별 HSR

Sheet 2
주간 Player Load

Sheet 3
Sprint Count

Sheet 4
Team Baseline
```

`Season = 2026` Filter를 Sheet 1에 만들었다고 해서 Sheet 2~4에 자동으로 동일하게 적용되는 것은 아니다.

<br>

> ## **15-2) Apply to Worksheets 선택**

대표적인 범위:

```text
Only This Worksheet

Selected Worksheets

All Using This Data Source

All Using Related Data Sources
```

상황에 따라 Filter 적용 범위를 선택할 수 있다.

<br>

> ## **15-3) Selected Worksheets**

예를 들어 Season Filter를

```text
선수 HSR

Player Load

Sprint Count
```

에만 적용하고

```text
Historical Baseline
```

에는 적용하지 않을 수 있다.

```text
Season Filter
    ↓
Selected Worksheets

HSR Sheet       O
Load Sheet      O
Sprint Sheet    O
Baseline Sheet  X
```

Dashboard 지표의 의미를 유지하기 위해 중요한 설계이다.


<br><br>

# **16. 모든 Worksheet에 같은 Filter를 적용하면 안 되는 경우**

> ## **16-1) 현재 선수와 팀 Baseline 비교**

Dashboard:

```text
① 선택 선수 HSR

② 선택 선수 Load

③ 팀 전체 평균 HSR

④ 선택 선수 vs 팀 평균
```

사용자가

```text
Player = P001
```

을 선택한다.

모든 Sheet에 Player Filter를 적용하면

```text
팀 전체 평균
```

Sheet도 P001만 남을 수 있다.

그 결과

```text
팀 평균
= P001 평균
```

처럼 비교 기준이 무너질 수 있다.

<br>

> ## **16-2) 올바른 Filter 범위**

```text
Player Filter

① 선택 선수 HSR
→ 적용

② 선택 선수 Load
→ 적용

③ 팀 전체 평균
→ 적용하지 않음

④ 선수 vs 팀 평균
→ 계산 구조에 따라 선택
```

즉

```text
Filter 적용 범위
=
Dashboard 지표 의미
```

와 맞아야 한다.

# **17. 서로 다른 Data Source에 Filter 적용하기**

> ## **17-1) 관련 Data Source의 공통 Field**

Dashboard가 서로 다른 Data Source를 사용할 수도 있다.

예:

```text
GPS Data Source
→ Player ID / Load / HSR

Wellness Data Source
→ Athlete ID / Sleep / Soreness
```

두 데이터 원본에서

```text
Player ID ↔ Athlete ID
```

가 같은 선수를 나타낸다면 Field Relationship을 정의하여 Filter를 여러 Primary Data Source에 걸쳐 적용할 수 있다.

<br>

> ## **17-2) 주의할 점**

같은 이름이라고 반드시 같은 의미인 것은 아니다.

예:

```text
GPS Date
→ Session Date

Wellness Date
→ Survey Date
```

둘을 단순히 날짜 Field라는 이유만으로 연결하면 분석 의미가 달라질 수 있다.

따라서 Cross-data-source Filter에서는

```text
공통 Field의 의미

Data Type

Grain

값 Domain
```

을 확인해야 한다.

<br>

> ## **17-3) Blending의 Secondary Source 주의**

여러 Data Source를 Blend하는 경우 Filter 공유에는 Primary/Secondary Source와 관련된 제약이 존재할 수 있다.

따라서 서로 다른 Source를 하나의 Dashboard에서 공통 Filter로 제어하려면

```text
Relationship

Cross-Data-Source Filter

Data Model 구조
```

를 먼저 확인하는 것이 좋다.


<br><br>

# **24. Filter Design에서 자주 발생하는 실수**

> ## **24-1) Top N 모집단을 정의하지 않는다**

```text
Top 10
```

만으로는 부족하다.

```text
전체 중 Top 10?

팀 내 Top 10?

포지션 내 Top 10?

선택 시즌 Top 10?
```

를 정의해야 한다.

<br>

> ## **24-2) 모든 Filter를 Context로 만든다**

Context는

```text
다른 Filter의 기준 범위를 먼저 만들 필요가 있을 때
```

사용한다.

일반 Filter만으로 해결되는 문제에 Context를 남용할 필요는 없다.

<br>

> ## **24-3) 모든 Sheet에 Filter를 적용한다**

Dashboard에서

```text
현재 대상
```

과

```text
전체 Baseline
```

을 비교한다면 전체 Baseline Sheet에는 Filter를 적용하지 않아야 할 수 있다.

<br>

> ## **24-4) Quick Filter라는 이름만 보고 별도 Filter 종류라고 생각한다**

Filter Card는 사용자 Interface다.

실제 Order of Operations는 해당 Filter가

```text
Dimension

Measure

Context

Table Calculation
```

중 어떤 단계에 해당하는지에 따라 결정된다.

<br>

> ## **24-5) Table Calculation Filter가 Data Source를 먼저 줄인다고 생각한다**

Rank Filter 같은 Table Calculation Filter는 계산 단계가 늦다.

따라서 일반 Dimension Filter처럼 Query 초기에 데이터를 줄이는 것과 동일하게 이해하면 안 된다.

<br>

> ## **24-6) Filter Action과 Filter Card를 혼동한다**

```text
Filter Card
→ 사용자가 Field 값을 직접 선택

Filter Action
→ Source Viz의 Mark를 이용하여 다른 View 제한
```

이다.

# **28. 핵심정리**

1. Tableau Filter는 단순히 데이터를 숨기는 기능이 아니라 **분석에 사용할 데이터 범위와 계산 순서에 영향을 주는 기능**이다.

2. Filter를 이해할 때 다음 세 가지를 함께 확인해야 한다.

```text
무엇을 Filter하는가?

언제 Filter하는가?

어디까지 적용하는가?
```

3. Tableau는 Filter와 계산을 정해진 `Order of Operations`에 따라 수행한다.

4. 이번 과정에서 중요한 순서를 단순화하면 다음과 같다.

```text
Extract Filter
        ↓
Data Source Filter
        ↓
Context Filter
        ↓
FIXED LOD
        ↓
Dimension / Top Filter
        ↓
INCLUDE / EXCLUDE LOD
        ↓
Measure Filter
        ↓
Table Calculation
        ↓
Table Calculation Filter
```

5. `Extract Filter`는 Extract에 포함할 데이터 범위를 제한한다.

6. `Data Source Filter`는 해당 Data Source에서 분석에 사용할 기본 데이터 범위를 제한한다.

7. `Dimension Filter`는 Region, Position, Player, Category와 같은 Dimension Member를 기준으로 데이터를 제한한다.

8. `Measure Filter`는 다음처럼 Aggregate Measure의 결과를 기준으로 제한한다.

```text
SUM([HSR])
>= 10,000
```

9. `Context Filter`는 다른 일반 Dimension Filter보다 먼저 적용되어 **후속 Filter가 사용할 기준 데이터 범위**를 만든다.

10. Context Filter의 대표적인 활용은 특정 범위 내부의 Top N이다.

```text
Winger
    ↓
Context
    ↓
Winger 중 HSR Top 5
```

11. 다음 두 질문은 서로 다르다.

```text
전체 Top 5 중 Winger

Winger 중 Top 5
```

12. 따라서 Top N에서는 반드시 **모집단을 먼저 정의**해야 한다.

13. Context Filter는 무조건 성능을 높이는 기능이 아니다.

14. Context의 핵심은

```text
Filter 실행 순서를 조절하고
후속 계산의 기준 범위를 만드는 것
```

이다.

15. `FIXED LOD`는 일반 Dimension Filter보다 먼저 계산될 수 있다.

16. 따라서 일반 Dimension Filter를 적용했는데도 FIXED 값이 그대로 유지되는 상황이 발생할 수 있다.

17. 특정 Filter가 FIXED 계산보다 먼저 적용되어야 한다면 Context Filter를 검토할 수 있다.

18. 그러나 Context만 사용하기 전에 LOD 자체의 Grain을 수정하는 것이 더 명확한 설계인지도 확인해야 한다.

19. `Table Calculation Filter`는 Table Calculation 이후 단계에서 결과 Mark를 제한한다.

20. 따라서

```text
Dimension Top N Filter
```

와

```text
RANK() 기반 Table Calculation Filter
```

는 비슷한 화면을 만들더라도 실행 단계가 다르다.

21. `RANK()` 방식에서는 Compute Using, Addressing, Partitioning이 결과에 영향을 준다.

22. 과거의 `Quick Filter`는 독립된 Order of Operations 단계가 아니다.

23. 현재는 `Show Filter`를 통해 표시되는 Interactive Filter 또는 Filter Card로 이해하는 것이 정확하다.

24. Filter Card는 다음과 같은 UI 형태로 제공할 수 있다.

```text
Single Value List

Single Value Dropdown

Multiple Values List

Multiple Values Dropdown

Range
```

25. `Only Relevant Values`를 사용하면 다른 Filter의 선택에 따라 현재 Filter에서 선택 가능한 값을 제한할 수 있다.

26. Filter는 기본적으로 현재 Worksheet에만 적용된다.

27. `Apply to Worksheets`를 이용하면 다음과 같이 범위를 조절할 수 있다.

```text
Only This Worksheet

Selected Worksheets

All Using This Data Source

All Using Related Data Sources
```

28. 모든 Dashboard Sheet에 동일한 Filter를 적용하는 것이 항상 올바른 것은 아니다.

29. 특히 다음처럼 비교 기준이 필요한 Sheet는 Filter에서 제외해야 할 수 있다.

```text
선택 선수
vs
전체 Team 평균

선택 지역
vs
전국 평균
```

30. 서로 다른 Data Source에 동일한 Filter를 적용하려면 공통 Field와 Data Source 관계를 확인해야 한다.

31. 공통 Field는 단순히 이름이 같은지만 확인할 것이 아니라 다음을 검증해야 한다.

```text
Data Type

값의 의미

Granularity

Domain
```

32. Dashboard의 `Filter Action`을 사용하면 하나의 View에서 선택한 Mark로 다른 View를 Filter할 수 있다.

33. 예를 들어

```text
Position Bar 선택
        ↓
Filter Action
        ↓
Player Trend Filter
```

와 같은 Interactive Dashboard를 만들 수 있다.

34. `Filter Card`와 `Filter Action`은 역할이 다르다.

```text
Filter Card
→ 사용자가 Field 값을 직접 선택

Filter Action
→ 사용자가 Visualization의 Mark를 선택
```

35. Filter와 Parameter도 구분해야 한다.

```text
Filter
→ Data 범위 변경

Parameter
→ 분석 기준값 변경
```

36. Dashboard에서는 여러 기능을 조합할 수 있다.

```text
Season
→ Filter Card

Position
→ Filter Action

Metric
→ Parameter

Player
→ Parameter Action
```

37. 이를 이용하면 사용자가

```text
큰 범위 선택
    ↓
세부 Category 탐색
    ↓
Metric 변경
    ↓
특정 개체 상세 분석
```

순서로 자연스럽게 Dashboard를 탐색할 수 있다.

38. 스포츠 Dashboard의 대표적인 Filter 활용은 다음과 같다.

```text
축구 GPS
→ Season / Position Filter

수영
→ Event / Competition Filter

야구
→ Pitcher / Pitch Type Filter

운동역학
→ Group / Condition Filter

운동처방
→ Program / Intensity Filter

웨어러블
→ Athlete / Date Range Filter
```

39. Filter 설계에서 가장 중요한 것은 Filter 개수가 아니다.

40. 핵심은 각 지표가 **어떤 데이터 범위를 기준으로 계산되어야 하는지 유지하는 것**이다.

41. Filter 결과가 이상하면 다음 순서로 점검한다.

```text
Filter Type
        ↓
Order of Operations
        ↓
Top N Population
        ↓
LOD Order
        ↓
Table Calculation
        ↓
Apply to Worksheets
        ↓
Dashboard Action
```

42. 최종적으로 Filter 분석은 다음 흐름으로 이해할 수 있다.

```text
Analysis Question
        ↓
필요 Data 범위 정의
        ↓
Filter 대상 정의
        ↓
Filter 종류 결정
        ↓
실행 순서 확인
        ↓
Context 필요 여부
        ↓
LOD / Top N /
Table Calculation 관계 확인
        ↓
Worksheet 적용 범위 결정
        ↓
Filter Card /
Filter Action 결정
        ↓
Dashboard Interaction
        ↓
Sample 검증
        ↓
Interpretation
```

"어떤 데이터를 남길 것인가?"
