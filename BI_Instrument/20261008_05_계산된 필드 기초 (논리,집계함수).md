# **1. Calculated Field - 원본에 없는 지표 만들기**

> ## **1-1) Calculated Field란?**

실제 분석에서는 원본 데이터에 저장된 값만 사용하는 것이 아니라 **분석 질문에 필요한 새로운 지표를 직접 정의**해야 하는 경우가 많다.

예를 들어 축구 경기 데이터에 다음 Field가 있다고 가정한다.

```text
match_id
team_score
opponent_score
shots
goals
possession_pct
```

하지만 실제 분석에서는 다음과 같은 지표가 필요할 수 있다.

```text
득실점 차이

슈팅 득점 전환율

경기 결과

목표 득점 달성 여부
```

원본에 이러한 Field가 없다면 Tableau의 `Calculated Field`를 이용하여 새롭게 만들 수 있다.

```text
기존 Field
    ↓
계산식
    ↓
Calculated Field
    ↓
Visualization
```

Calculated Field는 기존 Field, 상수, 연산자, 함수 등을 이용해 새로운 값을 정의한다.

Calculated Field를 생성해도 원본 Database나 CSV에 실제 Column이 추가되는 것은 아니며, Tableau에서 사용할 수 있는 새로운 계산 Field가 만들어진다.

<br>

> ## **1-2) 축구 경기 점수차 계산**

[ Tableau : code ] "축구 경기별 득실점 차이 계산"

```text
[Team Score] - [Opponent Score]
```

Field 이름:

```text
Goal Difference
```

원본 데이터가 다음과 같다면

```text
Match   Team Score   Opponent Score

M001         3              1
M002         1              1
M003         0              2
```

[ Result ]

```text
Match   Goal Difference

M001          2
M002          0
M003         -2
```

해석:

```text
양수
→ 상대보다 더 많은 득점

0
→ 동점

음수
→ 상대보다 적은 득점
```

이 계산은 각 행에서 수행되는 **Row-level Calculation**이다.

<br>

> ## **1-3) 계산된 Field는 다른 계산에도 사용할 수 있다**

앞에서 만든 `[Goal Difference]`를 이용하여 다시 경기 결과를 만들 수도 있다.

[ Tableau : code ] "득실점 차이를 이용한 경기 결과 분류"

```text
IF [Goal Difference] > 0 THEN "Win"
ELSEIF [Goal Difference] = 0 THEN "Draw"
ELSE "Loss"
END
```

[ Result ]

```text
M001 → Win
M002 → Draw
M003 → Loss
```

즉 Calculated Field는 한 번 만든 뒤

```text
Rows / Columns

Color

Label

Filter

다른 Calculated Field
```

등에서 일반 Field처럼 활용할 수 있다.

# **2. Row - level Calculation과 Aggregate Calculation**

> ## **2-1) Tableau 계산에서 매우 중요한 두 수준**

Calculated Field를 이해할 때 가장 중요한 것은

```text
계산이 어느 수준에서 수행되는가?
```

이다.

기본적으로 다음 두 계산을 구분해야 한다.

| 구분 | 계산 시점 | 예 |
| --- | --- | --- |
| Row-level | 원본 각 행 | `[Goals] / [Shots]` |
| Aggregate | 현재 View의 집계 수준 | `SUM([Goals]) / SUM([Shots])` |

Tableau의 기본 계산식에서 집계되지 않은 Data Source Field를 직접 참조하면 원본 데이터의 Row Level에서 계산된다.

반대로 `SUM()`, `AVG()` 등의 Aggregate를 사용한 계산은 View의 Dimension 구성에 따른 집계 수준에서 계산된다.

<br>

> ## **2-2) Row-level 계산**

다음과 같은 팀별 경기 데이터가 있다고 하자.

```text
Match   Goals   Shots

M001      2       10
M002      1        2
```

다음 계산은

[ Tableau : code ] "경기별 슈팅 득점률 계산"

```text
[Goals] / [Shots]
```

각 행마다 수행된다.

[ Result ]

```text
M001
2 / 10
= 0.20
= 20%

M002
1 / 2
= 0.50
= 50%
```

즉 새로운 Row-level Field는

```text
20%
50%
```

가 된다.

<br>

> ## **2-3) Aggregate 계산**

이번에는 전체 두 경기의 슈팅 전환율을 계산한다고 하자.

지표 정의는

```text
                 전체 득점
전체 득점률 = ─────────────
                 전체 슈팅
```

이다.

따라서 다음 계산이 적절하다.

[ Tableau : code ] "전체 슈팅 대비 전체 득점 전환율"

```text
SUM([Goals])
/
SUM([Shots])
```

계산하면

```text
전체 Goals
= 2 + 1
= 3

전체 Shots
= 10 + 2
= 12
```

[ Result ]

```text
3
──
12

= 0.25
= 25%
```

이 계산은 현재 View의 수준에서 `Goals`와 `Shots`를 각각 집계한 뒤 비율을 계산한다.

<br>

> ## **2-4) 평균 비율과 전체 비율은 다를 수 있다**

각 경기의 전환율을 먼저 계산한 뒤 평균을 내면

```text
20% + 50%
──────────
     2

= 35%
```

이다.

하지만 전체 득점률은

```text
3
──
12

= 25%
```

이다.

즉,

```text
AVG([Goals] / [Shots])
```

와

```text
SUM([Goals]) / SUM([Shots])
```

는 같은 계산이 아니다.

| 계산 | 결과 | 의미 |
| --- | ---: | --- |
| `AVG([Goals] / [Shots])` | 35% | 경기별 전환율의 단순 평균 |
| `SUM([Goals]) / SUM([Shots])` | 25% | 전체 슈팅 대비 전체 득점 |

실무 지표에서는 **계산식을 작성하기 전에 지표의 정의를 먼저 결정해야 한다.**

# **3. Row-level과 Aggregate를 혼합할 때 발생하는 오류**

> ## **3-1) Aggregate와 Non-Aggregate를 그대로 혼합할 수 없다**

다음 계산을 생각해보자.

```text
SUM([Total Distance M]) / [Match Duration Min]
```

`SUM([Total Distance M])`는 Aggregate이다.

반면

```text
[Match Duration Min]
```

은 Row-level Field이다.

따라서 Tableau에서는 이러한 계산에서

```text
Cannot mix aggregate and non-aggregate...
```

유형의 오류가 발생할 수 있다.

Tableau Aggregate Calculation에서는 계산식의 인수들이 같은 집계 수준을 가져야 한다.

<br>

> ## **3-2) 올바르게 수준 맞추기**

현재 View에서 총 이동거리와 총 경기시간을 이용한 평균 거리 비율이 목적이라면

[ Tableau : code ] "집계 수준을 맞춘 계산"

```text
SUM([Total Distance M])
/
SUM([Match Duration Min])
```

처럼 양쪽을 Aggregate할 수 있다.

반대로 각 행 수준에서 계산해야 한다면

```text
[Total Distance M]
/
[Match Duration Min]
```

처럼 둘 다 Row-level로 계산할 수 있다.

```text
Row-level
+
Row-level
→ 가능

Aggregate
+
Aggregate
→ 가능

Aggregate
+
Row-level
→ 일반적으로 불가
```

라고 이해하면 된다.

<br>

> ## **3-3) Aggregate Calculated Field의 AGG 표시**

예를 들어 다음 Calculated Field를 만든다고 하자.

```text
SUM([Goals]) / SUM([Shots])
```

Field 이름:

```text
Shot Conversion Rate
```

이를 View에 배치하면 Tableau에서는 일반적인 `SUM(Field)` 대신

```text
AGG(Shot Conversion Rate)
```

형태로 표시될 수 있다.

이는 해당 Field 자체가 이미 Aggregate Calculation이기 때문이다.

# **4. IF - 조건에 따라 데이터를 분류하기**

> ## **4-1) IF 기본 구조**

`IF`는 조건을 평가한 뒤 결과를 반환한다.

기본 구조는 다음과 같다.

```text
IF 조건 THEN 결과
ELSE 결과
END
```

여러 조건이 있다면

```text
IF 조건1 THEN 결과1
ELSEIF 조건2 THEN 결과2
ELSE 결과3
END
```

처럼 사용할 수 있다.

<br>

> ## **4-2) 축구 GPS Training Load 분류**

선수의 `Player Load`를 다음 기준으로 분류한다고 가정한다.

```text
700 이상
→ High

550 이상
→ Moderate

그 외
→ Low
```

[ Tableau : code ] "선수 세션 부하 수준 분류"

```text
IF [Player Load] >= 700 THEN "High"
ELSEIF [Player Load] >= 550 THEN "Moderate"
ELSE "Low"
END
```

데이터가

```text
Player    Player Load

P001          742
P002          618
P003          491
```

이라면

[ Result ]

```text
P001 → High
P002 → Moderate
P003 → Low
```

<br>

> ## **4-3) IF 조건의 순서가 중요하다**

다음과 같이 조건 순서를 반대로 작성하면 문제가 생긴다.

```text
IF [Player Load] >= 550 THEN "Moderate"
ELSEIF [Player Load] >= 700 THEN "High"
...
```

`742`는 첫 번째 조건인

```text
742 >= 550
```

에서 이미 `TRUE`가 된다.

따라서 결과는 `High`가 아니라

```text
Moderate
```

가 되어 버린다.

범위를 구분할 때는 일반적으로

```text
가장 높은 기준
    ↓
낮은 기준
```

순서로 조건을 배치해야 한다.

# **5. CASE - 하나의 값에 따라 Category 재분류**

> ## **5-1) CASE의 특징**

`CASE`는 하나의 Expression 결과를 여러 값과 비교할 때 사용하기 편리하다.

기본 구조는

```text
CASE [Field]
    WHEN "A" THEN 결과1
    WHEN "B" THEN 결과2
    ELSE 결과3
END
```

이다.

`CASE`는 특히

```text
Position = "CB"

Position = "FB"

Position = "CM"
```

처럼 **하나의 Field의 값 자체를 비교**할 때 간결하다.

`IF`처럼 각 분기에서 서로 다른 복잡한 논리 조건을 자유롭게 검사하는 구조와는 차이가 있다.

<br>

> ## **5-2) 축구 포지션 그룹화**

[ Tableau : code ] "세부 포지션을 큰 포지션 그룹으로 재분류"

```text
CASE [Position]

    WHEN "CB" THEN "Defender"
    WHEN "FB" THEN "Defender"

    WHEN "CM" THEN "Midfielder"
    WHEN "DM" THEN "Midfielder"
    WHEN "WM" THEN "Midfielder"

    WHEN "ST" THEN "Forward"

    ELSE "Other"

END
```

[ Result ]

```text
CB → Defender
FB → Defender
CM → Midfielder
DM → Midfielder
ST → Forward
GK → Other
```

<br>

> ## **5-3) IF와 CASE 비교**

| 상황 | IF | CASE |
| --- | --- | --- |
| 숫자 범위 비교 | 적합 | 일반 CASE에는 부적합 |
| 여러 Field를 함께 조건에 사용 | 적합 | 제한적 |
| 하나의 Field 값 재분류 | 가능 | 매우 적합 |
| 복잡한 Boolean 조건 | 적합 | 제한적 |

예를 들어

```text
Player Load >= 700
AND
Sleep < 6
```

처럼 여러 조건을 조합한다면 `IF`가 자연스럽다.

반대로

```text
Position = CB / FB / CM / ST
```

처럼 하나의 값을 재분류한다면 `CASE`가 읽기 쉽다.

# **6. IIF - True / False / Unknown을 간단하게 처리**

> ## **6-1) IIF 기본 구조**

`IIF`의 기본 문법은 다음과 같다.

```text
IIF(
    조건,
    True 결과,
    False 결과
)
```

Tableau의 `IIF`는 선택적으로 네 번째 인수를 사용할 수 있다.

```text
IIF(
    조건,
    True 결과,
    False 결과,
    Unknown 결과
)
```

조건의 결과가 `NULL`, 즉 Unknown인 경우 네 번째 값을 반환하도록 지정할 수 있다. 네 번째 값을 지정하지 않으면 Unknown 결과는 `NULL`이다.

<br>

> ## **6-2) 경기 출전 가능 여부**

선수의 복귀 예정일이 경기일 이전인지 판단한다고 가정한다.

[ Tableau : code ] "복귀 예정일 기반 경기 출전 가능 여부"

```text
IIF(
    [Return Date] <= [Match Date],
    "Available",
    "Unavailable",
    "Unknown"
)
```

데이터:

```text
Player   Return Date   Match Date

P001     2026-03-10    2026-03-15
P002     2026-03-20    2026-03-15
P003     NULL          2026-03-15
```

[ Result ]

```text
P001 → Available
P002 → Unavailable
P003 → Unknown
```

`P003`처럼 비교 자체를 판단할 수 없는 경우를 `Unknown`으로 별도 관리할 수 있다.

<br>

> ## **6-3) IF와 IIF의 NULL 처리 차이**

`IF`에서는 Test가 `NULL`이면 `TRUE`가 아니므로 일반적으로 `ELSE` 쪽으로 처리된다.

반면 `IIF`는 선택적인 `Unknown` 반환값을 별도로 지정할 수 있다.

따라서 Missing Value를

```text
False와 동일하게 처리할 것인가?

Unknown으로 구분할 것인가?
```

를 먼저 결정해야 한다.

# **7. 논리 함수 선택 기준**

> ## **7-1) IF / CASE / IIF 비교**

| 함수 | 적합한 상황 | 스포츠 예 |
| --- | --- | --- |
| `IF` | 범위·복합조건·여러 조건 | Training Load 분류 |
| `CASE` | 하나의 Field 값 재분류 | 포지션 그룹화 |
| `IIF` | 간단한 True/False 분기 | 목표 기록 달성 여부 |
| `IIF` 4번째 인수 | Unknown 별도 처리 | 복귀일 NULL 처리 |

선택 방법은 다음과 같이 생각할 수 있다.

```text
범위를 비교하는가?
→ IF

하나의 Field 값과
여러 Category를 비교하는가?
→ CASE

단순 True / False인가?
→ IIF

NULL을 False와 구분해야 하는가?
→ IIF의 Unknown 처리 고려
```

# **8. Aggregate Function(집계함수) - 여러 행을 하나의 지표로 요약**

> ## **8-1) Aggregate의 의미**

`Aggregate Function`은 여러 Row의 값을 하나의 값으로 요약한다.

Tableau에서 Measure를 View에 추가하면 기본적으로 `SUM`, `AVG` 등의 Aggregation이 적용되는 경우가 많다.

대표적인 함수는 다음과 같다.

| 함수 | 의미 | 스포츠 예 |
| --- | --- | --- |
| `SUM` | 합계 | 전체 이동거리 |
| `AVG` | 평균 | 평균 구속 |
| `MIN` | 최솟값 | 최소 Lap Time |
| `MAX` | 최댓값 | 최고 속도 |
| `COUNT` | Non-Null 값 개수 | 기록이 존재하는 행 수 |
| `COUNTD` | Non-Null 고유 값 개수 | 고유 선수 수 |

<br>

> ## **8-2) 수영 종목별 평균 기록**

[ Tableau : code ] "100m 자유형 평균 기록"

```text
AVG([Race Time Sec])
```

원본:

```text
Athlete   Race Time

A           53.20
B           54.10
C           52.70
D           53.60
```

[ Result ]

```text
53.40 sec
```

계산:

```text
53.20 + 54.10 + 52.70 + 53.60
─────────────────────────────
              4

= 53.40
```

<br>

> ## **8-3) 최고 속도**

[ Tableau : code ] "야구 투수 최고 구속"

```text
MAX([Pitch Velocity Kmh])
```

데이터:

```text
148.2
151.3
149.8
153.1
150.7
```

[ Result ]

```text
153.1 km/h
```

# **9. COUNT와 COUNTD의 차이**

> ## **9-1) COUNT는 행 개수와 완전히 같은 말이 아니다**

`COUNT([Field])`는 해당 Expression에서 **NULL이 아닌 값의 개수**를 계산한다. (중복을 포함한 행의 개수 : python에서 count()에 해당)

`COUNTD([Field])`는 **NULL을 제외한 고유 값의 개수**를 계산한다. (고유값이므로 중복을 포함하지 않는 행의 개수 : python에서 n_unique()에 해당)

예를 들어 데이터가 다음과 같다고 하자.

```text
Row   Player ID

1     P001
2     P001
3     P002
4     NULL
5     P003
```

다음 계산은

```text
COUNT([Player ID])
```

[ Result ]

```text
4
```

이다.

`NULL`은 Count되지 않는다.

<br>

> ## **9-2) COUNTD**

[ Tableau : code ] "실제 참여한 고유 선수 수 계산"

```text
COUNTD([Player ID])
```

[ Result ]

```text
3
```

고유 값은

```text
P001
P002
P003
```

이므로 3명이다.

<br>

> ## **9-3) 실무에서 COUNTD가 중요한 이유**

GPS Dataset에서 한 선수가 여러 경기와 세션에 반복적으로 존재한다고 하자.

```text
P001
P001
P001
P002
P002
P003
```

`COUNT([Player ID])`

```text
6
```

은 관측된 Non-Null 값의 수이고,

`COUNTD([Player ID])`

```text
3
```

은 고유 선수 수이다.

따라서

```text
선수 수
사용자 수
경기 수
세션 수
```

처럼 Entity 개수를 계산할 때는 `COUNTD`가 필요한지 확인해야 한다.

# **10. 실무 지표 계산 - 비율은 정의가 가장 중요하다**

> ## **10-1) 축구 Shot Conversion Rate**

경기 데이터가

```text
Goals
Shots
```

로 저장되어 있고 전체 득점률을 계산한다면

[ Tableau : code ] "전체 슈팅 전환율"

```text
SUM([Goals])
/
SUM([Shots])
```

만약

```text
Goals = 12
Shots = 80
```

이라면

[ Result ]

```text
12
──
80

= 0.15
= 15%
```

<br>

> ## **10-2) 경기당 평균 득점**

전체 득점을 경기 수로 나누고 싶다면

[ Tableau : code ] "경기당 평균 득점"

```text
SUM([Goals])
/
COUNTD([Match ID])
```

전체 득점이 `36`이고 고유 경기 수가 `18`이라면

[ Result ]

```text
36
──
18

= 2.0 Goals / Match
```

<br>

> ## **10-3) 지표의 분모를 먼저 확인한다**

비율 계산에서는 특히 분모의 의미가 중요하다.

예를 들어

```text
부상률
```

이라는 이름만으로는 계산식을 결정할 수 없다.

다음처럼 여러 정의가 가능하다.

```text
부상 선수 수
────────────
전체 선수 수
```

또는

```text
부상 사건 수
────────────
1000 Exposure Hours
```

또는

```text
부상 경기 수
────────────
전체 경기 수
```

즉, 계산식을 먼저 만드는 것이 아니라

```text
지표 정의
    ↓
분자
    ↓
분모
    ↓
계산 수준
```

을 먼저 결정해야 한다.

# **11. NULL 처리**

> ## **11-1) NULL과 0은 같은 값이 아니다**

스포츠 데이터에서 `NULL`은 다음과 같은 의미일 수 있다.

```text
측정하지 않음

센서 오류

선수가 참가하지 않음

데이터 미수집
```

반면 `0`은

```text
측정했지만 실제 값이 0
```

일 수 있다.

따라서

```text
NULL = 0
```

으로 무조건 변경하면 분석 의미가 달라질 수 있다.

<br>

> ## **11-2) ISNULL**

NULL 여부를 확인하려면 `ISNULL()`을 사용할 수 있다.

[ Tableau : code ] "GPS 데이터 누락 여부 표시"

```text
IF ISNULL([HSR Distance M]) THEN "Missing"
ELSE "Recorded"
END
```

[ Result ]

```text
1180 → Recorded
NULL → Missing
890  → Recorded
```

<br>

> ## **11-3) IFNULL**

NULL일 때 다른 값을 반환하도록 만들 수도 있다.

```text
IFNULL([Field], 대체값)
```

예를 들어

[ Tableau : code ] "부상 분류 누락값을 별도 Category로 처리"

```text
IFNULL([Injury Type], "No Record")
```

<br>

> ## **11-4) ZN**

`ZN()`은 값이 NULL이 아니면 원래 값을 반환하고, NULL이면 `0`을 반환한다.

```text
ZN([Sprint Count])
```

하지만

```text
NULL
→ 0
```

으로 바꾸는 것이 분석적으로 타당할 때만 사용해야 한다.

```text
측정 누락
≠
Sprint 0회
```

일 수 있기 때문이다.

# **12. String Function - 문자형 Field 가공**

> ## **12-1) 문자열 함수의 역할**

실무에서는 ID나 코드에 여러 정보가 함께 저장되는 경우가 있다.

예를 들어 선수 코드가 다음과 같다고 하자.

```text
U23-P017
U18-P031
PRO-P008
```

분석에서는

```text
U23
U18
PRO
```

부분만 추출하고 싶을 수 있다.

문자열 함수에는 다음과 같은 함수가 있다.

| 함수 | 역할 |
| --- | --- |
| `LEFT` | 왼쪽에서 문자 추출 |
| `RIGHT` | 오른쪽에서 문자 추출 |
| `MID` | 지정 위치에서 문자 추출 |
| `CONTAINS` | 문자열 포함 여부 |
| `SPLIT` | 구분자로 문자열 분리 |

문자열 함수의 세부 지원 범위는 Data Source에 따라 일부 차이가 있을 수 있다. 특히 `SPLIT` 기능에는 Connector별 제한이 있을 수 있다.

<br>

> ## **12-2) LEFT**

[ Tableau : code ] "선수 코드에서 연령 그룹 추출"

```text
LEFT([Athlete Code], 3)
```

데이터:

```text
U23-P017
U18-P031
```

[ Result ]

```text
U23
U18
```

<br>

> ## **12-3) CONTAINS**

다음처럼 세션 이름에 `MATCH`가 포함된 데이터를 구분할 수도 있다.

[ Tableau : code ] "경기 세션과 훈련 세션 분류"

```text
IF CONTAINS([Session Name], "MATCH") THEN "Match"
ELSE "Training"
END
```

[ Result ]

```text
MATCH_20261001
→ Match

TRAINING_MD-2
→ Training
```

# **13. Date Function - 데이터의 시간 계산**

> ## **13-1) 날짜 함수**

대표적인 날짜 함수에는 다음이 있다.

| 함수 | 역할 |
| --- | --- |
| `YEAR()` | 연도 |
| `MONTH()` | 월 |
| `DAY()` | 일 |
| `DATEADD()` | 날짜 증감 |
| `DATEDIFF()` | 두 날짜 간 Date Part 차이 |
| `DATETRUNC()` | 날짜를 특정 단위 시작점으로 절삭 |

Tableau의 `DATEDIFF`는 두 날짜 사이의 차이를 지정한 `date_part` 단위로 반환하고, `DATETRUNC`는 날짜를 지정된 단위의 시작 시점에 맞춘 새로운 Date 값을 반환한다.

<br>

> ## **13-2) 부상 후 복귀 소요일**

다음 Field가 있다고 하자.

```text
Injury Date
Return To Play Date
```

[ Tableau : code ] "부상 발생일부터 복귀일까지 일수 계산"

```text
DATEDIFF(
    'day',
    [Injury Date],
    [Return To Play Date]
)
```

예:

```text
Injury Date
2026-03-01

Return Date
2026-03-15
```

[ Result ]

```text
14 days
```

이를 이용하면

```text
부상 유형별 평균 복귀 기간

포지션별 복귀 기간

시즌별 평균 결장 기간
```

등을 분석할 수 있다.

<br>

> ## **13-3) 월 단위 날짜 만들기**

일별 GPS Data를 월 단위 추세로 분석하고 싶다면

[ Tableau : code ] "세션 날짜를 월 시작일 기준으로 통일"

```text
DATETRUNC(
    'month',
    [Session Date]
)
```

예:

```text
2026-03-05
2026-03-18
2026-03-29
```

[ Result ]

```text
2026-03-01
2026-03-01
2026-03-01
```

즉 같은 달의 날짜가 동일한 월 기준 Date로 정리된다.

# **14. Parameter - 사용자가 계산 기준을 변경하기**

> ## **14-1) Parameter의 정확한 역할**

Parameter는 Workbook에서 사용할 수 있는 숫자, 문자열, 날짜 등의 **변수 값**이다.

Parameter는 생성한 것만으로 데이터를 변경하거나 Filtering하지 않는다.

다음과 같은 요소에서 Parameter를 실제로 참조해야 동작한다.

```text
Calculated Field

Filter

Reference Line

기타 Parameter를 지원하는 요소
```

Tableau의 Parameter는 Workbook 전체에서 사용할 수 있고 Parameter Control, Parameter Action, Dynamic Parameter 등을 이용해 값을 변경할 수 있다.

<br>

> ## **14-2) Player Load 기준 Parameter**

고부하 기준을 고정값

```text
700
```

으로 계산식 안에 직접 쓰면 기준을 변경할 때 계산식을 수정해야 한다.

대신

```text
[High Load Threshold]
```

라는 Parameter를 만든다고 하자.

초깃값:

```text
700
```

[ Tableau : code ] "Parameter 기반 고부하 세션 분류"

```text
IF [Player Load] >= [High Load Threshold]
THEN "High Load"
ELSE "Normal"
END
```

Player Load가

```text
742
618
701
```

이고 Parameter가

```text
700
```

이라면

[ Result ]

```text
742 → High Load
618 → Normal
701 → High Load
```

Parameter를

```text
650
```

으로 변경하면 계산 결과도 즉시 변경된다.

```text
742 → High Load
618 → Normal
701 → High Load
```

`P002 = 660`이었다면 기준 변경에 따라

```text
700 기준 → Normal
650 기준 → High Load
```

처럼 결과가 달라진다.

<br>

> ## **14-3) Parameter와 Filter 차이**

| 구분 | Parameter | Filter |
| --- | --- | --- |
| 기본 역할 | 값 입력 | 데이터 범위 제한 |
| 자체적으로 Row 제외 | X | O |
| 계산식 기준 변경 | O | 직접적인 목적은 아님 |
| Reference Line 제어 | O | 일반적인 역할 아님 |
| 값 선택 | 하나의 현재 Parameter 값 | Field의 여러 Member 선택 가능 |

따라서

```text
어떤 선수를 화면에서 제외할 것인가?
→ Filter

고부하 기준을 650 / 700 / 750으로
사용자가 바꾸게 할 것인가?
→ Parameter
```

처럼 구분할 수 있다.

# **16. 실무형 예제 - 운동역학 비대칭 지표**

> ## **16-1) 좌우 Force 비대칭**

Countermovement Jump에서 좌우 Peak Force가 다음과 같이 기록되었다고 하자.

```text
Left Peak Force
Right Peak Force
```

단순 차이는

[ Tableau : code ] "좌우 Peak Force 절대 차이"

```text
ABS(
    [Left Peak Force N]
    -
    [Right Peak Force N]
)
```

데이터:

```text
Left  = 1120 N
Right = 980 N
```

[ Result ]

```text
140 N
```

<br>

> ## **16-2) 비대칭 백분율**

연구나 실무에서 비율형 비대칭 지표를 정의했다고 가정한다.

```text
                    |Left - Right|
Asymmetry (%) = ───────────────────── × 100
                   (Left + Right) / 2
```

[ Tableau : code ] "좌우 Peak Force 평균 대비 비대칭률"

```text
ABS(
    [Left Peak Force N]
    -
    [Right Peak Force N]
)
/
(
    (
        [Left Peak Force N]
        +
        [Right Peak Force N]
    )
    / 2
)
* 100
```

계산:

```text
       140
──────────────── × 100
 (1120+980) / 2
```

[ Result ]

```text
13.33%
```

이 계산은 각 측정 Trial에 대해 수행되는 Row-level Calculation이다.

<br>

> ## **16-3) 평균 비대칭을 볼 때**

각 Trial에서 비대칭률을 계산한 뒤 선수별 평균을 보고 싶다면

```text
AVG([Asymmetry %])
```

를 사용할 수 있다.

여기서

```text
선수별 각 Trial의 비대칭률 평균
```

과

```text
선수의 전체 Left 평균과
전체 Right 평균으로 다시 계산한 비대칭률
```

은 서로 다른 지표일 수 있다.

따라서 연구 분석에서는 **계산 순서도 지표 정의의 일부**이다.

# **18. 자주 발생하는 계산 실수**

> ## **18-1) 행별 비율 평균을 전체 비율이라고 생각한다**

```text
AVG([Goals] / [Shots])
```

과

```text
SUM([Goals]) / SUM([Shots])
```

는 다를 수 있다.

전체 전환율이 필요하다면 일반적으로 **전체 분자 ÷ 전체 분모**라는 지표 정의와 맞는지 확인해야 한다.

<br>

> ## **18-2) Aggregate와 Row-level Field를 섞는다**

잘못된 예:

```text
SUM([Goals]) / [Shots]
```

현재 목적이 Aggregate 계산이라면

```text
SUM([Goals]) / SUM([Shots])
```

처럼 수준을 맞춘다.

<br>

> ## **18-3) COUNT를 고유 개수라고 생각한다**

```text
COUNT([Player ID])
```

는 고유 선수 수가 아니다.

고유 선수 수라면

```text
COUNTD([Player ID])
```

를 검토한다.

<br>

> ## **18-4) NULL을 무조건 0으로 변경한다**

```text
NULL
→ 데이터 없음

0
→ 실제 값 0
```

일 수 있다.

따라서 `ZN()`이나 `IFNULL()`을 사용하기 전에 Missing의 의미를 확인해야 한다.

<br>

> ## **18-5) CASE로 복잡한 범위 조건을 억지로 만든다**

```text
700 이상
550 이상
```

처럼 범위를 판단하는 문제는 `IF / ELSEIF`가 자연스럽다.

`CASE`는 하나의 Expression을 여러 값과 비교하는 데 더 적합하다.

<br>

> ## **18-6) Parameter를 Filter라고 생각한다**

Parameter는 Workbook Variable이며 자체적으로 데이터를 제거하지 않는다.

```text
Parameter
    ↓
Calculated Field / Filter / Reference Line 등에 연결
    ↓
실제 동작
```

이라는 구조를 이해해야 한다.

```text
10
5
15
```

에서 먼저 직접 계산한다.

```text
Total Goals
= 6

Total Shots
= 30
```

```text
6
──
30

= 20%
```

Tableau 결과도

```text
20%
```

인지 확인한다.

```text
Field Data Type이 올바른가?

Row-level인가 Aggregate인가?

SUM과 AVG 중 무엇이 필요한가?

COUNT와 COUNTD 중 무엇이 필요한가?

NULL은 어떤 의미인가?

분모가 0이 될 가능성이 있는가?

날짜 Grain은 올바른가?

View의 Dimension이 바뀌면

```

# **20. Advanced 추가 학습**

> ## **20-1) LOD Expression**

일반 Aggregate Calculation은 현재 View의 Dimension 구성에 영향을 받는다.

반면 LOD Expression을 사용하면

```text
선수별

경기별

시즌 전체
```

등 특정 Level of Detail에서 계산하도록 지정할 수 있다.

대표적인 형태는

```text
FIXED

INCLUDE

EXCLUDE
```

이다.

계산 수준을 View와 독립적으로 제어해야 할 때 추가로 학습하면 좋다. Tableau의 Calculated Field는 기본 표현식뿐 아니라 LOD Expression과 Table Calculation 같은 다른 계산 유형도 지원한다.

<br>

> ## **20-2) Table Calculation**

Table Calculation은 Data Source의 원본 Row에서 직접 계산하는 것이 아니라 **현재 Visualization에 표시된 결과를 기반으로 계산**한다.

예를 들어

```text
Running Total

Percent of Total

Moving Average

Rank
```

등이 대표적이다.

<br>

> ## **20-3) Dynamic Parameter와 Parameter Action**

Parameter는 고정된 목록만 사용하는 것이 아니라 Data Source를 기준으로 값 목록이나 현재 값을 새로 고치는 Dynamic Parameter로 구성할 수도 있다.

또한 Parameter Action을 이용하면 사용자가 Visualization의 Mark를 클릭하여 Parameter 값을 바꾸는 Interaction도 만들 수 있다.

# **21. 핵심정리**

1. `Calculated Field`는 기존 Field와 함수·연산자를 이용하여 **원본 데이터에 직접 존재하지 않는 새로운 분석 지표를 정의하는 기능**이다.

2. Calculated Field를 생성한다고 해서 원본 Database나 파일 자체에 Column이 추가되는 것은 아니다.

3. Tableau 계산을 이해할 때 가장 먼저 구분해야 하는 것은 다음 두 가지이다.

```text
Row-level Calculation
→ 각 원본 Row에서 계산

Aggregate Calculation
→ 여러 Row를 현재 View 수준에서 집계하여 계산
```

4. 다음 두 식은 계산 수준과 의미가 다르다.

```text
[Goals] / [Shots]
```

```text
SUM([Goals]) / SUM([Shots])
```

5. Row-level 비율의 평균과 전체 비율은 서로 다른 결과를 만들 수 있으므로 **지표 정의를 먼저 결정해야 한다.**

6. 비율 지표는 다음 순서로 설계하는 것이 중요하다.

```text
지표 의미 정의
    ↓
분자 정의
    ↓
분모 정의
    ↓
계산 Grain 정의
    ↓
계산식 작성
```

7. Aggregate Calculation에서는 일반적으로 Aggregate와 Non-Aggregate 값을 그대로 혼합할 수 없다.

```text
SUM([Sales]) - [Cost]
→ 오류 가능

SUM([Sales]) - SUM([Cost])
→ Aggregate 수준 일치
```

8. Aggregate Calculated Field를 View에서 사용할 경우 Tableau에서 `AGG(...)` 형태로 표시될 수 있다.

9. `IF`는 범위 또는 복잡한 Boolean 조건을 처리할 때 적합하다.

```text
IF 조건 THEN
ELSEIF 조건 THEN
ELSE
END
```

10. 여러 `ELSEIF`를 사용할 때는 **조건 평가 순서**가 결과에 영향을 줄 수 있으므로 범위 분류에서는 조건 순서에 주의해야 한다.

11. `CASE`는 하나의 Expression 결과를 여러 값과 비교하여 재분류할 때 적합하다.

```text
CASE [Position]
WHEN "CB" THEN "Defender"
...
END
```

12. 모든 `IF` 조건을 `CASE`로 자연스럽게 바꿀 수 있는 것은 아니다. 여러 Field나 복잡한 Boolean 조건을 사용하는 경우 `IF`가 더 적합할 수 있다.

13. `IIF`의 기본 구조는 다음과 같다.

```text
IIF(
    Test,
    True Result,
    False Result,
    Optional Unknown Result
)
```

14. `IIF`는 조건이 `NULL/Unknown`일 때 반환할 결과를 별도로 정의할 수 있다는 특징이 있다.

15. 대표 Aggregate Function은 다음과 같다.

```text
SUM
AVG
MIN
MAX
COUNT
COUNTD
```

16. `COUNT([Field])`는 해당 Field에서 `NULL`이 아닌 값의 수를 계산한다.

17. `COUNTD([Field])`는 `NULL`을 제외한 고유 값의 수를 계산한다.

18. 따라서 반복 측정 데이터에서

```text
COUNT(Player ID)
```

와

```text
COUNTD(Player ID)
```

는 전혀 다른 의미를 가질 수 있다.

19. `NULL`과 `0`은 동일하지 않다.

```text
NULL
→ 값이 없거나 알 수 없음

0
→ 측정된 실제 0
```

일 수 있으므로 무조건 변환해서는 안 된다.

20. `ISNULL()`은 NULL 여부를 판단하고, `IFNULL()`은 NULL일 때 대체 값을 지정하는 데 사용할 수 있다.

21. `ZN()`은 NULL을 0으로 바꿀 수 있지만 Missing과 실제 0이 같은 의미인지 먼저 확인해야 한다.

22. String Function을 사용하면 ID나 코드에서 필요한 문자열을 추출하거나 특정 문자열 포함 여부를 확인할 수 있다.

```text
LEFT
RIGHT
MID
CONTAINS
SPLIT
```

23. Date Function을 사용하면 스포츠 데이터의 기간과 시간 Grain을 계산할 수 있다.

```text
YEAR
MONTH
DAY
DATEADD
DATEDIFF
DATETRUNC
```

24. `DATEDIFF()`는 두 날짜의 차이를 지정된 Date Part 단위로 계산한다.

25. `DATETRUNC()`는 날짜를 해당 연도·분기·월·주 등의 시작 시점으로 맞춘 새로운 Date 값을 반환한다.

26. Parameter는 계산에 사용할 수 있는 Workbook Variable이며 **Parameter 자체가 데이터를 Filtering하는 것은 아니다.**

27. Parameter는 다음 요소와 연결하여 활용할 수 있다.

```text
Calculated Field

Filter

Reference Line

Parameter Action
```

28. 다음과 같은 문제에는 Parameter가 특히 유용하다.

```text
목표값 변경

Threshold 변경

Top N 변경

사용 지표 선택

기준 날짜 변경
```

29. Calculated Field의 실무 설계에서는 함수 문법보다 다음 질문이 더 중요하다.

```text
어떤 지표가 필요한가?

한 행에서 계산하는가?

여러 행을 집계하는가?

분자와 분모는 무엇인가?

NULL은 어떤 의미인가?

현재 View의 Grain은 무엇인가?
```

30. 스포츠 데이터에서는 다음과 같이 활용할 수 있다.

```text
축구
→ Shot Conversion Rate

수영
→ 평균 Race Time

야구
→ 최고 Pitch Velocity

운동역학
→ 좌우 Force Asymmetry

부상 분석
→ Return-to-Play Days

GPS
→ Training Load Category

Dashboard
→ Parameter 기반 Threshold
```

31. 복잡한 계산을 만들었을 때는 작은 Sample Data를 이용하여 **수작업 결과와 Tableau 계산 결과를 반드시 비교**하는 것이 좋다.

32. Calculated Field의 전체 사고 흐름은 다음과 같다.

```text
Analysis Question
        ↓
Metric Definition
        ↓
Row-level / Aggregate 판단
        ↓
필요 Function 선택
        ↓
IF / CASE / IIF
SUM / AVG / COUNTD
String / Date
Parameter
        ↓
NULL 처리
        ↓
계산식 작성
        ↓
Sample 검증
        ↓
Visualization
        ↓
Interpretation
```

33. 결국 계산된 필드의 핵심은

```text
"어떤 함수를 사용할까?"
```

보다

```text
"내가 계산하려는 지표는
어떤 Grain에서,
어떤 분자와 분모를 이용하여,
어떤 의미를 나타내야 하는가?"
```

를 먼저 결정하는 것이다.
