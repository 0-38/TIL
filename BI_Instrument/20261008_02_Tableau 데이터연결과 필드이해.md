# **1. Tableau에서 데이터를 바라보는 기본 구조**

> ## **1-1) Tableau 분석은 질문과 필드에서 시작한다**

Tableau에서는 데이터를 연결한 뒤 각 Column이 **Field(필드)**로 나타난다.

예를 들어 축구 GPS 데이터가 다음과 같다고 가정한다.

| player_id | session_date | position | total_distance_m | hsr_distance_m | sprint_count | player_load |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| P001 | 2026-03-01 | Winger | 10240 | 1120 | 31 | 682 |
| P002 | 2026-03-01 | Midfielder | 10850 | 890 | 22 | 641 |
| P003 | 2026-03-01 | Centerback | 9350 | 520 | 12 | 557 |

Tableau에서는 다음 항목이 각각 하나의 Field가 된다.

```text
player_id
session_date
position
total_distance_m
hsr_distance_m
sprint_count
player_load
```

하지만 모든 Field를 한 번에 사용하는 것이 아니라 **현재 분석 질문에 필요한 Field를 선택한다.**

예를 들어 다음과 같다.

```text
포지션별 평균 Player Load는?
→ position + player_load

선수별 Sprint 횟수는?
→ player_id + sprint_count

주간 HSR 거리는 어떻게 변했는가?
→ session_date + hsr_distance_m
```

즉 Tableau 분석의 기본 사고 과정은 다음과 같다.

```text
분석 질문
    ↓
필요 Field 선택
    ↓
각 Field의 역할 판단
    ↓
Dimension / Measure
    ↓
Discrete / Continuous
    ↓
Rows / Columns / Marks에 배치
    ↓
Visualization
```

<br>

> ## **1-2) Tableau의 주요 분석 영역**

Tableau에서 주로 사용하는 개념은 다음과 같다.

| 영역 | 역할 |
| --- | --- |
| Data Source(데이터 원본) | 분석할 원본 데이터 연결 |
| Data Pane(데이터 창) | 연결된 Field 확인 |
| Columns(열) | 가로 방향 시각화 구조 구성 |
| Rows(행) | 세로 방향 시각화 구조 구성 |
| Marks(마크 카드) | 색상, 크기, 레이블, 세부정보 등의 데이터 표현 방법 조절 |
| View(뷰) | 실제 차트가 표시되는 영역 |
| Show Me | 선택한 Field에 따라 사용할 수 있는 시각화 유형 확인 |

중요한 것은 버튼 위치를 암기하는 것이 아니다.

예를 들어

```text
position → Columns
AVG(player_load) → Rows
```

에 배치했다면 의미는 다음과 같다.

```text
position
→ 데이터를 포지션별로 나눈다.

AVG(player_load)
→ 각 포지션의 평균 Player Load를 계산한다.
```

Tableau의 시각화는 결국 **데이터를 어떤 기준으로 나누고 어떤 값을 계산할지 정의하는 과정**이다.

# **2. 데이터 연결과 Data Type**

> ## **2-1) 데이터 연결 후 가장 먼저 확인할 것**

Tableau는 Excel, CSV, Database 등 다양한 Data Source를 연결하여 사용할 수 있다.

Tableau에 데이터를 연결하면 각 필드의 값을 확인하여 데이터 유형(Data Type)을 인식한다.

데이터를 연결했다고 바로 차트를 만드는 것이 아니라 먼저 다음을 확인해야 한다.

```text
Field 이름이 올바른가?

Date가 Date Type으로 들어왔는가?

숫자가 Number Type으로 인식되었는가?

ID가 계산 대상으로 잘못 인식되지 않았는가?

결측값이나 비정상 값은 없는가?

분석에 필요한 Field가 모두 존재하는가?
```

전체 과정은 다음과 같다.

```text
Data Source 연결
      ↓
Field 확인
      ↓
Data Type 확인
      ↓
Field 의미 확인
      ↓
Dimension / Measure 역할 판단
      ↓
Visualization
```

<br>

> ## **2-2) 주요 Data Type**

Tableau의 Data Type은 **Field에 어떤 종류의 값이 저장되어 있는지**를 의미한다.

| Data Type | 스포츠 데이터 예시 |
| --- | --- |
| String | 선수명, 포지션, 종목 |
| Number | 이동거리, 속도, 심박수 |
| Date | 경기 날짜, 훈련 날짜 |
| Date & Time | 센서 측정 시각 |
| Boolean | 부상 여부, 성공 여부 |

예를 들어 수영 데이터가 다음과 같다고 하자.

```text
athlete_id
race_date
event
reaction_time_sec
race_time_sec
qualified
```

각 Data Type은 다음과 같이 생각할 수 있다.

```text
athlete_id
→ String 또는 식별용 Number

race_date
→ Date

event
→ String

reaction_time_sec
→ Number

race_time_sec
→ Number

qualified
→ Boolean
```

<br>

> ## **2-3) Data Type과 분석 역할은 다른 개념이다**

다음 세 개념을 혼동하면 안 된다.

| 구분 | 질문 |
| --- | --- |
| Data Type | 어떤 종류의 값인가? |
| Dimension / Measure | 분석에서 어떤 역할을 하는가? |
| Discrete / Continuous | View에서 어떻게 표현할 것인가? |

예를 들어 `player_id = 1001`처럼 숫자로 저장되어 있다고 하자.

`player_id`의 Data Type은 Number일 수 있지만

```text
AVG(player_id)
SUM(player_id)
```

는 분석적으로 의미가 없다.

선수를 구분하는 기준이므로 Dimension으로 사용하는 것이 자연스럽다.

```text
숫자 Field
≠
항상 Measure
```

이다.

# **3. Dimension과 Measure**

> ## **3-1) Dimension은 데이터를 나누는 기준이다**

`Dimension`(차원)은 데이터를 **어떤 기준으로 나누거나 그룹화할 것인지** 결정한다.

예를 들어 핸드볼 슈팅 데이터를 분석한다고 가정한다.

```text
player
position
shot_zone
match_id
shot_speed
shot_distance
goal
```

다음 질문이 있다.

```text
포지션별 평균 슈팅 속도는?
```

이때

```text
position
→ 포지션별로 데이터를 나눔
→ Dimension
```

이다.

Dimension은 일반적으로 분석 질문의 **~별**에 해당한다.

```text
선수별
→ player

포지션별
→ position

경기별
→ match_id

슈팅 구역별
→ shot_zone
```

<br>

> ## **3-2) Measure는 그룹에서 계산할 값이다**

`Measure`(측정값)는 Dimension으로 나눈 그룹 안에서 **합계, 평균, 최댓값 등으로 계산하여 확인하는 값**이다.

위 질문에서는

```text
shot_speed
→ 포지션별 평균을 계산
→ Measure
```

가 된다.

따라서

```text
포지션별 평균 슈팅 속도

position
→ Dimension

AVG(shot_speed)
→ Measure
```

로 구성된다.

<br>

> ## **3-3) 스포츠 데이터 Dimension / Measure 예제**

| 분석 질문 | Dimension(차원) | Measure(측정값) |
| --- | --- | --- |
| 축구 포지션별 평균 HSR | `position` | `AVG(hsr_distance_m)` |
| 수영 종목별 평균 기록 | `event` | `AVG(race_time_sec)` |
| 야구 투수별 평균 구속 | `pitcher` | `AVG(velocity_kmh)` |
| 배드민턴 샷 유형별 득점 수 | `shot_type` | `SUM(point)` |
| 보행 집단별 평균 보행속도 | `group` | `AVG(gait_speed)` |

<br>

> ## **3-4) 숫자가 Dimension이 되는 경우**

숫자가 모두 Measure는 아니다.

예를 들어

```text
player_id = 101
player_id = 102
player_id = 103
```

이라고 하자.

이 값을

```text
SUM(player_id)
```

하면 분석적으로 의미가 없다.

선수 식별을 위한 기준이므로 Dimension으로 사용하는 것이 적절하다.

다음 Field들도 비슷하다.

```text
등번호
센서 ID
경기 ID
Trial 번호
우편번호
```

즉,

```text
숫자인가?
```

보다

```text
이 Field를 계산할 것인가,
그룹을 나누는 기준으로 사용할 것인가?
```

가 더 중요하다.

# **4. Aggregation - Measure를 어떻게 계산할 것인가**

> ## **4-1) 같은 Measure도 집계 방법에 따라 의미가 달라진다**

Measure는 Tableau View에 배치할 때 일반적으로 Aggregation이 적용된다.

대표적인 집계는 다음과 같다.

| Aggregation | 의미 |
| --- | --- |
| `SUM()` | 합계 |
| `AVG()` | 평균 |
| `MIN()` | 최솟값 |
| `MAX()` | 최댓값 |
| `COUNT()` | 행 개수 |
| `COUNTD()` | 고유값 개수 |

예를 들어 축구의 `player_load`라는 같은 Field라도 질문에 따라 계산 방식이 달라진다.

```text
이번 주 전체 Player Load
→ SUM(player_load)

선수당 평균 Player Load
→ AVG(player_load)

가장 높은 Session Load
→ MAX(player_load)
```

따라서 Measure를 사용할 때는 

**Field만 선택하는 것이 아니라 Aggregation의 의미까지 확인해야 한다.**

<br>

> ## **4-2) Tableau 계산 예제**

[ Tableau : code ] "포지션별 평균 Player Load 계산"

```text
AVG([player_load])
```

`position`을 Dimension으로 함께 사용한다고 가정한다.

[ Result ]

```text
Position       AVG(Player Load)

Winger              654.2
Fullback            631.8
Midfielder          612.5
Forward             584.9
Centerback          548.7
```

이 결과는 각 포지션에 포함된 관측값의 `player_load`를 평균낸 것이다.

<br>

> ## **4-3) COUNT와 COUNTD의 차이**

예를 들어 센서 데이터에 한 선수가 하루에 여러 행을 가지고 있다고 하자.

```text
player_id
P001
P001
P001
P002
P002
```

`COUNT(player_id)`는

```text
5
```

이지만

`COUNTD(player_id)`는

```text
2
```

이다.

| 계산 | 의미 |
| --- | --- |
| `COUNT([player_id])` | 전체 행 또는 값의 개수 |
| `COUNTD([player_id])` | 고유 선수 수 |

사용자 수, 선수 수, 경기 수를 계산할 때 `COUNT`와 `COUNTD`를 잘못 선택하면 결과가 크게 달라질 수 있다.

# **5. Discrete(불연속형)와 Continuous(연속형)**

> ## **5-1) Discrete(불연속형) - 구분된 항목으로 표현**

Discrete는 Field 값을 **서로 구분된 Category나 Header 형태로 표현**한다.

Tableau에서는 일반적으로 **파란색 Pill**로 표시된다.

예를 들어 경기 연도를 각각 비교하고 싶다고 하자.

```text
2024 | 2025 | 2026
```

각 연도를 독립적인 항목으로 보는 방식이다.

```text
YEAR(match_date)
→ Discrete

2024
2025
2026
```

이 경우 각 연도별 막대나 Column을 만들기 쉽다.

<br>

> ## **5-2) Continuous(연속형) - 이어지는 Axis로 표현**

Continuous는 값을 **연속적인 범위와 Axis로 표현**한다.

Tableau에서는 일반적으로 **초록색 Pill**로 표시된다.

예를 들어 경기 날짜에 따른 관중 수의 추세를 확인한다면

```text
2026-01
──────
2026-02
──────
2026-03
──────
2026-04
```

처럼 시간의 흐름을 이어지는 Axis로 표현하는 것이 자연스럽다.

```text
Continuous Date
+
SUM(attendance)
→ Line Chart
```

<br>

> ## **5-3) Header와 Axis의 차이**

Discrete / Continuous 차이는 Tableau View의 구조에도 영향을 준다.

| 구분 | Discrete | Continuous |
| --- | --- | --- |
| Tableau 색 | 파란색 | 초록색 |
| 표현 | 구분된 항목 | 이어진 범위 |
| View | Header | Axis |
| 예 | Winger, MF, DF | 0~1000m |
| 날짜 예 | 2024 / 2025 / 2026 | 시간축 2024→2026 |

<br>

> ## **5-4) Dimension / Measure와 다른 기준이다**

매우 중요한 개념이다.

```text
Dimension / Measure
→ 분석에서 Field의 역할

Discrete / Continuous
→ View에서 Field의 표현 방식
```

따라서 다음 공식은 틀렸다.

```text
Dimension = 파란색
Measure = 초록색
```

정확하게는

```text
파란색
→ Discrete

초록색
→ Continuous
```

이다.

Measure도 Discrete로 표현할 수 있고, 일부 Dimension 역시 Continuous하게 표현할 수 있다.

<br>

> ## **5-5) 같은 날짜도 다르게 사용할 수 있다**

예를 들어 `race_date`라는 수영 경기 날짜가 있다.

질문 1:

```text
2024년, 2025년, 2026년의
평균 기록을 각각 비교하고 싶다.
```

이 경우

```text
YEAR(race_date)
→ Discrete
```

로 사용할 수 있다.

질문 2:

```text
2024~2026년 동안
기록이 어떻게 변화했는지 보고 싶다.
```

이 경우에는

```text
race_date
→ Continuous
```

가 더 자연스럽다.

즉,

```text
같은 Field
+
다른 분석 질문
=
다른 표현 방식
```

이 가능하다.

# **6. 데이터로 Dimension / Measure / Discrete / Continuous 구분하기**

> ## **6-1) 축구 GPS 예제**

다음 데이터가 있다고 하자.

```text
player_id
position
session_date
total_distance_m
hsr_distance_m
max_speed_ms
player_load
```

일반적인 역할은 다음과 같이 생각할 수 있다.

| Field | Data Type | 분석 역할 예 | 표현 예 |
| --- | --- | --- | --- |
| `player_id` | String | Dimension | Discrete |
| `position` | String | Dimension | Discrete |
| `session_date` | Date | Dimension | Discrete / Continuous |
| `total_distance_m` | Number | Measure | Continuous |
| `hsr_distance_m` | Number | Measure | Continuous |
| `max_speed_ms` | Number | Measure | Continuous |
| `player_load` | Number | Measure | Continuous |

그러나 이것은 절대적인 규칙이 아니라 **대표적인 사용 방식**이다.

<br>

> ## **6-2) 운동역학 보행 데이터 예제**

다음 Field를 생각해보자.

```text
subject_id
group
trial
gait_speed_ms
step_length_m
cadence_spm
knee_rom_deg
```

질문이

```text
환자군과 대조군의 평균 보행속도를 비교한다.
```

라면

```text
group
→ Dimension / Discrete

gait_speed_ms
→ Measure / Continuous
```

이다.

질문이

```text
Trial 1, Trial 2, Trial 3의
평균 보행속도를 각각 비교한다.
```

라면 `trial`이 숫자로 저장되어 있더라도

```text
trial
→ Dimension / Discrete
```

로 사용하는 것이 적절하다.

<br>

> ## **6-3) 수영 데이터 예제**

```text
athlete_id
event
race_date
reaction_time
turn_time
race_time
```

질문:

```text
종목별 평균 기록은?
```

이면

```text
event
→ Dimension

AVG(race_time)
→ Measure
```

질문:

```text
선수의 시즌 기록 변화는?
```

이면

```text
race_date
→ Continuous Date

race_time
→ Continuous Measure
```

를 이용한 Line Chart가 적합하다.

# **7. Tableau Field 배치 실무 예제**

> ## **7-1) 포지션별 평균 HSR 비교**

분석 질문:

```text
어떤 포지션의 평균
고강도 주행거리가 가장 높은가?
```

필요 Field:

```text
position
hsr_distance_m
```

Tableau에서는 다음처럼 생각할 수 있다.

```text
Columns
→ position

Rows
→ AVG(hsr_distance_m)

Marks
→ Bar
```

[ Tableau : code ] "포지션별 평균 HSR 계산"

```text
AVG([hsr_distance_m])
```

[ Result ]

```text
Winger        1048m
Fullback       931m
Midfielder     804m
Forward        756m
Centerback     512m
```

해석:

```text
Winger의 평균 HSR이 가장 높다.
```

단, 이것만으로

```text
Winger 포지션 때문에
고강도 주행이 증가했다.
```

라는 인과관계까지 주장할 수는 없다.

<br>

> ## **7-2) 월별 부상 건수 추세**

분석 질문:

```text
시즌 동안 부상 발생 건수가
어떻게 변화했는가?
```

필요 Field:

```text
injury_date
injury_id
```

구성:

```text
Columns
→ Continuous MONTH(injury_date)

Rows
→ COUNT(injury_id)

Marks
→ Line
```

[ Tableau : code ] "월 단위 날짜 생성"

```text
DATETRUNC('month', [injury_date])
```

[ Result ]

```text
2026-03    3건
2026-04    5건
2026-05    4건
2026-06    8건
2026-07    7건
```

이 경우 날짜를 Continuous하게 표현하면 시간의 흐름에 따른 부상 건수 변화를 보기 쉽다.

# **8. Live와 Extract**

> ## **8-1) Live Connection**

Live는 Tableau가 분석할 때 **원본 Data Source에 직접 Query를 보내 결과를 가져오는 방식**이다.

real time processing 처리가 가능하다 (실시간 처리).

```text
Tableau
   ↓ Query
Database
   ↓ Result
Tableau View
```

장점은 원본 데이터의 최신 상태를 반영하기 쉽다는 것이다.

하지만 성능은 다음 요소의 영향을 받을 수 있다.

```text
Database 성능
Network
Query 복잡도
동시 사용자 수
원본 데이터 크기
```

<br>

> ## **8-2) Extract**

Extract는 원본 데이터의 일부 또는 전체를 Tableau 분석용으로 추출하여 저장한 뒤 사용하는 방식이다.

near real time processing 처리가 가능하다 (실시간 처리를 안해도 되는 상황).

```text
Database
    ↓
Extract 생성
    ↓
Tableau용 Data
    ↓
Dashboard
```

원본 시스템을 매번 직접 조회하지 않아도 되고 분석 성능 측면에서 유리할 수 있다.

다만 최신 데이터는 **마지막 Extract Refresh 시점**을 기준으로 한다.

<br>

> ## **8-3) Live와 Extract 비교**

| 구분 | Live | Extract |
| --- | --- | --- |
| 데이터 조회 | 원본 직접 조회 | 추출 데이터 조회 |
| 최신성 | 높은 최신성 확보 가능 | Refresh 시점 기준 |
| 속도 | 원본 DB 영향을 받음 | 빠른 분석에 유리할 수 있음 |
| 원본 부하 | Query에 따라 발생 | 상대적으로 줄일 수 있음 |
| 네트워크 | 영향을 받을 수 있음 | 원본 의존 감소 |
| 활용 | 실시간 운영 Dashboard | 주기적 분석 Dashboard |

<br>

> ## **8-4) 스포츠 실무 상황별 선택**

상황 A:

```text
프로축구 경기 중
선수 GPS 데이터가 실시간으로 들어오고
코칭스태프가 현재 부하를 확인해야 한다.
```

→ Live 또는 실시간 데이터 구조를 우선 검토할 수 있다.

상황 B:

```text
매일 오전 전날까지의
훈련 데이터를 분석하는 Dashboard를 사용한다.
```

→ 야간 Extract Refresh를 수행하는 구조를 고려할 수 있다.

상황 C:

```text
논문 분석용으로 연구 종료 시점의
고정된 데이터를 사용한다.
```

→ Extract를 사용하면 특정 분석 시점의 데이터 Snapshot을 관리하기 편리할 수 있다.

중요한 것은

```text
Live가 무조건 좋다.
Extract가 무조건 빠르다.
```

라고 단정하는 것이 아니라

```text
최신성
성능
데이터 규모
원본 DB 부하
Refresh 주기
분석 목적
```

을 함께 고려하는 것이다.

# **9. 실무형 Tableau 분석 흐름**

> ## **9-1) 축구 퍼포먼스 Dashboard 구축 예시**

분석 요구사항이 다음과 같다고 하자.

```text
1. 포지션별 평균 Player Load 비교

2. 선수별 Sprint 횟수 확인

3. 최근 8주 Player Load 추세 확인

4. 특정 선수와 날짜를 Filter로 선택
```

전체 흐름은 다음과 같다.

```text
GPS Database
     ↓
Data Source 연결
     ↓
Field / Data Type 확인
     ↓
Dimension / Measure 판단
     ↓
┌─────────────────────────┐
│ position                │ → Dimension
│ player_id               │ → Dimension
│ session_date            │ → Dimension
│ player_load             │ → Measure
│ sprint_count            │ → Measure
└─────────────────────────┘
     ↓
Discrete / Continuous 결정
     ↓
Worksheet 생성
     │
     ├─ Position Load Bar
     ├─ Player Sprint Bar
     └─ Weekly Load Line
     ↓
Dashboard
     ↓
Player / Date Filter
     ↓
코칭스태프 모니터링
```

<br>

> ## **9-2) 분석 질문별 Field 구성**

| 질문 | Dimension | Measure | 표현 |
| --- | --- | --- | --- |
| 포지션별 평균 Load | Position | AVG(Player Load) | Bar |
| 선수별 Sprint | Player | SUM(Sprint Count) | Bar |
| 주간 Load 변화 | Session Date | AVG(Player Load) | Line |
| 선수 수 | Position | COUNTD(Player ID) | Bar / Text |

이처럼 Tableau에서 차트를 만드는 핵심은 **필드를 끌어다 놓는 기술보다 질문을 Field 역할로 변환하는 능력**이다.

# **10. 초보자가 자주 하는 실수**

> ## **10-1) 숫자를 모두 Measure로 생각한다**

```text
subject_id = 1001
```

이라고 해서

```text
AVG(subject_id)
```

를 계산하는 것은 의미가 없다.

ID는 일반적으로 Dimension이다.

<br>

> ## **10-2) Dimension은 무조건 파란색이라고 생각한다**

틀린 기억법:

```text
Dimension = Blue
Measure = Green
```

정확한 구분:

```text
Blue
→ Discrete

Green
→ Continuous
```

Dimension과 Measure는 분석 역할이고, Blue / Green은 View에서 표현되는 방식이다.

<br>

> ## **10-3) SUM과 AVG를 확인하지 않는다**

예를 들어 선수 체중을 분석하면서

```text
SUM(weight_kg)
```

를 사용하면 선수별 측정 행이 여러 개 존재할 경우 매우 큰 숫자가 나올 수 있다.

실제 질문이 평균 체중이라면

```text
AVG(weight_kg)
```

가 필요하다.

따라서 Tableau에서 자동으로 생성된 Aggregation을 그대로 사용하지 말고 **현재 질문의 의미와 맞는지 확인해야 한다.**

<br>

> ## **10-4) Date를 문자열로 사용한다**

날짜가

```text
"2026-03-01"
```

이라는 String으로 인식되면 날짜 계층과 시간축을 제대로 활용하기 어렵다.

따라서 연결 직후 Data Type을 확인한다.

<br>

> ## **10-5) Live와 Extract를 성능만 보고 선택한다**

Extract가 빠를 수 있다는 이유만으로 선택하는 것도 위험하다.

만약 경기 운영 Dashboard에서 초 단위 최신 데이터가 필요하다면 하루 한 번 Refresh되는 Extract는 목적에 맞지 않는다.

```text
기술 선택
→ 분석 및 운영 요구사항 기준
```

# **11. Dimension / Measure / Discrete / Continuous 한 번에 구분하기**

> ## **11-1) 네 가지 개념을 질문으로 구분**

Field를 만났을 때 다음 순서로 생각하면 된다.

```text
1. 어떤 종류의 값인가?
→ Data Type

2. 데이터를 나누는 기준인가?
   계산할 값인가?
→ Dimension / Measure

3. 화면에서 항목으로 나눌 것인가?
   이어진 Axis로 표현할 것인가?
→ Discrete / Continuous

4. Measure라면 어떻게 계산할 것인가?
→ SUM / AVG / COUNT / COUNTD ...
```

<br>

> ## **11-2) 예시**

`race_date`

```text
Data Type
→ Date

역할
→ 경기 날짜별로 데이터를 나누므로 Dimension

연도별 막대 비교
→ Discrete

시간 변화 Line Chart
→ Continuous
```

`race_time_sec`

```text
Data Type
→ Number

역할
→ 기록을 계산하므로 Measure

AVG(race_time_sec)
→ 평균 기록

Continuous
→ 기록시간 Axis
```

`athlete_id`

```text
Data Type
→ String 또는 Number

역할
→ 선수 구분 기준이므로 Dimension

Discrete
→ 선수별 Category
```

# **12. Advanced 추가 학습**

> ## **12-1) Date Part와 Date Value**

Tableau의 날짜는 같은 `YEAR`, `MONTH`라도 **구분된 날짜 부분으로 사용할지 연속적인 날짜 축으로 사용할지**에 따라 View가 달라질 수 있다.

따라서

```text
연도별 비교
```

와

```text
연도에 따른 추세
```

를 구분해서 생각하는 것이 중요하다.

<br>

> ## **12-2) Measure Names와 Measure Values**

여러 Measure를 동시에 비교하고 싶을 때 Tableau의 `Measure Names`와 `Measure Values`를 사용할 수 있다.

예를 들어 선수별

```text
Total Distance
HSR Distance
Sprint Count
Player Load
```

를 한 View에서 비교하는 데 활용할 수 있다.

<br>

> ## **12-3) Data Source 설계**

실무에서는 Tableau에서 모든 계산을 해결하기보다

```text
Database / SQL
→ 분석에 필요한 Table 생성

Tableau
→ 시각화와 사용자 탐색
```

처럼 역할을 나누는 경우가 많다.

대규모 원본 데이터를 그대로 연결하기보다 분석 목적에 맞는 집계 Table이나 Data Mart를 설계하면 Dashboard 성능과 관리 측면에서 유리할 수 있다.

# **13. 핵심정리**

1. Tableau에서는 연결된 데이터의 각 Column이 **Field**로 나타나며, 분석 질문에 필요한 Field를 선택하여 시각화를 구성한다.

2. Tableau 분석의 기본적인 사고 과정은 다음과 같다.

```text
분석 질문
    ↓
필요 Field
    ↓
Data Type
    ↓
Dimension / Measure
    ↓
Discrete / Continuous
    ↓
Aggregation
    ↓
Visualization
```

3. **Data Type**은 Field가 문자열, 숫자, 날짜 등 어떤 종류의 값을 가지고 있는지를 나타낸다.

4. Data Type과 Dimension / Measure는 같은 개념이 아니다. 숫자형 Field라도 ID처럼 데이터를 구분하는 용도라면 Dimension으로 사용하는 것이 자연스럽다.

5. Dimension은 데이터를 나누거나 그룹화하는 기준이다.

```text
포지션별
선수별
경기별
종목별
```

에서 `포지션`, `선수`, `경기`, `종목`이 Dimension의 역할을 한다.

6. Measure는 Dimension으로 나눈 각 그룹에서 계산하여 확인하려는 값이다.

```text
SUM(Sales)
AVG(Player Load)
MAX(Speed)
COUNT(Injury)
```

등이 이에 해당한다.

7. 같은 Measure도 질문에 따라 Aggregation이 달라질 수 있다.

```text
SUM
AVG
MIN
MAX
COUNT
COUNTD
```

중 어떤 계산이 질문에 맞는지 확인해야 한다.

8. 특히 `COUNT()`와 `COUNTD()`는 의미가 다르다.

```text
COUNT
→ 전체 관측값 개수

COUNTD
→ 고유한 값의 개수
```

9. Discrete는 Field를 서로 구분된 항목이나 Header로 표현하며 Tableau에서 일반적으로 **파란색**으로 표시된다.

10. Continuous는 Field를 이어지는 범위의 Axis로 표현하며 Tableau에서 일반적으로 **초록색**으로 표시된다.

11. 가장 중요한 구분은 다음과 같다.

```text
Dimension / Measure
→ 분석에서 어떤 역할을 하는가?

Discrete / Continuous
→ View에서 어떻게 표현하는가?
```

12. 따라서 다음 공식은 잘못된 이해이다.

```text
Dimension = Blue
Measure = Green
```

정확한 이해는 다음과 같다.

```text
Blue = Discrete
Green = Continuous
```

13. 같은 날짜 Field라도 분석 목적에 따라 Discrete와 Continuous를 다르게 사용할 수 있다.

```text
2024 / 2025 / 2026 비교
→ Discrete

2024 ─ 2025 ─ 2026 추세
→ Continuous
```

14. Tableau에 데이터를 연결한 뒤에는 바로 시각화를 시작하기보다 Data Type과 Field의 의미가 올바른지 확인하는 것이 중요하다.

15. Live는 Tableau가 원본 Data Source를 직접 조회하는 방식이고, Extract는 데이터를 추출하여 Tableau 분석용 데이터로 사용하는 방식이다.

16. Live와 Extract는 다음 기준을 고려하여 선택해야 한다.

```text
최신성
Query 성능
원본 DB 부하
Data Size
Network
Refresh 주기
Dashboard 사용 목적
```

17. 실시간 또는 높은 최신성이 필요한 Dashboard에서는 Live를 고려할 수 있고, 일정 주기의 데이터 분석과 빠른 탐색이 중요하다면 Extract를 고려할 수 있다.

18. Tableau의 핵심은 Field를 드래그하는 기능 자체가 아니라 다음을 판단하는 능력이다.

```text
무엇을 알고 싶은가?

어떤 Field가 필요한가?

무엇을 기준으로 데이터를 나눌 것인가?

어떤 값을 계산할 것인가?

어떤 Aggregation이 적절한가?

Field를 Header로 볼 것인가?

Axis로 볼 것인가?
```

19. 스포츠 데이터에서는 다음과 같이 적용할 수 있다.

```text
포지션별 평균 HSR
→ position + AVG(hsr_distance_m)

수영 종목별 평균 기록
→ event + AVG(race_time_sec)

보행 집단별 평균 보행속도
→ group + AVG(gait_speed_ms)

시즌별 부상 추세
→ Continuous injury_date + COUNT(injury_id)
```

20. Tableau 필드 이해의 핵심은 다음 한 줄로 정리할 수 있다.

```text
Dimension은 "무엇을 기준으로 나눌 것인가?"

Measure는 "무엇을 계산할 것인가?"

Discrete는 "구분해서 보여줄 것인가?"

Continuous는 "이어진 축으로 보여줄 것인가?"
```
