# **1. Tableau 시각화의 기본 구조**

> ## **1-1) 필드 배치가 시각화의 뼈대를 만든다**

Tableau에서는 차트 이름을 먼저 선택하기보다 **분석 질문에 필요한 필드를 Rows와 Columns에 배치하면서 시각화의 구조를 만든다.**

예를 들어 축구 GPS 데이터가 다음과 같다고 가정한다.

| player_id | position | match_date | total_distance_m | hsr_distance_m | sprint_count | player_load |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| P001 | Winger | 2026-03-01 | 10,420 | 1,180 | 32 | 682 |
| P002 | Midfielder | 2026-03-01 | 10,870 | 890 | 24 | 643 |
| P003 | Centerback | 2026-03-01 | 9,310 | 510 | 12 | 548 |

질문이

```text
포지션별 평균 고강도 주행거리는 얼마인가?
```

라면 필요한 필드는

```text
position
hsr_distance_m
```

이다.

역할은 다음과 같다.

```text
position
→ 데이터를 포지션별로 나누는 Dimension

hsr_distance_m
→ 각 포지션에서 평균을 계산할 Measure
```

Tableau에서는 예를 들어 다음과 같이 배치할 수 있다.

```text
Columns
→ position

Rows
→ AVG(hsr_distance_m)
```

그러면 각 포지션의 평균 HSR을 비교하는 View가 만들어진다.

즉, Tableau 시각화의 기본 구조는 다음과 같다.

```text
분석 질문
    ↓
필요 Field 선택
    ↓
Dimension / Measure 판단
    ↓
Rows / Columns 배치
    ↓
Mark Type 선택
    ↓
Marks Card로 추가 정보 표현
    ↓
Visualization
```

<br>

> ## **1-2) Rows와 Columns의 역할**

`Rows`와 `Columns`는 **`View`의 좌표 구조를 만드는 영역**이다.

예를 들어

```text
Columns → position
Rows    → AVG(player_load)
```

이면

```text
가로 방향
→ Position

세로 방향
→ 평균 Player Load
```

가 만들어진다.

반대로 배치하면 차트 방향이 달라질 수 있다.

```text
Columns → AVG(player_load)
Rows    → position
```

이 경우 수평 막대 차트 형태로 표현할 수 있다.

| 배치 | 일반적인 결과 |
| --- | --- |
| Dimension → Columns, Measure → Rows | 세로 막대 |
| Measure → Columns, Dimension → Rows | 가로 막대 |
| Date → Columns, Measure → Rows | 시간 추세 |
| Measure → Columns, Measure → Rows | 산점도 |

따라서 같은 Field를 사용하더라도 **어디에 배치하는지에 따라 View의 구조가 달라진다.**

# **2. Mark와 Mark Type**

> ## **2-1) Mark란?**

`Mark`는 Tableau View에서 **하나의 데이터를 시각적으로 나타내는 요소**이다.

차트에 따라 Mark의 형태가 달라진다.

```text
Bar Chart
→ 막대 하나가 Mark

Scatter Plot
→ 점 하나가 Mark

Line Chart
→ 데이터 Point와 이를 연결한 선

Highlight Table
→ Cell 하나가 Mark
```

즉, Tableau에서 데이터는 `Mark`를 통해 화면에 표현된다.

<br>

> ## **2-2) 대표적인 Mark Type**

| `Mark Type` | 주요 표현 | 활용 예 |
| --- | --- | --- |
| Bar | 막대 | 포지션별 HSR 비교 |
| Line | 선 | 주간 Player Load 추세 |
| Circle | 원 | 두 Measure 관계 |
| Square | 사각형 | Heat Map |
| Text | 텍스트 | Crosstab |
| Area | 영역 | 시간에 따른 구성 변화 |
| Automatic | Tableau 자동 선택 | Field 배치에 따른 기본 표현 |

`Automatic`을 사용하면 Tableau가 배치된 Field를 기준으로 적절한 Mark Type을 자동 선택한다.

하지만 자동으로 선택된 Mark가 반드시 현재 분석 질문에 가장 적절한 것은 아니다.

따라서

```text
Tableau가 자동으로 선택했다.
        ↓
그대로 사용한다.
```

보다

```text
현재 질문에 이 Mark Type이 적절한가?
```

를 다시 판단해야 한다.

<br>

> ## **2-3) 같은 데이터도 Mark Type에 따라 의미가 달라진다**

수영 선수의 월별 훈련거리 데이터를 생각해보자.

```text
training_month
distance_km
```

Bar를 사용하면

```text
각 월의 훈련량 크기 비교
```

에 초점이 맞춰진다.

Line을 사용하면

```text
시간에 따른 훈련량 변화
```

가 더 강조된다.

Area를 사용하면

```text
시간 변화
+
전체 양의 규모
```

를 강조할 수 있다.

따라서

```text
동일한 Field
+
다른 Mark Type
=
다른 분석 강조점
```

이 될 수 있다.

# **3. Marks Card로 정보를 추가한다**

> ## **3-1) Marks Card의 주요 속성**

`Marks Card`는 Mark가 **어떤 방식으로 보일지 결정하는 영역**이다.

대표적인 속성은 다음과 같다.

| 속성 | 역할 | 스포츠 데이터 예 |
| --- | --- | --- |
| `Color` | 범주 또는 값 구분 | 포지션별 색상 |
| `Size` | 값의 크기 표현 | Player Load가 클수록 큰 원 |
| `Label` | 값 또는 이름 표시 | 평균 HSR 숫자 표시 |
|`Detail` | Mark 세분화 | 선수별 점 생성 |
| `Tooltip` | 마우스 Hover 추가정보 | 선수명, HSR, Load 표시 |

<br>

> ## **3-2) Color**

축구의 포지션별 HSR 막대 차트를 만든 뒤 `position`을 Color에 넣으면 포지션별 색상을 구분할 수 있다.

또 다른 Dimension인 `match_type`을 Color에 넣는다면

```text
League
Cup
Friendly
```

경기 유형별 구성도 표현할 수 있다.

Color에는 범주형 Dimension뿐 아니라 Measure도 사용할 수 있다.

예를 들어

```text
AVG(player_load)
→ Color
```

를 적용하면 값의 크기에 따라 색의 강도가 달라질 수 있다.

즉,

```text
Dimension → Color
→ 범주 구분

Measure → Color
→ 값의 크기 표현
```

으로 이해할 수 있다.

<br>

> ## **3-3) Size**

산점도에서 원의 크기로 추가 Measure를 표현할 수 있다.

예를 들어 야구 투수 데이터에서

```text
X축 → 평균 구속
Y축 → 회전수
Size → 투구 수
```

로 구성하면

```text
구속
+
회전수
+
투구량
```

이라는 세 정보를 하나의 `View`에 표현할 수 있다.

그러나 너무 많은 정보를 `Size`와 `Color`에 동시에 넣으면 차트가 복잡해질 수 있다.

<br>

> ## **3-4) Label**

`Label`은 값을 직접 표시할 때 사용한다.

예를 들어 배드민턴 선수별 공격 성공률을 막대 차트로 만들고

```text
AVG(attack_success_rate)
→ Label
```

로 넣으면 각 막대 위에

```text
62.4%
57.1%
54.8%
```

같은 값을 직접 표시할 수 있다.

정확한 수치를 전달할 때 유용하지만 Mark가 많을 경우 Label이 겹칠 수 있으므로 필요한 데이터에만 사용하는 것이 좋다.

<br>

> ## **3-5) Detail**

`Detail`은 **색상이나 크기를 바꾸지 않고 View의 Mark 개수를 세분화**한다.

예를 들어 산점도에서

```text
Columns → AVG(total_distance_m)
Rows    → AVG(player_load)
```

만 사용하면 집계 수준에 따라 하나의 Mark만 나타날 수 있다.

여기에

```text
player_id
→ Detail
```

을 넣으면 선수별 Mark가 생성된다.

```text
Player 1 ●
Player 2 ●
Player 3 ●
...
```

즉, Detail은 **View의 분석 단위(Level of Detail)** 를 세분화하는 데 매우 중요하다.

<br>

> ## **3-6) Tooltip**

`Tooltip`은 화면에 항상 표시할 필요는 없지만 사용자가 특정 Mark를 선택했을 때 확인하고 싶은 정보를 제공한다.

예를 들어 쇼트트랙 Lap 분석에서 Tooltip을 다음처럼 구성할 수 있다.

```text
선수: P001
Lap: 8
Lap Time: 9.21 sec
Rank: 2
Max Speed: 49.8 km/h
```

Dashboard에서 필요한 정보를 화면에 모두 표시하지 않고 **상호작용을 통해 세부정보를 제공할 수 있다는 장점**이 있다.

# **4. Bar Chart - 항목 간 비교**

> ## **4-1) 막대 차트를 언제 사용하는가?**

Bar Chart는 **여러 Category의 Measure 크기를 비교**할 때 사용한다.

예를 들어

```text
어떤 포지션의 평균 Player Load가 높은가?
```

라는 질문은 Comparison 문제이다.

필드는

```text
position
→ Dimension

player_load
→ Measure
```

이다.

[ Tableau : code ] "축구 포지션별 평균 Player Load 막대 차트"

```text
Rows
→ [Position]

Columns
→ AVG([Player Load])

Marks
→ Bar
```

[ Result ]

```text
Winger        654.2
Fullback      631.8
Midfielder    612.5
Forward       584.9
Centerback    548.7
```

Winger의 평균 Player Load가 가장 높은 것을 쉽게 비교할 수 있다.

<br>

> ## **4-2) 정렬을 함께 사용하면 비교가 쉬워진다**

Category 순서가 임의라면 값의 크기를 비교하기 어려울 수 있다.

따라서

```text
AVG(Player Load) 기준으로 
내림차순 정렬
```

을 적용하면

```text
Winger
Fullback
Midfielder
Forward
Centerback
```

처럼 값이 높은 순서로 표현할 수 있다.

설명적 시각화에서는 Category 이름순보다 **Measure 크기 순 정렬이 메시지를 더 명확하게 만드는 경우가 많다.**

<br>

> ## **4-3) 막대 차트 활용 예**

| 종목 | 질문 | Dimension | Measure |
| --- | --- | --- | --- |
| 축구 | 포지션별 HSR | Position | AVG(HSR) |
| 야구 | 투수별 탈삼진 | Pitcher | SUM(Strikeout) |
| 배드민턴 | 샷별 득점 | Shot Type | SUM(Point) |
| 수영 | 종목별 평균 기록 | Event | AVG(Race Time) |
| 운동역학 | 집단별 Peak GRF | Group | AVG(Peak GRF) |

# **5. Stacked Bar Chart - 전체와 구성**

> ## **5-1) 누적 막대 차트**

Stacked Bar Chart는 전체 값과 그 내부 구성을 함께 확인할 때 사용할 수 있다.

예를 들어 핸드볼 포지션별 슈팅 시도를

```text
Goal
Miss
Saved
```

결과로 나누어 보고 싶다고 하자.

기본 구조는

```text
Position
+
COUNT(Shot)
```

이고 여기에 `shot_result`를 Color에 추가한다.

[ Tableau : code ] "핸드볼 포지션별 슈팅 결과 구성"

```text
Rows
→ [Position]

Columns
→ COUNT([Shot ID])

Color
→ [Shot Result]

Marks
→ Bar
```

[ Result ]

```text
Wing
→ Goal 72 / Saved 19 / Miss 14

Back
→ Goal 58 / Saved 27 / Miss 21

Pivot
→ Goal 43 / Saved 13 / Miss 9
```

이 View에서는

```text
전체 슈팅량
+
Goal / Saved / Miss 구성
```

을 함께 확인할 수 있다.

<br>

> ## **5-2) 누적 막대의 한계**

누적 막대에서 첫 번째 Segment를 제외하면 다른 Segment는 시작 위치가 서로 다르기 때문에 정확한 비교가 어려울 수 있다.

예를 들어 각 포지션의 `Miss`만 직접 비교하는 것이 목적이라면 별도 Bar Chart가 더 명확할 수 있다.

따라서

```text
전체 + 내부 구성
→ Stacked Bar

특정 Category의 값 비교
→ 일반 Bar
```

처럼 목적을 구분한다.

# **6. Line Chart - 시간에 따른 추세**

> ## **6-1) 시간 변화 분석**

Line Chart는 시간에 따라 Measure가 어떻게 변하는지 확인할 때 적합하다.

예를 들어 쇼트트랙 선수의 Lap별 속도를 분석한다고 하자.

```text
Lap
1 → 42.3 km/h
2 → 43.1 km/h
3 → 44.0 km/h
...
8 → 49.1 km/h
```

[ Tableau : code ] "쇼트트랙 Lap별 속도 변화"

```text
Columns
→ [Lap]

Rows
→ AVG([Speed])

Marks
→ Line
```

[ Result ]

```text
Lap 1    42.3
Lap 2    43.1
Lap 3    44.0
Lap 4    44.7
Lap 5    45.8
Lap 6    46.9
Lap 7    48.0
Lap 8    49.1
```

후반 Lap으로 갈수록 속도가 증가하는 경기 전략 패턴을 확인할 수 있다.

<br>

> ## **6-2) 날짜는 Continuous로 사용하는 경우가 많다**

예를 들어 축구팀의 최근 8주 Player Load를 분석한다면

```text
Columns
→ Continuous WEEK(session_date)

Rows
→ AVG(player_load)

Marks
→ Line
```

으로 구성할 수 있다.

시간의 흐름을 연결하여 보여주므로

```text
증가
감소
급격한 변화
반복 패턴
```

을 확인하기 쉽다.

<br>

> ## **6-3) 여러 선수의 추세 비교**

`player_id`를 Color에 추가하면 선수별 Line을 생성할 수 있다.

```text
Columns
→ WEEK(session_date)

Rows
→ AVG(player_load)

Color
→ player_id
```

그러나 선수 수가 너무 많으면 수십 개의 Line이 겹쳐서 읽기 어려워질 수 있다.

이 경우

```text
Filter
Highlight
Small Multiples
```

등의 방법을 고려할 수 있다.

# **7. Scatter Plot - 두 Measure의 관계**

> ## **7-1) 산점도의 기본 구조**

Scatter Plot은 **두 Measure 사이의 관계를 확인**할 때 사용한다.

예를 들어 야구 투수의

```text
평균 구속
팔꿈치 Varus Torque
```

관계를 보고 싶다고 하자.

[ Tableau : code ] "투수별 구속과 팔꿈치 토크 관계"

```text
Columns
→ AVG([Velocity kmh])

Rows
→ AVG([Elbow Torque Nm])

Detail
→ [Pitcher ID]

Marks
→ Circle
```

[ Result ]

```text
Pitcher A → 143 km/h / 48 Nm
Pitcher B → 147 km/h / 54 Nm
Pitcher C → 151 km/h / 61 Nm
Pitcher D → 154 km/h / 66 Nm
```

투수마다 하나의 점이 생성된다.

<br>

> ## **7-2) Detail이 중요한 이유**

`Pitcher ID`를 Detail에 넣지 않으면 Tableau가 전체 데이터를 집계하여

```text
AVG(Velocity)
AVG(Elbow Torque)
```

라는 하나의 Mark만 만들 수 있다.

```text
Measure + Measure
        ↓
하나의 Aggregate Mark
```

여기에 분석 단위를 추가해야 한다.

```text
Pitcher ID → Detail
        ↓
Pitcher별 Mark 생성
```

즉 산점도에서는 **한 점이 무엇을 의미해야 하는지** 명확하게 정의해야 한다.

<br>

> ## **7-3) 관계와 인과관계를 구분한다**

산점도에서

```text
구속 증가
+
토크 증가
```

패턴이 보인다고 해서

```text
구속을 높였기 때문에
팔꿈치 부상이 발생한다.
```

고 해석할 수는 없다.

산점도는 **관계와 패턴을 보여주는 시각화**이며 인과관계를 증명하는 도구는 아니다.

# **8. Heat Map과 Highlight Table**

> ## **8-1) Heat Map**

Heat Map은 두 개 이상의 Dimension 조합에서 Measure의 크기를 색상 또는 크기로 표현한다.

예를 들어 배드민턴 경기에서

```text
선수
×
Shot Type
```

조합별 득점률을 보고 싶다고 하자.

[ Tableau : code ] "선수와 샷 유형별 득점률 Heat Map"

```text
Rows
→ [Player]

Columns
→ [Shot Type]

Color
→ AVG([Point Rate])

Marks
→ Square
```

[ Result ]

```text
             Smash   Drop   Clear   Drive

Player A      0.68   0.42    0.25    0.51
Player B      0.61   0.49    0.31    0.46
Player C      0.72   0.38    0.28    0.55
```

색이 강한 Cell을 통해 높은 득점률 조합을 빠르게 찾을 수 있다.

<br>

> ## **8-2) Highlight Table**

Highlight Table은 Heat Map과 비슷하지만 **색과 함께 숫자 자체를 보여준다.**

구성은 다음과 같다.

```text
Rows
→ Player

Columns
→ Shot Type

Color
→ AVG(Point Rate)

Label
→ AVG(Point Rate)

Marks
→ Square
```

따라서

```text
색상
→ 패턴을 빠르게 탐색

숫자
→ 정확한 값 확인
```

을 동시에 수행할 수 있다.

<br>

> ## **8-3) Heat Map과 Highlight Table 비교**

| 구분 | Heat Map | Highlight Table |
| --- | --- | --- |
| 패턴 탐색 | 매우 좋음 | 좋음 |
| 정확한 값 | 제한적 | 확인 가능 |
| 주요 Encoding | Color / Size | Color + Text |
| 데이터가 많을 때 | 유리 | Text가 많으면 복잡 |

# **9. Crosstab - 정확한 수치 확인**

> ## **9-1) Crosstab의 목적**

차트보다 정확한 숫자를 확인하는 것이 더 중요한 경우도 있다.

예를 들어 운동역학 실험에서 Group별 지표를 연구자가 확인해야 한다고 하자.

```text
Control / Injury
×
Knee Flexion / GRF / Loading Rate
```

Crosstab은 Dimension을 행과 열에 배치하고 Measure를 Text로 표현한다.

[ Tableau : code ] "운동역학 집단별 평균 지표 Crosstab"

```text
Rows
→ [Group]

Measure Values
→ AVG([Knee Flexion])
→ AVG([Peak GRF])
→ AVG([Loading Rate])

Marks
→ Text
```

[ Result ]

```text
Group      Knee Flexion   Peak GRF   Loading Rate

Control        52.4         2.71          41.8
Injury         43.1         3.42          57.6
```

Dashboard에서는 차트로 전체 패턴을 보여주고 Crosstab을 통해 상세한 숫자를 제공하는 방식도 사용할 수 있다.

# **10. Dual Axis와 Combined Axis**

> ## **10-1) Dual Axis(이중 축)**

Dual Axis는 두 Measure를 **서로 다른 각각의 축으로 표현하는 방법**이다.

예를 들어 수영 선수의 훈련량과 평균 기록 변화를 함께 보고 싶다고 하자.

```text
주간 훈련거리
→ km

100m 평균 기록
→ sec
```

단위가 다르다.

[ Tableau : code ] "주간 훈련거리와 수영 기록 이중 축 비교"

```text
Columns
→ WEEK([Training Date])

Rows
→ SUM([Training Distance Km])
→ AVG([Race Time Sec])

두 번째 Measure
→ Dual Axis

Marks
Training Distance → Bar
Race Time → Line
```

[ Result ]

```text
Week 1 → 42km / 54.8sec
Week 2 → 45km / 54.4sec
Week 3 → 49km / 54.1sec
Week 4 → 51km / 53.9sec
```

한 화면에서 두 지표의 변화를 비교할 수 있다.

<br>

> ## **10-2) Dual Axis 해석 주의**

두 축의 범위가 서로 독립적이기 때문에 시각적으로 관계가 강해 보이도록 축 범위를 조정할 수도 있다.

따라서 Dual Axis에서는 반드시

```text
왼쪽 축 단위
오른쪽 축 단위
축 범위
```

를 확인해야 한다.

두 지표의 Scale이 같을 필요가 있는 경우에만 `Synchronize Axis`를 신중하게 고려한다.

단위가 본질적으로 다른 Measure를 무조건 동기화하는 것은 적절하지 않을 수 있다.

<br>

> ## **10-3) Combined Axis(결합 축)**

Combined Axis는 여러 Measure를 **하나의 공통 Axis에서 직접 비교**한다.

예를 들어 축구 GPS에서

```text
Total Distance
HSR Distance
```

처럼 단위가 모두 `m`라면 같은 축에서 비교하기 쉽다.

```text
Measure Names
+
Measure Values
```

를 이용하여 여러 Measure를 같은 Axis에 배치할 수 있다.

<br>

> ## **10-4) Dual Axis와 Combined Axis 비교**

| 구분 | Dual Axis | Combined Axis |
| --- | --- | --- |
| 축 | 2개 | 1개 |
| 단위 | 달라도 사용 가능 | 같은 단위가 더 적합 |
| Mark Type | Measure마다 다르게 가능 | 동일 축 중심 |
| 예 | 매출 + 이익률 | HSR + 총 이동거리 |
| 주의점 | 축 범위 왜곡 | Scale 차이가 크면 비교 어려움 |


<br><br>

# **11. Filter와 Sort**

> ## **11-1) Filter**

Filter는 View에 표시할 데이터를 제한한다.

예를 들어 축구 Dashboard에서 전체 선수 중

```text
Position = Winger
```

만 확인하고 싶다면 `position`을 Filter에 사용한다.

다음과 같은 Filter를 만들 수 있다.

```text
선수
포지션
경기 날짜
훈련 / 경기
홈 / 원정
```

Filter를 사용하면 하나의 Dashboard를 여러 조건에서 재사용할 수 있다.

<br>

> ## **11-2) Filter 사용 시 질문**

Filter를 추가할 때도 많이 넣는 것이 목적은 아니다.

다음과 같이 생각한다.

```text
사용자가 실제로
어떤 조건을 바꾸어 볼 필요가 있는가?
```

예를 들어 퍼포먼스 코치에게는

```text
Player
Position
Date
Session Type
```

이 중요할 수 있다.

반면 경영진에게 같은 수준의 세부 Filter가 모두 필요하지 않을 수 있다.

<br>

> ## **11-3) Sort**

Sort는 Category 순서를 바꾼다.

예를 들어 양궁 선수별 평균 점수를

```text
선수 이름순
```

으로 보는 것보다

```text
평균 점수 내림차순
```

으로 정렬하면 상위 선수를 빠르게 확인할 수 있다.

[ Tableau : code ] "양궁 선수 평균 점수 내림차순 정렬 기준"

```text
Sort [Athlete]
→ By Field
→ AVG([Score])
→ Descending
```

[ Result ]

```text
Athlete C    9.42
Athlete A    9.18
Athlete D    8.96
Athlete B    8.81
```

# **12. Group과 Hierarchy**

> ## **12-1) Group**

Group은 여러 Dimension Member를 새로운 하나의 집단으로 묶을 때 사용한다.

예를 들어 축구 포지션을 다음과 같이 재분류한다고 하자.

```text
Centerback
Fullback
→ Defender

Central Midfielder
Winger
→ Midfielder

Striker
→ Forward
```

Group을 만들면 기존 세부 포지션을 더 큰 분석 범주로 비교할 수 있다.

```text
세부 Category
        ↓
업무 목적에 맞게 묶음
        ↓
새로운 Group
```

<br>

> ## **12-2) Hierarchy**

Hierarchy는 서로 관련된 Dimension을 **상위 → 하위 관계로 연결**한다.

예를 들어 스포츠 경기 데이터에서는

```text
Season
   ↓
Competition
   ↓
Match
   ↓
Player
```

와 같은 Hierarchy를 만들 수 있다.

또는 지역 데이터라면

```text
Country
   ↓
Region
   ↓
City
   ↓
Venue
```

처럼 사용할 수 있다.

사용자는 전체 수준에서 시작하여 필요한 경우 하위 수준으로 Drill Down할 수 있다.

<br>

> ## **12-3) Group과 Hierarchy 차이**

| 구분 | Group | Hierarchy |
| --- | --- | --- |
| 목적 | 여러 값을 묶음 | 단계적 탐색 구조 생성 |
| 예 | CB + FB → Defender | Season → Match → Player |
| 결과 | 새로운 Category | Drill Down 경로 |
| 활용 | 분석용 재분류 | 상세 탐색 |

# **14. 자주 발생하는 시각화 실수**

> ## **14-1) 하나의 차트에 정보를 너무 많이 넣는다**

예를 들어 산점도에

```text
Color
Size
Shape
Label
Detail
```

을 모두 사용하면 정보량은 많아지지만 사용자가 해석하기 어려울 수 있다.

```text
정보가 많다
≠
좋은 시각화
```

이다.

핵심 질문에 필요한 Encoding부터 사용한다.

<br>

> ## **14-2) Color를 장식처럼 사용한다**

색상은 의미가 있어야 한다.

```text
Position 구분
Risk Level
Positive / Negative
```

처럼 분석적 의미를 전달하는 것이 좋다.

필요 없는 Category까지 모두 다른 색으로 표현하면 사용자의 주의가 분산될 수 있다.

<br>

> ## **14-3) 정확한 비교가 필요한데 Size를 사용한다**

사람은 길이보다 면적의 차이를 정확하게 비교하기 어렵다.

예를 들어 선수별 기록을 정확히 비교해야 한다면 Circle Size보다 Bar Length가 더 적합할 수 있다.

```text
정확한 크기 비교
→ Bar

대략적인 규모 표현
→ Size 활용 가능
```

<br>

> ## **14-4) Line Chart에 순서가 없는 Category를 연결한다**

라인은 **연속적인 순서와 흐름**을 암시한다.

다음처럼 순서가 없는 Category를 연결하면 부적절할 수 있다.

```text
Goalkeeper
Defender
Midfielder
Forward
```

포지션은 시간 순서가 아니므로 일반적으로 Bar가 더 자연스럽다.

<br>

> ## **14-5) Dual Axis에서 축을 확인하지 않는다**

두 Line이 거의 동일한 모양이라고 해서 실제 변화량이 동일하다는 의미는 아니다.

각 축의 범위가 다르면 시각적으로 비슷하게 보일 수 있다.

따라서 Dual Axis에서는 반드시

```text
Measure
단위
축 Range
```

를 함께 확인한다.

# **15. 차트 선택 사고법**

> ## **15-1) 질문에 따라 차트를 선택한다**

차트를 선택할 때 다음 순서로 판단할 수 있다.

```text
현재 질문은 무엇인가?
       ↓
무엇을 비교하려는가?
       ↓
┌────────────────────────────────┐
│ Category 간 크기?               │ → Bar
│ 시간 변화?                      │ → Line
│ 두 수치의 관계?                  │ → Scatter
│ 전체 + 내부 구성?                │ → Stacked Bar
│ 두 Dimension 조합 패턴?          | → Heat Map
│ 정확한 숫자?                     │ → Crosstab
│ 숫자 + 패턴 모두?                │ → Highlight Table
│ 서로 다른 두 지표 동시 비교?       │ → Dual Axis
└────────────────────────────────┘
```

즉, 차트는 기능 목록에서 선택하는 것이 아니라 **분석 질문을 시각적 구조로 변환한 결과**이다.

# **16. Advanced 추가 학습**

> ## **16-1) Reference Line**

평균값, 목표값, 기준값을 View에 추가하면 현재 값이 기준보다 높은지 낮은지 쉽게 판단할 수 있다.

예를 들어 선수 Load Dashboard에서

```text
Reference Line
→ 팀 평균 Player Load
```

를 표시하면 선수별 부하가 팀 평균보다 높은지 비교할 수 있다.

<br>

> ## **16-2) Trend Line**

Scatter Plot에서 두 Measure 사이의 전체적인 관계를 보기 위해 Trend Line을 추가할 수 있다.

```text
HSR Distance
        ↘
         Trend Line
             ↘
             Player Load
```

단, Trend Line이 존재한다고 인과관계를 의미하는 것은 아니다.

<br>

> ## **16-3) Set**

Set은 특정 조건에 해당하는 Member 집합을 만들어 비교하는 기능이다.

예를 들어

```text
Top 5 Player Load 선수
vs
나머지 선수
```

처럼 분석할 수 있다.

Group이 여러 Member를 새로운 Category로 묶는 개념이라면 Set은 **조건에 따라 In / Out 집합을 구성할 수 있다는 차이**가 있다.

# **17. 핵심정리**

1. Tableau의 시각화는 **분석 질문에 필요한 Field를 Rows와 Columns에 배치하여 기본 구조를 만드는 것**에서 시작한다.

2. Rows와 Columns는 View의 가로·세로 구조를 결정하며 같은 Field라도 배치 방향에 따라 차트의 방향이 달라질 수 있다.

3. Mark는 View에서 데이터를 표현하는 실제 시각 요소이며 Bar, Line, Circle, Square, Text 등의 Mark Type을 사용할 수 있다.

4. `Automatic`은 Tableau가 현재 Field 구조를 보고 Mark Type을 선택하지만, 분석자가 현재 질문에 적합한 표현인지 다시 판단해야 한다.

5. Marks Card의 대표적인 역할은 다음과 같다.

```text
Color
→ 범주 또는 값 차이 표현

Size
→ 값의 크기 표현

Label
→ 숫자나 이름 직접 표시

Detail
→ Mark의 세분화 수준 증가

Tooltip
→ Hover 시 추가 정보 표시
```

6. Detail은 산점도와 같이 **각 Mark가 어떤 분석 단위를 나타내는지 결정하는 데 매우 중요**하다.

7. Bar Chart는 Category 간 Measure 크기를 비교하는 데 적합하다.

8. 값의 크기를 빠르게 비교해야 한다면 Bar를 Measure 기준으로 정렬하는 것이 효과적일 수 있다.

9. Stacked Bar는 전체 Measure와 내부 Category 구성을 동시에 확인할 수 있지만 Segment가 많아질수록 개별 크기 비교가 어려워진다.

10. Line Chart는 시간 또는 순서에 따른 변화를 확인하는 데 적합하며 순서가 없는 Category를 선으로 연결하는 것은 피하는 것이 좋다.

11. Scatter Plot은 두 Measure의 관계를 분석하며 `Detail`에 분석 단위를 추가하여 여러 Mark를 생성할 수 있다.

12. 산점도에서 관계가 나타나더라도 그것만으로 두 변수 사이의 인과관계를 증명할 수는 없다.

13. Heat Map은 두 Dimension의 조합에서 Measure의 패턴을 빠르게 찾는 데 적합하다.

14. Highlight Table은

```text
정확한 값
+
색상을 이용한 패턴
```

을 함께 확인하고 싶을 때 활용할 수 있다.

15. Crosstab은 시각적 패턴보다 정확한 수치를 확인하는 것이 중요한 경우 유용하다.

16. Dual Axis는 두 Measure를 서로 다른 축으로 하나의 View에 겹쳐 표현할 수 있다.

17. Dual Axis를 사용할 때는 단위와 축 범위를 반드시 확인해야 하며 축 설정에 따라 관계가 과장되어 보일 수 있다.

18. Combined Axis는 여러 Measure를 하나의 공통 축에서 비교하며 같은 단위를 가진 Measure를 직접 비교하는 데 특히 유용하다.

19. Filter는 필요한 데이터만 선택하고 Sort는 중요한 값이 빠르게 보이도록 순서를 정리한다.

20. Group과 Hierarchy의 차이는 다음과 같다.

```text
Group
→ 여러 Member를 새로운 집단으로 묶음

Hierarchy
→ Dimension을 상위 → 하위 단계로 연결
```

21. 하나의 View에 Color, Size, Label 등을 지나치게 많이 사용하면 오히려 분석이 어려워질 수 있다.

22. 좋은 시각화는 많은 정보를 담는 시각화가 아니라 **현재 분석 질문에 필요한 정보를 가장 명확하게 보여주는 시각화**이다.
