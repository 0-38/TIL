# **1. 테이블 간 관계(Relationship)**

관계형 데이터베이스에서는 데이터를 하나의 거대한 테이블에 모두 저장하지 않고, 역할에 따라 여러 테이블로 나누어 관리함.

이때 각 테이블의 데이터가 서로 어떻게 연결되는지를 **관계**(Relationship)라고 함.

대표적인 관계는 다음 세 가지.

| 관계 | 의미 | 대표 예 |
|---|---|---|
| `1:1` | 하나 ↔ 하나 | 선수 : 선수 상세정보 |
| `1:N` | 하나 ↔ 여러 개 | 선수 : 경기 기록 |
| `N:M` | 여러 개 ↔ 여러 개 | 선수 : 대회 |

<br>

> ## **1-1 ) 1:1 관계(One-to-One)**

한 테이블의 한 Row가 다른 테이블의 최대 한 Row와 연결되는 관계.

예를 들어 선수마다 하나의 상세 프로필을 관리한다고 가정.

#### `athletes`

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |

#### `athlete_profiles`

| profile_id | athlete_id | height_cm |
|---:|---:|---:|
| 101 | 1 | 172.5 |
| 102 | 2 | 181.2 |

관계.

```text
athletes
   1
   │
   │
   1
athlete_profiles
```

`athletes : athlete_profiles = 1:1`

단순히 FK를 하나 만들었다고 자동으로 1:1이 되는 것은 아님.

자식 테이블의 FK에도 `UNIQUE` 등의 제약이 있어야 한 선수에 여러 Profile이 연결되는 것을 방지할 수 있음.

[ sql : code ] "UNIQUE를 이용하여 선수와 프로필의 1:1 관계 생성"

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50) NOT NULL
);

CREATE TABLE athlete_profiles (
    profile_id INTEGER PRIMARY KEY,
    athlete_id INTEGER UNIQUE
        REFERENCES athletes(athlete_id),
    height_cm NUMERIC(5, 2)
);
```

`athlete_profiles.athlete_id`가 `UNIQUE`이므로 동일한 `athlete_id`를 여러 Row에서 반복 사용할 수 없음.

<br>

> ## **1-2 ) 1:N 관계(One-to-Many)**

한쪽의 한 Row가 다른쪽의 여러 Row와 연결될 수 있는 관계.

스포츠 데이터에서 매우 흔하게 나타남.

예를 들어 한 명의 선수는 여러 번의 경기 기록을 가질 수 있음.

#### `athletes`

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |

#### `match_records`

| record_id | athlete_id | score |
|---:|---:|---:|
| 101 | 1 | 22 |
| 102 | 1 | 27 |
| 103 | 2 | 18 |

지민 선수는 경기 기록 `101`, `102` 두 개와 연결됨.

```text
athletes
   1
   │
   │
   N
match_records
```

따라서.

```text
athletes : match_records
          1 : N
```

[ sql : code ] "선수와 경기 기록의 1:N 관계 생성"

```sql
CREATE TABLE match_records (
    record_id INTEGER PRIMARY KEY,
    athlete_id INTEGER NOT NULL
        REFERENCES athletes(athlete_id),
    score INTEGER NOT NULL
);
```

`match_records` 쪽에 FK인 `athlete_id`가 존재함.

즉, 일반적으로 **1:N 관계에서는 N쪽 테이블이 1쪽 테이블의 PK를 FK로 가짐**.

<br>

> ## **1-3 ) N:M 관계(Many-to-Many)**

양쪽의 하나의 Row가 상대방의 여러 Row와 연결될 수 있는 관계.

예를 들어.

```text
선수 한 명
→ 여러 대회 참가 가능

대회 하나
→ 여러 선수 참가 가능
```

따라서.

```text
athletes : competitions
       N : M
```

관계형 데이터베이스에서는 일반적으로 N:M 관계를 `연결 테이블(Junction Table / Associative Table)`을 이용하여 두 개의 1:N 관계로 표현함.

```text
athletes
   1
   │
   N
competition_entries
   N
   │
   1
competitions
```

결과적으로.

```text
athletes : competition_entries
       1 : N

competitions : competition_entries
           1 : N
```

<br>

> ## **1-4 ) N:M 관계 구현**

[ sql : code ] "선수와 대회의 N:M 관계를 중간 테이블로 구현"

```sql
CREATE TABLE competitions (
    competition_id INTEGER PRIMARY KEY,
    competition_name VARCHAR(100) NOT NULL
);

CREATE TABLE competition_entries (
    athlete_id INTEGER
        REFERENCES athletes(athlete_id),
    competition_id INTEGER
        REFERENCES competitions(competition_id),

    PRIMARY KEY (
        athlete_id,
        competition_id
    )
);
```

`competition_entries`가 선수와 대회를 연결하는 중간 테이블.

복합 PK를 사용했으므로 동일한 선수가 동일한 대회에 중복 등록되는 것을 방지함.

<br>

> ## **1-5 ) 1:N과 N:M 구분하기**

### 1:N

```text
선수 1명
↓
경기 기록 여러 개

하지만

경기 기록 1개
↓
특정 선수 1명
```

### N:M

```text
선수 1명
↓
여러 대회

대회 1개
↓
여러 선수
```

| 질문 | 1:N | N:M |
|---|---|---|
| 왼쪽 하나가 오른쪽 여러 개와 연결? | O | O |
| 오른쪽 하나도 왼쪽 여러 개와 연결? | X | O |
| 중간 테이블이 일반적으로 필요한가? | X | O |

# **2. 관계에 따른 JOIN 결과 이해**

테이블의 관계를 이해해야 `JOIN` 결과가 몇 Row로 증가할 수 있는지도 예측 가능.

> ## **2-1 ) 1:N 관계에서 JOIN하면 Row가 증가할 수 있음**

다음 데이터가 있다고 가정.

#### `athletes`

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |

#### `match_records`

| record_id | athlete_id | score |
|---:|---:|---:|
| 101 | 1 | 22 |
| 102 | 1 | 27 |
| 103 | 2 | 18 |

[ sql : code ] "선수와 경기 기록 JOIN"

```sql
SELECT
    a.athlete_name,
    m.record_id,
    m.score
FROM athletes AS a
JOIN match_records AS m
    ON a.athlete_id = m.athlete_id
ORDER BY m.record_id;
```

[ Result ]

| athlete_name | record_id | score |
|---|---:|---:|
| 지민 | 101 | 22 |
| 지민 | 102 | 27 |
| 현우 | 103 | 18 |

`athletes`에서 지민은 한 Row이지만 연결된 경기 기록이 두 개이므로 JOIN 결과에서는 지민이 두 Row로 나타남.

```text
지민
 ↓
101
102

JOIN

지민 | 101
지민 | 102
```

따라서 분석할 때 테이블 관계를 확인하지 않고 JOIN하면 예상보다 Row 수가 증가할 수 있음.

# **3. ERD(Entity Relationship Diagram)**

ERD는 데이터베이스의 Entity와 Entity 사이 관계를 시각적으로 표현한 Diagram.

실무에서는 복잡한 기호 자체를 전부 암기하기보다 다음 세 가지를 파악하는 것이 중요.

```text
1. 필요한 데이터가 어느 Table에 있는가?
2. 어떤 PK/FK를 통해 연결되는가?
3. 연결 관계가 1:1, 1:N, N:M 중 무엇인가?
```

<br>

> ## **3-1 ) ERD의 주요 구성 요소**

| 구성 요소 | 의미 | 관계형 DB |
|---|---|---|
| Entity | 관리하려는 데이터 대상 | Table |
| Attribute | Entity의 속성 | Column |
| Relationship | Entity 사이 연결 | Table 관계 |

예.

```text
┌────────────────────┐
│ athletes           │
├────────────────────┤
│ PK athlete_id      │
│ athlete_name       │
│ sport              │
└────────────────────┘
          │
          │
          ▼
┌────────────────────┐
│ match_records      │
├────────────────────┤
│ PK record_id       │
│ FK athlete_id      │
│ score              │
└────────────────────┘
```

<br>

> ## **3-2 ) ERD에서 가장 먼저 확인할 것**

ERD를 처음부터 모두 해석하려 하지 않고 **필요한 데이터부터 찾음**.

예를 들어 다음 요청.

```text
"선수 이름과 선수가 참가한 대회 이름을 조회하라."
```

데이터 위치.

```text
athlete_name
→ athletes

competition_name
→ competitions
```

두 Table은 직접 연결되지 않음.

따라서 PK와 FK를 따라감.

```text
athletes.athlete_id
        ↓
competition_entries.athlete_id

competitions.competition_id
        ↓
competition_entries.competition_id
```

연결 경로.

```text
athletes
    ↓
competition_entries
    ↓
competitions
```

<br>

> ## **3-3 ) ERD를 이용해 JOIN 경로 찾기**

[ sql : code ] "ERD의 PK와 FK를 따라 선수와 대회 연결"

```sql
SELECT
    a.athlete_name,
    c.competition_name
FROM athletes AS a
JOIN competition_entries AS ce
    ON a.athlete_id = ce.athlete_id
JOIN competitions AS c
    ON ce.competition_id = c.competition_id
ORDER BY
    a.athlete_name,
    c.competition_name;
```

예를 들어 데이터가 다음과 같다고 가정.

#### `athletes`

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |

#### `competitions`

| competition_id | competition_name |
|---:|---|
| 10 | 전국체전 |
| 20 | 대학선수권 |

#### `competition_entries`

| athlete_id | competition_id |
|---:|---:|
| 1 | 10 |
| 1 | 20 |
| 2 | 10 |

[ Result ]

| athlete_name | competition_name |
|---|---|
| 지민 | 대학선수권 |
| 지민 | 전국체전 |
| 현우 | 전국체전 |

<br>

> ## **3-4 ) ERD 읽기 흐름**

```text
분석하려는 데이터 결정
        ↓
데이터가 위치한 Table 확인
        ↓
각 Table의 PK 확인
        ↓
PK를 참조하는 FK 확인
        ↓
Table 관계 확인
        ↓
JOIN 경로 결정
        ↓
JOIN 조건 작성
```

# **4. Crow's Foot 표기법**

ERD에서는 관계의 최소·최대 개수를 나타내기 위해 Crow's Foot 표기법을 많이 사용함.

도구마다 그림 모양이 조금씩 다를 수 있으므로 의미를 중심으로 이해하는 것이 중요.

> ## **4-1 ) 주요 관계 표현**

| 표현 | 의미 |
|---|---|
| `0..1` | 0개 또는 1개 |
| `1..1` | 정확히 1개 |
| `0..N` | 0개 이상 |
| `1..N` | 1개 이상 |

Crow's Foot에서는 보통.

```text
○
→ 0 가능

|
→ 1

까마귀발
→ 여러 개
```

로 해석.

<br>

> ## **4-2 ) 선수와 경기 기록 관계**

한 선수에게 경기 기록이 없을 수도 있고 여러 개 있을 수도 있다고 가정.

```text
athlete
1
│
│
0..N
match_records
```

의미.

```text
선수 한 명
→ 경기 기록 0개 이상 가능

경기 기록 하나
→ 특정 선수 한 명과 연결
```

따라서 기본 관계는.

```text
athletes : match_records
          1 : N
```

<br>

> ## **4-3 ) ERD에서 관계와 실제 제약조건 함께 확인하기**

ERD의 선만 보고 판단하는 것보다 실제 Column 정의를 함께 보는 것이 정확함.

예.

```sql
athlete_id INTEGER NOT NULL
    REFERENCES athletes(athlete_id)
```

`NOT NULL`이 있으므로 경기 기록에 선수 ID가 반드시 필요함.

반대로.

```sql
athlete_id INTEGER
    REFERENCES athletes(athlete_id)
```

라면 `athlete_id` 자체가 NULL일 수 있음.

즉, 실제 선택성(Optionality)을 판단할 때는 ERD뿐 아니라 `NULL / NOT NULL`, `UNIQUE`, FK 제약조건도 함께 확인하는 것이 좋음.

# **5. SQL 명령어 분류**

SQL 명령은 목적에 따라 여러 종류로 구분할 수 있음.

이번 학습에서는 특히 `DDL`과 `DML`의 차이를 이해하는 것이 중요.

> ## **5-1 ) DDL(Data Definition Language)**

Database의 **구조를 정의하거나 변경하는 명령**.

대표 명령.

```text
CREATE
ALTER
DROP
```

예.

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50)
);
```

Table이라는 구조를 생성하므로 DDL.

<br>

> ## **5-2 ) DML(Data Manipulation Language)**

Table 안에 저장된 데이터를 다루는 명령.

대표적으로.

```text
INSERT
UPDATE
DELETE
```

`SELECT`는 교재나 분류 기준에 따라 DML에 포함시키기도 하고 별도의 `DQL(Data Query Language)`로 구분하기도 함.

실무에서 중요한 것은 분류 자체를 암기하는 것보다 각 명령의 역할을 이해하는 것.

<br>

> ## **5-3 ) DDL과 DML 비교**

| 구분 | DDL | DML |
|---|---|---|
| 전체 이름 | Data Definition Language | Data Manipulation Language |
| 대상 | Database 구조 | Table의 데이터 |
| 예 | `CREATE` | `INSERT` |
| 예 | `ALTER` | `UPDATE` |
| 예 | `DROP` | `DELETE` |

비유.

```text
DDL
→ 경기장을 건설하거나 구조를 변경

DML
→ 경기장 안에서 실제 선수 데이터를 등록·수정
```

# **6. CREATE TABLE**

`CREATE TABLE`은 새로운 Table을 생성하는 DDL 명령.

> ## **6-1 ) 기본 문법**

```sql
CREATE TABLE 테이블명 (
    컬럼명 데이터타입 제약조건,
    컬럼명 데이터타입 제약조건
);
```

예.

[ sql : code ] "선수 정보를 저장할 Table 생성"

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50) NOT NULL,
    sport VARCHAR(30) NOT NULL,
    active BOOLEAN DEFAULT TRUE
);
```

Table 구조.

| Column | Type | Constraint |
|---|---|---|
| `athlete_id` | `INTEGER` | `PRIMARY KEY` |
| `athlete_name` | `VARCHAR(50)` | `NOT NULL` |
| `sport` | `VARCHAR(30)` | `NOT NULL` |
| `active` | `BOOLEAN` | `DEFAULT TRUE` |

`CREATE TABLE` 자체는 일반적으로 조회 결과 Table을 반환하는 명령이 아니므로 `[ Result ]`는 생성된 구조로 이해하면 됨.

[ Result ]

```text
athletes Table 생성

athlete_id
athlete_name
sport
active
```

<br>

> ## **6-2 ) 주요 Constraint**

| Constraint | 의미 |
|---|---|
| `PRIMARY KEY` | 중복·NULL 불가, Row 식별 |
| `NOT NULL` | NULL 입력 금지 |
| `UNIQUE` | 중복 값을 제한 |
| `DEFAULT` | 값 생략 시 기본값 |
| `REFERENCES` | 다른 Table의 Key 참조 |
| `CHECK` | 값에 조건 적용 |

<br>

> ## **6-3 ) UNIQUE와 NULL 주의**

다음 Column.

```sql
email VARCHAR(100) UNIQUE
```

PostgreSQL의 기본 `UNIQUE` 제약은 일반적으로 여러 개의 `NULL` 값을 허용함.

따라서.

```text
NULL
NULL
```

두 Row가 존재할 수 있음.

하지만 동일한 실제 값.

```text
runner@example.com
runner@example.com
```

을 두 번 저장하면 UNIQUE 위반.

NULL도 서로 같은 값으로 취급하도록 강제해야 하는 특별한 경우에는 PostgreSQL의 추가 기능을 사용할 수 있지만 초급 단계에서는 `UNIQUE`의 기본 동작만 이해하면 충분함.

# **7. DEFAULT 값**

`DEFAULT`는 INSERT에서 특정 Column 값을 생략했을 때 사용할 기본값을 지정함.

> ## **7-1 ) 선수 등록일과 활성 상태 기본값**

[ sql : code ] "DEFAULT를 사용한 선수 Table 생성"

```sql
CREATE TABLE athlete_members (
    member_id INTEGER PRIMARY KEY,
    member_name VARCHAR(50) NOT NULL,
    active BOOLEAN DEFAULT TRUE,
    created_at DATE DEFAULT CURRENT_DATE
);
```

다음과 같이 `active`, `created_at`을 생략 가능.

```sql
INSERT INTO athlete_members (
    member_id,
    member_name
)
VALUES (
    1,
    '서연'
);
```

2026년 9월 12일에 실행한다고 가정하면.

[ Result ]

| member_id | member_name | active | created_at |
|---:|---|---|---|
| 1 | 서연 | true | 2026-09-12 |

`CURRENT_DATE` 결과는 실제 SQL 실행 날짜에 따라 달라짐.

# **8. REFERENCES를 이용한 Foreign Key**

`REFERENCES`를 사용하면 다른 Table의 Key를 참조하는 FK를 정의 가능.

> ## **8-1 ) 선수와 훈련 기록 연결**

[ sql : code ] "훈련 기록의 athlete_id를 선수 Table과 연결"

```sql
CREATE TABLE training_sessions (
    session_id INTEGER PRIMARY KEY,
    athlete_id INTEGER NOT NULL
        REFERENCES athletes(athlete_id),
    session_date DATE NOT NULL,
    duration_min INTEGER
        CHECK (duration_min >= 0)
);
```

관계.

```text

athlete_id FK
```

# **12. DROP TABLE**

`DROP TABLE`은 Table 구조 자체를 삭제하는 DDL 명령.

Table을 삭제하면 그 Table에 저장된 데이터도 함께 제거됨.

> ## **12-1 ) 기본 사용법**

```sql
DROP TABLE running_records;
```

[ Result ]

```text
running_records Table 삭제
```

<br>

> ## **12-2 ) FK 관계가 있는 Table 삭제 순서**

다음 관계가 있다고 가정.

```text
athletes
    ↑
    │ FK
training_sessions
```

`training_sessions`가 `athletes`를 참조하고 있으므로 일반적으로 자식 Table부터 삭제.

```sql
DROP TABLE training_sessions;
DROP TABLE athletes;
```

흐름.

```text
training_sessions 삭제
        ↓
athletes를 참조하는 FK 제거
        ↓
athletes 삭제
```

<br>

> ## **12-3 ) IF EXISTS**

실무에서는 Table이 없을 때 발생하는 오류를 피하기 위해 다음 형태도 자주 사용.

```sql
DROP TABLE IF EXISTS training_sessions;
```

Table이 존재하면 삭제하고, 존재하지 않으면 치명적인 오류 대신 Notice 수준의 메시지로 넘어갈 수 있음.

<br>

> ## **12-4 ) DROP TABLE과 트랜잭션**

`DROP TABLE`은 매우 위험한 명령이므로 실제 운영 DB에서는 특히 주의해야 함.

다만 PostgreSQL의 많은 DDL 작업은 트랜잭션 안에서 실행 가능하므로, 아직 `COMMIT`하지 않았다면 상황에 따라 `ROLLBACK`으로 되돌릴 수 있음.

따라서 단순히

```text
DROP TABLE = 어떤 상황에서도 절대 복구 불가능
```

이라고 이해하는 것은 정확하지 않음.

하지만 Commit된 삭제나 운영 데이터 손실은 복구가 매우 어려울 수 있으므로 실무에서는 백업과 권한 관리가 중요함.

# **14. ERD와 SQL을 연결해서 생각하기**

ERD는 단순히 데이터베이스 그림을 보는 학습이 아니라 이후 작성할 `JOIN` SQL을 설계하는 지도 역할을 함.

다음 구조를 가정.

```text
athletes
────────────────
PK athlete_id
athlete_name
      │
      │ 1:N
      ↓
training_sessions
────────────────
PK session_id
FK athlete_id
duration_min
```

분석 질문.

```text
"선수별 총 훈련시간을 구하라."
```

필요한 데이터.

```text
선수 이름
→ athletes.athlete_name

훈련시간
→ training_sessions.duration_min
```

연결 Column.

```text
athletes.athlete_id
=
training_sessions.athlete_id
```

따라서 SQL.

[ sql : code ] "ERD를 이용하여 선수별 총 훈련시간 분석"

```sql
SELECT
    a.athlete_name,
    SUM(t.duration_min) AS total_minutes
FROM athletes AS a
JOIN training_sessions AS t
    ON a.athlete_id = t.athlete_id
GROUP BY
    a.athlete_id,
    a.athlete_name
ORDER BY
    total_minutes DESC;
```

ERD를 읽을 때 최종 목표.

```text
어디에 데이터가 있는가?
        ↓
어떤 Table이 필요한가?
        ↓
어떤 PK/FK가 연결되는가?
        ↓
관계가 1:N인가 N:M인가?
        ↓
JOIN했을 때 Row가 어떻게 변하는가?
        ↓
어떤 JOIN 조건을 작성해야 하는가?
```

# **15. 관계 유형 전체 비교**

| 항목 | 1:1 | 1:N | N:M |
|---|---|---|---|
| 왼쪽 Row 하나 | 최대 한 Row 연결 | 여러 Row 연결 | 여러 Row 연결 |
| 오른쪽 Row 하나 | 최대 한 Row 연결 | 일반적으로 왼쪽 하나와 연결 | 여러 Row 연결 |
| FK | 한쪽에 배치 + 보통 UNIQUE | N쪽에 배치 | Junction Table에 배치 |
| 중간 Table | 보통 불필요 | 불필요 | 일반적으로 필요 |
| 스포츠 예 | 선수 : 상세 프로필 | 선수 : 경기 기록 | 선수 : 대회 |

<br>

> ## **15-1 ) 관계를 판단하는 질문**

관계를 볼 때 다음 질문을 양쪽 방향으로 해보면 쉬움.

```text
선수 한 명은 경기 기록을 여러 개 가질 수 있는가?
→ Yes

경기 기록 한 개는 여러 선수에게 속할 수 있는가?
→ No

따라서
선수 : 경기 기록 = 1:N
```

반면.

```text
선수 한 명은 여러 대회에 참가 가능한가?
→ Yes

대회 하나에 여러 선수가 참가 가능한가?
→ Yes

따라서
선수 : 대회 = N:M
```

# **17. Advanced 추가 학습**

> ## **17-1 ) Junction Table에 추가 정보를 저장할 수도 있음**

N:M 관계의 중간 Table은 단순히 두 FK만 저장하는 것이 아님.

선수와 대회의 관계라면 다음 정보도 저장 가능.

```sql
CREATE TABLE competition_entries (
    athlete_id INTEGER
        REFERENCES athletes(athlete_id),

    competition_id INTEGER
        REFERENCES competitions(competition_id),

    bib_number INTEGER,
    final_rank INTEGER,

    PRIMARY KEY (
        athlete_id,
        competition_id
    )
);
```

즉, Junction Table 자체가 하나의 중요한 Entity 역할을 할 수도 있음.

<br>

> ## **17-2 ) CREATE TABLE IF NOT EXISTS**

Table이 이미 존재할 가능성이 있다면 다음 문법 사용 가능.

```sql
CREATE TABLE IF NOT EXISTS athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50)
);
```

이미 같은 이름의 Table이 존재하면 새로 만들지 않음.

다만 기존 Table의 구조가 원하는 구조와 같은지를 자동으로 검증하거나 수정해 주는 것은 아님.

<br>

> ## **17-3 ) INSERT RETURNING**

PostgreSQL에서는 INSERT 직후 저장된 값을 `RETURNING`으로 확인 가능.

```sql
INSERT INTO athletes (
    athlete_id,
    athlete_name,
    sport
)
VALUES (
    10,
    '하린',
    '수영'
)
RETURNING
    athlete_id,
    athlete_name,
    sport;
```

[ Result ]

| athlete_id | athlete_name | sport |
|---:|---|---|
| 10 | 하린 | 수영 |

INSERT 후 다시 SELECT하지 않고 입력된 Row를 바로 확인할 수 있어 유용함.

# **18. 핵심정리**

- 관계형 데이터베이스의 Table은 서로 독립적으로 존재하는 것이 아니라 PK와 FK를 이용해 관계를 형성함.
- 대표적인 Table 관계는 `1:1`, `1:N`, `N:M` 세 가지임.
- `1:1`은 한 Row가 상대 Table의 최대 한 Row와 연결되는 관계임.
- 실제 1:1 관계를 강제하려면 FK에 `UNIQUE` 등의 제약이 필요한 경우가 있음.
- `1:N`은 한쪽의 한 Row가 상대 Table의 여러 Row와 연결되는 관계임.
- 일반적으로 `1:N`에서는 N쪽 Table이 1쪽 Table의 PK를 FK로 가짐.
- `N:M`은 양쪽 모두 상대방의 여러 Row와 연결될 수 있는 관계임.
- N:M 관계는 관계형 설계에서 일반적으로 Junction Table을 이용해 두 개의 `1:N` 관계로 구현함.
- `1:N` Table을 JOIN하면 1쪽의 한 Row가 결과에서 여러 번 나타날 수 있으므로 분석 시 Row 수 증가에 주의해야 함.
- ERD는 Database의 Entity, Attribute, Relationship을 시각적으로 나타낸 Diagram임.
- ERD의 모든 기호를 암기하기보다 필요한 데이터의 위치와 PK/FK 연결 경로를 찾는 능력이 중요함.
- ERD를 읽을 때 `필요한 데이터 → Table → PK/FK → JOIN 경로` 순서로 접근하면 이해하기 쉬움.
- Crow's Foot 표기법은 관계의 최소·최대 개수를 표현함.
- 관계의 선택성까지 정확하게 이해하려면 ERD뿐 아니라 `NOT NULL`, `UNIQUE`, FK 등의 실제 제약조건도 함께 확인하는 것이 좋음.
- DDL은 데이터베이스 구조를 정의하는 명령이며 `CREATE`, `ALTER`, `DROP` 등이 대표적임.
- DML은 저장된 데이터를 다루는 명령이며 `INSERT`, `UPDATE`, `DELETE` 등이 대표적임.
- `SELECT`는 분류 체계에 따라 DML에 포함하거나 별도의 DQL로 구분하기도 함.
- `CREATE TABLE`에서는 Column 이름, 데이터 타입, Constraint를 함께 정의함.
- `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `DEFAULT`, `REFERENCES`, `CHECK` 등이 자주 사용되는 Constraint임.
- PostgreSQL에서 일반적인 `UNIQUE` 제약은 여러 NULL을 허용할 수 있으므로 `UNIQUE = NULL까지 무조건 하나만 가능`으로 이해하면 안 됨.
- `DEFAULT`는 INSERT에서 값을 생략했을 때 사용할 기본값을 지정함.
- `REFERENCES`를 사용하면 다른 Table을 참조하는 FK 관계를 설정할 수 있음.
- `INSERT INTO`는 Table에 새로운 Row를 추가함.
- INSERT 시 Column 이름을 명시하는 방식이 코드의 의미가 명확하고 Table 구조 변경에도 상대적으로 안전함.
- Column 이름을 생략한 INSERT에서는 Table에 정의된 대상 Column 순서와 값의 순서를 정확히 맞춰야 함.
- 하나의 `INSERT INTO`에서 여러 값 묶음을 쉼표로 구분하여 여러 Row를 한 번에 저장할 수 있음.
- 입력 데이터는 대상 Column의 데이터 타입과 제약조건을 만족해야 함.
- `DROP TABLE`은 Table 구조와 그 데이터를 삭제하므로 운영 환경에서 매우 신중하게 사용해야 함.
- FK 관계가 있는 Table을 삭제할 때는 일반적으로 참조하는 자식 Table을 먼저 삭제함.
- PostgreSQL에서는 많은 DDL 작업을 트랜잭션으로 처리할 수 있으므로 `DROP TABLE`을 어떤 상황에서도 절대 되돌릴 수 없다고 단정하면 정확하지 않음.
- PostgreSQL의 `INSERT ... RETURNING`을 이용하면 새로 입력된 Row를 바로 반환받을 수 있음.
- SQL을 학습할 때 가장 중요한 것은 문법만 암기하는 것이 아니라 **Table이 어떤 관계로 연결되고 그 관계가 JOIN 결과의 Row 수에 어떤 영향을 미치는지 이해하는 것**임.
