# **1. 서브쿼리(Subquery)의 기본 개념**

서브쿼리(Subquery)는 **하나의 SQL 문 내부에 포함된 또 다른 `SELECT` 문**을 의미함.

바깥쪽 SQL을 `외부 쿼리(Outer Query)`, 내부에 포함된 SQL을 `서브쿼리(Inner Query)`라고 함.

```sql
SELECT ...
FROM ...
WHERE column > (
    SELECT ...
    FROM ...
);
```

서브쿼리는 반드시 `( )`로 감싸서 작성함.

이번 TIL에서는 다음 스포츠 데이터를 예제로 사용함.

#### `players`

| player_id | player_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |
| 3 | 서연 | 농구 |
| 4 | 민재 | 야구 |
| 5 | 수빈 | 사이클 |

#### `match_records`

| record_id | player_id | score |
|---:|---:|---:|
| 101 | 1 | 88 |
| 102 | 1 | 92 |
| 103 | 2 | 75 |
| 104 | 3 | 95 |
| 105 | 4 | 82 |
| 106 | 2 | 90 |

#### `training_sessions`

| session_id | player_id | duration_min |
|---:|---:|---:|
| 201 | 1 | 60 |
| 202 | 1 | 45 |
| 203 | 2 | 80 |
| 204 | 2 | 70 |
| 205 | 3 | 50 |
| 206 | 4 | 90 |
| 207 | 4 | 30 |

<br>

> ## **1-1 ) 서브쿼리가 필요한 이유**

예를 들어 다음 조건의 선수를 찾는다고 가정함.

```text
전체 경기 기록의 평균 점수보다
높은 점수를 기록한 경기 조회
```

먼저 평균 점수를 직접 계산할 수 있음.

[ sql : code ] "전체 경기 점수 평균 계산"

```sql
SELECT AVG(score) AS avg_score
FROM match_records;
```

계산.

```text
(88 + 92 + 75 + 95 + 82 + 90) / 6
= 87
```

[ Result ]

| avg_score |
|---:|
| 87.0000 |

평균값 `87`을 직접 입력하면 다음과 같이 작성 가능함.

```sql
SELECT *
FROM match_records
WHERE score > 87;
```

하지만 데이터가 변경되면 평균도 변경되므로 `87`을 다시 계산해야 함.

이때 평균 계산 SQL 자체를 조건 안에 넣을 수 있음.

[ sql : code ] "전체 평균보다 높은 경기 기록 조회"

```sql
SELECT
    record_id,
    player_id,
    score
FROM match_records
WHERE score > (
    SELECT AVG(score)
    FROM match_records
)
ORDER BY record_id;
```

[ Result ]

| record_id | player_id | score |
|---:|---:|---:|
| 101 | 1 | 88 |
| 102 | 1 | 92 |
| 104 | 3 | 95 |
| 106 | 2 | 90 |

개념적으로 보면.

```text
서브쿼리
SELECT AVG(score)
        ↓
       87
        ↓
외부 쿼리
WHERE score > 87
        ↓
평균보다 높은 기록 조회
```

데이터가 변경되어 평균이 달라져도 SQL 자체를 수정할 필요가 없음.

<br>

> ## **1-2 ) 가장 높은 기록 찾기**

`MAX()`를 사용하면 가장 높은 점수를 서브쿼리에서 계산 가능.

[ sql : code ] "전체 경기 중 최고 점수 기록 조회"

```sql
SELECT
    record_id,
    player_id,
    score
FROM match_records
WHERE score = (
    SELECT MAX(score)
    FROM match_records
);
```

서브쿼리.

```text
MAX(score)
→ 95
```

외부 쿼리.

```text
score = 95
```

[ Result ]

| record_id | player_id | score |
|---:|---:|---:|
| 104 | 3 | 95 |

최고 점수를 기록한 사람이 여러 명이라면 외부 쿼리 결과도 여러 Row가 나올 수 있음.

# **2. 위치에 따른 서브쿼리 종류**

서브쿼리는 SQL의 어느 위치에 작성하는지에 따라 역할이 달라짐.

| 위치 | 이름 | 주요 역할 |
|---|---|---|
| `WHERE` | WHERE절 서브쿼리 | 조건값 또는 비교 대상 생성 |
| `FROM` | 인라인 뷰(Inline View) | 조회 결과를 임시 Table처럼 사용 |
| `SELECT` | 스칼라 서브쿼리(Scalar Subquery) | 하나의 값을 새로운 Column으로 추가 |

<br>

> ## **2-1 ) WHERE절 서브쿼리**

```sql
SELECT *
FROM match_records
WHERE score > (
    SELECT AVG(score)
    FROM match_records
);
```

서브쿼리의 결과를 **조건값**으로 사용.

<br>

> ## **2-2 ) FROM절 서브쿼리**

```sql
SELECT *
FROM (
    SELECT
        player_id,
        AVG(score) AS avg_score
    FROM match_records
    GROUP BY player_id
) AS player_summary;
```

안쪽 쿼리 결과를 외부에서 **Table처럼 사용**.

<br>

> ## **2-3 ) SELECT절 서브쿼리**

```sql
SELECT
    player_name,
    (
        SELECT AVG(score)
        FROM match_records
    ) AS overall_avg
FROM players;
```

서브쿼리의 결과가 하나의 새로운 Column처럼 추가됨.


<br><br>

# **3. WHERE절 서브쿼리**

WHERE절 서브쿼리는 **조건에 사용할 값을 데이터에서 동적으로 계산할 때** 많이 사용함.

> ## **3-1 ) 평균보다 낮은 경기 기록 조회**

[ sql : code ] "전체 경기 평균보다 낮은 점수 조회"

```sql
SELECT
    record_id,
    player_id,
    score
FROM match_records
WHERE score < (
    SELECT AVG(score)
    FROM match_records
)
ORDER BY record_id;
```

평균.

```text
87
```

87보다 작은 점수.

```text
75
82
```

[ Result ]

| record_id | player_id | score |
|---:|---:|---:|
| 103 | 2 | 75 |
| 105 | 4 | 82 |

<br>

> ## **3-2 ) 가장 낮은 경기 기록 조회**

[ sql : code ] "최저 점수와 동일한 경기 기록 조회"

```sql
SELECT
    record_id,
    player_id,
    score
FROM match_records
WHERE score = (
    SELECT MIN(score)
    FROM match_records
);
```

[ Result ]

| record_id | player_id | score |
|---:|---:|---:|
| 103 | 2 | 75 |

<br>

> ## **3-3 ) 비교 연산자와 서브쿼리**

서브쿼리가 **하나의 값**을 반환한다면 일반적인 비교 연산자 사용 가능.

```sql
=
>
<
>=
<=
<>
!=
```

예.

```sql
WHERE score > (
    SELECT AVG(score)
    FROM match_records
)
```

여기서 중요한 점은 `>` 오른쪽 서브쿼리가 하나의 값만 반환해야 한다는 것.

다음처럼 여러 Row가 반환될 수 있는 서브쿼리를 `=`과 바로 비교하면 문제가 발생함.

```sql
-- 잘못된 형태
WHERE player_id = (
    SELECT player_id
    FROM match_records
);
```

`match_records`에는 여러 `player_id`가 있기 때문에 서브쿼리가 여러 Row를 반환할 수 있음.

여러 값과 비교하려면 `IN` 등을 사용해야 함.

# **4. IN과 서브쿼리**

`IN`은 하나의 값이 **여러 후보 값 중 하나와 일치하는지** 검사함.

서브쿼리가 여러 Row를 반환할 때 자주 사용.

> ## **4-1 ) 경기 기록이 있는 선수 찾기**

먼저 경기 기록이 존재하는 선수 ID 확인.

```sql
SELECT DISTINCT player_id
FROM match_records;
```

[ Result ]

```text
1
2
3
4
```

이 목록에 포함되는 선수만 `players`에서 찾음.

[ sql : code ] "경기 출전 기록이 있는 선수 조회"

```sql
SELECT
    player_id,
    player_name,
    sport
FROM players
WHERE player_id IN (
    SELECT player_id
    FROM match_records
)
ORDER BY player_id;
```

[ Result ]

| player_id | player_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |
| 3 | 서연 | 농구 |
| 4 | 민재 | 야구 |

수빈은 경기 기록이 없으므로 제외됨.

<br>

> ## **4-2 ) IN의 동작 구조**

```text
서브쿼리

player_id
---------
1
1
2
3
4
2

        ↓

IN

player_id IN (1, 1, 2, 3, 4, 2)

        ↓

players의 각 player_id 확인

1 → 포함
2 → 포함
3 → 포함
4 → 포함
5 → 제외
```

존재 여부만 판단하는 경우에는 서브쿼리 내부에서 `DISTINCT`를 반드시 사용할 필요는 없음.

다음도 같은 선수들을 반환함.

```sql
WHERE player_id IN (
    SELECT player_id
    FROM match_records
)
```

중복값이 존재하더라도 `IN`은 해당 값이 목록에 존재하는지만 판단함.

# **5. NOT IN과 서브쿼리**

`NOT IN`은 서브쿼리의 결과 목록에 **포함되지 않은 값**을 찾을 때 사용.

> ## **5-1 ) 경기 기록이 없는 선수 조회**

[ sql : code ] "한 번도 경기 기록이 없는 선수 조회"

```sql
SELECT
    player_id,
    player_name,
    sport
FROM players
WHERE player_id NOT IN (
    SELECT player_id
    FROM match_records
)
ORDER BY player_id;
```

서브쿼리 결과.

```text
1
2
3
4
```

외부 쿼리.

```text
1 → 제외
2 → 제외
3 → 제외
4 → 제외
5 → 포함
```

[ Result ]

| player_id | player_name | sport |
|---:|---|---|
| 5 | 수빈 | 사이클 |

<br>

> ## **5-2 ) NOT IN과 NULL 주의**

`NOT IN`은 서브쿼리 결과에 `NULL`이 포함될 수 있다면 특히 주의해야 함.

예를 들어 서브쿼리 결과가.

```text
1
2
3
NULL
```

이라고 가정.

다음 조건을 검사하면.

```sql
WHERE player_id NOT IN (1, 2, 3, NULL)
```

SQL의 `NULL`은 **알 수 없는 값**(UNKNOWN)을 의미하기 때문에 비교 결과가 예상과 달라질 수 있음.

결과적으로 원하는 Row가 조회되지 않을 수 있음.

NULL을 제거할 수 있다면.

```sql
SELECT player_id
FROM match_records
WHERE player_id IS NOT NULL
```

처럼 작성 가능.

하지만 **존재하지 않는 데이터를 찾는 목적**이라면 `NOT EXISTS`가 더 명확한 경우가 많음.


<br><br>

# **6. EXISTS와 NOT EXISTS**

`EXISTS`는 서브쿼리가 반환하는 **값 자체가 아니라 조건을 만족하는 Row가 존재하는지** 확인함.

```text
조건에 맞는 Row 존재
→ TRUE

조건에 맞는 Row 없음
→ FALSE
```

<br>

> ## **6-1 ) 경기 기록이 있는 선수 EXISTS로 조회**

[ sql : code ] "경기 기록의 존재 여부를 이용하여 선수 조회"

```sql
SELECT
    p.player_id,
    p.player_name,
    p.sport
FROM players AS p
WHERE EXISTS (
    SELECT 1
    FROM match_records AS m
    WHERE m.player_id = p.player_id
)
ORDER BY p.player_id;
```

[ Result ]

| player_id | player_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |
| 3 | 서연 | 농구 |
| 4 | 민재 | 야구 |

<br>

> ## **6-2 ) EXISTS의 실행 논리**

지민을 검사한다고 가정.

```text
외부 Row
p.player_id = 1
        ↓
서브쿼리
match_records에서
m.player_id = 1인 Row 존재?
        ↓
101번 기록 존재
        ↓
EXISTS = TRUE
        ↓
지민 출력
```

수빈.

```text
외부 Row
p.player_id = 5
        ↓
서브쿼리
m.player_id = 5인 Row 존재?
        ↓
없음
        ↓
EXISTS = FALSE
        ↓
수빈 제외
```

<br>

> ## **6-3 ) SELECT 1의 의미**

다음 코드에서.

```sql
SELECT 1
FROM match_records AS m
WHERE m.player_id = p.player_id
```

`1`이라는 숫자를 실제 분석 결과로 가져오려는 목적이 아님.

`EXISTS`에서는.

```text
어떤 값이 반환되는가?
```

보다.

```text
조건을 만족하는 Row가 존재하는가?
```

가 중요함.

따라서 관례적으로.

```sql
SELECT 1
```

을 많이 사용함.

<br>

> ## **6-4 ) 경기 기록이 없는 선수 NOT EXISTS로 조회**

[ sql : code ] "경기 기록이 존재하지 않는 선수 조회"

```sql
SELECT
    p.player_id,
    p.player_name,
    p.sport
FROM players AS p
WHERE NOT EXISTS (
    SELECT 1
    FROM match_records AS m
    WHERE m.player_id = p.player_id
)
ORDER BY p.player_id;
```

[ Result ]

| player_id | player_name | sport |
|---:|---|---|
| 5 | 수빈 | 사이클 |

`NOT EXISTS`는 조건에 일치하는 Row가 하나도 없을 때 `TRUE`.

```text
EXISTS
→ 존재하면 선택

NOT EXISTS
→ 존재하지 않으면 선택
```

# **7. IN과 EXISTS 비교**

`IN`과 `EXISTS`는 같은 결과를 만들 수 있는 경우가 많지만 사고 방식이 다름.

> ## **7-1 ) IN 방식**

```sql
SELECT
    player_id,
    player_name
FROM players
WHERE player_id IN (
    SELECT player_id
    FROM match_records
);
```

생각하는 방식.

```text
경기 기록이 있는 player_id 목록을 구함
↓
현재 player_id가 목록 안에 있는가?
```

<br>

> ## **7-2 ) EXISTS 방식**

```sql
SELECT
    p.player_id,
    p.player_name
FROM players AS p
WHERE EXISTS (
    SELECT 1
    FROM match_records AS m
    WHERE m.player_id = p.player_id
);
```

생각하는 방식.

```text
현재 선수와 일치하는 경기 기록이
하나라도 존재하는가?
```

<br>

> ## **7-3 ) 비교**

| 구분 | `IN` | `EXISTS` |
|---|---|---|
| 핵심 질문 | 값이 목록 안에 있는가? | 조건을 만족하는 Row가 존재하는가? |
| 서브쿼리 | 여러 값 반환 가능 | 존재 여부가 중요 |
| 외부 Row 참조 | 필수 아님 | 상관 서브쿼리 형태로 자주 사용 |
| 부정형 | `NOT IN` | `NOT EXISTS` |
| NULL | `NOT IN`에서 특히 주의 | 존재 여부 판단에 적합 |

무조건 어느 한쪽이 더 빠르다고 단정할 수는 없음.

PostgreSQL의 옵티마이저가 쿼리를 변환하여 비슷한 실행 계획을 만들 수도 있으므로 실제 성능은 데이터 구조, 인덱스, 데이터량, 통계 정보 등에 따라 달라짐.


<br><br>

# **8. 상관 서브쿼리(Correlated Subquery)**

상관 서브쿼리는 서브쿼리 내부에서 **외부 쿼리의 현재 Row 값을 참조하는 서브쿼리**.

앞의 `EXISTS` 예제가 대표적.

```sql
SELECT
    p.player_id,
    p.player_name
FROM players AS p
WHERE EXISTS (
    SELECT 1
    FROM match_records AS m
    WHERE m.player_id = p.player_id
);
```

서브쿼리 내부의.

```sql
p.player_id
```

가 외부 쿼리 `players`의 값을 참조함.

<br>

> ## **8-1 ) 각 선수의 경기 횟수 계산**

[ sql : code ] "상관 서브쿼리로 선수마다 경기 기록 개수 계산"

```sql
SELECT
    p.player_id,
    p.player_name,
    (
        SELECT COUNT(*)
        FROM match_records AS m
        WHERE m.player_id = p.player_id
    ) AS match_count
FROM players AS p
ORDER BY p.player_id;
```

각 선수마다 논리적으로 다음 조건을 확인.

```text
지민(player_id = 1)
→ player_id = 1 경기 수 COUNT
→ 2

현우(player_id = 2)
→ 2

서연(player_id = 3)
→ 1

민재(player_id = 4)
→ 1

수빈(player_id = 5)
→ 0
```

[ Result ]

| player_id | player_name | match_count |
|---:|---|---:|
| 1 | 지민 | 2 |
| 2 | 현우 | 2 |
| 3 | 서연 | 1 |
| 4 | 민재 | 1 |
| 5 | 수빈 | 0 |

### 흐름

```text
players 첫 번째 Row
player_id = 1
        ↓
서브쿼리에 1 전달
        ↓
match_records에서 1의 기록 COUNT
        ↓
2 반환
        ↓
다음 선수

player_id = 2
        ↓
COUNT
        ↓
2 반환
        ↓
...
```

상관 서브쿼리는 논리적으로 외부 Row와 연결되어 동작한다고 이해하면 됨.

실제 실행 과정은 데이터베이스 옵티마이저가 다른 형태로 최적화할 수도 있음.

# **9. FROM절 서브쿼리 - 인라인 뷰(Inline View)**

`FROM` 안에 작성한 서브쿼리는 결과 자체를 **하나의 임시 Table처럼** 사용할 수 있음.

```sql
SELECT ...
FROM (
    SELECT ...
) AS 별칭;
```

<br>

> ## **9-1 ) 선수별 총 훈련시간을 먼저 계산하기**

먼저 선수별 훈련시간 집계.

```sql
SELECT
    player_id,
    SUM(duration_min) AS total_minutes
FROM training_sessions
GROUP BY player_id;
```

[ Result ]

| player_id | total_minutes |
|---:|---:|
| 1 | 105 |
| 2 | 150 |
| 3 | 50 |
| 4 | 120 |

이 결과를 하나의 Table처럼 외부 쿼리에서 사용.

[ sql : code ] "선수별 훈련시간을 집계한 뒤 100분 이상인 선수만 조회"

```sql
SELECT
    player_id,
    total_minutes
FROM (
    SELECT
        player_id,
        SUM(duration_min) AS total_minutes
    FROM training_sessions
    GROUP BY player_id
) AS training_summary
WHERE total_minutes >= 100
ORDER BY player_id;
```

[ Result ]

| player_id | total_minutes |
|---:|---:|
| 1 | 105 |
| 2 | 150 |
| 4 | 120 |

### 처리 구조

```text
training_sessions
        ↓
GROUP BY player_id
        ↓
선수별 SUM(duration_min)
        ↓
┌─────────────────────┐
│ player_id | total   │
│ 1         | 105     │
│ 2         | 150     │
│ 3         | 50      │
│ 4         | 120     │
└─────────────────────┘
        ↓
인라인 뷰
training_summary
        ↓
WHERE total_minutes >= 100
        ↓
1 / 2 / 4번 선수
```

<br>

> ## **9-2 ) 인라인 뷰의 Column 별칭 사용**

안쪽 쿼리에서.

```sql
SUM(duration_min) AS total_minutes
```

라고 이름을 지정했기 때문에 외부 쿼리에서.

```sql
WHERE total_minutes >= 100
```

처럼 사용 가능.

따라서 집계 결과에는 의미 있는 별칭을 지정하는 것이 좋음.

<br>

> ## **9-3 ) HAVING으로 더 간단하게 가능한 경우**

위 예제는 사실 `HAVING`만으로도 작성 가능.

```sql
SELECT
    player_id,
    SUM(duration_min) AS total_minutes
FROM training_sessions
GROUP BY player_id
HAVING SUM(duration_min) >= 100
ORDER BY player_id;
```

즉.

```text
집계 결과를 단순히 필터링
→ HAVING으로 충분할 수 있음

집계 결과를 다시 JOIN하거나
추가 계산·정렬·가공해야 함
→ 인라인 뷰가 유용할 수 있음
```

서브쿼리를 사용할 수 있다고 해서 항상 서브쿼리가 필요한 것은 아님.

# **10. SELECT절 서브쿼리 - 스칼라 서브쿼리**

SELECT절에 작성되는 서브쿼리를 스칼라 서브쿼리(Scalar Subquery)라고 부름.

스칼라는 **단일 값**을 의미함.

따라서 스칼라 서브쿼리는 기본적으로 하나의 Column과 최대 하나의 Row에 해당하는 값을 표현함.

<br>

> ## **10-1 ) 모든 선수 옆에 전체 평균 점수 표시**

[ sql : code ] "각 선수 정보 옆에 전체 경기 평균 점수 추가"

```sql
SELECT
    p.player_id,
    p.player_name,
    (
        SELECT AVG(score)
        FROM match_records
    ) AS overall_avg_score
FROM players AS p
ORDER BY p.player_id;
```

전체 평균.

```text
87
```

[ Result ]

| player_id | player_name | overall_avg_score |
|---:|---|---:|
| 1 | 지민 | 87.0000 |
| 2 | 현우 | 87.0000 |
| 3 | 서연 | 87.0000 |
| 4 | 민재 | 87.0000 |
| 5 | 수빈 | 87.0000 |

서브쿼리가 외부 Row와 관계없이 항상 동일한 전체 평균을 계산하므로 모든 선수에게 `87`이 표시됨.

<br>

> ## **10-2 ) 각 선수별 경기 횟수를 새로운 Column으로 추가**

상관 스칼라 서브쿼리 사용.

```sql
SELECT
    p.player_name,
    (
        SELECT COUNT(*)
        FROM match_records AS m
        WHERE m.player_id = p.player_id
    ) AS match_count
FROM players AS p
ORDER BY p.player_id;
```

[ Result ]

| player_name | match_count |
|---|---:|
| 지민 | 2 |
| 현우 | 2 |
| 서연 | 1 |
| 민재 | 1 |
| 수빈 | 0 |

<br>

> ## **10-3 ) 스칼라 서브쿼리가 여러 Row를 반환하면**

다음 SQL.

```sql
SELECT
    player_name,
    (
        SELECT score
        FROM match_records
    ) AS score
FROM players;
```

`match_records`에는 여러 Row가 존재함.

```text
88
92
75
95
82
90
```

스칼라 서브쿼리는 하나의 값이 필요한데 여러 Row가 반환되므로 오류 발생.

대표적인 오류 의미.

```text
서브쿼리가 표현식으로 사용되었는데
2개 이상의 Row를 반환함
```

따라서.

```sql
AVG()
MAX()
MIN()
COUNT()
SUM()
```

등의 집계함수 또는 충분한 조건을 사용하여 최대 한 Row가 반환되도록 설계해야 함.

<br>

> ## **10-4 ) 스칼라 서브쿼리 결과가 없는 경우**

스칼라 서브쿼리가 아무 Row도 반환하지 않으면 해당 결과는 `NULL`로 처리될 수 있음.

예.

```sql
SELECT (
    SELECT score
    FROM match_records
    WHERE player_id = 999
) AS score;
```

조건을 만족하는 Row가 없으므로.

[ Result ]

```text
NULL
```

# **11. 집계 상관 서브쿼리와 NULL**

`COUNT()`와 `SUM()`은 데이터가 없을 때 결과가 다를 수 있어 주의.

> ## **11-1 ) COUNT**

```sql
SELECT
    p.player_name,
    (
        SELECT COUNT(*)
        FROM match_records AS m
        WHERE m.player_id = p.player_id
    ) AS match_count
FROM players AS p;
```

경기 기록이 없는 수빈.

```text
COUNT(*) → 0
```

<br>

> ## **11-2 ) SUM**

[ sql : code ] "각 선수의 총 훈련시간 계산"

```sql
SELECT
    p.player_name,
    (
        SELECT SUM(t.duration_min)
        FROM training_sessions AS t
        WHERE t.player_id = p.player_id
    ) AS total_minutes
FROM players AS p
ORDER BY p.player_id;
```

[ Result ]

| player_name | total_minutes |
|---|---:|
| 지민 | 105 |
| 현우 | 150 |
| 서연 | 50 |
| 민재 | 120 |
| 수빈 | NULL |

수빈에게는 훈련 데이터가 없기 때문에 `SUM()`의 결과가 `0`이 아니라 `NULL`.

`0`으로 표현하고 싶다면 `COALESCE()` 사용 가능.

```sql
SELECT
    p.player_name,
    COALESCE(
        (
            SELECT SUM(t.duration_min)
            FROM training_sessions AS t
            WHERE t.player_id = p.player_id
        ),
        0
    ) AS total_minutes
FROM players AS p
ORDER BY p.player_id;
```

[ Result ]

| player_name | total_minutes |
|---|---:|
| 지민 | 105 |
| 현우 | 150 |
| 서연 | 50 |
| 민재 | 120 |
| 수빈 | 0 |

# **12. 서브쿼리와 JOIN 비교**

서브쿼리와 JOIN은 서로 완전히 다른 기능이라기보다 **같은 문제를 서로 다른 방식으로 해결할 수 있는 경우가 많음**.

> ## **12-1 ) 경기 기록이 있는 선수 - 서브쿼리**

```sql
SELECT
    player_id,
    player_name
FROM players
WHERE player_id IN (
    SELECT player_id
    FROM match_records
)
ORDER BY player_id;
```

[ Result ]

| player_id | player_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |
| 3 | 서연 |
| 4 | 민재 |

<br>

> ## **12-2 ) 같은 결과를 JOIN으로 작성**

단순 JOIN.

```sql
SELECT
    p.player_id,
    p.player_name
FROM players AS p
JOIN match_records AS m
    ON p.player_id = m.player_id;
```

그런데 지민과 현우는 경기 기록이 2개씩 존재함.

따라서 단순 JOIN 결과.

```text
지민
지민
현우
현우
서연
민재
```

중복 발생.

같은 선수 목록만 필요하다면 `DISTINCT` 추가.

```sql
SELECT DISTINCT
    p.player_id,
    p.player_name
FROM players AS p
JOIN match_records AS m
    ON p.player_id = m.player_id
ORDER BY p.player_id;
```

[ Result ]

| player_id | player_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |
| 3 | 서연 |
| 4 | 민재 |

<br>

> ## **12-3 ) 언제 서브쿼리가 자연스러운가**

요청.

```text
경기를 한 적이 있는 선수만 보여줘
```

필요한 것은.

```text
match_records의 실제 score나 record_id
X

해당 선수가 존재하는지
O
```

이 경우.

```sql
IN
EXISTS
```

등의 서브쿼리가 자연스러울 수 있음.

<br>

> ## **12-4 ) 언제 JOIN이 자연스러운가**

요청.

```text
선수 이름과 경기 점수를 함께 보여줘
```

두 Table의 실제 Column이 모두 필요함.

```sql
SELECT
    p.player_name,
    m.score
FROM players AS p
JOIN match_records AS m
    ON p.player_id = m.player_id;
```

[ Result ]

| player_name | score |
|---|---:|
| 지민 | 88 |
| 지민 | 92 |
| 현우 | 75 |
| 서연 | 95 |
| 민재 | 82 |
| 현우 | 90 |

따라서 다른 Table의 실제 Column까지 가져와야 한다면 JOIN이 자연스러움.

<br>

> ## **12-5 ) 서브쿼리와 JOIN 비교표**

| 구분 | 서브쿼리 | JOIN |
|---|---|---|
| 핵심 목적 | 조건·계산·존재 여부 활용 | 여러 Table 정보 연결 |
| 다른 Table Column 출력 | 상황에 따라 제한적 | 자유롭게 가능 |
| 존재 여부 확인 | `EXISTS`가 직관적 | JOIN + DISTINCT 등 가능 |
| 집계 결과 활용 | 매우 편리 | GROUP BY와 함께 가능 |
| 1:N 관계 | 외부 Row 수 유지 가능 | Row가 증가할 수 있음 |
| 성능 | 상황마다 다름 | 상황마다 다름 |

```text
다른 Table을
조건으로만 사용할 것인가?
        ↓
서브쿼리 고려

다른 Table의 Column을
결과에 같이 보여줄 것인가?
        ↓
JOIN 고려
```

# **13. 종합 실습 - 평균 이상 경기력을 가진 선수 분석**

조건.

```text
1. 선수별 평균 경기 점수를 계산
2. 선수들의 평균 점수 중 전체 평균 이상인 선수만 조회
3. 선수 이름까지 함께 출력
4. 높은 평균 점수 순서대로 정렬
```

먼저 선수별 평균 점수.

```sql
SELECT
    player_id,
    AVG(score) AS avg_score
FROM match_records
GROUP BY player_id;
```

[ Result ]

| player_id | avg_score |
|---:|---:|
| 1 | 90.0 |
| 2 | 82.5 |
| 3 | 95.0 |
| 4 | 82.0 |

이 선수별 평균을 인라인 뷰로 사용.

전체 선수 평균 기록은.

```text
(90 + 82.5 + 95 + 82) / 4
= 87.375
```

[ sql : code ] "인라인 뷰와 서브쿼리를 결합한 경기력 분석"

```sql
SELECT
    p.player_id,
    p.player_name,
    s.avg_score
FROM players AS p
JOIN (
    SELECT
        player_id,
        AVG(score) AS avg_score
    FROM match_records
    GROUP BY player_id
) AS s
    ON p.player_id = s.player_id
WHERE s.avg_score >= (
    SELECT AVG(player_avg)
    FROM (
        SELECT
            AVG(score) AS player_avg
        FROM match_records
        GROUP BY player_id
    ) AS avg_summary
)
ORDER BY s.avg_score DESC;
```

[ Result ]

| player_id | player_name | avg_score |
|---:|---|---:|
| 3 | 서연 | 95.0 |
| 1 | 지민 | 90.0 |

### 결과 해석

선수별 평균 점수.

```text
서연 → 95
지민 → 90
현우 → 82.5
민재 → 82
```

선수 평균들의 전체 평균.

```text
87.375
```

따라서.

```text
서연 95   → 포함
지민 90   → 포함
현우 82.5 → 제외
민재 82   → 제외
```

### 흐름

```text
match_records
      ↓
GROUP BY player_id
      ↓
선수별 평균 계산
      ↓
┌─────────────────┐
│ 1 → 90          │
│ 2 → 82.5        │
│ 3 → 95          │
│ 4 → 82          │
└─────────────────┘
      ↓
선수 평균들의 평균
      ↓
87.375
      ↓
avg_score >= 87.375
      ↓
1번 지민 / 3번 서연
      ↓
players JOIN
      ↓
선수 이름 연결
      ↓
평균 내림차순 정렬
```

# **14. Advanced 추가 학습**

> ## **14-1 ) 서브쿼리가 항상 먼저 실행되는 것은 아님**

초보 단계에서는 일반 서브쿼리를.

```text
안쪽 SQL 계산
↓
결과 전달
↓
바깥 SQL 실행
```

으로 이해하면 편리함.

하지만 상관 서브쿼리는 외부 Row를 참조함.

```sql
WHERE m.player_id = p.player_id
```

따라서 논리적으로 외부 Row와 연결되어 판단됨.

또한 실제 PostgreSQL은 옵티마이저가 SQL을 분석하여 JOIN 등 다른 실행 방식으로 변경할 수도 있음.

즉.

```text
SQL에 작성된 모양
≠
실제 내부 실행 방식이 항상 동일
```

<br>

> ## **14-2 ) NOT IN보다 NOT EXISTS가 유용한 상황**

다음처럼 서브쿼리 결과에 `NULL` 가능성이 있다면.

```sql
WHERE player_id NOT IN (
    SELECT player_id
    FROM some_table
)
```

예상하지 못한 결과가 발생할 수 있음.

존재 여부를 확인하려는 목적이면.

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM some_table AS s
    WHERE s.player_id = p.player_id
)
```

형태가 더 명확한 경우가 많음.

<br>

> ## **14-3 ) EXISTS 안의 SELECT 값은 중요하지 않음**

다음은 존재 여부 관점에서 같은 의도를 표현함.

```sql
EXISTS (
    SELECT 1
    FROM match_records
    WHERE ...
)
```

```sql
EXISTS (
    SELECT *
    FROM match_records
    WHERE ...
)
```

학습과 가독성을 위해 일반적으로 `SELECT 1`을 많이 사용함.

<br>

> ## **14-4 ) 중첩 서브쿼리가 너무 깊어지면 CTE 고려**

다음처럼.

```text
SELECT
 └─ FROM 서브쿼리
      └─ WHERE 서브쿼리
           └─ FROM 서브쿼리
```

구조가 너무 깊어지면 읽기가 어려워질 수 있음.

이후 학습하는 CTE(`WITH`)를 사용하면 중간 결과에 이름을 붙여 SQL을 단계별로 표현할 수 있음.

<br>

> ## **14-5 ) 성능은 문법만 보고 단정하지 않기**

다음 두 SQL이 같은 결과를 만든다고 해서.

```text
서브쿼리가 무조건 느림
JOIN이 무조건 빠름
```

이라고 단정할 수 없음.

PostgreSQL 옵티마이저가 실행 방법을 결정하므로 실제 성능은.

```text
데이터량
인덱스
Table 관계
통계 정보
필터 조건
집계 방식
```

등에 영향을 받음.

실제 실행 계획과 시간을 확인할 때.

```sql
EXPLAIN ANALYZE
SELECT ...;
```

사용 가능.

`EXPLAIN ANALYZE`는 SQL을 실제로 실행하면서 실행 계획과 수행 정보를 확인하므로 데이터 변경 SQL에 사용할 때는 특히 주의해야 함.

# **15. 핵심정리**

- 서브쿼리(Subquery)는 SQL 내부에 포함된 또 다른 `SELECT` 문임.
- 바깥 SQL은 외부 쿼리(Outer Query), 안쪽 SQL은 서브쿼리(Inner Query)라고 부름.
- 서브쿼리는 `( )`로 감싸서 작성함.
- 서브쿼리는 외부 쿼리에 필요한 조건값, 목록, 임시 Table, 계산값 등을 제공할 수 있음.
- WHERE절 서브쿼리는 조건에 필요한 값을 동적으로 계산할 때 사용함.
- `AVG()`, `MAX()`, `MIN()` 등으로 하나의 값을 반환하는 서브쿼리는 `=`, `>`, `<` 등의 비교 연산자와 함께 사용할 수 있음.
- `=`이나 `>` 같은 단일 값 비교에서 서브쿼리가 여러 Row를 반환하면 오류가 발생할 수 있음.
- 여러 값 중 하나와 비교하려면 `IN`을 사용할 수 있음.
- `IN`은 서브쿼리가 반환한 값 목록에 현재 값이 포함되는지 검사함.
- `NOT IN`은 서브쿼리 결과 목록에 포함되지 않는 값을 찾음.
- `NOT IN`은 서브쿼리 결과에 `NULL`이 포함되는 경우 SQL의 NULL 논리 때문에 예상하지 못한 결과가 발생할 수 있으므로 주의해야 함.
- 존재하지 않는 데이터를 찾을 때 `NOT EXISTS`가 더 명확한 경우가 많음.
- `EXISTS`는 서브쿼리의 실제 반환값보다 조건을 만족하는 Row가 존재하는지를 확인함.
- `NOT EXISTS`는 조건을 만족하는 Row가 존재하지 않을 때 TRUE가 됨.
- `EXISTS` 내부에서는 존재 여부만 중요하므로 `SELECT 1` 형태를 자주 사용함.
- 상관 서브쿼리(Correlated Subquery)는 내부 서브쿼리에서 외부 쿼리의 현재 Row를 참조함.
- 상관 서브쿼리는 선수별 경기 횟수처럼 외부 Row마다 관련된 값을 계산할 때 사용할 수 있음.
- FROM절 서브쿼리는 인라인 뷰(Inline View)라고 부르며 결과를 임시 Table처럼 활용함.
- 인라인 뷰의 집계 결과에 의미 있는 Column 별칭을 지정하면 외부 쿼리에서 쉽게 활용 가능함.
- 단순히 GROUP BY 결과에 조건을 적용하려는 경우에는 인라인 뷰 대신 `HAVING`으로 더 간단하게 작성할 수도 있음.
- SELECT절 서브쿼리는 스칼라 서브쿼리(Scalar Subquery)라고 부름.
- 스칼라 서브쿼리는 표현식이므로 최대 하나의 Row에 해당하는 단일 값을 반환하도록 작성해야 함.
- 스칼라 서브쿼리가 여러 Row를 반환하면 오류가 발생함.
- 스칼라 서브쿼리가 아무 Row도 반환하지 않으면 결과가 `NULL`이 될 수 있음.
- `COUNT(*)`는 일치하는 Row가 없으면 `0`을 반환하지만 `SUM()`은 일치 데이터가 없으면 `NULL`이 될 수 있음.
- `COALESCE(value, 0)`를 사용하면 NULL을 0 등 원하는 기본값으로 변경 가능함.
- 서브쿼리와 JOIN은 같은 문제를 해결할 수 있는 경우가 많음.
- 다른 Table의 데이터를 **조건이나 존재 여부 확인에만 사용**한다면 `IN`, `EXISTS` 등의 서브쿼리가 직관적일 수 있음.
- 다른 Table의 실제 Column까지 **결과에 함께 출력**해야 한다면 JOIN이 자연스러운 경우가 많음.
- 1:N 관계를 JOIN하면 한 Row가 여러 Row로 증가할 수 있으므로 단순 존재 여부 목록을 만들 때는 `DISTINCT`가 필요할 수 있음.
- 서브쿼리가 무조건 느리고 JOIN이 무조건 빠른 것은 아니며 실제 성능은 PostgreSQL의 실행 계획과 데이터 구조에 따라 달라짐.
- 복잡한 SQL의 성능을 확인할 때 `EXPLAIN ANALYZE`를 활용할 수 있음.
- 서브쿼리의 핵심은 `"먼저 필요한 값이나 데이터 집합을 만들고, 그 결과를 다른 SQL에서 활용한다"`는 구조로 이해하면 됨.
