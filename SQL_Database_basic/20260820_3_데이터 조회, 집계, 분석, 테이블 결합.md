# **2. SELECT와 FROM으로 데이터 조회하기**

`SELECT`는 조회할 Column을 선택하고, `FROM`은 데이터를 가져올 Table을 지정함.

> ## **2-1 ) 특정 Column 조회**

[ sql : code ] "선수의 이름과 종목만 조회"

```sql
SELECT
    athlete_name,
    sport
FROM athletes
ORDER BY athlete_id;
```

[ Result ]

| athlete_name | sport |
|---|---|
| 지민 | 육상 |
| 현우 | 수영 |
| 서연 | 농구 |
| 민재 | 야구 |
| 수빈 | 사이클 |

`athletes`에는 여러 Column이 있지만 `SELECT`에서 지정한 `athlete_name`, `sport`만 결과에 출력됨.

<br>

> ## **2-2 ) 모든 Column 조회**

모든 Column을 확인하려면 `*` 사용.

```sql
SELECT *
FROM athletes;
```

학습이나 데이터 구조 탐색 단계에서는 편리하지만 실무 분석에서는 필요한 Column을 직접 지정하는 것이 권장됨.

```sql
SELECT
    athlete_id,
    athlete_name,
    sport
FROM athletes;
```

#### `SELECT *`를 남용하지 않는 이유

| 이유 | 설명 |
|---|---|
| 불필요한 데이터 | 사용하지 않는 Column까지 조회 |
| 가독성 | 어떤 데이터가 필요한지 코드만 보고 알기 어려움 |
| 구조 변경 | Table에 새로운 Column이 생기면 결과도 달라짐 |
| 네트워크·I/O | 큰 Table에서는 불필요한 데이터 전송 증가 |

<br>

> ## **2-3 ) SELECT와 FROM의 기본 구조**

```sql
SELECT 컬럼1, 컬럼2
FROM 테이블명;
```

흐름.

```text
FROM
↓
어느 Table에서 가져올지 결정

SELECT
↓
어떤 Column을 결과에 보여줄지 결정
```

# **3. DISTINCT로 중복 제거하기**

`DISTINCT`는 조회 결과에서 중복된 조합을 제거하고 고유한 값만 반환함.

> ## **3-1 ) 선수들의 도시 종류 확인**

[ sql : code ] "선수가 등록된 도시를 중복 없이 조회"

```sql
SELECT DISTINCT city
FROM athletes;
```

현재 데이터.

```text
서울
부산
서울
인천
서울
```

중복된 `서울`이 제거됨.

[ Result ]

```text
서울
부산
인천
```

결과의 **행 순서는 `ORDER BY`가 없다면 보장되지 않음**.

<br>

> ## **3-2 ) 여러 Column에 DISTINCT 사용**

```sql
SELECT DISTINCT
    team_id,
    city
FROM athletes;
```

`DISTINCT`는 각각의 Column을 따로 중복 제거하는 것이 아니라 **SELECT한 전체 Column 조합**을 기준으로 중복 제거함.

예.

```text
team_id | city
----------------
10      | 서울
10      | 서울
20      | 부산
```

이라면.

[ Result ]

```text
10 | 서울
20 | 부산
```

<br>

> ## **3-3 ) DISTINCT의 핵심**

```text
SELECT
→ 모든 값 조회

SELECT DISTINCT
→ 중복 조합 제거
```

`NULL`이 여러 Row에 존재하더라도 `SELECT DISTINCT` 결과에서는 하나의 `NULL` 값으로 나타날 수 있음.

# **4. WHERE로 필요한 Row만 조회하기**

`WHERE`는 Table의 모든 Row 중 조건이 `TRUE`인 Row만 남기는 필터링 구문.

> ## **4-1 ) 특정 점수 이상의 기록 조회**

[ sql : code ] "점수가 90점 이상인 경기 기록 조회"

```sql
SELECT
    record_id,
    athlete_id,
    score
FROM performance_records
WHERE score >= 90
ORDER BY record_id;
```

조건을 하나씩 확인하면.

```text
88 → 제외
92 → 포함
75 → 제외
95 → 포함
82 → 제외
90 → 포함
```

[ Result ]

| record_id | athlete_id | score |
|---:|---:|---:|
| 102 | 1 | 92 |
| 104 | 3 | 95 |
| 106 | 2 | 90 |

<br>

> ## **4-2 ) WHERE 기본 구조**

```sql
SELECT 컬럼
FROM 테이블
WHERE 조건;
```

논리적 처리 흐름.

```text
FROM
↓
Table 선택
↓
WHERE
조건이 TRUE인 Row 선택
↓
SELECT
필요한 Column 출력
```

<br>

> ## **4-3 ) 주요 비교 연산자**

| 연산자 | 의미 |
|---|---|
| `=` | 같다 |
| `!=` 또는 `<>` | 같지 않다 |
| `>` | 초과 |
| `<` | 미만 |
| `>=` | 이상 |
| `<=` | 이하 |

SQL에서 같다는 의미는 Python의 `==`가 아니라 `=` 사용.

<br>

> ## **4-4 ) 여러 조건 AND**

다음 조건.

```text
훈련시간 60분 이상
그리고
훈련강도 8 이상
```

[ sql : code ] "훈련시간과 강도를 모두 만족하는 세션 조회"

```sql
SELECT
    session_id,
    athlete_id,
    duration_min,
    intensity
FROM training_sessions
WHERE duration_min >= 60
  AND intensity >= 8
ORDER BY session_id;
```

확인.

```text
201 → 60분 / 강도7 → 제외
203 → 80분 / 강도8 → 포함
204 → 70분 / 강도9 → 포함
206 → 90분 / 강도8 → 포함
```

[ Result ]

| session_id | athlete_id | duration_min | intensity |
|---:|---:|---:|---:|
| 203 | 2 | 80 | 8 |
| 204 | 2 | 70 | 9 |
| 206 | 4 | 90 | 8 |

<br>

> ## **4-5 ) OR 조건**

[ sql : code ] "육상 또는 수영 선수 조회"

```sql
SELECT
    athlete_id,
    athlete_name,
    sport
FROM athletes
WHERE sport = '육상'
   OR sport = '수영'
ORDER BY athlete_id;
```

[ Result ]

| athlete_id | athlete_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |

같은 조건은 `IN`으로 더 간단하게 표현 가능.

```sql
WHERE sport IN ('육상', '수영')
```

# **5. CASE WHEN으로 조건에 따라 값 만들기**

`CASE WHEN`은 기존 Row를 제거하는 것이 아니라 조건에 따라 **새로운 값을 만들어 반환**하는 조건식.

Python의 `if - elif - else`와 비슷한 역할.

> ## **5-1 ) 경기 점수 등급 만들기**

다음 기준 사용.

```text
90 이상 → 우수
80 이상 → 보통
그 외   → 개선필요
```

[ sql : code ] "경기 점수를 등급으로 분류"

```sql
SELECT
    record_id,
    score,
    CASE
        WHEN score >= 90 THEN '우수'
        WHEN score >= 80 THEN '보통'
        ELSE '개선필요'
    END AS score_grade
FROM performance_records
ORDER BY record_id;
```

[ Result ]

| record_id | score | score_grade |
|---:|---:|---|
| 101 | 88 | 보통 |
| 102 | 92 | 우수 |
| 103 | 75 | 개선필요 |
| 104 | 95 | 우수 |
| 105 | 82 | 보통 |
| 106 | 90 | 우수 |

<br>

> ## **5-2 ) CASE WHEN은 위에서부터 평가함**

예를 들어 `score = 95`.

```text
WHEN score >= 90
→ TRUE
→ '우수' 반환
→ 아래 WHEN은 더 이상 검사하지 않음
```

따라서 조건 순서가 중요함.

잘못된 예.

```sql
CASE
    WHEN score >= 80 THEN '보통'
    WHEN score >= 90 THEN '우수'
END
```

`95`도 첫 조건인 `>= 80`을 먼저 만족하므로 `"보통"`이 됨.

올바른 순서.

```sql
CASE
    WHEN score >= 90 THEN '우수'
    WHEN score >= 80 THEN '보통'
    ELSE '개선필요'
END
```

<br>

> ## **5-3 ) ELSE를 생략하면**

```sql
CASE
    WHEN active = TRUE THEN '활동중'
END
```

조건을 만족하지 않는 Row는 `NULL` 반환.

따라서 모든 경우를 명확하게 분류하려면 일반적으로 `ELSE`를 작성하는 것이 좋음.

<br>

> ## **5-4 ) WHERE와 CASE WHEN 차이**

| 구문 | 목적 |
|---|---|
| `WHERE` | Row를 제거 |
| `CASE WHEN` | Row를 유지하면서 새로운 값 생성 |

예.

```text
WHERE score >= 90
→ 90점 이상 Row만 남김

CASE WHEN score >= 90 ...
→ 모든 Row는 유지
→ 각 Row에 등급을 추가
```

# **6. 조건문에서 사용하는 주요 연산자**

> ## **6-1 ) BETWEEN**

`BETWEEN A AND B`는 **A 이상 B 이하**.

[ sql : code ] "80점 이상 90점 이하의 경기 기록 조회"

```sql
SELECT
    record_id,
    score
FROM performance_records
WHERE score BETWEEN 80 AND 90
ORDER BY record_id;
```

즉.

```sql
score >= 80
AND score <= 90
```

와 동일한 범위.

[ Result ]

| record_id | score |
|---:|---:|
| 101 | 88 |
| 105 | 82 |
| 106 | 90 |

경계값 `80`, `90`도 포함됨.

<br>

> ## **6-2 ) IN**

여러 값 중 하나와 정확하게 일치하는 데이터 조회.

```sql
SELECT
    athlete_name,
    sport
FROM athletes
WHERE sport IN ('육상', '수영', '야구')
ORDER BY athlete_id;
```

[ Result ]

| athlete_name | sport |
|---|---|
| 지민 | 육상 |
| 현우 | 수영 |
| 민재 | 야구 |

다음과 유사함.

```sql
WHERE sport = '육상'
   OR sport = '수영'
   OR sport = '야구'
```

<br>

> ## **6-3 ) NOT IN**

```sql
WHERE sport NOT IN ('육상', '수영')
```

목록에 포함되지 않은 값 선택.

단, 대상 값이나 목록에 `NULL`이 포함되는 경우 SQL의 NULL 논리 때문에 예상과 다른 결과가 발생할 수 있으므로 주의.

<br>

> ## **6-4 ) LIKE**

문자열 패턴 검색.

```text
% → 문자 0개 이상
_ → 문자 정확히 1개
```

예.

```sql
WHERE athlete_name LIKE '%민%'
```

이름에 `"민"`이 들어간 값 조회.

PostgreSQL에서 `LIKE`는 일반적으로 대소문자를 구분함.

대소문자를 구분하지 않는 검색이 필요하면 PostgreSQL의 `ILIKE` 사용 가능.

```sql
WHERE name ILIKE '%kim%'
```

<br>

> ## **6-5 ) IN과 LIKE 차이**

```sql
sport IN ('수영')
```

정확하게 `"수영"`인 값.

```sql
sport LIKE '%수영%'
```

문자열 중 `"수영"`이 포함된 값.

예.

| 값 | `IN ('수영')` | `LIKE '%수영%'` |
|---|---|---|
| 수영 | O | O |
| 자유형수영 | X | O |
| 수영선수 | X | O |

<br>

> ## **6-6 ) NULL 확인**

NULL은 일반적인 값이 아니므로 다음처럼 비교하면 안 됨.

```sql
team_id = NULL
```

올바른 방법.

```sql
team_id IS NULL
```

또는.

```sql
team_id IS NOT NULL
```

[ sql : code ] "팀이 지정되지 않은 선수 조회"

```sql
SELECT
    athlete_id,
    athlete_name,
    team_id
FROM athletes
WHERE team_id IS NULL;
```

[ Result ]

| athlete_id | athlete_name | team_id |
|---:|---|---|
| 5 | 수빈 | NULL |

<br>

> ## **6-7 ) NOT**

PostgreSQL에서는 논리 부정에 `NOT` 사용.

```sql
WHERE NOT active
```

또는.

```sql
WHERE active = FALSE
```

Python처럼 단독 `!`을 SQL의 일반적인 NOT 연산자로 사용하지 않음.

# **7. ORDER BY로 결과 정렬하기**

`ORDER BY`는 조회된 결과의 순서를 지정함.

> ## **7-1 ) 오름차순 ASC**

[ sql : code ] "경기 점수를 낮은 순서부터 정렬"

```sql
SELECT
    record_id,
    score
FROM performance_records
ORDER BY score ASC;
```

[ Result ]

| record_id | score |
|---:|---:|
| 103 | 75 |
| 105 | 82 |
| 101 | 88 |
| 106 | 90 |
| 102 | 92 |
| 104 | 95 |

`ASC`는 기본값이므로 생략 가능.

```sql
ORDER BY score;
```

<br>

> ## **7-2 ) 내림차순 DESC**

```sql
SELECT
    record_id,
    score
FROM performance_records
ORDER BY score DESC;
```

[ Result ]

| record_id | score |
|---:|---:|
| 104 | 95 |
| 102 | 92 |
| 106 | 90 |
| 101 | 88 |
| 105 | 82 |
| 103 | 75 |

<br>

> ## **7-3 ) 다중 정렬**

[ sql : code ] "팀을 먼저 정렬하고 같은 팀에서는 선수ID로 정렬"

```sql
SELECT
    athlete_id,
    athlete_name,
    team_id
FROM athletes
WHERE team_id IS NOT NULL
ORDER BY
    team_id ASC,
    athlete_id DESC;
```

[ Result ]

| athlete_id | athlete_name | team_id |
|---:|---|---:|
| 3 | 서연 | 10 |
| 1 | 지민 | 10 |
| 2 | 현우 | 20 |
| 4 | 민재 | 30 |

정렬 순서.

```text
1순위 → team_id ASC

team_id가 같은 경우
↓
2순위 → athlete_id DESC
```

<br>

> ## **7-4 ) Column 번호보다 Column 이름 권장**

다음 문법도 가능.

```sql
ORDER BY 1 DESC;
```

하지만 SELECT Column 위치가 변경되면 의미도 바뀌므로.

```sql
ORDER BY record_date DESC;
```

처럼 Column 이름을 직접 작성하는 것이 유지보수하기 쉬움.

# **8. SQL 집계함수**

집계함수(Aggregate Function)는 여러 Row를 계산하여 요약된 값을 반환함.

대표 함수.

| 함수 | 의미 |
|---|---|
| `COUNT()` | 개수 |
| `SUM()` | 합계 |
| `AVG()` | 평균 |
| `MIN()` | 최솟값 |
| `MAX()` | 최댓값 |

> ## **8-1 ) 경기 기록 전체 요약**

[ sql : code ] "경기 기록의 개수·평균·최소·최대 점수 계산"

```sql
SELECT
    COUNT(*) AS record_count,
    AVG(score) AS avg_score,
    MIN(score) AS min_score,
    MAX(score) AS max_score
FROM performance_records;
```

점수.

```text
88 + 92 + 75 + 95 + 82 + 90
= 522

522 / 6
= 87
```

[ Result ]

| record_count | avg_score | min_score | max_score |
|---:|---:|---:|---:|
| 6 | 87.0000 | 75 | 95 |

`AVG()`의 표시 소수 자릿수는 데이터 타입이나 SQL 도구 설정에 따라 다르게 보일 수 있지만 계산값은 `87`.

<br>

> ## **8-2 ) SUM**

[ sql : code ] "전체 훈련시간 계산"

```sql
SELECT
    SUM(duration_min) AS total_minutes
FROM training_sessions;
```

계산.

```text
60 + 45 + 80 + 70 + 50 + 90 + 30
= 425
```

[ Result ]

| total_minutes |
|---:|
| 425 |

<br>

> ## **8-3 ) COUNT(*)와 COUNT(Column)**

`COUNT(*)`

```text
NULL 포함
모든 Row 개수
```

`COUNT(column)`

```text
해당 Column이 NULL이 아닌 Row만 계산
```

예를 들어.

| athlete_id | team_id |
|---:|---:|
| 1 | 10 |
| 2 | 20 |
| 3 | 10 |
| 4 | 30 |
| 5 | NULL |

```sql
SELECT
    COUNT(*) AS athlete_count,
    COUNT(team_id) AS team_assigned_count
FROM athletes;
```

[ Result ]

| athlete_count | team_assigned_count |
|---:|---:|
| 5 | 4 |

<br>

> ## **8-4 ) NULL과 집계함수**

대부분의 일반 집계함수는 NULL을 계산에서 제외함.

```text
AVG(column)
SUM(column)
MIN(column)
MAX(column)
COUNT(column)

→ NULL 제외
```

`COUNT(*)`만 Row 자체를 세므로 NULL 여부와 무관.

# **9. GROUP BY로 기준별 집계하기**

집계함수만 사용하면 전체 데이터를 하나로 요약함.

`GROUP BY`를 사용하면 특정 기준으로 데이터를 나눈 뒤 각 그룹마다 집계 가능.

> ## **9-1 ) 선수별 경기 기록 수**

[ sql : code ] "선수별 경기 기록 개수 계산"

```sql
SELECT
    athlete_id,
    COUNT(*) AS record_count
FROM performance_records
GROUP BY athlete_id
ORDER BY athlete_id;
```

그룹 형성.

```text
athlete_id = 1
→ record 101, 102
→ 2개

athlete_id = 2
→ record 103, 106
→ 2개

athlete_id = 3
→ record 104
→ 1개

athlete_id = 4
→ record 105
→ 1개
```

[ Result ]

| athlete_id | record_count |
|---:|---:|
| 1 | 2 |
| 2 | 2 |
| 3 | 1 |
| 4 | 1 |

<br>

> ## **9-2 ) 선수별 평균 점수**

```sql
SELECT
    athlete_id,
    AVG(score) AS avg_score
FROM performance_records
GROUP BY athlete_id
ORDER BY athlete_id;
```

계산.

```text
선수 1
(88 + 92) / 2 = 90

선수 2
(75 + 90) / 2 = 82.5

선수 3
95

선수 4
82
```

[ Result ]

| athlete_id | avg_score |
|---:|---:|
| 1 | 90.0000 |
| 2 | 82.5000 |
| 3 | 95.0000 |
| 4 | 82.0000 |

<br>

> ## **9-3 ) 선수별 총 훈련시간**

[ sql : code ] "선수별 훈련시간 합계"

```sql
SELECT
    athlete_id,
    SUM(duration_min) AS total_minutes
FROM training_sessions
GROUP BY athlete_id
ORDER BY athlete_id;
```

계산.

```text
선수 1 → 60 + 45 = 105
선수 2 → 80 + 70 = 150
선수 3 → 50
선수 4 → 90 + 30 = 120
```

[ Result ]

| athlete_id | total_minutes |
|---:|---:|
| 1 | 105 |
| 2 | 150 |
| 3 | 50 |
| 4 | 120 |

<br>

> ## **9-4 ) SELECT와 GROUP BY 규칙**

일반적으로 SELECT에 집계함수가 아닌 Column이 있다면 해당 Column을 `GROUP BY` 기준에 포함해야 함.

잘못된 형태.

```sql
SELECT
    athlete_id,
    session_id,
    SUM(duration_min)
FROM training_sessions
GROUP BY athlete_id;
```

`athlete_id = 1` 그룹에는.

```text
session_id = 201
session_id = 202
```

두 값이 있으므로 SQL 입장에서는 어떤 `session_id`를 출력해야 하는지 결정할 수 없음.

따라서 그룹 기준이 아닌 Column을 무작정 SELECT할 수 없음.

# **10. WHERE와 HAVING의 차이**

`WHERE`와 `HAVING` 모두 데이터를 필터링하지만 적용되는 시점이 다름.

| 구문 | 시점 | 대상 |
|---|---|---|
| `WHERE` | GROUP BY 이전 | 개별 Row |
| `HAVING` | GROUP BY 이후 | 그룹·집계 결과 |

> ## **10-1 ) WHERE → GROUP BY → HAVING**

조건.

```text
훈련시간 40분 이상인 세션만 사용
↓
선수별로 그룹화
↓
총 훈련시간이 100분 이상인 선수만 조회
```

[ sql : code ] "개별 훈련을 WHERE로 필터링한 뒤 그룹 결과를 HAVING으로 필터링"

```sql
SELECT
    athlete_id,
    SUM(duration_min) AS total_minutes
FROM training_sessions
WHERE duration_min >= 40
GROUP BY athlete_id
HAVING SUM(duration_min) >= 100
ORDER BY athlete_id;
```

### 1단계 — WHERE

원본.

```text
201 → 60
202 → 45
203 → 80
204 → 70
205 → 50
206 → 90
207 → 30
```

`duration_min >= 40`

```text
207의 30분 제거
```

### 2단계 — GROUP BY

```text
선수 1 → 60 + 45 = 105
선수 2 → 80 + 70 = 150
선수 3 → 50
선수 4 → 90
```

### 3단계 — HAVING

```text
SUM >= 100

선수 1 → 포함
선수 2 → 포함
선수 3 → 제외
선수 4 → 제외
```

[ Result ]

| athlete_id | total_minutes |
|---:|---:|
| 1 | 105 |
| 2 | 150 |

<br>

> ## **10-2 ) WHERE에 집계함수를 사용할 수 없는 이유**

잘못된 예.

```sql
SELECT
    athlete_id,
    AVG(score)
FROM performance_records
WHERE AVG(score) >= 90
GROUP BY athlete_id;
```

논리적 실행 순서.

```text
FROM
↓
WHERE
↓
GROUP BY
↓
HAVING
↓
SELECT
↓
ORDER BY
```

`WHERE`가 실행되는 시점에는 아직 그룹도 만들어지지 않았으므로 `AVG(score)` 결과가 존재하지 않음.

올바른 코드.

```sql
SELECT
    athlete_id,
    AVG(score) AS avg_score
FROM performance_records
GROUP BY athlete_id
HAVING AVG(score) >= 90
ORDER BY athlete_id;
```

[ Result ]

| athlete_id | avg_score |
|---:|---:|
| 1 | 90.0000 |
| 3 | 95.0000 |

<br>

> ## **10-3 ) 실행 흐름**

```text
FROM
 ↓
원본 Table 선택
 ↓
WHERE
개별 Row 필터링
 ↓
GROUP BY
조건을 통과한 Row 그룹화
 ↓
HAVING
그룹·집계 결과 필터링
 ↓
SELECT
최종 Column 생성
 ↓
ORDER BY
결과 정렬
```

# **11. UNION으로 결과를 행 방향으로 결합하기**

`UNION`은 두 개 이상의 SELECT 결과를 **세로 방향으로 이어 붙임**.

```text
SELECT 결과 A
────────────
SELECT 결과 B
```

> ## **11-1 ) UNION**

서울 선수.

```text
1 지민
3 서연
5 수빈
```

활동 중인 선수.

```text
1 지민
2 현우
4 민재
5 수빈
```

[ sql : code ] "두 조건의 선수 목록을 합치고 중복 제거"

```sql
SELECT
    athlete_id,
    athlete_name
FROM athletes
WHERE city = '서울'

UNION

SELECT
    athlete_id,
    athlete_name
FROM athletes
WHERE active = TRUE

ORDER BY athlete_id;
```

`1 지민`, `5 수빈`은 양쪽 결과에 모두 있지만 `UNION`이 중복 제거.

[ Result ]

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |
| 3 | 서연 |
| 4 | 민재 |
| 5 | 수빈 |

<br>

> ## **11-2 ) UNION ALL**

`UNION ALL`은 중복 제거 없이 모든 Row를 유지.

```sql
SELECT
    athlete_id,
    athlete_name
FROM athletes
WHERE city = '서울'

UNION ALL

SELECT
    athlete_id,
    athlete_name
FROM athletes
WHERE active = TRUE

ORDER BY athlete_id;
```

[ Result ]

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 1 | 지민 |
| 2 | 현우 |
| 3 | 서연 |
| 4 | 민재 |
| 5 | 수빈 |
| 5 | 수빈 |

<br>

> ## **11-3 ) UNION과 UNION ALL 비교**

| 구문 | 중복 |
|---|---|
| `UNION` | 제거 |
| `UNION ALL` | 유지 |

중복 제거가 필요하지 않으면 일반적으로 `UNION ALL`이 불필요한 중복 제거 연산을 하지 않으므로 더 단순함.

<br>

> ## **11-4 ) UNION 사용 조건**

두 SELECT의.

```text
Column 개수
→ 같아야 함

대응하는 Column의 데이터 타입
→ 서로 호환 가능해야 함
```

가능.

```sql
SELECT athlete_id, athlete_name
FROM athletes

UNION

SELECT athlete_id, athlete_name
FROM retired_athletes;
```

불가능한 형태.

```text
첫 번째 SELECT → Column 2개
두 번째 SELECT → Column 3개
```

<br>

> ## **11-5 ) UNION 결과의 Column 이름**

```sql
SELECT athlete_id AS id,
       athlete_name AS name
FROM athletes

UNION

SELECT player_id,
       player_name
FROM retired_players;
```

최종 결과 Column 이름은 첫 번째 SELECT를 기준으로.

```text
id
name
```

이 됨.

# **12. JOIN으로 Table을 열 방향으로 결합하기**

`JOIN`은 서로 관련 있는 Table의 정보를 **가로 방향으로 연결**함.

예.

```text
athletes

athlete_id | athlete_name
1          | 지민

+

performance_records

athlete_id | score
1          | 88
1          | 92

↓

JOIN

athlete_name | score
지민         | 88
지민         | 92
```

> ## **12-1 ) 기본 JOIN**

[ sql : code ] "선수 이름과 경기 기록을 함께 조회"

```sql
SELECT
    p.record_id,
    a.athlete_name,
    p.score
FROM performance_records AS p
JOIN athletes AS a
    ON p.athlete_id = a.athlete_id
ORDER BY p.record_id;
```

[ Result ]

| record_id | athlete_name | score |
|---:|---|---:|
| 101 | 지민 | 88 |
| 102 | 지민 | 92 |
| 103 | 현우 | 75 |
| 104 | 서연 | 95 |
| 105 | 민재 | 82 |
| 106 | 현우 | 90 |

`JOIN`만 작성하면 기본적으로 `INNER JOIN`.

<br>

> ## **12-2 ) ON 절**

```sql
ON p.athlete_id = a.athlete_id
```

두 Table의 어떤 Row를 서로 연결할지 지정함.

일반적으로.

```text
Parent Table PK
=
Child Table FK
```

형태.

```text
athletes.athlete_id
       PK
        ↓
performance_records.athlete_id
       FK
```

<br>

> ## **12-3 ) Table Alias**

긴 Table 이름을 반복하지 않기 위해 별칭 사용.

```sql
FROM performance_records AS p
JOIN athletes AS a
```

`AS` 생략 가능.

```sql
FROM performance_records p
JOIN athletes a
```

이후.

```sql
p.score
a.athlete_name
```

처럼 사용.

특히 여러 Table에 동일한 Column 이름이 있을 때 별칭을 붙이면 어느 Table의 Column인지 명확하게 구분 가능.

# **13. INNER JOIN**

`INNER JOIN`은 양쪽 Table에서 JOIN 조건이 일치하는 Row만 반환.

> ## **13-1 ) 선수와 경기 기록 INNER JOIN**

현재 `수빈(athlete_id = 5)`은 경기 기록이 없음.

```sql
SELECT
    a.athlete_id,
    a.athlete_name,
    p.record_id,
    p.score
FROM athletes AS a
INNER JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
ORDER BY
    a.athlete_id,
    p.record_id;
```

[ Result ]

| athlete_id | athlete_name | record_id | score |
|---:|---|---:|---:|
| 1 | 지민 | 101 | 88 |
| 1 | 지민 | 102 | 92 |
| 2 | 현우 | 103 | 75 |
| 2 | 현우 | 106 | 90 |
| 3 | 서연 | 104 | 95 |
| 4 | 민재 | 105 | 82 |

수빈은 `performance_records`에 일치하는 Row가 없으므로 결과에서 제외됨.

```text
INNER JOIN
=
양쪽 모두 존재하는 데이터만
=
교집합
```

# **14. LEFT JOIN**

`LEFT JOIN`은 왼쪽 Table의 모든 Row를 유지하고 오른쪽 Table의 일치하는 데이터를 연결함.

오른쪽에 대응하는 데이터가 없으면 `NULL`.

> ## **14-1 ) 경기 기록이 없는 선수까지 조회**

```sql
SELECT
    a.athlete_id,
    a.athlete_name,
    p.record_id,
    p.score
FROM athletes AS a
LEFT JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
ORDER BY
    a.athlete_id,
    p.record_id;
```

[ Result ]

| athlete_id | athlete_name | record_id | score |
|---:|---|---:|---:|
| 1 | 지민 | 101 | 88 |
| 1 | 지민 | 102 | 92 |
| 2 | 현우 | 103 | 75 |
| 2 | 현우 | 106 | 90 |
| 3 | 서연 | 104 | 95 |
| 4 | 민재 | 105 | 82 |
| 5 | 수빈 | NULL | NULL |

수빈은 기록이 없지만 왼쪽 `athletes` Table의 Row이므로 결과에 유지됨.

```text
LEFT JOIN

왼쪽
→ 반드시 유지

오른쪽
→ 일치하면 연결
→ 없으면 NULL
```

<br>

> ## **14-2 ) 기록이 없는 선수 찾기**

LEFT JOIN과 NULL 조건을 함께 활용하면 연결 데이터가 없는 Row를 찾을 수 있음.

```sql
SELECT
    a.athlete_id,
    a.athlete_name
FROM athletes AS a
LEFT JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
WHERE p.record_id IS NULL;
```

[ Result ]

| athlete_id | athlete_name |
|---:|---|
| 5 | 수빈 |

# **15. RIGHT JOIN**

`RIGHT JOIN`은 오른쪽 Table의 모든 Row를 유지함.

```text
LEFT JOIN
← 왼쪽 전체 유지

RIGHT JOIN
→ 오른쪽 전체 유지
```

예.

```sql
SELECT
    a.athlete_name,
    t.team_id,
    t.team_name
FROM athletes AS a
RIGHT JOIN teams AS t
    ON a.team_id = t.team_id;
```

하지만 실무에서는 Table의 위치를 바꾸어 `LEFT JOIN`으로 작성하는 경우가 많음.

```sql
SELECT
    a.athlete_name,
    t.team_id,
    t.team_name
FROM teams AS t
LEFT JOIN athletes AS a
    ON t.team_id = a.team_id;
```

두 SQL은 같은 방향의 데이터를 표현할 수 있음.

초보 단계에서는 `LEFT JOIN`을 기준으로 사고하는 것이 비교적 직관적.

# **16. FULL OUTER JOIN**

`FULL OUTER JOIN`은 양쪽 Table의 모든 Row를 결과에 포함.

```text
A에만 존재
→ 포함

B에만 존재
→ 포함

A와 B 모두 존재
→ 연결하여 포함
```

일치하는 상대방이 없는 부분에는 `NULL`.

PostgreSQL에서는.

```sql
FULL OUTER JOIN
```

또는.

```sql
FULL JOIN
```

사용 가능.

<br>

> ## **16-1 ) JOIN 종류 비교**

| JOIN | 남기는 데이터 |
|---|---|
| `INNER JOIN` | 양쪽에 모두 존재 |
| `LEFT JOIN` | 왼쪽 전체 |
| `RIGHT JOIN` | 오른쪽 전체 |
| `FULL OUTER JOIN` | 양쪽 전체 |

개념도.

```text
INNER
A ∩ B

LEFT
A 전체 + A와 연결되는 B

RIGHT
B 전체 + B와 연결되는 A

FULL
A ∪ B
```

# **17. JOIN에서 Row 수가 증가하는 이유**

JOIN을 하면 단순히 Column만 늘어나는 것이 아니라 관계에 따라 Row 수도 증가할 수 있음.

> ## **17-1 ) 1:N JOIN**

지민 선수.

```text
athletes
1 | 지민
```

경기 기록.

```text
101 | athlete_id 1 | 88
102 | athlete_id 1 | 92
```

JOIN.

```text
지민 | 101 | 88
지민 | 102 | 92
```

즉.

```text
선수 1명
×
경기기록 2개

→ JOIN 결과 2 Row
```

따라서 JOIN 전에 반드시 Table 관계가.

```text
1:1
1:N
N:M
```

중 무엇인지 확인하는 것이 중요함.

분석 결과의 Row 수가 예상보다 크게 증가했다면 JOIN Key의 중복 여부를 먼저 확인하는 것이 좋음.

# **18. 여러 Table JOIN하기**

실제 분석에서는 두 개보다 많은 Table을 연결하는 경우가 많음.

> ## **18-1 ) 선수 이름 + 팀 이름 + 경기 기록 조회**

필요한 데이터.

```text
선수 이름
→ athletes

팀 이름
→ teams

경기 점수
→ performance_records
```

연결 관계.

```text
teams.team_id
     ↓
athletes.team_id

athletes.athlete_id
     ↓
performance_records.athlete_id
```

[ sql : code ] "세 Table을 JOIN하여 선수·팀·경기 기록 조회"

```sql
SELECT
    a.athlete_name,
    t.team_name,
    p.record_id,
    p.score
FROM athletes AS a
JOIN teams AS t
    ON a.team_id = t.team_id
JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
ORDER BY p.record_id;
```

[ Result ]

| athlete_name | team_name | record_id | score |
|---|---|---:|---:|
| 지민 | Falcons | 101 | 88 |
| 지민 | Falcons | 102 | 92 |
| 현우 | Waves | 103 | 75 |
| 서연 | Falcons | 104 | 95 |
| 민재 | Tigers | 105 | 82 |
| 현우 | Waves | 106 | 90 |

수빈은 `team_id = NULL`이고 경기 기록도 없으므로 INNER JOIN 결과에 포함되지 않음.

<br>

> ## **18-2 ) 다중 JOIN 사고 흐름**

```text
필요한 결과 Column 확인
        ↓
각 Column이 어느 Table에 있는지 확인
        ↓
Table 사이 PK/FK 확인
        ↓
JOIN 경로 결정
        ↓
JOIN 조건 작성
        ↓
1:N 관계에 따른 Row 증가 확인
```

ERD를 사용하는 목적도 이 JOIN 경로를 찾기 위함.

# **19. JOIN과 GROUP BY 함께 사용하기**

JOIN으로 데이터를 연결한 뒤 GROUP BY로 집계하는 형태는 실무 분석에서 매우 자주 사용됨.

> ## **19-1 ) 선수 이름별 평균 경기 점수**

```sql
SELECT
    a.athlete_id,
    a.athlete_name,
    AVG(p.score) AS avg_score
FROM athletes AS a
JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
GROUP BY
    a.athlete_id,
    a.athlete_name
ORDER BY a.athlete_id;
```

[ Result ]

| athlete_id | athlete_name | avg_score |
|---:|---|---:|
| 1 | 지민 | 90.0000 |
| 2 | 현우 | 82.5000 |
| 3 | 서연 | 95.0000 |
| 4 | 민재 | 82.0000 |

<br>

> ## **19-2 ) 평균 점수가 90 이상인 선수**

```sql
SELECT
    a.athlete_id,
    a.athlete_name,
    AVG(p.score) AS avg_score
FROM athletes AS a
JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
GROUP BY
    a.athlete_id,
    a.athlete_name
HAVING AVG(p.score) >= 90
ORDER BY a.athlete_id;
```

[ Result ]

| athlete_id | athlete_name | avg_score |
|---:|---|---:|
| 1 | 지민 | 90.0000 |
| 3 | 서연 | 95.0000 |

실행 흐름.

```text
athletes
     +
performance_records
        ↓
       JOIN
        ↓
선수 이름과 경기 점수 연결
        ↓
    GROUP BY
        ↓
선수별 그룹 생성
        ↓
     AVG()
        ↓
선수별 평균 계산
        ↓
     HAVING
        ↓
평균 90 이상만 남김
```

# **20. UNION과 JOIN 비교**

둘 다 데이터를 결합하지만 목적과 방향이 완전히 다름.

> ## **20-1 ) UNION**

같은 구조의 결과를 **아래로 쌓음**.

```text
육상 선수
────────
지민

+

수영 선수
────────
현우

↓

지민
현우
```

Column 수는 그대로이고 Row가 증가하는 형태.

<br>

> ## **20-2 ) JOIN**

관련 정보를 **옆으로 붙임**.

```text
선수

1 | 지민

+

기록

1 | 88

↓

1 | 지민 | 88
```

Column이 증가하는 형태.

<br>

> ## **20-3 ) 비교표**

| 구분 | UNION | JOIN |
|---|---|---|
| 방향 | 세로 | 가로 |
| 증가 | Row | 주로 Column, 관계에 따라 Row도 증가 |
| 목적 | 같은 구조의 데이터 합치기 | 관련 정보 연결 |
| 기준 | Column 개수·호환 타입 | JOIN 조건 |
| 중복 | `UNION`은 제거 | 자동 제거하지 않음 |
| 대표 사용 | 여러 기간 데이터 통합 | 선수 + 기록 |

쉽게 기억하면.

```text
UNION
→ 쌓는다

JOIN
→ 붙인다
```

# **21. SQL 전체 작성 순서와 실행 순서**

조회·집계 SQL을 작성하는 대표 순서.

```sql
SELECT
FROM
JOIN
WHERE
GROUP BY
HAVING
ORDER BY
```

하지만 논리적 실행 순서는 다름.

```text
FROM / JOIN
      ↓
WHERE
      ↓
GROUP BY
      ↓
HAVING
      ↓
SELECT
      ↓
DISTINCT
      ↓
ORDER BY
```

> ## **21-1 ) 종합 예제**

조건.

```text
1. 선수와 경기 기록 연결
2. 80점 이상 기록만 사용
3. 선수별 평균 계산
4. 평균 85 이상 선수만 남김
5. 평균 점수가 높은 순서로 정렬
```

[ sql : code ] "JOIN부터 HAVING까지 연결한 종합 분석"

```sql
SELECT
    a.athlete_id,
    a.athlete_name,
    AVG(p.score) AS avg_score
FROM athletes AS a
JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
WHERE p.score >= 80
GROUP BY
    a.athlete_id,
    a.athlete_name
HAVING AVG(p.score) >= 85
ORDER BY avg_score DESC;
```

### 1. JOIN

```text
지민 → 88, 92
현우 → 75, 90
서연 → 95
민재 → 82
```

### 2. WHERE `score >= 80`

```text
지민 → 88, 92
현우 → 90
서연 → 95
민재 → 82
```

`75` 제거.

### 3. GROUP BY + AVG

```text
지민 → 90
현우 → 90
서연 → 95
민재 → 82
```

### 4. HAVING `AVG >= 85`

```text
서연 → 95
지민 → 90
현우 → 90
```

민재 제외.

### 5. ORDER BY

[ Result ]

| athlete_id | athlete_name | avg_score |
|---:|---|---:|
| 3 | 서연 | 95.0000 |
| 1 | 지민 | 90.0000 |
| 2 | 현우 | 90.0000 |

`지민`과 `현우`의 평균이 동일하므로 둘 사이의 순서를 완전히 고정하려면 보조 정렬 기준을 추가해야 함.

```sql
ORDER BY
    avg_score DESC,
    a.athlete_id ASC;
```

이렇게 작성하면 위 Result 순서가 명확하게 보장됨.

# **23. Advanced 추가 학습**

> ## **23-1 ) COUNT(DISTINCT)**

고유한 선수 수를 바로 계산할 수 있음.

```sql
SELECT
    COUNT(DISTINCT athlete_id) AS athlete_count
FROM performance_records;
```

현재 기록이 있는 선수.

```text
1
2
3
4
```

[ Result ]

```text
4
```

<br>

> ## **23-2 ) LEFT JOIN 뒤 WHERE 조건 주의**

다음 SQL.

```sql
SELECT
    a.athlete_name,
    p.score
FROM athletes AS a
LEFT JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
WHERE p.score >= 90;
```

기록이 없는 수빈은.

```text
p.score = NULL
```

이므로 `WHERE p.score >= 90`을 통과하지 못함.

결과적으로 오른쪽 Table과 일치하지 않는 Row가 제거되어 LEFT JOIN의 장점이 사라질 수 있음.

조건을 JOIN 자체에 적용하고 왼쪽 Row를 유지하고 싶다면.

```sql
SELECT
    a.athlete_name,
    p.score
FROM athletes AS a
LEFT JOIN performance_records AS p
    ON a.athlete_id = p.athlete_id
   AND p.score >= 90;
```

처럼 `ON`에 조건을 배치하는 방법도 있음.

두 SQL은 의미가 다르므로 분석 목적에 맞게 선택해야 함.

<br>

> ## **23-3 ) 날짜 검색은 데이터 타입을 확인**

`DATE` Column에서 2026년 9월 데이터를 조회한다면.

```sql
WHERE record_date BETWEEN '2026-09-01'
                      AND '2026-09-30'
```

사용 가능.

하지만 `TIMESTAMP`처럼 시간까지 저장된 Column은 다음과 같은 반개방 구간이 더 안전한 경우가 많음.

```sql
WHERE created_at >= '2026-09-01'
  AND created_at <  '2026-10-01'
```

예를 들어.

```text
2026-09-30 23:59:59
```

도 자연스럽게 포함됨.

<br>

> ## **23-4 ) 결과 순서를 보장하려면 ORDER BY**

SQL Table에는 본질적인 출력 순서가 없음.

다음 SQL 결과가 현재 우연히 ID 순서대로 보이더라도.

```sql
SELECT *
FROM athletes;
```

그 순서가 항상 보장되는 것은 아님.

순서가 중요하다면 반드시.

```sql
ORDER BY athlete_id;
```

를 명시하는 것이 안전함.

<br>

> ## **23-5 ) INNER JOIN과 JOIN**

다음 두 문법은 동일한 의미.

```sql
INNER JOIN athletes AS a
```

```sql
JOIN athletes AS a
```

즉, JOIN 종류를 생략한 일반 `JOIN`은 `INNER JOIN`.

<br>

> ## **23-6 ) GROUP BY 후 HAVING 없이도 가능한 경우**

`HAVING`은 반드시 사용해야 하는 구문이 아님.

```sql
SELECT
    athlete_id,
    AVG(score)
FROM performance_records
GROUP BY athlete_id;
```

처럼 모든 그룹을 보고 싶다면 `HAVING` 생략.

특정 그룹만 보고 싶을 때.

```sql
HAVING AVG(score) >= 90
```

추가.

# **24. 핵심정리**

- `SELECT`는 결과에 보여줄 Column을 지정함.
- `FROM`은 데이터를 가져올 Table을 지정함.
- `SELECT *`는 모든 Column을 조회하지만 실무에서는 필요한 Column만 명시하는 것이 권장됨.
- `DISTINCT`는 SELECT 결과의 중복 Row 또는 Column 조합을 제거함.
- SQL 결과의 Row 순서는 `ORDER BY`가 없으면 보장되지 않음.
- `WHERE`는 조건을 만족하는 개별 Row만 남김.
- SQL의 같은 값 비교는 `=`, 다른 값 비교는 `!=` 또는 `<>` 사용.
- `AND`는 모든 조건을 만족해야 하고 `OR`는 하나 이상 만족하면 됨.
- `CASE WHEN`은 Row를 제거하지 않고 조건에 따라 새로운 값을 생성함.
- 여러 `WHEN`이 있다면 위에서부터 검사하여 처음으로 TRUE가 된 결과를 반환함.
- `ELSE`를 생략하고 모든 WHEN 조건이 FALSE이면 NULL이 반환됨.
- `BETWEEN A AND B`는 A와 B를 모두 포함하는 범위임.
- `IN`은 여러 값 중 정확히 일치하는 값을 찾을 때 사용함.
- `LIKE`는 문자열 패턴 검색에 사용하며 `%`는 문자 0개 이상을 의미함.
- PostgreSQL에서 대소문자를 구분하지 않는 패턴 검색에는 `ILIKE`를 사용할 수 있음.
- NULL 여부는 `= NULL`이 아니라 `IS NULL`, `IS NOT NULL`로 검사함.
- SQL의 논리 부정에는 `NOT`을 사용함.
- `ORDER BY ... ASC`는 오름차순이며 ASC는 기본값이라 생략 가능함.
- `ORDER BY ... DESC`는 내림차순임.
- 여러 정렬 조건에서는 앞에 작성한 Column이 우선순위가 높음.
- `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`는 대표적인 집계함수임.
- `COUNT(*)`는 전체 Row를 세고 `COUNT(column)`은 해당 Column이 NULL이 아닌 Row만 계산함.
- `SUM`, `AVG`, `MIN`, `MAX`도 일반적으로 NULL을 계산에서 제외함.
- `GROUP BY`는 동일한 값을 가진 Row를 그룹으로 묶어 그룹별 집계를 가능하게 함.
- 일반적으로 SELECT의 비집계 Column은 GROUP BY에도 포함해야 함.
- `WHERE`는 그룹화 전 개별 Row를 필터링함.
- `HAVING`은 GROUP BY 이후 생성된 그룹과 집계 결과를 필터링함.
- 집계함수 결과에 조건을 적용하려면 일반적으로 `HAVING`을 사용함.
- 대표적인 논리적 실행 흐름은 `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY`로 이해할 수 있음.
- `UNION`은 여러 SELECT 결과를 행 방향으로 결합함.
- `UNION`은 중복 Row를 제거하고 `UNION ALL`은 중복을 유지함.
- UNION되는 각 SELECT는 Column 수가 같고 대응 Column의 타입이 서로 호환되어야 함.
- UNION 결과의 Column 이름은 첫 번째 SELECT를 기준으로 결정됨.
- `JOIN`은 관련된 여러 Table의 정보를 열 방향으로 연결함.
- JOIN의 `ON`에는 두 Table을 어떤 기준으로 연결할지 작성함.
- 일반적으로 PK와 이를 참조하는 FK를 연결함.
- `JOIN`만 작성하면 기본적으로 `INNER JOIN`을 의미함.
- `INNER JOIN`은 양쪽에 일치하는 Row만 반환함.
- `LEFT JOIN`은 왼쪽 Table의 모든 Row를 유지하고 대응하는 오른쪽 데이터가 없으면 NULL을 반환함.
- `RIGHT JOIN`은 오른쪽 Table의 모든 Row를 유지함.
- `FULL OUTER JOIN`은 양쪽 Table의 모든 Row를 유지함.
- 실무에서는 RIGHT JOIN보다 Table 순서를 바꾸어 LEFT JOIN으로 표현하는 경우가 많음.
- LEFT JOIN 후 오른쪽 Table의 Column을 WHERE에서 필터링하면 일치하지 않는 NULL Row가 제거될 수 있으므로 주의해야 함.
- 1:N 관계를 JOIN하면 1쪽의 한 Row가 N쪽 Row 수만큼 반복될 수 있으므로 JOIN 전 관계와 Key의 중복 여부를 확인해야 함.
- 여러 Table을 JOIN할 때는 `필요한 데이터 → 해당 Table → PK/FK → JOIN 경로` 순서로 생각하면 됨.
- `JOIN + GROUP BY + HAVING` 조합은 실무 데이터 분석에서 매우 자주 사용됨.
- UNION과 JOIN을 구분할 때는 **같은 구조의 데이터를 아래로 쌓는가, 서로 다른 정보를 옆으로 붙이는가**를 기준으로 판단하면 쉬움.
- `UNION = 쌓기`, `JOIN = 붙이기`로 기억하면 됨.
