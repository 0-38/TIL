# **1. 데이터 사이언티스트와 SQL**

데이터 사이언티스트(Data Scientist)는 데이터를 수집·정제·분석하고 통계, 머신러닝, AI 모델을 활용하여 실제 문제 해결에 필요한 인사이트를 도출하는 역할을 수행함.

실무에서는 데이터가 대부분 데이터베이스(Database)에 저장되어 있으므로 모델링을 시작하기 전에 **필요한 데이터를 직접 조회하고 가공하는 능력**이 필요함.

이때 가장 많이 사용하는 언어 중 하나가 `SQL(Structured Query Language)`임.

> ## **1-1 ) 데이터 사이언티스트가 SQL을 사용하는 이유**

데이터 사이언스 업무의 일반적인 흐름은 다음과 같음.

```text
비즈니스 문제 정의
        ↓
필요한 데이터 정의
        ↓
SQL로 데이터 조회
        ↓
데이터 전처리 및 EDA
        ↓
통계 분석 / 머신러닝
        ↓
모델 평가
        ↓
인사이트 도출
        ↓
서비스·비즈니스 적용
```

SQL은 특히 다음 단계에서 중요하게 사용됨.

| 업무 | 주요 역할 | 주로 사용하는 도구 |
|---|---|---|
| 데이터 추출 | DB에서 필요한 데이터 조회 | SQL |
| 데이터 전처리 | 필터링·집계·결합 | SQL, Python |
| 탐색적 분석 | 분포와 패턴 확인 | Python, SQL |
| 모델링 | 예측·분류 모델 구축 | Python |
| 모델 평가 | 성능 지표 계산 | Python |
| 결과 전달 | 리포트·대시보드·발표 | Python, BI 도구 |

<br>

> ## **1-2 ) 스포츠 데이터 분석에서 SQL 활용 예시**

선수별 경기 기록이 데이터베이스에 저장되어 있다고 가정함.

분석 전에 최근 경기에서 20점 이상 기록한 농구 선수만 조회할 수 있음.

[ sql : code ] "20점 이상 기록한 농구 선수 조회"

```sql
SELECT
    player_name,
    points
FROM basketball_stats
WHERE points >= 20
ORDER BY points DESC;
```

[ Result ]

| player_name | points |
|---|---:|
| 서준 | 31 |
| 지후 | 27 |
| 민재 | 22 |

SQL을 이용하면 전체 데이터 중 분석에 필요한 데이터만 데이터베이스 단계에서 먼저 추출 가능.

# **2. 데이터(Data), 데이터베이스(DB), 쿼리(Query), SQL**

SQL을 이해하려면 먼저 `Data`, `Database`, `Query`, `SQL`의 관계를 구분해야 함.

> ## **2-1 ) Data란 무엇인가**

데이터(Data)는 사실이나 현상을 표현하는 개별 값.

스포츠 데이터에서는 다음과 같은 값들이 모두 데이터에 해당함.

```text
선수명      → "지민"
종목        → "육상"
100m 기록   → 11.24
측정일      → 2026-09-01
부상 여부   → false
```

<br>

> ## **2-2 ) Database란 무엇인가**

데이터베이스(Database)는 데이터를 **체계적으로 저장하고 관리하는 데이터의 집합**.

예를 들어 선수 정보를 다음과 같이 저장할 수 있음.

| athlete_id | athlete_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |
| 3 | 서연 | 농구 |

<br>

> ## **2-3 ) Query와 SQL**

Query는 데이터베이스에 전달하는 **질문 또는 명령**.

예를 들어 자연어로 다음과 같은 질문을 할 수 있음.

```text
"육상 선수만 보여줘."
```

이를 SQL로 표현하면 다음과 같음.

[ sql : code ] "육상 종목 선수 조회"

```sql
SELECT
    athlete_id,
    athlete_name
FROM athletes
WHERE sport = '육상';
```

[ Result ]

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |

<br>

> ## **2-4 ) Data, DB, Query, SQL 비교**

| 개념 | 의미 | 예 |
|---|---|---|
| Data | 개별 사실이나 값 | `11.24`, `"지민"` |
| Database | 데이터를 구조적으로 저장하는 공간 | 선수 데이터베이스 |
| Query | DB에 전달하는 질문·명령 | 육상 선수 조회 |
| SQL | Query를 표현하는 언어 | `SELECT ...` |

# **3. DBMS(Database Management System)**

DBMS는 데이터베이스를 생성·관리하고 사용자의 SQL 요청을 처리하는 소프트웨어.

SQL 자체가 데이터베이스 프로그램인 것은 아님.

```text
사용자
  ↓
SQL 작성
  ↓
DBMS
  ↓
Database
  ↓
결과 반환
```

> ## **3-1 ) SQL과 DBMS의 차이**

| 구분 | SQL | DBMS |
|---|---|---|
| 의미 | 데이터베이스 명령 언어 | 데이터베이스 관리 소프트웨어 |
| 역할 | 무엇을 원하는지 표현 | SQL을 해석하고 실제 작업 수행 |
| 예 | `SELECT`, `INSERT` | PostgreSQL, MySQL |
| 비유 | 주문서 | 주문을 처리하는 시스템 |

<br>

> ## **3-2 ) 대표적인 관계형 DBMS**

| DBMS | 특징 | 활용 예 |
|---|---|---|
| PostgreSQL | 오픈소스, 확장성이 높고 다양한 SQL 기능 지원 | 분석 시스템, 웹 서비스 |
| MySQL | 오픈소스, 웹 서비스에서 널리 사용 | 웹 서비스 |
| Oracle Database | 상용 엔터프라이즈 DBMS | 금융·대규모 기업 시스템 |
| SQL Server | Microsoft의 관계형 DBMS | 기업 데이터 시스템 |
| SQLite | 별도 서버가 필요 없는 파일 기반 DB | 모바일·임베디드 |
| MariaDB | MySQL 계열에서 파생된 오픈소스 DBMS | 웹 서비스 |

이번 학습에서는 `PostgreSQL`을 기준으로 SQL을 사용함.

DBMS마다 세부 함수와 데이터 타입에는 차이가 있을 수 있지만 `SELECT`, `WHERE`, `JOIN`, `GROUP BY` 같은 핵심 SQL 개념은 상당 부분 공통됨.

# **4. 관계형 데이터베이스(RDBMS)**

관계형 데이터베이스는 데이터를 **행(Row)과 열(Column)로 구성된 테이블(Table)** 형태로 관리함.

관련된 데이터를 여러 테이블에 나누어 저장하고 서로 연결하여 사용 가능.

> ## **4-1 ) 선수와 훈련 기록을 별도 테이블로 관리**

선수 테이블.

| athlete_id | athlete_name | sport |
|---:|---|---|
| 1 | 지민 | 육상 |
| 2 | 현우 | 수영 |
| 3 | 서연 | 농구 |

훈련 기록 테이블.

| session_id | athlete_id | duration_min |
|---:|---:|---:|
| 101 | 1 | 60 |
| 102 | 1 | 45 |
| 103 | 2 | 50 |
| 104 | 3 | 90 |

두 테이블에서 공통으로 사용되는 `athlete_id`를 이용하면 선수와 훈련 데이터를 연결 가능.

[ sql : code ] "선수 정보와 훈련 기록을 JOIN하는 방법"

```sql
SELECT
    a.athlete_name,
    a.sport,
    t.duration_min
FROM athletes AS a
JOIN training_sessions AS t
    ON a.athlete_id = t.athlete_id
ORDER BY t.session_id;
```

[ Result ]

| athlete_name | sport | duration_min |
|---|---|---:|
| 지민 | 육상 | 60 |
| 지민 | 육상 | 45 |
| 현우 | 수영 | 50 |
| 서연 | 농구 | 90 |

<br>

> ## **4-2 ) 주요 데이터 저장 모델**

| 모델 | 구조 | 특징 |
|---|---|---|
| 계층형 | 트리 구조 | 부모-자식 관계 중심 |
| 관계형 | 테이블 구조 | 테이블 간 관계를 이용 |
| 네트워크형 | 그래프와 유사한 연결 구조 | 복잡한 다대다 관계 표현 가능 |

관계형 모델은 현재 기업의 업무 시스템에서 매우 널리 사용되는 데이터 모델 중 하나임.

현대 데이터베이스에는 이 외에도 Document, Key-Value, Graph 등의 다양한 모델도 존재함.

# **5. 관계형 데이터베이스의 테이블 구조**

관계형 데이터베이스에서 데이터를 이해하기 위해 가장 먼저 알아야 하는 개념은 `Table`, `Row`, `Column`, `Value`임.

> ## **5-1 ) 선수 테이블 예시**

| athlete_id | athlete_name | sport | height_cm |
|---:|---|---|---:|
| 1 | 지민 | 육상 | 172.5 |
| 2 | 현우 | 수영 | 181.2 |
| 3 | 서연 | 농구 | 177.8 |

각 구성 요소는 다음과 같음.

| 용어 | 의미 | 예 |
|---|---|---|
| Table | 관련 데이터의 집합 | `athletes` |
| Row | 한 개체에 대한 하나의 기록 | 지민 선수의 전체 정보 |
| Column | 데이터의 속성 | `sport` |
| Value | 특정 행과 열에 저장된 값 | `"육상"` |

`Cell`이라는 표현도 표 형태를 설명할 때 사용할 수 있지만 SQL에서는 일반적으로 특정 Column의 `값(Value)`이라고 표현하는 경우가 많음.

<br>

> ## **5-2 ) 특정 Column만 조회하기**

[ sql : code ] "선수명과 종목 Column만 선택하여 조회"

```sql
SELECT
    athlete_name,
    sport
FROM athletes
ORDER BY athlete_id;
```

[ Result ]

| athlete_name | sport |
|---|---|
| 지민 | 육상 |

# **6. SQL의 작성 순서와 논리적 처리 순서**

SQL은 작성하는 순서와 논리적으로 데이터를 처리하는 순서가 다름.

> ## **6-1 ) SQL 작성 순서**

일반적인 작성 순서.

```text
SELECT
    ↓
FROM
    ↓
WHERE
    ↓
GROUP BY
    ↓
HAVING
    ↓
ORDER BY
```

<br>

> ## **6-2 ) SQL의 논리적 처리 순서**

초보 단계에서 다음 순서로 이해하면 됨.

```text
FROM
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
```

실제 SQL 처리 과정은 JOIN, DISTINCT, LIMIT 등의 요소까지 포함하면 더 복잡하지만 기본 집계 Query를 이해하기에는 위 순서가 중요함.

<br>

> ## **6-3 ) 종목별 완료 훈련시간 집계**

다음 데이터가 있다고 가정.

| sport | duration_min | status |
|---|---:|---|
| 육상 | 60 | 완료 |
| 육상 | 55 | 완료 |
| 수영 | 70 | 완료 |
| 수영 | 40 | 완료 |
| 농구 | 90 | 완료 |
| 농구 | 30 | 예정 |

[ sql : code ] "완료된 훈련만 이용하여 종목별 총 훈련시간 집계"

```sql
SELECT
    sport,
    SUM(duration_min) AS total_minutes
FROM training_log
WHERE status = '완료'
GROUP BY sport
HAVING SUM(duration_min) >= 100
ORDER BY total_minutes DESC;
```

[ Result ]

| sport | total_minutes |
|---|---:|
| 육상 | 115 |
| 수영 | 110 |

실행 흐름.

```text
FROM training_log
        ↓
training_log 데이터 확인
        ↓
WHERE status = '완료'
        ↓
예정된 농구 30분 제외
        ↓
GROUP BY sport
        ↓
육상 / 수영 / 농구 그룹 생성
        ↓
SUM(duration_min)
        ↓
육상 = 115
수영 = 110
농구 = 90
        ↓
HAVING SUM(duration_min) >= 100
        ↓
농구 제외
        ↓
SELECT
        ↓
sport, total_minutes 생성
        ↓
ORDER BY total_minutes DESC
        ↓
115 → 110 순으로 정렬
```

<br>

> ## **6-4 ) SELECT 별칭을 WHERE에서 사용할 수 없는 이유**

다음 SQL은 PostgreSQL에서 오류가 발생함.

```sql
SELECT
    distance_km / time_hour AS speed
FROM running_records
WHERE speed >= 12;
```

`WHERE`가 `SELECT`보다 논리적으로 먼저 처리되므로 `speed`라는 SELECT 별칭이 아직 만들어지지 않은 시점임.

다음처럼 표현식을 직접 작성 가능.

```sql
SELECT
    distance_km / time_hour AS speed
FROM running_records
WHERE distance_km / time_hour >= 12;
```

또는 서브쿼리를 이용할 수도 있음.

# **8. 데이터 타입(Data Type)**

Data Type은 Column에 저장할 수 있는 데이터의 종류를 정의함.

적절한 데이터 타입을 지정하면 잘못된 형식의 데이터 저장을 방지하고 데이터 처리 규칙을 명확하게 만들 수 있음.

> ## **8-1 ) PostgreSQL 주요 데이터 타입**

| 데이터 타입 | 설명 | 스포츠 데이터 예 |
|---|---|---|
| `INTEGER` | 정수 | 경기 수 `20` |
| `VARCHAR(n)` | 최대 길이가 `n`인 문자열 | 선수명 |
| `TEXT` | 길이 제한을 별도로 두지 않는 문자열 | 경기 메모 |
| `DATE` | 날짜 | 경기일 |
| `NUMERIC(p, s)` | 정확한 소수 | 기록 `10.72` |
| `BOOLEAN` | 참/거짓 | 출전 여부 |

PostgreSQL에서는 `DECIMAL`과 `NUMERIC`이 같은 계열의 정확한 숫자 타입으로 사용됨.

<br>

> ## **8-2 ) 선수 테이블 생성**

[ sql : code ] "스포츠 선수 데이터에 적절한 데이터 타입 지정"

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50) NOT NULL,
    sport VARCHAR(30) NOT NULL,
    birth_date DATE,
    height_cm NUMERIC(5, 2),
    active BOOLEAN DEFAULT TRUE,
    note TEXT
);
```

각 Column의 의미.

| Column | 데이터 타입 | 저장 예 |
|---|---|---|
| `athlete_id` | `INTEGER` | `1` |
| `athlete_name` | `VARCHAR(50)` | `"지민"` |
| `sport` | `VARCHAR(30)` | `"육상"` |
| `birth_date` | `DATE` | `2002-05-12` |
| `height_cm` | `NUMERIC(5,2)` | `172.50` |
| `active` | `BOOLEAN` | `TRUE` |
| `note` | `TEXT` | `"하계 시즌 참가"` |

<br>

> ## **8-3 ) `VARCHAR(n)`과 `TEXT` 차이**

PostgreSQL에서는 `VARCHAR(n)`과 `TEXT` 사이에 일반적으로 큰 성능 차이가 있는 것으로 생각할 필요는 없음.

핵심 차이는 **길이 제한 규칙**.

| 구분 | `VARCHAR(n)` | `TEXT` |
|---|---|---|
| 길이 제한 | 최대 `n`자 제한 | 선언된 최대 길이 없음 |
| 용도 | 길이 제한 자체가 규칙일 때 | 별도 길이 제한이 필요 없을 때 |
| 예 | 국가코드, 제한된 사용자명 | 자유로운 메모·본문 |

예를 들어 선수 이름을 최대 50자로 제한하려는 **업무 규칙**이 있다면 `VARCHAR(50)` 사용 가능.

# **9. 스키마(Schema)**

Schema라는 단어는 문맥에 따라 의미가 조금 다르게 사용됨.

일반적인 데이터 설계에서는 데이터베이스의 **전체 구조와 규칙**을 설명하는 의미로 사용할 수 있음.

PostgreSQL에서는 Database 안에서 Table 등을 묶는 **논리적 Namespace**라는 더 구체적인 의미도 가짐.

> ## **9-1 ) 데이터베이스 설계에서의 스키마**

다음 구조 자체를 데이터베이스 스키마의 일부라고 볼 수 있음.

| Column | Data Type | Constraint |
|---|---|---|
| `athlete_id` | `INTEGER` | `PRIMARY KEY` |
| `athlete_name` | `VARCHAR(50)` | `NOT NULL` |
| `email` | `VARCHAR(100)` | `UNIQUE` |
| `active` | `BOOLEAN` | `DEFAULT TRUE` |

<br>

> ## **9-2 ) PostgreSQL에서의 Schema**

PostgreSQL에서는 다음과 같이 이름을 사용할 수 있음.

```sql
SELECT *
FROM public.athletes;
```

여기서.

```text
public
↓
Schema 이름

athletes
↓
Table 이름
```

따라서 `public.athletes`는 `public` Schema 안에 존재하는 `athletes` Table을 의미함.

# **10. 제약조건(Constraint)과 데이터 무결성**

데이터 무결성(Data Integrity)은 데이터가 **정확하고 일관된 상태를 유지하도록 관리하는 것**을 의미함.

잘못된 데이터가 들어오는 것을 방지하기 위해 Constraint 사용.

> ## **10-1 ) 대표적인 제약조건**

| Constraint | 역할 | 예 |
|---|---|---|
| `PRIMARY KEY` | Row를 고유하게 식별 | 선수 ID |
| `NOT NULL` | NULL 저장 방지 | 선수명 |
| `UNIQUE` | 중복 값 제한 | 이메일 |
| `FOREIGN KEY` | Table 간 참조 관계 유지 | 훈련 기록의 선수 ID |
| `CHECK` | 값의 조건 제한 | 훈련시간 ≥ 0 |
| `DEFAULT` | 값이 생략됐을 때 기본값 사용 | `active = TRUE` |

<br>

> ## **10-2 ) CHECK를 이용한 데이터 검증**

[ sql : code ] "음수 훈련시간이 저장되지 않도록 제한"

```sql
CREATE TABLE training_records (
    record_id INTEGER PRIMARY KEY,
    duration_min INTEGER
        CHECK (duration_min >= 0)
);
```

다음 값은 조건을 만족함.

```sql
INSERT INTO training_records
VALUES (1, 60);
```

[ Result ]

```text
60은 0 이상이므로 정상 저장
```

반면.

```sql
INSERT INTO training_records
VALUES (2, -30);
```

는 `CHECK (duration_min >= 0)` 조건을 만족하지 못하므로 저장이 거부됨.

데이터 무결성에서 중요한 것은 단순히 데이터 타입뿐 아니라 **업무적으로 허용 가능한 값인지까지 규칙으로 정의하는 것**.


<br><br>

# **11. 기본키(PK, Primary Key)**

Primary Key는 Table에서 각 Row를 **유일하게 식별하는 키**.

> ## **11-1 ) PK의 핵심 규칙**

Primary Key에는 다음 두 특성이 적용됨.

```text
1. 중복 불가
2. NULL 불가
```

예.

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |
| 3 | 서연 |

`athlete_id`를 PK로 지정하면 각각의 선수를 정확하게 구분 가능.

<br>

> ## **11-2 ) Primary Key는 Table당 하나**

하나의 Table에는 **Primary Key 제약조건이 하나** 존재함.

하지만 하나의 Column만 사용해야 하는 것은 아님.

여러 Column을 묶어 하나의 PK를 구성할 수 있음.

이를 `복합 기본키(Composite Primary Key)`라고 함.

예를 들어 선수가 대회에 참가한 정보를 저장한다고 가정.

```sql
CREATE TABLE competition_entries (
    athlete_id INTEGER,
    competition_id INTEGER,

    PRIMARY KEY (
        athlete_id,
        competition_id
    )
);
```

다음 조합들은 서로 다른 PK임.

```text
athlete_id | competition_id
-----------+---------------
1          | 100
1          | 101
2          | 100
```

하지만 `(1, 100)` 조합을 다시 저장하는 것은 불가능.


<br><br>

# **12. 외래키(FK, Foreign Key)**

Foreign Key는 다른 Table의 Key를 참조하여 Table 사이에 관계를 만드는 Column 또는 Column들의 집합.

FK는 반드시 PK만 참조해야 하는 것은 아니며, PostgreSQL에서는 일반적으로 **Primary Key 또는 UNIQUE 제약조건으로 고유성이 보장된 Key**를 참조함.

> ## **12-1 ) 선수와 훈련 기록 연결**

[ sql : code ] "athletes와 training_sessions 테이블을 PK와 FK로 연결"

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50) NOT NULL
);

CREATE TABLE training_sessions (
    session_id INTEGER PRIMARY KEY,
    athlete_id INTEGER NOT NULL,

    FOREIGN KEY (athlete_id)
        REFERENCES athletes(athlete_id)
);
```

구조.

```text
athletes
────────────────────
athlete_id  PK
athlete_name
      ↑
      │ 참조
      │
training_sessions
────────────────────
session_id  PK
athlete_id  FK
```

<br>

> ## **12-2 ) PK와 FK 비교**

| 구분 | PK | FK |
|---|---|---|
| 목적 | Row 고유 식별 | 다른 Table과 관계 생성 |
| 중복 | 불가 | 가능 |
| NULL | 불가 | 별도 `NOT NULL`이 없다면 가능할 수 있음 |
| Table당 개수 | PK 제약은 하나 | 여러 개 가능 |
| 여러 Column 사용 | 가능 | 가능 |

`FK`에 NULL을 허용하면 NULL은 **특정 부모 Row를 참조하지 않는 상태**로 사용할 수 있음.

따라서 단순히 "FK는 항상 값이 존재해야 한다"고 이해하면 정확하지 않음.


<br><br>

# **13. 참조 무결성(Referential Integrity)**

참조 무결성은 FK를 통해 연결된 Table 사이의 관계가 유효하게 유지되도록 하는 규칙.

> ## **13-1 ) 존재하지 않는 선수를 훈련 기록에 등록할 수 없음**

선수 Table.

| athlete_id | athlete_name |
|---:|---|
| 1 | 지민 |
| 2 | 현우 |

다음 훈련 기록은 정상.

```sql
INSERT INTO training_sessions (
    session_id,
    athlete_id
)
VALUES (
    101,
    1
);
```

`athlete_id = 1`이 실제로 존재하기 때문.

하지만.

```sql
INSERT INTO training_sessions (
    session_id,
    athlete_id
)
VALUES (
    102,
    999
);
```

는 `athletes`에 `athlete_id = 999`가 존재하지 않는다면 FK 제약조건을 위반하게 됨.

[ Result ]

```text
Foreign Key 제약조건 위반으로 INSERT 실패
```

<br>

> ## **13-2 ) 부모 Row 삭제와 FK**

PostgreSQL에서 별도의 삭제 동작을 지정하지 않은 FK는 기본적으로 참조 관계를 깨뜨리는 삭제를 허용하지 않음.

예.

```text
athletes

1 | 지민
        ↑
        │
training_sessions

101 | 1
```

훈련 기록이 지민 선수를 참조 중인 상태에서 지민 선수 Row를 바로 삭제하면 참조 무결성 문제가 발생.

<br>

> ## **13-3 ) ON DELETE 옵션**

| 옵션 | 부모 Row 삭제 시 |
|---|---|
| 기본 동작 | 참조 관계를 깨는 삭제를 거부 |
| `ON DELETE CASCADE` | 연결된 자식 Row도 삭제 |
| `ON DELETE SET NULL` | 자식 FK를 NULL로 변경 |

`SET NULL`을 사용하려면 해당 FK Column이 NULL을 허용해야 함.

`CASCADE`는 편리하지만 예상하지 못한 데이터까지 연쇄 삭제될 수 있으므로 설계 시 주의 필요.


<br><br>

# **14. 정규화(Normalization)**

정규화는 데이터 중복과 데이터 수정 과정의 이상 현상을 줄이기 위해 데이터를 여러 Table로 체계적으로 분리하는 설계 과정.

> ## **14-1 ) 정규화 전 데이터**

다음과 같이 선수 정보가 경기마다 반복된다고 가정.

| match_id | athlete_id | athlete_name | email | score |
|---:|---:|---|---|---:|
| 101 | 1 | 지민 | jimin@a.com | 12.1 |
| 102 | 1 | 지민 | jimin@a.com | 11.9 |
| 103 | 1 | 지민 | jimin@a.com | 12.0 |

선수의 이메일이 변경되면 모든 Row를 수정해야 함.

한 Row만 수정하면.

```text
101 → new@a.com
102 → jimin@a.com
103 → jimin@a.com
```

같은 선수가 서로 다른 이메일을 가진 것처럼 데이터가 불일치하게 됨.

이를 `갱신 이상(Update Anomaly)`의 예로 볼 수 있음.

<br>

> ## **14-2 ) 정규화 후 데이터**

선수 정보.

| athlete_id | athlete_name | email |
|---:|---|---|
| 1 | 지민 | jimin@a.com |

경기 기록.

| match_id | athlete_id | score |
|---:|---:|---:|
| 101 | 1 | 12.1 |
| 102 | 1 | 11.9 |
| 103 | 1 | 12.0 |

이제 이메일이 변경될 경우 한 Row만 수정하면 됨.

[ sql : code ] "정규화된 선수 테이블의 이메일 수정"

```sql
UPDATE athletes
SET email = 'new@a.com'
WHERE athlete_id = 1;
```

[ Result ]

```text
UPDATE 1
```

PostgreSQL의 `UPDATE 1`은 한 개의 Row가 변경되었다는 의미.

<br>

> ## **14-3 ) 정규화 목적**

```text
중복 데이터 발견
        ↓
역할에 따라 Table 분리
        ↓
PK 지정
        ↓
FK로 관계 연결
        ↓
중복 감소
        ↓
수정·삭제 시 오류 가능성 감소
        ↓
데이터 일관성 향상
```

<br>

> ## **14-4 ) 정규화의 대표적인 단계**

| 단계 | 기본 개념 |
|---|---|
| 1NF | 하나의 Column에 원자적인 값 저장 |
| 2NF | 복합키의 일부에만 의존하는 속성 분리 |
| 3NF | Key가 아닌 Column 사이의 불필요한 의존 관계 분리 |

초보 단계에서는 각 정규형을 완벽하게 암기하기보다 **왜 중복되는 데이터를 분리하는지**를 이해하는 것이 중요.

<br>

> ## **14-5 ) 정규화를 많이 하면 항상 좋은가**

항상 그런 것은 아님.

정규화를 과도하게 적용하면 Table이 많이 분리되어 조회 시 `JOIN`이 늘어날 수 있음.

```text
정규화
→ 중복 감소
→ 무결성 관리에 유리

하지만

지나친 Table 분리
→ JOIN 증가
→ Query 복잡성 증가
```

실제 시스템에서는 데이터 일관성과 조회 성능 등을 고려해 설계하며, 분석 목적에서는 경우에 따라 비정규화된 구조를 별도로 사용하는 경우도 있음.


<br><br>

# **15. PK와 FK를 이용한 스포츠 데이터 종합 예제**

> ## **15-1 ) 선수 Table 생성**

[ sql : code ] "선수와 훈련 기록을 저장할 관계형 테이블 생성"

```sql
CREATE TABLE athletes (
    athlete_id INTEGER PRIMARY KEY,
    athlete_name VARCHAR(50) NOT NULL,
    sport VARCHAR(30) NOT NULL
);

CREATE TABLE training_sessions (
    session_id INTEGER PRIMARY KEY,
    athlete_id INTEGER NOT NULL,
    duration_min INTEGER
        CHECK (duration_min >= 0),

    FOREIGN KEY (athlete_id)
        REFERENCES athletes(athlete_id)
);
```

<br>

> ## **15-2 ) 데이터 입력**

[ sql : code ] "선수와 훈련 기록 데이터 입력"

```sql
INSERT INTO athletes
VALUES
    (1, '지민', '육상'),
    (2, '현우', '수영'),
    (3, '서연', '농구');

INSERT INTO training_sessions
VALUES
    (101, 1, 60),
    (102, 1, 45),
    (103, 2, 50),
    (104, 3, 90);
```

[ Result ]

```text
athletes         → 3개 Row 저장
training_sessions → 4개 Row 저장
```

<br>

> ## **15-3 ) 선수별 총 훈련시간 조회**

[ sql : code ] "JOIN과 GROUP BY를 사용하여 선수별 총 훈련시간 계산"

```sql
SELECT
    a.athlete_name,
    a.sport,
    SUM(t.duration_min) AS total_minutes
FROM athletes AS a
JOIN training_sessions AS t
    ON a.athlete_id = t.athlete_id
GROUP BY
    a.athlete_id,
    a.athlete_name,
    a.sport
ORDER BY
    total_minutes DESC;
```

[ Result ]

| athlete_name | sport | total_minutes |
|---|---|---:|
| 지민 | 육상 | 105 |
| 서연 | 농구 | 90 |
| 현우 | 수영 | 50 |

결과 계산.

```text
지민
60 + 45
= 105분

서연
90분

현우
50분
```

<br>

> ## **15-4 ) 실행 흐름도**

```text
athletes
        +
training_sessions
        ↓
athlete_id 기준 JOIN
        ↓
선수와 훈련 기록 연결
        ↓
GROUP BY 선수
        ↓
SUM(duration_min)
        ↓
지민 = 105
현우 = 50
서연 = 90
        ↓
ORDER BY total_minutes DESC
        ↓
지민 → 서연 → 현우
```

# **18. Advanced 추가 학습**

> ## **18-1 ) 후보키와 UNIQUE**

Primary Key 외에도 Row를 유일하게 구분할 수 있는 Column이 존재할 수 있음.

예를 들어 선수 이메일이 중복되면 안 된다면.

```sql
email VARCHAR(100) UNIQUE
```

처럼 설정 가능.

<br>

> ## **18-2 ) NULL은 0이나 빈 문자열이 아님**

SQL에서 `NULL`은 값이 `0`이라는 의미가 아니라 **값이 없거나 알 수 없음**을 나타냄.

따라서.

```sql
WHERE value = NULL
```

이 아니라.

```sql
WHERE value IS NULL
```

사용.

<br>

> ## **18-3 ) 현대 데이터베이스 모델**

관계형 DB 외에도 목적에 따라 다음과 같은 데이터베이스가 사용됨.

```text
Document DB
Key-Value DB
Graph DB
Column-oriented DB
```

따라서 모든 데이터 문제에서 RDBMS만 사용하는 것은 아니며 데이터 구조와 서비스 목적에 따라 적절한 시스템을 선택함.

# **19. 핵심정리**

- 데이터 사이언티스트는 모델링 전에 필요한 데이터를 직접 정의하고 추출할 수 있어야 하며 SQL이 중요한 역할을 함.
- `Data`는 개별 사실이나 값이고 `Database`는 데이터를 체계적으로 저장한 집합임.
- Query는 데이터베이스에 보내는 요청이며 SQL은 Query를 표현하는 언어임.
- PostgreSQL, MySQL, Oracle Database, SQL Server 등은 SQL을 처리하고 Database를 관리하는 DBMS임.
- 관계형 데이터베이스는 데이터를 Table 형태로 저장하고 여러 Table 사이의 관계를 이용함.
- Table은 Row와 Column으로 구성됨.
- Row는 하나의 개체에 대한 기록이고 Column은 데이터의 속성을 나타냄.
- SQL은 작성 순서와 논리적인 처리 순서가 다름.
- 기본적인 SQL 처리 순서는 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`로 이해하면 됨.
- `WHERE`가 `SELECT`보다 먼저 처리되므로 일반적으로 SELECT에서 만든 Alias를 WHERE에서 바로 사용할 수 없음.
- Data Type은 Column에 저장될 값의 종류와 규칙을 정의함.
- PostgreSQL에서는 `INTEGER`, `VARCHAR`, `TEXT`, `DATE`, `NUMERIC`, `BOOLEAN` 등이 자주 사용됨.
- PostgreSQL에서 `VARCHAR(n)`은 길이 제한 규칙이 필요할 때 사용하고 `TEXT`는 별도의 최대 길이 제한이 필요하지 않을 때 사용 가능.
- Schema는 넓은 의미에서는 데이터베이스 구조의 설계도를 뜻하며 PostgreSQL에서는 Database 내부의 Namespace라는 의미로도 사용됨.
- Constraint는 잘못된 데이터가 저장되지 않도록 규칙을 정의함.
- `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK`, `DEFAULT` 등이 대표적인 Constraint.
- Primary Key는 각 Row를 유일하게 식별하며 중복과 NULL을 허용하지 않음.
- 한 Table의 Primary Key 제약조건은 하나이지만 여러 Column을 조합한 복합 Primary Key를 만들 수 있음.
- Foreign Key는 Table 간 관계를 생성하며 한 Table에 여러 FK가 존재할 수 있음.
- FK는 반드시 PK만 참조하는 것이 아니라 고유성이 보장된 참조 가능한 Key를 대상으로 할 수도 있음.
- FK Column은 별도의 `NOT NULL` 조건이 없다면 NULL을 허용할 수 있음.
- 데이터 무결성은 데이터의 정확성과 일관성을 유지하는 것을 의미함.
- 참조 무결성은 FK를 이용한 Table 사이의 관계가 유효하게 유지되도록 하는 규칙임.
- `ON DELETE CASCADE`를 사용하면 부모 Row 삭제 시 관련 자식 Row도 함께 삭제할 수 있음.
- `ON DELETE SET NULL`은 부모 Row 삭제 시 FK를 NULL로 변경할 수 있음.
- 정규화는 불필요한 데이터 중복을 줄이고 데이터 수정 과정에서 발생할 수 있는 이상 현상을 줄이기 위한 설계 방법임.
- 정규화된 Table들은 PK와 FK를 이용하여 관계를 맺고 필요한 경우 `JOIN`으로 다시 연결하여 분석 가능.
- SQL과 데이터베이스 학습에서 가장 중요한 것은 문법만 외우는 것이 아니라 **데이터가 어떤 구조로 저장되고 어떤 관계로 연결되어 있는지 이해하는 것**임.
