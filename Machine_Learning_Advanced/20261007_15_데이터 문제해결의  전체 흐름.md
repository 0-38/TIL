# **15. 데이터 문제 해결의 전체 흐름**

<br>

# 데이터 문제해결의 기본 문제  

> ## **1-1) 데이터 업무는 기술이 아니라 문제에서 시작한다**

실제 데이터 업무에서는 다음과 같은 요청이 더 자주 주어진다.

```text
"최근 시즌 홈경기 티켓 매출이 감소했습니다.
원인을 분석하고 개선할 방법을 찾아주세요."
```

처음부터 다음과 같이 요청되는 경우는 상대적으로 적다.

```text
Random Forest를 사용해주세요.
XGBoost를 만들어주세요.
Funnel 분석을 해주세요.
```

따라서 데이터 분석의 시작점은 **사용할 기술을 결정하는 것**이 아니라 **해결해야 할 문제를 정확하게 정의하는 것**이다.

```text
비즈니스 문제
        ↓
질문 정의
        ↓
필요한 데이터 확인
        ↓
데이터 품질 검증
        ↓
현재 상황 분석
        ↓
문제 구체화
        ↓
적절한 방법 선택
        ↓
분석 / 모델링
        ↓
검증
        ↓
결과 해석
        ↓
의사결정
        ↓
실제 적용
        ↓
재측정 및 개선
```

데이터 사이언티스트의 핵심 역할은 특정 알고리즘을 사용하는 것이 아니라 **현재 문제를 데이터로 답할 수 있는 질문으로 바꾸고, 그 질문에 적합한 방법을 선택하는 것**이다.

<br>

> ## **1-2) 기술은 서로 독립된 과목이 아니다**

Python, SQL, 통계, 프로덕트 분석, 머신러닝, 시계열 분석은 서로 별개의 작업처럼 보이지만 실제 프로젝트에서는 하나의 문제를 해결하기 위해 연결된다.

| 도구 / 방법 | 실제 역할 |
| --- | --- |
| SQL | 필요한 데이터를 추출하고 결합 |
| Python | 전처리, 분석, 시각화, 모델링 자동화 |
| EDA | 현재 상황과 데이터 패턴 파악 |
| Product Analysis | 행동 과정과 전환 문제 분석 |
| Statistics | 관찰한 차이가 우연인지 검증 |
| Machine Learning | 새로운 데이터의 결과 예측 |
| Time Series | 시간에 따른 미래 값 예측 |
| SHAP | 모델이 예측한 이유 해석 |
| Pipeline | 분석된 모델을 재현 가능하게 운영 |
| A/B Test | 개선안이 실제 효과를 만드는지 검증 |

즉,

```text
SQL을 배웠다.
→ SQL을 써야 한다. X
```

가 아니라

```text
필요한 데이터가 여러 Table에 존재한다.
→ SQL JOIN이 필요하다. O
```

처럼 **문제에 따라 도구를 선택하는 사고방식**이 중요하다.

# **2. 문제 정의와 질문 구체화**

> ## **2-1) 모호한 문제를 분석 가능한 질문으로 바꾸기**

프로축구 구단 데이터팀에서 다음과 같은 문제가 발생했다고 가정한다.

```text
최근 홈경기 티켓 매출이 감소했다.
```

이 상태에서는 아직 어떤 분석을 해야 하는지 결정하기 어렵다.

먼저 문제를 여러 질문으로 나눌 수 있다.

```text
언제부터 매출이 감소했는가?

관중 수가 감소했는가?

티켓 구매 전환율이 감소했는가?

특정 좌석 등급에서 감소했는가?

신규 팬과 기존 팬 중 어디에서 감소했는가?

모바일 앱과 웹 중 어디에서 문제가 발생했는가?

특정 경기에서만 나타난 현상인가?
```

이러한 질문을 통해 문제를 점점 구체화한다.

```text
[처음 문제]

홈경기 매출 감소

        ↓

[분석 후]

방문자 수는 유사하지만
Mobile 구매 완료율이 감소

        ↓

[더 구체적인 문제]

Mobile 결제 단계에서
구매 이탈이 증가하고 있음
```

좋은 문제 정의는 분석 범위를 줄이고 불필요한 모델링을 방지한다.

<br>

> ## **2-2) 비즈니스 문제와 분석 문제를 구분한다**

비즈니스 문제와 분석 문제는 같은 것이 아니다.

예를 들어

```text
비즈니스 문제
→ 홈경기 티켓 매출 감소
```

를 데이터 분석 관점에서는 다음처럼 바꿀 수 있다.

```text
분석 질문 1
→ 월별 티켓 구매 전환율이 변화했는가?

분석 질문 2
→ 어떤 채널의 전환율이 감소했는가?

분석 질문 3
→ 결제 Funnel의 어느 단계에서 이탈이 증가했는가?

분석 질문 4
→ 구매 가능성이 높은 사용자를 예측할 수 있는가?
```

| 구분 | 예 |
| --- | --- |
| 비즈니스 문제 | 티켓 매출이 감소했다 |
| 분석 질문 | 모바일 결제 완료율이 감소했는가? |
| 통계 질문 | PC와 Mobile 구매율 차이가 유의한가? |
| ML 질문 | 어떤 팬이 티켓을 구매할 가능성이 높은가? |
| 시계열 질문 | 다음 달 티켓 매출은 얼마인가? |

하나의 비즈니스 문제에서도 **여러 분석 질문이 파생될 수 있다.**

# **3. 필요한 데이터를 찾고 품질을 검증한다**

> ## **3-1) 필요한 데이터는 여러 Table에 분산되어 있다**

실제 서비스에서는 하나의 DataFrame에 모든 데이터가 들어 있지 않은 경우가 많다.

프로스포츠 티켓 서비스가 다음과 같이 구성되어 있다고 가정한다.

```text
users
→ 팬 정보

matches
→ 경기 정보

tickets
→ 티켓 구매 정보

events
→ 앱 / 웹 행동 로그

payments
→ 결제 결과

campaigns
→ 마케팅 캠페인
```

질문에 따라 필요한 Table이 달라진다.

| 질문 | 필요한 데이터 |
| --- | --- |
| 매출이 언제 감소했는가? | `payments`, `matches` |
| 좌석별 매출은? | `tickets`, `matches` |
| 어떤 팬의 구매가 감소했는가? | `users`, `tickets` |
| 결제 Funnel 이탈 위치는? | `events`, `payments` |
| 광고 유입별 구매율은? | `campaigns`, `events`, `tickets` |

<br>

> ## **3-2) SQL로 분석용 데이터 구성**

[ SQL : code ] "경기별 티켓 구매 건수와 매출 집계"

```sql
SELECT
    m.match_id,
    m.match_date,
    m.opponent,
    COUNT(t.ticket_id) AS ticket_count,
    SUM(t.price) AS revenue
FROM matches AS m
LEFT JOIN tickets AS t
    ON m.match_id = t.match_id
WHERE m.match_date >= '2026-01-01'
GROUP BY
    m.match_id,
    m.match_date,
    m.opponent
ORDER BY m.match_date;
```

[ Result ]

```text
match_id | match_date | opponent | ticket_count | revenue
----------------------------------------------------------
101      | 2026-03-08 | Team A   | 18420        | 721500000
102      | 2026-03-21 | Team B   | 17680        | 688400000
103      | 2026-04-05 | Team C   | 15930        | 612700000
104      | 2026-04-18 | Team D   | 14810        | 564200000
```

이 결과를 통해 매출 감소 시점을 먼저 확인할 수 있다.

<br>

> ## **3-3) 분석보다 먼저 Data Quality를 확인한다**

분석용 데이터를 만들었다고 바로 모델링하면 안 된다.

다음 항목을 먼저 확인해야 한다.

```text
결측치
중복
비정상 값
날짜 범위
단위
Category 표기
데이터 수집 누락
Target 정의
Feature 생성 시점
```

예를 들어 GPS 선수 데이터에서

```text
total_distance_m = -350
```

처럼 음수 거리가 존재한다면 센서 오류 또는 전처리 오류일 가능성이 있다.

또

```text
speed = 72 m/s
```

와 같이 실제 스포츠 상황에서 불가능한 값이 존재할 수도 있다.

[ Python : code ] "GPS 데이터 기본 품질 검사"

```python
print(df.isna().sum())

print(
    df[["total_distance_m", "max_speed_ms"]]
    .describe()
)

duplicated_count = df.duplicated().sum()

print("중복:", duplicated_count)
```

[ Result ]

```text
player_id             0
total_distance_m     12
max_speed_ms          4
player_load           7
injury                0

중복: 3
```

분석 결과의 신뢰성은 모델의 복잡도보다 **입력 데이터의 품질에 먼저 의존한다.**

# **4. EDA를 통해 현재 상황을 이해한다**

> ## **4-1) EDA의 목적**

EDA(Exploratory Data Analysis)의 목적은 단순히 그래프를 많이 만드는 것이 아니다.

현재 데이터에서

```text
무슨 일이 발생하고 있는가?
```

를 파악하는 것이 핵심이다.

예를 들어 티켓 서비스에서 다음과 같은 결과가 나타났다고 하자.

```text
서비스 방문자 수
→ 큰 변화 없음

경기 상세 조회
→ 큰 변화 없음

좌석 선택
→ 큰 변화 없음

결제 완료
→ 감소

매출
→ 감소
```

이 결과로 문제를 다음처럼 구체화할 수 있다.

```text
Traffic 문제 X

구매 Funnel 후반부 문제 가능성 O
```

즉 EDA는 단순 요약을 넘어 **다음 질문을 만드는 과정**이다.

<br>

> ## **4-2) Python으로 기간별 전환율 확인**

[ Python : code ] "경기별 상세 조회 대비 티켓 구매 전환율 계산"

```python
summary = (
    df.groupby("match_id")
      .agg(
          viewers=("user_id", "nunique"),
          buyers=("buyer_id", "nunique")
      )
)

summary["conversion_rate"] = summary["buyers"] / summary["viewers"]

print(summary.round(3))
```

[ Result ]

```text
          viewers  buyers  conversion_rate
match_id
101         24800    6210            0.250
102         25120    6020            0.240
103         24950    5110            0.205
104         25230    4690            0.186
```

방문자는 크게 감소하지 않았지만 Conversion Rate가

```text
25.0%
→ 24.0%
→ 20.5%
→ 18.6%
```

로 감소하고 있다.

따라서 다음 분석 질문은

```text
"왜 구매 전환율이 감소했는가?"
```

로 발전한다.

# **5. 질문에 따라 분석 방법을 선택한다**

> ## **5-1) 분석 방법을 먼저 고르지 않는다**

다음처럼 생각하는 것은 좋지 않다.

```text
Random Forest를 배웠다.
        ↓
Random Forest를 사용하자.
```

올바른 접근은

```text
현재 질문은 무엇인가?
        ↓
데이터 구조는 어떠한가?
        ↓
어떤 방법이 질문에 답할 수 있는가?
```

이다.

| 질문 | 적절한 방법 |
| --- | --- |
| 현재 무엇이 발생하고 있는가? | EDA |
| 사용자가 어디에서 이탈하는가? | Funnel |
| 사용자 집단별 차이는? | Segmentation |
| 차이가 우연인지 알고 싶은가? | Statistical Test |
| 새로운 데이터 결과를 예측할 것인가? | Machine Learning |
| 미래 시간값을 예측할 것인가? | Time Series |
| 개선안이 실제 효과가 있는가? | A/B Test |
| 모델이 왜 예측했는가? | Feature Importance / SHAP |

# **6. Product Analysis로 행동 과정의 문제를 찾는다**

> ## **6-1) Funnel Analysis**

티켓 구매 과정이 다음과 같다고 가정한다.

```text
서비스 방문
    ↓
경기 조회
    ↓
좌석 선택
    ↓
결제 시작
    ↓
결제 완료
```

현재 결과가 다음과 같다고 하자.

| 단계 | 사용자 수 | 이전 단계 전환율 |
| --- | ---: | ---: |
| 서비스 방문 | 30,000 | - |
| 경기 조회 | 24,000 | 80.0% |
| 좌석 선택 | 15,600 | 65.0% |
| 결제 시작 | 12,480 | 80.0% |
| 결제 완료 | 7,488 | 60.0% |

가장 큰 문제를 단순히 사용자 수 감소만으로 판단하지 않고 **단계별 Conversion Rate**로 분석할 수 있다.

```text
결제 시작
12,480

        ↓ 60%

결제 완료
7,488
```

이 단계의 이탈이 특히 크다면 결제 시스템 문제를 더 확인할 수 있다.

<br>

> ## **6-2) Segmentation**

전체 평균만 보면 중요한 문제가 숨겨질 수 있다.

예를 들어 Device별 결과가

| Device | 결제 완료율 |
| --- | ---: |
| PC | 72% |
| Mobile | 49% |
| Tablet | 65% |

라면 전체 Funnel 문제보다

```text
Mobile Payment Funnel
```

에 집중할 근거가 생긴다.

다음과 같이 추가 Segmentation도 가능하다.

```text
신규 / 기존 팬
광고 / 검색 / 직접유입
홈팀 / 원정팀 팬
회원 / 비회원
Android / iOS
좌석 등급
```

Segmentation의 목적은 **문제가 어디에서 특히 크게 나타나는지 찾는 것**이다.

# **7. 통계 분석으로 관찰한 차이를 검증한다**

> ## **7-1) 차이가 있다고 원인이라고 결론 내리면 안 된다**

다음 결과가 있다고 하자.

```text
PC 구매율
= 48%

Mobile 구매율
= 34%
```

관찰된 데이터에서는 차이가 있다.

하지만

```text
Mobile이기 때문에 구매율이 낮다.
```

라고 바로 결론 내릴 수 없다.

먼저

```text
이 정도 차이가 Sampling Variation으로
발생할 가능성은 어느 정도인가?
```

를 검토할 수 있다.

<br>

> ## **7-2) 비율 차이에 대한 통계 검정 예제**

[ Python : code ] "PC와 Mobile 구매율 차이 검정"

```python
from statsmodels.stats.proportion import proportions_ztest

success = [480, 340]
total = [1000, 1000]

z_stat, p_value = proportions_ztest(success, total)

print("z:", round(z_stat, 3))
print("p-value:", round(p_value, 5))
```

[ Result ]

```text
z: 6.351
p-value: 0.00000
```

현재 표본에서는 두 그룹의 구매 비율 차이가 우연한 표본 변동만으로 설명되기 어렵다는 통계적 근거가 나타났다.

하지만 이것도 다음을 의미하지는 않는다.

```text
Mobile 사용
        ↓
구매 감소의 원인
```

통계적 유의성은 **인과관계를 자동으로 증명하지 않는다.**

<br>

> ## **7-3) 통계적 유의성과 실무적 중요성**

다음 두 결과를 생각해보자.

```text
Case A

차이 = 0.1%
p-value < 0.001
```

```text
Case B

차이 = 8%
p-value = 0.04
```

표본이 매우 크면 아주 작은 차이도 통계적으로 유의하게 나타날 수 있다.

따라서 실제 의사결정에서는

```text
p-value
+
Effect Size
+
Business Impact
```

를 함께 확인해야 한다.

# **8. Machine Learning이 필요한 질문**

> ## **8-1) 설명과 예측을 구분한다**

다음 질문은 머신러닝 문제로 바꿀 수 있다.

```text
"다음 홈경기 티켓을 구매할 가능성이 높은 팬은 누구인가?"
```

Target을

```text
ticket_purchase

0 = 구매하지 않음
1 = 구매
```

으로 정의하면 Binary Classification 문제이다.

Feature는 **예측 시점 이전에 알 수 있는 정보만 사용해야 한다.**

예를 들어

```text
최근 30일 앱 방문 횟수
최근 경기 조회 횟수
과거 티켓 구매 횟수
팬 가입 기간
선호 좌석 등급
마케팅 유입 채널
```

등을 사용할 수 있다.

<br>

> ## **8-2) Prediction Time을 먼저 정의한다**

Prediction Time을 정의하지 않으면 Data Leakage가 발생하기 쉽다.

예를 들어 경기 3일 전에 구매 가능성을 예측한다고 하자.

```text
Prediction Time
2026-04-10
```

그렇다면 Feature에는

```text
2026-04-10까지 알고 있는 정보
```

만 사용할 수 있다.

다음 Feature는 문제가 있다.

```text
결제 완료 후 발생한 Event
티켓 발급 여부
경기 당일 입장 여부
```

이미 Target 이후 정보를 포함하고 있기 때문이다.

```text
Prediction Time
      ↓
Feature Cut-off
      ↓
Target Window
```

를 명확하게 정의하는 것이 실무 ML의 핵심이다.

<br>

> ## **8-3) 모델링 흐름**

```text
문제 정의
    ↓
Prediction Time 정의
    ↓
Feature / Target 생성
    ↓
Train / Validation / Test
    ↓
Preprocessing
    ↓
Baseline Model
    ↓
Evaluation
    ↓
Error Analysis
    ↓
필요한 개선 방법 선택
    ↓
CV / Tuning
    ↓
Final Test
```

모델의 문제가 무엇인지에 따라 개선 방법을 선택한다.

| 문제 | 고려 방법 |
| --- | --- |
| Underfitting | 모델 복잡도 증가, Feature 개선 |
| Overfitting | Regularization, 단순화, 데이터 확대 |
| Class Imbalance | Class Weight, Sampling, Metric 변경 |
| 높은 Variance | CV, Bagging |
| 성능 부족 | Boosting, Feature Engineering |
| Hyperparameter 불확실 | Grid / Random / Optuna |

# **10. Time Series가 필요한 질문**

> ## **10-1) 미래 값을 예측하는 문제**

다음 질문은 일반적인 Classification과 다르다.

```text
"다음 달 홈경기 티켓 매출은 얼마인가?"
```

Target은 시간 순서가 존재한다.

```text
1월 매출
    ↓
2월 매출
    ↓
3월 매출
    ↓
...
    ↓
다음 달?
```

이 경우 Random Split은 시간 구조를 파괴할 수 있다.

따라서

```text
과거 → Train
미래 → Validation
```

구조를 유지해야 한다.

<br>

> ## **10-2) 스포츠 시계열 예제**

다음과 같은 문제도 Time Series에 해당할 수 있다.

| 문제 | 예측 대상 |
| --- | --- |
| 구단 티켓 매출 | 다음 경기 / 다음 달 매출 |
| 선수 Training Load | 다음 주 부하 |
| 웨어러블 데이터 | 다음 날 안정시 심박수 |
| 수영 훈련 | 다음 주 기록 변화 |
| 야구 | 경기별 관중 수 |
| 스키 리조트 | 일별 이용객 수 |

시간 데이터에서는

```text
Trend
Seasonality
Lag
Rolling Statistics
Event Effect
```

등을 고려할 수 있다.

# **11. 결과를 해석하고 실제 원인과 구분한다**

> ## **11-1) 관찰된 사실과 원인 추론**

다음과 같은 결과가 나왔다고 하자.

```text
Mobile 사용자의 구매 완료율이 낮다.
```

이것은 **관찰된 사실**이다.

아직

```text
Mobile UI가 구매율 감소의 원인이다.
```

라고 단정할 수 없다.

추가로 확인할 데이터는

```text
결제 오류 로그
페이지 Loading Time
OS Version
Payment Provider
사용자 문의
이탈 Event
```

등이 있다.

분석 과정에서는 항상 다음을 구분해야 한다.

| 구분 | 의미 |
| --- | --- |
| Observation | 데이터에서 실제로 확인한 현상 |
| Interpretation | 현상에 대한 해석 |
| Hypothesis | 원인에 대한 가설 |
| Causal Evidence | 원인임을 지지하는 추가 근거 |

<br>

> ## **11-2) 모델 해석도 인과관계가 아니다**

예를 들어 티켓 구매 예측 XGBoost의 SHAP 결과에서

```text
최근 앱 방문 횟수
SHAP = +0.35
```

가 나타났다고 하자.

이는

```text
현재 모델에서는
이 사용자의 앱 방문 횟수가
구매 방향의 Model Output을
높이는 데 기여했다.
```

는 의미이다.

다음 의미는 아니다.

```text
앱 방문 횟수를 강제로 늘리면
구매가 증가한다.
```

Feature Importance와 SHAP은 **모델의 판단을 설명**하지만 현실의 인과관계를 자동으로 설명하지 않는다.

# **12. 분석 결과를 의사결정으로 연결한다**

> ## **12-1) 분석 결과 자체가 최종 목적은 아니다**

분석 결과가 다음과 같다고 하자.

```text
Mobile Payment Conversion
48% → 34%

특정 Payment Provider에서
오류율 증가 확인
```

분석을 여기서 끝내면

```text
"Mobile 결제율이 낮았습니다."
```

라는 보고서만 남는다.

실제 문제 해결에서는 다음 단계가 필요하다.

```text
분석 결과
        ↓
문제 원인 후보
        ↓
개선안
        ↓
실행 가능성 검토
        ↓
실험
        ↓
결과 확인
```

예를 들어

```text
[문제]

Mobile 결제 오류 증가

        ↓

[개선안]

결제 단계 단순화
Payment Provider 변경
오류 처리 개선

        ↓

[검증]

A/B Test
```

로 연결할 수 있다.

<br>

> ## **12-2) Actionable Insight**

좋은 분석 결과는 행동으로 연결될 수 있어야 한다.

```text
나쁜 형태

Mobile 구매율이 낮다.
```

보다

```text
좋은 형태

Mobile 사용자의 결제 시작 → 완료 전환율이
PC 대비 낮으며, 차이는 특정 Payment Provider의
오류율 증가 구간에 집중되어 있다.

따라서 Mobile Payment Error 개선을 우선 적용하고
결제 완료율과 오류율을 Primary / Guardrail Metric으로
설정하여 A/B Test를 진행한다.
```

처럼 **다음 행동이 명확한 결과**가 더 유용하다.

# **13. A/B Test를 이용한 개선안 검증**

> ## **13-1) 개선 전후 단순 비교의 한계**

Mobile 결제 화면을 개선한 후

```text
Before
구매율 = 34%

After
구매율 = 39%
```

가 되었다고 하자.

단순 Before / After 비교만으로 개선안 효과라고 단정하기 어렵다.

같은 시기에

```text
인기 경기
할인 이벤트
시즌 개막
광고 캠페인
```

등이 영향을 줬을 수도 있다.

따라서 가능하다면 A/B Test를 통해 비교할 수 있다.

```text
사용자
  ↓
Random Assignment
  ↓
┌─────────────┬─────────────┐
│ Control     │ Treatment   │
│ 기존 결제   │ 개선 결제    │
└─────────────┴─────────────┘
        ↓
Conversion 비교
```

<br>

> ## **13-2) Metric 설계**

실험에서는 하나의 지표만 보지 않는다.

예를 들어

```text
Primary Metric
→ Payment Conversion Rate

Guardrail Metric
→ 결제 오류율
→ 결제 취소율
→ 고객 문의율
→ 결제 처리시간
```

을 함께 사용할 수 있다.

개선안이 구매율은 높였지만 오류나 취소율을 크게 악화시켰다면 실제 적용 여부를 다시 판단해야 한다.

# **14. 모델을 실제 서비스에 적용한다**

> ## **14-1) Notebook 성능이 끝이 아니다**

좋은 머신러닝 모델을 만들었다고 실제 서비스에서 바로 사용할 수 있는 것은 아니다.

새로운 데이터에도 학습 시 사용한 처리 과정이 동일하게 적용되어야 한다.

```text
New User Data
      ↓
Missing Value 처리
      ↓
Encoding
      ↓
Scaling
      ↓
Model
      ↓
Prediction
```

이를 위해 앞에서 배운 Pipeline을 사용할 수 있다.

```text
Raw Data
    ↓
Pipeline
    │
    ├─ Preprocessing
    ├─ Feature Processing
    └─ Model
    ↓
Prediction
```

<br>

> ## **14-2) 운영 활용 예시**

티켓 구매 예측 확률을 얻었다고 하자.

```text
Fan A → 0.82
Fan B → 0.21
Fan C → 0.67
```

이 결과를 활용하는 방법은 모델의 기술적 성능만으로 결정하지 않는다.

예를 들어

```text
구매 가능성이 높은 팬
→ 적절한 좌석 추천

구매를 망설이는 팬
→ 경기 정보 / 혜택 안내
```

등의 활용이 가능하다.

그러나 과도한 알림이나 불필요한 Targeting은 사용자 경험을 악화시킬 수도 있으므로 **비즈니스 효과와 사용자 영향 모두 고려해야 한다.**

# **15. 적용 이후 다시 측정한다**

> ## **15-1) 데이터 문제 해결은 한 번으로 끝나지 않는다**

분석이나 모델을 서비스에 적용하면 데이터 환경이 계속 변화한다.

```text
사용자 행동 변화
시장 변화
서비스 UI 변화
정책 변화
센서 변경
새로운 선수 영입
시즌 변화
```

따라서 과거에 잘 동작하던 분석이나 모델이 미래에도 동일하게 잘 동작한다는 보장은 없다.

전체 과정은 다음처럼 반복된다.

```text
문제 발견
    ↓
분석
    ↓
가설
    ↓
검증
    ↓
적용
    ↓
모니터링
    ↓
새로운 문제 발견
    ↓
재분석
```

<br>

> ## **15-2) 머신러닝 모델 모니터링**

축구 부상예측 모델을 운영한다고 하자.

다음 항목을 지속적으로 확인할 수 있다.

```text
Input Feature Distribution
Prediction Distribution
Precision
Recall
F1
False Negative
Calibration
```

예를 들어 새로운 GPS 장비 도입으로 `player_load` 값의 분포가 바뀐다면 모델 입력 자체가 달라질 수 있다.

```text
Training Data

player_load 평균 = 550
```

```text
운영 Data

player_load 평균 = 720
```

이처럼 Data Distribution이 변하면 모델 성능 저하가 발생할 수 있다.

이를 **Data Drift** 관점에서 확인할 수 있다.

# **18. 데이터 사이언티스트의 판단 과정**

> ## **18-1) 코드를 작성하기 전에 물어야 할 질문**

새로운 문제를 받으면 다음 질문부터 생각하는 것이 좋다.

```text
1. 실제 해결해야 하는 문제는 무엇인가?

2. 누구의 의사결정을 돕기 위한 분석인가?

3. 성공을 어떤 지표로 정의할 것인가?

4. 필요한 데이터가 존재하는가?

5. 데이터는 어떻게 생성되었는가?

6. 분석 단위는 무엇인가?

7. 시간 기준은 무엇인가?

8. 누수가 발생할 Feature는 없는가?

9. 어떤 분석 방법이 질문에 적합한가?

10. 결과를 어떻게 검증할 것인가?

11. 결과가 실제 행동으로 연결될 수 있는가?

12. 적용 후 무엇을 다시 측정할 것인가?
```

이 질문들이 명확하면 기술 선택도 자연스럽게 결정된다.

<br>

> ## **18-2) 생성형 AI를 사용할 때도 판단이 필요하다**

생성형 AI는 다음 작업을 빠르게 도울 수 있다.

```text
SQL 작성
Python 코드 작성
시각화
통계 코드
머신러닝 Pipeline
문서 작성
```

하지만 AI가 생성한 코드가

```text
현재 질문에 적합한가?

Data Leakage가 없는가?

Metric이 올바른가?

해석이 인과관계를 과장하지 않는가?

실제 운영 조건을 반영하는가?
```

는 별도로 판단해야 한다.

즉, AI가 코드 작성 속도를 높여도 **문제 정의와 검증, 해석, 의사결정의 중요성은 줄어들지 않는다.**

# **20. Advanced 추가 학습**

> ## **20-1) Causal Inference**

관찰 데이터에서 두 변수가 함께 움직인다고 해서 한 변수가 다른 변수의 원인이라고 단정할 수 없다.

```text
Correlation
≠
Causation
```

실험이 어려운 상황에서는 Matching, Difference-in-Differences, Instrumental Variable 등 인과추론 방법을 추가로 학습할 수 있다.

<br>

> ## **20-2) Data Drift와 Model Drift**

서비스 운영 이후에는 입력 데이터와 모델 성능이 변할 수 있다.

```text
Data Drift
→ 입력 데이터 분포 변화

Model Performance Drift
→ 실제 예측 성능 변화
```

모델 배포 이후에도 지속적인 모니터링과 재학습 정책이 필요하다.

<br>

> ## **20-3) Decision Threshold**

Classification Model에서 기본 Threshold `0.5`가 항상 최적은 아니다.

```text
Recall이 중요
→ Threshold를 낮추는 방향 검토

False Positive 비용이 큼
→ Threshold를 높이는 방향 검토
```

Threshold 역시 Validation Data와 실제 의사결정 비용을 기준으로 설정해야 하며 Test Data를 이용하여 조정해서는 안 된다.

# **21. 핵심정리**

1. 데이터 문제 해결은 특정 분석 방법이나 머신러닝 알고리즘에서 시작하지 않고 **실제 해결해야 하는 문제에서 시작한다.**

2. 비즈니스 문제를 바로 분석하기보다 데이터를 이용해 답할 수 있는 구체적인 질문으로 분해해야 한다.

3. 실제 데이터는 여러 Database Table에 분산되어 있을 수 있으므로 ERD를 이해하고 SQL을 이용하여 필요한 데이터를 구성할 수 있어야 한다.

4. 분석을 시작하기 전에 결측치, 중복, 이상값, 수집 누락, 단위, 기간 등의 **Data Quality를 먼저 검증해야 한다.**

5. EDA의 목적은 단순히 그래프를 만드는 것이 아니라 현재 상황을 이해하고 **다음 분석 질문을 발견하는 것**이다.

6. 분석 방법은 배운 순서대로 사용하는 것이 아니라 현재 질문에 따라 선택한다.

```text
행동 흐름
→ Product Analysis

집단 차이
→ Statistics

미래 Class 예측
→ Classification

연속값 예측
→ Regression

시간 기반 미래값
→ Time Series

개선안 검증
→ A/B Test
```

7. Funnel Analysis는 사용자가 행동 과정의 어느 단계에서 이탈하는지 확인하는 데 사용하고, Segmentation은 문제가 특정 사용자 집단에 집중되는지 확인하는 데 사용한다.

8. 관찰된 그룹 차이가 있다고 해서 원인이라고 바로 판단할 수 없다. 필요하면 통계적 검정과 추가 분석을 이용해 근거를 확인해야 한다.

9. 통계적으로 유의한 결과도 실제 효과가 매우 작을 수 있으므로 `p-value`뿐 아니라 **Effect Size와 실제 업무 영향**을 함께 고려해야 한다.

10. 머신러닝 문제에서는 모델을 만들기 전에 **Prediction Time과 Target을 명확하게 정의**해야 한다.

11. Feature에는 예측 시점에서 실제로 알 수 있는 정보만 포함해야 하며, Target 발생 이후 정보를 포함하면 Data Leakage가 발생한다.

12. 모델 성능이 부족할 때 모든 개선 방법을 무조건 사용하는 것이 아니라 현재 문제가

```text
Underfitting
Overfitting
Class Imbalance
High Variance
Feature 문제
Hyperparameter 문제
```

중 무엇인지 먼저 진단해야 한다.

13. Time Series 문제에서는 데이터의 시간 순서를 유지해야 하며 미래 정보를 과거 Training에 포함시키면 안 된다.

14. 분석 결과에서 **관찰된 사실과 원인에 대한 해석을 구분**해야 한다.

15. Feature Importance와 SHAP은 모델이 어떤 Feature를 이용하여 예측했는지를 설명하지만 현실의 인과관계를 증명하지 않는다.

16. 좋은 분석의 목적은 결과표나 그래프 자체가 아니라 **실제로 어떤 행동을 해야 하는지 결정할 수 있는 근거를 만드는 것**이다.

17. 제품 개선안을 적용하기 전에는 가능하면 A/B Test 등의 실험을 통해 실제 효과가 있는지 검증하는 것이 좋다.

18. 실험에서도 Primary Metric만 보지 않고 다른 중요한 지표가 악화되지 않는지 Guardrail Metric을 함께 확인해야 한다.

19. 머신러닝 모델을 실제 서비스에 적용할 때는 학습할 때 사용한 전처리와 모델을 동일하게 재현할 수 있도록 Pipeline을 구성하는 것이 중요하다.

20. 모델의 예측 결과를 실제 업무에 사용하는 방법은 모델 성능뿐 아니라 **False Positive와 False Negative가 만들어내는 실제 비용과 사용자 영향**까지 고려하여 결정해야 한다.

21. 분석이나 모델을 실제 서비스에 적용한 이후에도 데이터와 사용자 행동은 계속 변하기 때문에 결과를 지속적으로 다시 측정해야 한다.

22. 운영 중에는 Data Drift와 Model Performance 변화를 확인하고 필요한 경우 재학습이나 재분석을 수행해야 한다.

23. Python, SQL, 통계, 프로덕트 분석, 머신러닝은 서로 독립된 기술이 아니라 다음 하나의 과정에서 연결되는 도구이다.

```text
문제 이해
    ↓
데이터 확보
    ↓
분석
    ↓
검증
    ↓
해석
    ↓
의사결정
    ↓
적용
    ↓
재측정
```

24. 데이터 사이언티스트에게 가장 중요한 능력은 특정 모델을 많이 아는 것이 아니라 다음 질문에 답할 수 있는 능력이다.

```text
현재 문제는 무엇인가?

어떤 데이터가 필요한가?

어떤 방법이 적절한가?

결과를 신뢰할 수 있는가?

결과는 무엇을 의미하는가?

이 결과로 무엇을 해야 하는가?

적용 이후 무엇을 다시 확인해야 하는가?
```
