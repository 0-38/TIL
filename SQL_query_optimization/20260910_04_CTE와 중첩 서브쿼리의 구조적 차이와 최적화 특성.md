# **1. CTE란?**

CTE(Common Table Expression)는 `WITH`절을 사용해 **쿼리의 중간 결과에 이름을 붙이는 방법**.

복잡한 SQL을 단계별로 나눌 수 있으며, 만들어진 CTE는 같은 SQL문 안에서 테이블처럼 사용 가능.

기본 구조:

```text
원본 데이터
    ↓
CTE
    ↓
최종 SELECT
```

[ sql : code ]

```sql
WITH expensive_products AS (
    SELECT
        product_id,
        product_name,
        list_price
    FROM products
    WHERE list_price >= 3000
)
SELECT
    product_id,
    product_name,
    list_price
FROM expensive_products
ORDER BY list_price DESC;
```

[ Result ]

```text
product_id | product_name      | list_price
-----------|-------------------|-----------
3          | Carbon Bike       | 5200
7          | Mountain Bike Pro | 4100
2          | Road Bike         | 3500
```

`expensive_products`라는 중간 결과를 만든 후 최종 `SELECT`에서 사용.

# **2. CTE 기본 문법**

CTE의 기본 문법:

```sql
WITH CTE이름 AS (
    SELECT ...
)
SELECT ...
FROM CTE이름;
```

CTE는 실제 테이블을 만드는 것이 아니라 **현재 SQL문 안에서만 사용할 수 있는 임시 결과 집합**.

[ sql : code ]

```sql
WITH seoul_customers AS (
    SELECT
        customer_id,
        first_name,
        city
    FROM customers
    WHERE city = 'Seoul'
)
SELECT
    customer_id,
    first_name,
    city
FROM seoul_customers;
```

[ Result ]

```text
customer_id | first_name | city
------------|------------|-------
101         | Minjun     | Seoul
105         | Jisoo      | Seoul
112         | Yuna       | Seoul
```

# **3. 여러 개의 CTE 연결**

하나의 `WITH`절 안에서 여러 개의 CTE를 작성할 수 있음.

CTE 사이에는 `,`를 사용.

뒤쪽 CTE에서는 앞쪽 CTE의 결과를 다시 참조 가능.

```text
CTE 1
  ↓
CTE 2
  ↓
최종 SELECT
```

[ sql : code ]

```sql
WITH product_sales AS (
    SELECT
        product_id,
        SUM(quantity) AS total_quantity
    FROM order_items
    GROUP BY product_id
),

popular_products AS (
    SELECT
        product_id,
        total_quantity
    FROM product_sales
    WHERE total_quantity >= 100
)

SELECT
    product_id,
    total_quantity
FROM popular_products
ORDER BY total_quantity DESC;
```

[ Result ]

```text
product_id | total_quantity
-----------|---------------
10         | 245
4          | 183
7          | 121
```

처리 흐름:

```text
order_items
      ↓
product_sales
상품별 판매량 계산
      ↓
popular_products
100개 이상 필터링
      ↓
최종 결과
```

# **4. CTE에서 JOIN과 GROUP BY 사용**

CTE 내부에서도 일반 SQL처럼 `JOIN`, `GROUP BY`, 집계함수 사용 가능.

예를 들어 고객별 총 구매금액 계산:

```text
구매금액 = 수량 × 가격
```

[ sql : code ]

```sql
WITH customer_totals AS (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
)

SELECT
    customer_id,
    total_amount
FROM customer_totals
ORDER BY total_amount DESC;
```

[ Result ]

```text
customer_id | total_amount
------------|-------------
103         | 82500
101         | 64300
108         | 51200
105         | 28400
```

처리 과정:

```text
orders
   +
order_items
      ↓
order_id 기준 JOIN
      ↓
customer_id별 GROUP BY
      ↓
SUM(quantity × price)
```

# **5. CTE를 이용한 단계별 필터링**

첫 번째 CTE에서 계산하고, 두 번째 CTE에서 조건을 적용하는 방식.

[ sql : code ]

```sql
WITH customer_totals AS (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
),

high_value_customers AS (
    SELECT
        customer_id,
        total_amount
    FROM customer_totals
    WHERE total_amount >= 50000
)

SELECT
    customer_id,
    total_amount
FROM high_value_customers
ORDER BY total_amount DESC;
```

[ Result ]

```text
customer_id | total_amount
------------|-------------
103         | 82500
101         | 64300
108         | 51200
```

처리 흐름:

```text
orders + order_items
        ↓
customer_totals
고객별 구매금액 계산
        ↓
high_value_customers
50,000 이상 필터링
        ↓
최종 조회
```

# **6. CTE와 일반 테이블 JOIN**

CTE는 최종 쿼리에서 일반 테이블과 JOIN 가능.

예를 들어 우수 고객의 이름과 도시 정보를 추가할 수 있음.

[ sql : code ]

```sql
WITH customer_totals AS (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
),

high_value_customers AS (
    SELECT
        customer_id,
        total_amount
    FROM customer_totals
    WHERE total_amount >= 50000
)

SELECT
    c.customer_id,
    c.first_name,
    c.city,
    h.total_amount
FROM high_value_customers h
JOIN customers c
    ON c.customer_id = h.customer_id
ORDER BY h.total_amount DESC;
```

[ Result ]

```text
customer_id | first_name | city   | total_amount
------------|------------|--------|-------------
103         | Alex       | Seoul  | 82500
101         | Mina       | Busan  | 64300
108         | John       | Seoul  | 51200
```

# **7. CTE 결과를 다시 GROUP BY**

CTE로 만든 결과를 다른 테이블과 JOIN한 후 다시 집계 가능.

예를 들어 도시별 우수 고객 수와 구매금액 계산.

[ sql : code ]

```sql
WITH customer_totals AS (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
),

high_value_customers AS (
    SELECT
        customer_id,
        total_amount
    FROM customer_totals
    WHERE total_amount >= 50000
)

SELECT
    c.city,
    COUNT(*) AS vip_customer_count,
    SUM(h.total_amount) AS vip_total_amount
FROM high_value_customers h
JOIN customers c
    ON c.customer_id = h.customer_id
GROUP BY c.city
ORDER BY vip_total_amount DESC;
```

[ Result ]

```text
city   | vip_customer_count | vip_total_amount
-------|--------------------|-----------------
Seoul  | 2                  | 133700
Busan  | 1                  | 64300
```

`customer_totals`에서 이미 고객별 한 행으로 만들어졌기 때문에 `COUNT(*)`로 우수 고객 수 계산 가능.

# **8. 서브쿼리와 CTE 비교**

같은 데이터 처리 로직은 서브쿼리와 CTE 모두 작성 가능.

### 서브쿼리

[ sql : code ]

```sql
SELECT
    customer_id,
    total_amount
FROM (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
) AS customer_totals
WHERE total_amount >= 50000
ORDER BY total_amount DESC;
```

[ Result ]

```text
customer_id | total_amount
------------|-------------
103         | 82500
101         | 64300
108         | 51200
```

### CTE

[ sql : code ]

```sql
WITH customer_totals AS (
    SELECT
        o.customer_id,
        SUM(oi.quantity * oi.price) AS total_amount
    FROM orders o
    JOIN order_items oi
        ON oi.order_id = o.order_id
    GROUP BY o.customer_id
)

SELECT
    customer_id,
    total_amount
FROM customer_totals
WHERE total_amount >= 50000
ORDER BY total_amount DESC;
```

[ Result ]

```text
customer_id | total_amount
------------|-------------
103         | 82500
101         | 64300
108         | 51200
```

두 SQL의 작성 형태는 다르지만 결과는 동일.

| 항목 | 서브쿼리 | CTE |
|---|---|---|
| 작성 방식 | SQL 내부에 중첩 | `WITH`에서 분리 |
| 단순한 로직 | 사용하기 편함 | 다소 길어질 수 있음 |
| 복잡한 로직 | 중첩이 많아질 수 있음 | 단계별 분리 가능 |
| 가독성 | 중첩이 깊으면 감소 | 비교적 좋음 |
| 재사용 | 동일 SQL 반복 가능 | 이름으로 다시 참조 가능 |
| 성능 | 실행계획에 따라 결정 | 실행계획에 따라 결정 |

# **9. CTE의 인라이닝 (Inlining)**

CTE를 작성했다고 해서 PostgreSQL이 항상 CTE를 먼저 별도로 실행하는 것은 아님.

PostgreSQL은 조건에 따라 CTE를 본문 쿼리에 합쳐 최적화 가능.

이를 **Inlining**이라고 함.

```text
작성한 SQL

CTE
 ↓
본문 SELECT


실제 처리

CTE + SELECT
     ↓
하나의 실행계획
```

[ sql : code ]

```sql
EXPLAIN
WITH expensive_products AS (
    SELECT
        product_id,
        product_name,
        list_price
    FROM products
    WHERE list_price >= 3000
)

SELECT *
FROM expensive_products
WHERE list_price >= 4000;
```

[ Result ]

```text
Seq Scan on products
  Filter: (list_price >= 4000)
```

위 예시처럼 별도의 `CTE Scan` 없이 원본 테이블에 대한 실행계획이 나타난다면 CTE가 인라이닝된 것으로 볼 수 있음.

> 실제 실행계획은 PostgreSQL 버전, 데이터 크기, 통계정보에 따라 달라질 수 있음.

# **10. MATERIALIZED**

`MATERIALIZED`는 CTE 결과를 **먼저 계산하여 중간 결과로 만든 뒤 사용하도록 지정**하는 기능.

[ sql : code ]

```sql
EXPLAIN
WITH expensive_products AS MATERIALIZED (
    SELECT
        product_id,
        product_name,
        list_price
    FROM products
    WHERE list_price >= 3000
)

SELECT *
FROM expensive_products
WHERE list_price >= 4000;
```

[ Result ]

```text
CTE Scan on expensive_products
  Filter: (list_price >= 4000)

  CTE expensive_products
    -> Seq Scan on products
         Filter: (list_price >= 3000)
```

처리 흐름:

```text
products
    ↓
3,000 이상 데이터 계산
    ↓
중간 결과 생성
    ↓
CTE Scan
    ↓
4,000 이상 필터링
```

이 방식을 **Materialization(구체화)**이라고 함.

<br><br>

---

# **11. Inlining과 Materialization 비교**

| 방식 | 설명 |
|---|---|
| `Inlining` | CTE와 본문을 합쳐 하나의 실행계획으로 최적화 |
| `Materialization` | CTE 결과를 먼저 계산한 후 중간 결과 사용 |
| `MATERIALIZED` | 구체화를 명시적으로 지정 |
| `CTE Scan` | 만들어진 CTE 결과를 읽는 실행 단계 |

개념:

```text
Inlining

CTE + 본문
    ↓
함께 최적화
```

```text
Materialization

CTE 계산
   ↓
중간 결과
   ↓
본문에서 사용
```

`MATERIALIZED`를 사용한다고 항상 성능이 좋아지는 것은 아님.

중간 결과를 생성하고 읽는 추가 비용이 발생할 수 있음.

# **12. NOT MATERIALIZED**

`NOT MATERIALIZED`는 CTE를 별도의 결과로 고정하지 않고 본문과 함께 최적화할 수 있도록 지정.

[ sql : code ]

```sql
EXPLAIN
WITH filtered_products AS NOT MATERIALIZED (
    SELECT
        product_id,
        product_name,
        list_price
    FROM products
    WHERE list_price >= 1000
)

SELECT *
FROM filtered_products
WHERE product_id = 100;
```

[ Result ]

```text
Index Scan using products_pkey on products
  Index Cond: (product_id = 100)
  Filter: (list_price >= 1000)
```

개념적으로:

```text
MATERIALIZED
→ CTE 결과 먼저 생성

NOT MATERIALIZED
→ 본문과 함께 최적화 가능
```

실제 처리 방식은 `EXPLAIN`으로 확인.

# **13. EXPLAIN과 EXPLAIN ANALYZE**

`EXPLAIN`은 PostgreSQL이 쿼리를 어떻게 실행할 예정인지 확인.

[ sql : code ]

```sql

FROM products
```


# **14. CTE 성능 비교 방법**

일반 CTE와 `MATERIALIZED`의 성능 차이를 확인할 때 `EXPLAIN ANALYZE` 사용.

### 일반 CTE

[ sql : code ]

```sql
EXPLAIN ANALYZE
WITH product_sales AS (
    SELECT
        product_id,
        SUM(quantity) AS total_quantity
    FROM order_items
    GROUP BY product_id
)

SELECT *
FROM product_sales
WHERE total_quantity >= 100;
```

[ Result ]

```text
HashAggregate
  Group Key: product_id
  Filter: (sum(quantity) >= 100)

Planning Time: 0.180 ms
```


# **15. CTE는 언제 사용하는가?**

CTE는 다음과 같이 여러 처리 단계가 있을 때 유용.

```text
원본 데이터
     ↓
JOIN
     ↓
GROUP BY
     ↓
필터링
     ↓
다른 테이블 JOIN
     ↓
최종 결과
```

예:

```text
고객별 구매금액 계산
        ↓
VIP 고객 필터링
        ↓
고객 정보 JOIN
        ↓
도시별 집계
```

장점:

- 복잡한 로직을 단계별로 분리
- 중간 결과에 의미 있는 이름 사용
- 쿼리 흐름 파악 용이
- 동일 중간 결과 재사용 가능
- 유지보수 용이

단순한 SQL이라면 무조건 CTE로 작성할 필요는 없음.

# **16. CTE 이름 작성 방법**

CTE 이름은 **해당 결과가 무엇을 의미하는지 알 수 있도록 작성**하는 것이 좋음.

좋은 예:

```text
customer_totals
high_value_customers
product_sales
popular_products
monthly_sales
low_stocks
```

좋지 않은 예:

```text
cte1
cte2
data
temp
result
```

복잡한 SQL일수록 의미 있는 이름이 중요.

# **17. CTE 재사용**

하나의 CTE를 같은 SQL문에서 여러 번 참조 가능.

[ sql : code ]

```sql
WITH city_sales AS (
    SELECT
        city,
        SUM(amount) AS total_amount
    FROM sales
    GROUP BY city
)

SELECT
    a.city,
    a.total_amount
FROM city_sales a
WHERE a.total_amount > (
    SELECT AVG(b.total_amount)
    FROM city_sales b
)
ORDER BY a.total_amount DESC;
```

[ Result ]

```text
city   | total_amount
-------|-------------
Seoul  | 950000
Busan  | 720000
Daegu  | 610000
```

같은 `city_sales` 결과를:

```text
a
b
```

두 번 참조.

다만 CTE를 여러 번 참조할 때 실제 계산 방식은 실행계획을 통해 확인하는 것이 좋음.

# **18. 재귀 CTE**

`WITH RECURSIVE`를 사용하면 CTE가 자신의 결과를 다시 참조할 수 있음.

계층 구조나 반복적인 데이터를 처리할 때 사용.

[ sql : code ]

```sql
WITH RECURSIVE numbers AS (
    SELECT 1 AS num

    UNION ALL

    SELECT num + 1
    FROM numbers
    WHERE num < 5
)

SELECT *
FROM numbers;
```

[ Result ]

```text
num
---
1
2
3
4
5
```

처리 과정:

```text
1 생성
 ↓
2 생성
 ↓
3 생성
 ↓
4 생성
 ↓
5 생성
 ↓
종료
```

활용 예:

- 조직도
- 카테고리 계층
- 폴더 구조
- 부모 / 자식 관계
- 연속된 숫자나 날짜 생성

# **19. CTE와 임시 테이블 차이**

CTE와 Temporary Table은 서로 다른 개념.

| 항목 | CTE | TEMP TABLE |
|---|---|---|
| 사용 범위 | 하나의 SQL문 | 현재 세션의 여러 SQL문 |
| 생성 방식 | `WITH` | `CREATE TEMP TABLE` |
| 실제 테이블 생성 | X | O |
| 여러 SQL에서 사용 | X | O |
| 인덱스 생성 | 직접 불가 | 가능 |
| 목적 | 쿼리 구조화 | 중간 데이터를 실제로 저장하여 재사용 |

CTE:

```text
하나의 SQL 내부 로직 분리
```

TEMP TABLE:

```text
중간 결과를 여러 SQL에서 계속 사용
```

# **20. CTE 작성 시 주의점**

CTE를 사용했다고 무조건 성능이 좋아지는 것은 아님.

성능에 영향을 주는 요소:

```text
데이터 크기
JOIN 구조
필터 조건
집계 연산
인덱스
CTE 참조 횟수
Inlining 여부
Materialization 여부
PostgreSQL 버전
```

따라서:

```text
CTE가 항상 빠름 → X

서브쿼리가 항상 빠름 → X
```

실제 성능은:

```sql
EXPLAIN ANALYZE
```

로 비교하는 것이 가장 중요.

# **21. CTE 사용 판단 흐름**

```text
쿼리가 단순한가?
       │
       ├── YES
       │     ↓
       │ 일반 SELECT 또는 서브쿼리
       │
       └── NO
             ↓
      처리 단계가 여러 개인가?
             │
             ├── YES → CTE 고려
             │
             └── NO
                   ↓
      중간 결과를 재사용하는가?
             │
             ├── YES → CTE 고려
             └── NO → 상황에 따라 결정
                   
                   ↓
           성능 확인 필요
                   ↓
          EXPLAIN ANALYZE
```

# **22. 핵심 정리**

- **CTE**는 `WITH 이름 AS (...)` 형태로 중간 결과에 이름을 붙이는 방법.
- CTE는 같은 SQL문 안에서 테이블처럼 사용 가능.
- 여러 CTE는 `,`로 연결 가능.
- 뒤쪽 CTE에서 앞쪽 CTE를 참조 가능.
- CTE 내부에서 `JOIN`, `GROUP BY`, `SUM`, `WHERE` 등의 SQL 기능 사용 가능.
- 여러 단계의 복잡한 SQL을 분리할 때 가독성이 좋아짐.
- CTE와 서브쿼리는 같은 결과를 만들 수 있음.
- CTE를 사용했다고 반드시 CTE가 먼저 별도로 실행되는 것은 아님.
- CTE가 본문 쿼리와 합쳐져 최적화되는 방식을 **Inlining**이라고 함.
- `MATERIALIZED`는 CTE 결과를 먼저 계산하여 중간 결과로 만드는 방식.
- 구체화된 CTE는 실행계획에서 `CTE Scan`이 나타날 수 있음.
- `NOT MATERIALIZED`를 사용하면 본문과 함께 최적화되도록 허용 가능.
- `MATERIALIZED`가 항상 더 빠른 것은 아님.
- 실행계획은 `EXPLAIN`으로 확인.
- 실제 실행 성능은 `EXPLAIN ANALYZE`로 확인.
- `WITH RECURSIVE`를 사용하면 계층형 및 반복 구조 처리 가능.
- 간단한 SQL까지 무조건 CTE로 나눌 필요는 없음.
- 복잡한 분석에서는 **계산 → 필터링 → JOIN → 집계 → 최종 조회**처럼 단계별 CTE를 사용하면 이해하기 쉬움.
