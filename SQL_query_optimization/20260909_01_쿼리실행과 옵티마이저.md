# **[ 0. DDL과 DML의 차이 ]**

- DDL : 테이블의 구조를 만드는 작업


#### [ sql : code ] **테이블 생성 (DDL)**   
```sql
CREATE TABLE projects (
    project_id INT PRIMARY KEY,
    project_name VARCHAR(100) NOT NULL
) ;
```

- DML : 테이블 안의 데이터를 다루는 작업


#### [ sql : code ] **테이블 안의 데이터 추가 (DML)**   
```sql
--- 데이터 삽입

INSERT INTO projects (project_id, project_name)
VALUES (1, 'AI 챗봇 개발') ;
```

#### [ Result ]
```
projects 테이블 생성

project_id | project_name
-----------|-------------
1          | AI 챗봇 개발
```


#### [ DDL / DML 차이 ]
|구분|	이름|	역할|	대표 명령어|
|---|---|---|---|
|DDL|	Data Definition Language|	데이터베이스 구조(테이블, 스키마 등)를 정의·변경·삭제|`	CREATE`, `ALTER`, `DROP`|
|DML|	Data Manipulation Language|	테이블 내 데이터를 조회·삽입·수정·삭제|	`SELECT`, `INSERT`, `UPDATE`, `DELETE`|

# **[ 1. SQL 실행 흐름: 파싱부터 실행까지 ]**

- 단 한줄의 코드라도 SQL의 데이터베이스 내부에서는 이 코드를 어떻게 처리할지 고민을 한다.

- 그 흐름의 과정이 파싱-> 옵티마이저 -> 실행의 순서대로 거친다.

### 1단계: 파싱(Parsing)
- 데이터베이스가 SQL 문법에 문제가 없는지 확인

```sql
SELECCT *
FROM orders
WHERE wrong_column = 900 ;
```

```
SQL Error [42703]: 오류 "wrong_column" 이름의 칼럼은 없습니다 

> 만약 테이블에 찾으려고 하는 컬럼이 없으면 오류가 발생한다.
```


<br>

### 2단계: 옵티마이저(Optimizer)
- SQL 문법에 문제가 없다면 데이터베이스는 데이터를 어떤 방법으로 찾을지 결정한다.

- 예를들어, 다음과 같은 방법으로 확인할 수 있다.
    > 방법 1 : orders 테이블을 순서대로 확인한다.

    > 방법 2 : order_id에 사용할 수 있는 인덱스를 이용한다. 

    이 중 어떤 방법으로 실행할지는 옵티마이저가 결정한다.

<br>

### 3단계 실행(Execution)
- 마지막으로 선택된 실행계획에 따라 실제 데이터를 읽고 결과를 반환한다

- 실제 데이터에 접근하는 과정

```text
SQL 작성
   ↓
파싱: 문법, 테이블, 컬럼 확인
   ↓
최적화:데이터를 가져올 방법 결정
   ↓
실행:실제 데이터 조회
   ↓
결과 반환
```

# **[ 2. 옵티마이저 (Optimizer) ]**

- 결과를 낼때, 여러 실행계획 중에 가장 좋은 계획을 뽑아 실행하게끔 하는 DBMS의 구성요소

#### [옵티마이저의 데이터 조회 방법]
- 방법 1 : 테이블 순서대로 확인
   - 테이블의 데이터를 확인하면서 조건에 맞는 고객을 찾는 방식

- 방법 2 : 인덱스를 이용하여 탐색
   - 사용할 수 있는 인덱스가 있다면 인덱스를 이용하여 데이터를 찾는 방식

> 옵티마이저(Optimizer) : 데이터를 조회할 때 여러 실행방법을 검토하고 적절한 방법을 선택하는 역할

> 실행게획(Executation Plan) : 옵티마이저가 최종적으로 선택한 구체적인 SQL 실행방법

#### [옵티마이저의 실행계획]
```text
SQL
 ↓
옵티마이저
 ├─ 테이블을 순서대로 읽을까?
 └─ 인덱스를 사용할까?
 ↓
실행계획 선택
 ↓
실제 실행
```

# **[ 3. 쿼리 최적화가 실무에서 중요한 이유 ]**

```
[ 주문 데이터가 적을 때 ]                   [ 주문 데이터가 많아졌을 때 ]

      SQL 실행                                     SQL 실행
         ↓                                           ↓
   확인해야 할 데이터가 적음                       많은 데이터 확인
         ↓                                           ↓
   빠르게 결과 반환                         CPU / 메모리 / 디스크 작업 증가
                                                     ↓
                                                 응답시간 증가
```

- 동시에 여러 사용자가 비효율적인 쿼리를 실행하게 되면 데이터베이스의 자원을 많이 사용하게된다.

- 이는 다른 정상적인 쿼리까지 영향을 받을 수 있다. 

```
느린 쿼리
   ↓
데이터베이스 자원 사용 증가
   ↓
다른 쿼리도 영향을 받음
   ↓
서비스 전체 응답 속도 저하
```

- 느린 쿼리는 데이터베이스 서버의 CPU와 메모리를 과도하게 사용하게 된다.

- 클라우드 환경에서는 비효율적인 쿼리가 곧바로 인프라 비용 증가로 이어지게 된다.

- 따라서 효율적인 쿼리는 서비스 안정성과 운영비용 절감에 직결된다.
