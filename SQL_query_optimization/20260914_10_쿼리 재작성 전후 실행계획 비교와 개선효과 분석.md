# **1. 쿼리 튜닝 전 기준 성능 기록하기**

쿼리 튜닝에서 가장 먼저 해야 하는 일은 바로 인덱스를 만들거나 SQL을 수정하는 것이 아니라 **현재 상태를 측정하고 기록하는 것**이다.

튜닝 전 결과가 없으면 개선 후 실행 시간이 줄어들었더라도 실제로 얼마나 좋아졌는지 비교할 기준이 없다.

따라서 기본적인 튜닝 흐름은 다음과 같다.

```text
현재 성능 측정
      ↓
병목 확인
      ↓
개선 가설 설정
      ↓
인덱스 추가 또는 SQL 재작성
      ↓
동일한 조건으로 재측정
      ↓
개선 전후 비교
```

<br>

> ## **1-1 ) EXPLAIN ANALYZE로 기준값 측정**

`EXPLAIN ANALYZE`를 사용하면 PostgreSQL이 선택한 실행계획뿐 아니라 실제 실행 시간도 확인할 수 있다.

튜닝 전에는 최소한 다음 정보를 기록해두는 것이 좋다.

| 기록 항목 | 의미 |
|---|---|
| Scan 방식 | 데이터를 어떤 방법으로 읽는지 확인 |
| `cost` | PostgreSQL이 예상한 상대적인 비용 |
| 예상 `rows` | PostgreSQL이 예상한 처리 행 수 |
| 실제 `rows` | 실제 처리된 행 수 |
| `actual time` | 각 노드의 실제 실행 시간 |
| `Execution Time` | 전체 SQL 실행 시간 |
| `Buffers` | 메모리·디스크 접근 정보 |
| 병목 노드 | 가장 많은 시간이나 데이터를 처리하는 구간 |

<br>

> ## **1-2 ) 튜닝 전 실행계획 예제**

[ sql : code ] "특정 축구 선수의 경기 이벤트를 조회하기 전 현재 성능 측정"

```sql
EXPLAIN ANALYZE
SELECT
    event_id,
    player_id,
    event_type,
    event_time
FROM soccer_events
WHERE player_id = 50;
```

[ Result ]

※ 아래 실행계획은 학습을 위한 예시이며 실제 결과는 데이터 크기와 인덱스 상태에 따라 달라질 수 있다.

```text
Gather
(cost=1000.00..19306.87 rows=4775 width=24)
(actual time=0.555..256.860 rows=4689 loops=1)

  Workers Planned: 2
  Workers Launched: 2

  -> Parallel Seq Scan on soccer_events
       (cost=0.00..17829.37 rows=1990 width=24)
       (actual time=0.017..34.207 rows=1563 loops=3)

       Filter: (player_id = 50)
       Rows Removed by Filter: 511741

Planning Time: 0.162 ms
Execution Time: 257.162 ms
```

### 결과 해석

현재 주요 조회 방식은 다음과 같다.

```text
Parallel Seq Scan
```

즉, 여러 작업자가 `soccer_events` 테이블을 나누어 읽고 `player_id = 50`에 해당하는 행을 찾고 있다.

조회 결과는 약 `4,689행`인데, 조건에 맞지 않아 제거된 데이터는 매우 많다.

```text
Rows Removed by Filter: 511741
```

따라서 다음과 같이 기준 성능을 기록할 수 있다.

| 항목 | 튜닝 전 |
|---|---:|
| Scan 방식 | `Parallel Seq Scan` |
| 실제 조회 행 | 4,689 |
| 조건에서 제거된 행 | 511,741 |
| Execution Time | 257.162 ms |

### 실행 흐름

```text
soccer_events 대량 데이터 읽기 (Seq Scan)
             ↓
      player_id = 50 검사
             ↓
   필요 없는 행 대량 제거
             ↓
        4,689행 반환
             ↓
    Execution Time 약 257ms
```

이 결과가 이후 인덱스를 추가하거나 SQL을 재작성했을 때 비교하는 **Baseline, 즉 기준값**이 된다.

# **2. 개선 가설 설정과 변경 적용**

> ## **2-1 ) 튜닝은 가설을 세우고 진행한다**

튜닝은 단순히

```text
느리다 → 인덱스 생성
```

으로 진행하는 것이 아니다.

실행계획을 확인한 후 문제 원인을 추정하고 개선 방법에 대한 가설을 세우는 것이 중요하다.

예를 들어 다음 상황을 발견했다고 하자.

```text
큰 테이블
+
특정 player_id 몇 개만 조회
+
Parallel Seq Scan
+
많은 Rows Removed by Filter
```

이 경우 다음과 같은 가설을 세울 수 있다.

```text
player_id 조건으로 일부 행만 반복 조회한다.
        ↓
player_id 인덱스를 생성하면
전체 테이블을 읽지 않고 필요한 위치를 빠르게 찾을 수 있지 않을까?
```

<br>

> ## **2-2 ) 인덱스 추가**

[ sql : code ] "축구 선수 번호를 기준으로 빠르게 경기 이벤트를 찾을 수 있도록 인덱스 생성"

```sql
CREATE INDEX idx_soccer_events_player_id
ON soccer_events(player_id);
```

인덱스 생성 후 반드시 같은 쿼리를 다시 측정한다.

[ sql : code ] "인덱스 생성 후 동일한 조건에서 실행계획 재측정"

```sql
EXPLAIN ANALYZE
SELECT
    event_id,
    player_id,
    event_type,
    event_time
FROM soccer_events
WHERE player_id = 50;
```

[ Result ]

```text
Index Scan using idx_soccer_events_player_id
on soccer_events

(cost=0.43..188.55 rows=4775 width=24)
(actual time=0.041..5.821 rows=4689 loops=1)

Index Cond: (player_id = 50)

Planning Time: 0.188 ms
Execution Time: 6.147 ms
```

### 결과 해석

개선 전 Scan 방식은

```text
Parallel Seq Scan
```

이었지만 개선 후 Scan 방식은

```text
Index Scan using idx_soccer_events_player_id
```

로 변경되었다.

또한

```text
Index Cond: (player_id = 50)
```

을 통해 `player_id = 50` 조건에 인덱스가 실제로 사용되고 있음을 확인할 수 있다.

### 실행 흐름 변화

```text
[ 개선 전 ]

soccer_events 전체 범위 탐색
        ↓
player_id 하나씩 검사
        ↓
불필요한 행 대량 제거
        ↓
결과 반환


[ 개선 후 ]

player_id 인덱스 탐색
        ↓
player_id = 50 위치 확인
        ↓
필요한 행 조회
        ↓
결과 반환
```

<br>

> ## **2-3 ) 한 번에 하나씩 변경하는 이유**

성능 개선 과정에서는 가능하면 **한 번에 하나의 요소만 변경**하는 것이 좋다.

예를 들어 다음 세 작업을 동시에 했다고 생각해보자.

```text
인덱스 추가
+
서브쿼리 JOIN으로 변경
+
ORDER BY 제거
```

실행 시간이 크게 감소하더라도 **어떤 변경이 실제 성능 개선에 가장 큰 영향을 주었는지 판단하기 어렵다.**

따라서 다음과 같은 방식이 좋다.

```text
Baseline 측정
     ↓
인덱스 하나 추가
     ↓
재측정
     ↓
결과 기록
     ↓
SQL 구조 변경
     ↓
재측정
```

이를 통해 **원인과 결과를 명확하게 연결**할 수 있다.

# **3. 개선 전후 실행계획 비교하기**

> ## **3-1 ) 스캔 방식 비교**

가장 먼저 확인할 수 있는 것은 실행 방식의 변화이다.

```text
개선 전
Parallel Seq Scan
        ↓
개선 후
Index Scan
```

이를 표로 정리하면 다음과 같다.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| Scan | `Parallel Seq Scan` | `Index Scan` |
| 검색 방법 | 테이블의 많은 데이터를 읽음 | 인덱스에서 필요한 위치 탐색 |
| 조건 처리 | 행을 읽은 뒤 필터 | 인덱스 조건으로 바로 탐색 |
| 불필요한 읽기 | 많을 수 있음 | 상대적으로 감소 가능 |

단, 다음과 같이 이해하면 안 된다.

```text
Seq Scan = 항상 나쁨 X
Index Scan = 항상 좋음 X
```

전체 데이터의 대부분을 조회하는 쿼리에서는 PostgreSQL이 오히려 `Seq Scan`을 선택하는 것이 더 효율적일 수 있다.

<br>

> ## **3-2 ) cost 비교**

예를 들어 개선 전후의 주요 노드가 다음과 같다고 하자.

```text
개선 전
cost=0.00..1400.00

개선 후
cost=0.42..190.00
```

총 `cost`는 다음처럼 비교할 수 있다.

```text
개선 전 총 cost = 1400.00
개선 후 총 cost = 190.00
```

비용 감소율을 계산하면

```text
(1400 - 190) ÷ 1400 × 100
≈ 86.4%
```

약 `86.4%` 감소했다고 볼 수 있다.

하지만 `cost`는 실제 실행 시간이 아니다.

```text
cost
→ PostgreSQL의 예상 비용

Execution Time
→ 실제 실행 시간
```

따라서 성능 개선 여부는 `cost`뿐 아니라 반드시 실제 실행 시간을 함께 확인해야 한다.

<br>

> ## **3-3 ) Execution Time 비교**

예를 들어 다음과 같이 측정되었다고 하자.

```text
개선 전
Execution Time: 257.162 ms

개선 후
Execution Time: 6.147 ms
```

실행 시간 감소율은 다음 공식으로 계산한다.

```text
(개선 전 실행시간 - 개선 후 실행시간) ÷ 개선 전 실행시간 × 100
```

계산하면

```text
(257.162 - 6.147) ÷ 257.162 × 100

≈ 97.6%
```

즉, 예시 결과에서는 실행 시간이 약 `97.6% 감소`한 것이다.

또는 몇 배 빨라졌는지 계산할 수도 있다.

```text
개선 전 실행시간 ÷ 개선 후 실행시간

= 257.162 ÷ 6.147

≈ 41.8
```

약 `41.8배` 빠르게 실행된 것으로 표현할 수 있다.

# **4. 개선 전후 비교 보고서 작성**

> ## **4-1 ) 비교 보고서의 기본 구조**

튜닝 결과는 단순히

```text
인덱스를 만들어서 빨라졌다.
```

라고 작성하는 것보다 객관적인 측정값으로 비교해야 한다.

다음과 같은 표를 활용하면 효과적이다.

| 항목 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| Scan 방식 | `Parallel Seq Scan` | `Index Scan` | 인덱스 조회로 변경 |
| 주요 노드 cost | 19306.87 | 188.55 | 크게 감소 |
| Actual Rows | 4,689 | 4,689 | 동일 |
| Execution Time | 257.162 ms | 6.147 ms | 약 97.6% 감소 |
| 주요 조건 | Filter | Index Cond | 인덱스 조건 활용 |

조회 결과 행이 동일하면서 실행 방식과 시간이 개선되었다면 튜닝 전후 비교의 신뢰도가 높아진다.

<br>

> ## **4-2 ) 보고서 문장 작성 예제**

다음과 같이 정리할 수 있다.

```text
player_id 조건에 인덱스를 적용한 결과,
실행계획의 조회 방식이 Parallel Seq Scan에서 Index Scan으로 변경되었다.

동일한 4,689개의 행을 조회하는 조건에서
Execution Time은 257.162ms에서 6.147ms로 감소하여
약 97.6%의 실행 시간 감소를 확인하였다.

따라서 해당 조회 패턴에서는 player_id 인덱스가
실제 조회 성능 개선에 효과가 있는 것으로 판단된다.
```

성능 튜닝 보고서에는 **변경 내용 + 실행계획 변화 + 숫자 + 판단**이 함께 들어가는 것이 좋다.

# **5. 쿼리 재작성 전후 비교하기**

> ## **5-1 ) 상관 서브쿼리 재작성 예제**

튜닝은 인덱스 추가뿐 아니라 SQL 자체를 변경하여 진행할 수도 있다.

다음은 농구 선수별 평균 득점을 조회하는 예제이다.

[ sql : code ] "선수마다 평균 득점을 계산하기 위해 상관 서브쿼리를 사용하는 방식"

```sql
SELECT
    p.player_id,
    p.player_name,
    (
        SELECT AVG(g.points)
        FROM game_stats g
        WHERE g.player_id = p.player_id
    ) AS avg_points
FROM players p;
```

실행계획에서 다음과 같은 구조가 나타날 수 있다.

[ Result ]

```text
Seq Scan on players p
  SubPlan 1
    -> Aggregate
         -> Seq Scan on game_stats g
              Filter: (player_id = p.player_id)
```

### 실행 흐름

```text
선수 1명 조회
    ↓
game_stats 탐색
    ↓
평균 계산

선수 2명 조회
    ↓
game_stats 탐색
    ↓
평균 계산

선수 3명 조회
    ↓
game_stats 탐색
    ↓
평균 계산

...
```

`players`의 행이 많아질수록 `SubPlan`이 반복될 가능성이 있다.

<br>

> ## **5-2 ) GROUP BY + JOIN으로 재작성**

[ sql : code ] "경기 기록을 선수별로 먼저 집계한 후 선수 정보와 조인"

```sql
SELECT
    p.player_id,
    p.player_name,
    g.avg_points
FROM players p
LEFT JOIN (
    SELECT
        player_id,
        AVG(points) AS avg_points
    FROM game_stats
    GROUP BY player_id
) g
    ON p.player_id = g.player_id;
```

[ Result ]

예를 들어 실행계획이 다음처럼 변경될 수 있다.

```text
Hash Left Join
  Hash Cond: (p.player_id = g.player_id)

  -> Seq Scan on players p

  -> Hash
       -> HashAggregate
            Group Key: game_stats.player_id
            -> Seq Scan on game_stats
```

### 실행 흐름

```text
game_stats 전체 조회
        ↓
player_id별 평균 계산
        ↓
선수별 집계 결과 생성
        ↓
players와 Hash Join
        ↓
최종 결과
```

### 두 방식 비교

| 항목 | 상관 서브쿼리 | 집계 후 JOIN |
|---|---|---|
| 주요 실행 노드 | `SubPlan` | `HashAggregate`, `Hash Join` |
| 데이터 조회 | 선수마다 반복될 수 있음 | 전체 데이터를 한 번 집계 |
| 반복 처리 | 많아질 수 있음 | 상대적으로 감소 가능 |
| 항상 더 빠른가? | X | X |
| 최종 판단 | `EXPLAIN ANALYZE` 필요 | `EXPLAIN ANALYZE` 필요 |

중요한 것은 `JOIN`으로 바꾸면 무조건 빨라진다는 것이 아니라 **실제로 실행계획과 실행 시간이 개선되는지 비교하는 것**이다.

# **6. 인덱스가 항상 성능을 개선하지 않는 이유**

> ## **6-1 ) 조회되는 데이터 비율이 높은 경우**

다음 쿼리를 생각해보자.

```sql
SELECT *
FROM running_records
WHERE gender = 'M';
```

만약 전체 데이터의 약 70%가 `gender = 'M'`이라면 인덱스를 사용하여 많은 행을 하나씩 찾는 것보다 전체 테이블을 순차적으로 읽는 것이 더 효율적일 수 있다.

```text
전체 1,000,000행
       ↓
조건 만족 700,000행
       ↓
전체 데이터의 70%
```

이런 경우 PostgreSQL이 `Seq Scan`을 선택하더라도 잘못된 실행계획이라고 볼 수 없다.

<br>

> ## **6-2 ) 인덱스의 추가 비용**

인덱스는 조회 속도 향상에 도움을 줄 수 있지만 무료로 유지되는 것은 아니다.

| 작업 | 인덱스 영향 |
|---|---|
| `SELECT` | 특정 조회에서 성능 개선 가능 |
| `INSERT` | 새 인덱스 값도 함께 추가 |
| `UPDATE` | 인덱스 대상 값 변경 시 갱신 필요 |
| `DELETE` | 인덱스에서도 데이터 제거 필요 |
| 저장 공간 | 추가 디스크 공간 사용 |

따라서 인덱스가 너무 많으면 조회 성능은 일부 개선되더라도 데이터 입력·수정 성능이 저하될 수 있다.

```text
인덱스가 많을수록 무조건 좋다 X

자주 사용하는 조회 패턴을 기준으로
필요한 인덱스를 설계한다 O
```

<br>

> ## **6-3 ) 인덱스를 만들었는데 Seq Scan이 유지되는 경우**

인덱스를 생성한 후에도 다음과 같은 결과가 나올 수 있다.

```text
Seq Scan on athlete_records
```

가능한 이유는 다양하다.

| 이유 | 설명 |
|---|---|
| 조회 비율이 높음 | 대부분의 행을 가져와야 함 |
| 테이블이 작음 | 전체를 읽는 비용 자체가 낮음 |
| 통계 정보 | 옵티마이저가 Seq Scan이 더 저렴하다고 판단 |
| 조건 구조 | 생성한 인덱스를 효과적으로 사용하기 어려움 |
| 데이터 분포 | 특정 값이 지나치게 많이 존재 |

따라서 중요한 것은

```text
CREATE INDEX 성공
```

여부가 아니라

```text
EXPLAIN ANALYZE에서
실제로 성능이 개선되었는가?
```

이다.

# **7. 공정하게 튜닝 전후를 비교하는 방법**

> ## **7-1 ) 동일한 조건으로 측정하기**

성능 비교는 가능한 한 같은 조건에서 진행해야 한다.

```text
동일한 SQL
동일한 WHERE 조건
동일한 데이터
동일한 DB 환경
```

예를 들어 개선 전에는

```sql
WHERE player_id = 50
```

을 사용하고 개선 후에는

```sql
WHERE player_id = 3
```

을 사용했다면 데이터 분포가 다르기 때문에 정확한 비교가 어려울 수 있다.

<br>

> ## **7-2 ) 한 번의 실행시간만 맹신하지 않기**

SQL 실행 시간은 다음과 같은 요소의 영향을 받을 수 있다.

```text
캐시 상태
DB 서버 부하
디스크 상태
동시 실행 쿼리
메모리 상황
```

따라서 한 번 실행한 결과가

```text
100ms
```

였다고 해서 항상 100ms가 걸린다고 볼 수 없다.

실무에서는 여러 번 측정하여 실행 시간의 변화를 확인하는 것이 좋다.

```text
1차: 42ms
2차: 37ms
3차: 39ms
4차: 38ms
5차: 40ms
```

이 경우 평균 실행시간 등을 참고할 수 있다.

```text
평균 ≈ 39.2ms
```

<br>

> ## **7-3 ) Planning Time과 Execution Time 구분**

`EXPLAIN ANALYZE`에는 다음 두 시간이 나타날 수 있다.

```text
Planning Time: 0.188 ms
Execution Time: 6.147 ms
```

| 항목 | 의미 |
|---|---|
| `Planning Time` | 실행계획을 생성하는 데 사용된 시간 |
| `Execution Time` | 실제 SQL을 실행하는 데 사용된 시간 |

쿼리 자체의 실행 성능을 비교할 때는 일반적으로 `Execution Time`을 중심으로 확인한다.

# **8. 튜닝 사이클**

> ## **8-1 ) 전체 튜닝 과정**

튜닝은 한 번의 변경으로 끝나는 작업이라기보다 반복적으로 진행되는 과정이다.

```text
① 느린 SQL 발견
       ↓
② EXPLAIN ANALYZE 실행
       ↓
③ Baseline 기록
       ↓
④ 병목 노드 확인
       ↓
⑤ 개선 가설 설정
       ↓
⑥ 한 가지 변경 적용
       ↓
⑦ EXPLAIN ANALYZE 재실행
       ↓
⑧ 개선 전후 비교
       ↓
⑨ 효과 판단
       ↓
⑩ 남은 병목 확인
       ↓
필요하면 다시 개선
```

이를 **튜닝 사이클(Tuning Cycle)** 이라고 볼 수 있다.

<br>

> ## **8-2 ) 결과가 개선되지 않은 경우**

튜닝 후에도 실행 시간이 거의 달라지지 않을 수 있다.

```text
개선 전
Execution Time: 120ms

개선 후
Execution Time: 118ms
```

이 경우 실행시간 감소율은 매우 작다.

따라서

```text
"인덱스를 만들었다."
```

가 아니라

```text
"인덱스를 만들었지만 실행계획 또는 실행시간에
유의미한 변화가 없었다."
```

라고 판단하는 것이 더 정확하다.

튜닝에서 **개선되지 않았다는 결과 역시 중요한 분석 결과**이다.

<br><br>

# **9. 실행계획 비교 체크리스트**

> ## **9-1 ) 개선 전후 반드시 확인할 항목**

| 확인 항목 | 확인 질문 |
|---|---|
| Scan 방식 | `Seq Scan`에서 `Index Scan` 등으로 변경되었는가? |
| Join 방식 | 조인 방법이 변경되었는가? |
| Sort | 불필요한 정렬이 줄었는가? |
| `cost` | 예상 비용이 어떻게 달라졌는가? |
| 예상 `rows` | 옵티마이저의 예상 행 수가 적절한가? |
| 실제 `rows` | 실제 처리 데이터량은 얼마나 되는가? |
| `actual time` | 어떤 노드가 실제 시간을 많이 소비하는가? |
| `loops` | 반복 횟수가 감소했는가? |
| `Execution Time` | 실제 전체 실행시간이 감소했는가? |
| `Buffers` | 불필요한 블록 읽기가 감소했는가? |
| 결과값 | 튜닝 전후 SQL 결과가 동일한가? |

특히 쿼리를 재작성한 경우에는 성능뿐 아니라 **SQL 결과 자체가 동일한지**도 반드시 확인해야 한다.

```text
빠르지만 결과가 달라졌다
→ 잘못된 튜닝

같은 결과
+
실행시간 감소
→ 올바른 성능 개선 가능성
```

# **10. Advanced 추가 학습**

> ## **10-1 ) EXPLAIN (ANALYZE, BUFFERS)**

조금 더 자세한 튜닝에서는 다음과 같이 `BUFFERS` 옵션을 사용할 수 있다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM soccer_events
WHERE player_id = 50;
```

`BUFFERS`를 사용하면 실행시간뿐 아니라 데이터 블록을 메모리에서 읽었는지, 디스크에서 읽었는지 등을 추가로 확인할 수 있다.

```text
shared hit
→ 이미 메모리에 있던 데이터를 사용

shared read
→ 디스크에서 데이터를 읽음
```

초기 학습에서는 `Execution Time`과 실행계획 변화를 먼저 익히고 이후 함께 확인하면 된다.

<br>

> ## **10-2 ) 캐시 효과**

같은 SQL을 연속해서 실행하면 두 번째 실행이 더 빨라질 수 있다.

첫 실행에서 디스크 데이터를 메모리로 읽어놓았기 때문이다.

따라서 매우 정밀한 성능 테스트에서는 단순히 SQL 한 번의 결과만 비교하기보다 여러 번 실행하거나 캐시 상태까지 고려해야 한다.

<br>

> ## **10-3 ) 개선율과 속도 향상 배수**

성능 개선은 두 가지 방식으로 표현할 수 있다.

```text
실행시간 감소율
=
(개선 전 - 개선 후)
÷ 개선 전
× 100
```

```text
속도 향상 배수
=
개선 전 실행시간
÷ 개선 후 실행시간
```

예를 들어

```text
100ms → 20ms
```

라면

```text
실행시간 감소율
= 80%

속도 향상
= 5배
```

라고 표현할 수 있다.

# **11. 핵심정리**

- SQL 튜닝은 변경부터 시작하는 것이 아니라 먼저 `EXPLAIN ANALYZE`를 이용하여 **튜닝 전 기준값(Baseline)** 을 기록하는 것부터 시작한다.
- 기준값에는 `Scan`, `cost`, `rows`, `actual time`, `Execution Time` 등의 정보를 기록하는 것이 좋다.
- 튜닝은 **문제 확인 → 가설 설정 → 변경 → 재측정 → 비교** 순서로 진행한다.
- 한 번에 여러 요소를 변경하면 무엇이 실제 성능 개선에 영향을 주었는지 알기 어렵기 때문에 가능하면 하나씩 변경한다.
- 인덱스를 생성한 후에는 실제 실행계획에서 `Index Scan`, `Bitmap Index Scan` 등이 선택되었는지 확인한다.
- 인덱스를 생성했다고 항상 인덱스가 사용되는 것은 아니다.
- 많은 데이터를 조회하는 상황에서는 `Seq Scan`이 `Index Scan`보다 더 효율적일 수도 있다.
- `cost`는 PostgreSQL이 계산한 예상 상대 비용이며 실제 실행시간을 의미하지 않는다.
- 실제 성능 개선 판단에서는 `Execution Time`이 중요한 실측값이다.
- 개선율은 `(개선 전 시간 - 개선 후 시간) ÷ 개선 전 시간 × 100`으로 계산할 수 있다.
- `100ms → 20ms`라면 실행시간은 `80% 감소`, 속도는 약 `5배 향상`된 것이다.
- 튜닝 결과는 단순히 "빨라졌다"고 표현하지 않고 **실행계획 변화 + 수치 변화 + 개선율**을 함께 기록해야 한다.
- SQL을 재작성한 경우에는 실행시간뿐 아니라 **튜닝 전후 결과 데이터가 동일한지**도 확인해야 한다.
- 상관 서브쿼리가 반복 실행된다면 `JOIN`, 사전 집계 등의 구조로 재작성할 수 있지만 반드시 `EXPLAIN ANALYZE`를 통해 실제 개선 여부를 확인한다.
- 인덱스는 조회 성능을 개선할 수 있지만 `INSERT`, `UPDATE`, `DELETE`의 추가 비용과 저장 공간을 사용한다.
- 한 번의 실행시간만으로 성능을 단정하기보다 가능한 경우 여러 번 측정하여 결과를 비교하는 것이 좋다.
- `Planning Time`은 실행계획 생성 시간이고 `Execution Time`은 실제 SQL 실행시간이다.
- 튜닝 후 성능이 개선되지 않았다는 결과도 중요한 분석 결과이다.
- 성능 개선 후에는 남아 있는 다른 병목을 다시 확인하면서 튜닝 사이클을 반복할 수 있다.

```text
[ SQL 튜닝 핵심 흐름 ]

느린 SQL 발견
      ↓
EXPLAIN ANALYZE
      ↓
Baseline 기록
      ↓
병목 노드 확인
      ↓
개선 가설 설정
      ↓
인덱스 / SQL 재작성
      ↓
동일 조건 재측정
      ↓
실행계획 비교
      ↓
Execution Time 비교
      ↓
개선율 계산
      ↓
결과 동일성 확인
      ↓
효과 및 한계 판단
      ↓
남은 병목 확인
```
