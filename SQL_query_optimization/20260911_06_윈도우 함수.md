
# **1. 윈도우 함수(Window Function)**

윈도우 함수는 **여러 행을 참고하여 계산하면서 기존 행은 그대로 유지하는 함수**.

일반적인 집계 함수인 `SUM()`, `AVG()`, `COUNT()` 등에 `OVER()`를 붙여 윈도우 함수로 사용 가능.

예를 들어 선수별 득점 데이터가 다음과 같다고 가정.

| player_id | player_name | score |
|---:|---|---:|
| 1 | Kim | 10 |
| 2 | Lee | 20 |
| 3 | Park | 30 |

전체 선수의 평균 득점은 `20점`.

일반적인 `AVG()`를 사용하면 결과가 하나의 행으로 압축.

### [ sql : code ] "전체 선수의 평균 득점 계산"

```sql
SELECT
    AVG(score) AS avg_score
FROM player_stats;
```

### [ Result ]

```text
avg_score
---------
20
```

하지만 **각 선수의 점수와 전체 평균을 동시에 보고 싶다면** 윈도우 함수 사용.

### [ sql : code ] "각 선수의 점수를 유지하면서 전체 평균 함께 출력"

```sql
SELECT
    player_id,
    player_name,
    score,
    AVG(score) OVER () AS avg_score
FROM player_stats;
```

### [ Result ]

```text
player_id | player_name | score | avg_score
----------|-------------|-------|----------
1         | Kim         | 10    | 20
2         | Lee         | 20    | 20
3         | Park        | 30    | 20
```

### 코드 흐름

```text
전체 선수 데이터
      ↓
AVG(score)
      ↓
전체 평균 = 20
      ↓
OVER()
      ↓
기존 선수 행 유지
      ↓
각 선수 옆에 평균값 추가
```

### 결과 해석

`AVG(score)`만 사용하면 여러 행이 하나의 평균값으로 압축.

`AVG(score) OVER()`를 사용하면 기존 선수 행을 유지하면서 각 행에 전체 평균값 추가.

| 구분 | 결과 |
|---|---|
| `AVG(score)` | 여러 행 → 하나의 평균값 |
| `AVG(score) OVER()` | 기존 행 유지 + 평균값 추가 |

# **2. 윈도우 함수의 구성 요소**

윈도우 함수의 기본 구조.

### [ sql : code ] "윈도우 함수 기본 구조"

```sql
함수() OVER (
    PARTITION BY 그룹기준
    ORDER BY 정렬기준
    ROWS 또는 RANGE ...
)
```

모든 요소를 항상 사용할 필요는 없음.

필요한 계산에 따라 `PARTITION BY`, `ORDER BY`, `ROWS` 등을 선택해서 사용.


<br>


> ## **2-1 ) OVER() - 기존 행을 유지하면서 계산**

`OVER()`는 일반 함수를 **윈도우 함수로 동작하도록 만드는 핵심 문법**.

### [ sql : code ] "전체 행을 기준으로 평균 계산"

```sql
AVG(score) OVER ()
```

`OVER()` 안에 아무 조건도 없으면 전체 행을 하나의 계산 범위로 사용.

```text
전체 선수
    ↓
전체 평균 계산
    ↓
기존 선수 행 유지
    ↓
각 선수 행에 평균 추가
```

즉,

```text
OVER()
→ 기존 행을 유지하면서 여러 행을 참고하여 계산
```


<br>


> ## **2-2 ) PARTITION BY - 누구끼리 계산할 것인가?**

`PARTITION BY`는 데이터를 **그룹별로 나누어 윈도우 함수를 계산**할 때 사용.

예를 들어 다음과 같은 선수 데이터가 있다고 가정.

| team_id | player_name | score |
|---:|---|---:|
| 1 | Kim | 10 |
| 1 | Lee | 20 |
| 1 | Park | 30 |
| 2 | Choi | 40 |
| 2 | Jung | 50 |
| 2 | Han | 60 |

각 팀별 평균 득점을 선수 데이터와 함께 확인.

### [ sql : code ] "팀별 평균 득점을 선수별 행과 함께 출력"

```sql
SELECT
    team_id,
    player_name,
    score,
    AVG(score) OVER (
        PARTITION BY team_id
    ) AS team_avg_score
FROM player_stats
ORDER BY team_id, player_name;
```

### [ Result ]

```text
team_id | player_name | score | team_avg_score
--------|-------------|-------|---------------
1       | Kim         | 10    | 20
1       | Lee         | 20    | 20
1       | Park        | 30    | 20
2       | Choi        | 40    | 50
2       | Han         | 60    | 50
2       | Jung        | 50    | 50
```

### 코드 흐름

```text
전체 선수
    │
    │ PARTITION BY team_id
    ↓
팀 1 선수          팀 2 선수
10, 20, 30         40, 50, 60
    ↓                  ↓
평균 20             평균 50
    ↓                  ↓
각 선수 행에 팀 평균 추가
```

`PARTITION BY team_id`

```text
누구끼리 계산할 것인가?
        ↓
같은 팀 선수끼리
```


<br>


> ## **2-3 ) ORDER BY - 어떤 순서로 계산할 것인가?**

윈도우 함수 내부의 `ORDER BY`는 **윈도우 함수의 계산 순서** 지정.

예를 들어 선수들의 경기별 득점을 경기 순서대로 누적 계산.

### [ sql : code ] "선수별 경기 순서에 따른 누적 득점 계산"

```sql
SELECT
    player_name,
    game_id,
    score,
    SUM(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
    ) AS cumulative_score
FROM game_stats
ORDER BY player_name, game_id;
```

### [ Result ]

```text
player_name | game_id | score | cumulative_score
------------|---------|-------|-----------------
Kim         | 1       | 10    | 10
Kim         | 2       | 20    | 30
Kim         | 3       | 30    | 60
Kim         | 4       | 40    | 100
```

### 코드 흐름

```text
1경기
10
→ 10

2경기
10 + 20
→ 30

3경기
10 + 20 + 30
→ 60

4경기
10 + 20 + 30 + 40
→ 100
```

```text
PARTITION BY player_name
→ 누구끼리 계산?
→ 같은 선수의 경기끼리

ORDER BY game_id
→ 어떤 순서로 계산?
→ 경기 번호 순서대로
```

### 윈도우 함수 내부 `ORDER BY`와 일반 `ORDER BY` 차이

| 구분 | 역할 |
|---|---|
| `OVER(ORDER BY ...)` | 윈도우 함수의 계산 순서 결정 |
| SELECT 마지막 `ORDER BY` | 최종 조회 결과의 출력 순서 결정 |

### [ sql : code ] "윈도우 함수 계산 순서 지정"

```sql
SUM(score) OVER (
    ORDER BY game_id
)
```

여기서 `ORDER BY`는 누적합 계산 순서를 지정.

### [ sql : code ] "최종 조회 결과 출력 순서 지정"

```sql
SELECT
    *
FROM game_stats
ORDER BY game_id;
```

여기서 `ORDER BY`는 결과를 화면에 보여주는 순서를 지정.


<br>


> ## **2-4 ) ROWS - 실제로 어디까지 계산할 것인가?**

`ROWS`는 현재 행을 기준으로 **실제 계산에 포함할 행의 범위(Frame)** 지정.

예를 들어 최근 `3경기`의 평균 득점 계산.

### [ sql : code ] "현재 경기와 이전 2경기의 이동평균 계산"

```sql
SELECT
    player_name,
    game_id,
    score,
    AVG(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS moving_avg_score
FROM game_stats
ORDER BY player_name, game_id;
```

### [ Result ]

```text
player_name | game_id | score | moving_avg_score
------------|---------|-------|-----------------
Kim         | 1       | 10    | 10
Kim         | 2       | 20    | 15
Kim         | 3       | 30    | 20
Kim         | 4       | 40    | 30
```

`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`

```text
2 PRECEDING
→ 현재 행보다 앞의 2개 행

CURRENT ROW
→ 현재 행
```

따라서,

```text
이전 2개 행 + 현재 행
        ↓
최대 3개의 행 사용
```

### 계산 과정

```text
1경기
[10]
→ 평균 10

2경기
[10, 20]
→ 평균 15

3경기
[10, 20, 30]
→ 평균 20

4경기
[20, 30, 40]
→ 평균 30
```

앞에 충분한 행이 없다면 존재하는 행만 사용.


<br>


> ## **2-5 ) ROWS와 RANGE 차이**

`ROWS`와 `RANGE` 모두 윈도우의 계산 범위를 결정하지만 기준에 차이가 있음.

| 구분 | 기준 | 특징 |
|---|---|---|
| `ROWS` | 실제 행 위치 | 앞의 N개 행, 뒤의 N개 행 |
| `RANGE` | `ORDER BY` 값 | 같은 정렬값을 가진 행을 함께 고려 가능 |

처음 학습할 때는 실제 행 개수를 기준으로 이해하기 쉬운 `ROWS`부터 익히는 것이 좋음.


<br>


> ## **2-6 ) 윈도우 함수 구조 한 번에 이해하기**

### [ sql : code ] "팀별 경기 순서 기준 최근 3경기 평균 계산"

```sql
AVG(score) OVER (
    PARTITION BY team_id
    ORDER BY game_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

각 문법을 질문으로 이해.

```text
OVER()
→ 기존 행을 유지하면서 계산

PARTITION BY team_id
→ 누구끼리 계산할 것인가?
→ 같은 팀끼리

ORDER BY game_id
→ 어떤 순서로 계산할 것인가?
→ 경기 번호 순서대로

ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
→ 실제 어디까지 계산할 것인가?
→ 현재 행과 이전 2개 행
```

### 전체 흐름

```text
전체 경기 데이터
       │
       │ PARTITION BY
       │ 누구끼리?
       ↓
같은 팀의 데이터
       │
       │ ORDER BY
       │ 어떤 순서로?
       ↓
경기1 → 경기2 → 경기3 → 경기4
                       │
                       │ ROWS
                       │ 어디까지?
                       ↓
                [경기2 경기3 경기4]
                       │
                       ↓
                    AVG()
```

<br>

### **[ 윈도우 함수의 인자값 차이 테이블 ]**

|인자|`PARTITION BY`|`ORDER BY`|`Rows`|
|---|---|---|---|
|의미|누구끼리 계산할건지|어떤 순서로 계산할건지|실제로 어디까지 계산할 것인지<br>(데이터의 범위 지정)|
|사용|GROUP BY|ORDER BY|RANGE|
|작성방법|PARTITION BY **그룹별로 묶고싶은 컬럼명**|ORDER BY **순서가 필요한 컬럼명**|`ROWS BETWEEN` **현재 행에서 앞의 몇개를 볼것인지(int)** `PRECEDING AND CURRENT ROW`|

- 윈도우 함수의 인자를 어떤 순서로 작성하는지에 따라 계산결과 값도 달라짐.

# **3. GROUP BY와 윈도우 함수의 차이**

`GROUP BY`와 윈도우 함수 모두 `SUM()`, `AVG()`, `COUNT()` 등을 사용할 수 있지만 **결과 행을 처리하는 방식이 다름**.


<br>


> ## **3-1 ) GROUP BY - 행을 압축**

팀별 총 득점 계산.

### [ sql : code ] "GROUP BY를 이용한 팀별 총 득점 계산"

```sql
SELECT
    team_id,
    SUM(score) AS total_score
FROM player_stats
GROUP BY team_id
ORDER BY team_id;
```

### [ Result ]

```text
team_id | total_score
--------|------------
1       | 60
2       | 150
```

원본 데이터가 여러 행이어도 `GROUP BY` 이후에는 팀별 하나의 행만 남음.

```text
팀 1

Kim  | 10
Lee  | 20
Park | 30
        │
        │ GROUP BY
        ↓
팀 1 | 60
```


<br>


> ## **3-2 ) 윈도우 함수 - 행을 유지**

같은 계산을 윈도우 함수로 수행.

### [ sql : code ] "선수별 행을 유지하면서 팀별 총 득점 계산"

```sql
SELECT
    team_id,
    player_name,
    score,
    SUM(score) OVER (
        PARTITION BY team_id
    ) AS team_total_score
FROM player_stats
ORDER BY team_id, player_name;
```

### [ Result ]

```text
team_id | player_name | score | team_total_score
--------|-------------|-------|-----------------
1       | Kim         | 10    | 60
1       | Lee         | 20    | 60
1       | Park        | 30    | 60
2       | Choi        | 40    | 150
2       | Han         | 60    | 150
2       | Jung        | 50    | 150
```

### 차이

```text
GROUP BY

Kim  ─┐
Lee   ├──→ 팀 1 | 총점 60
Park ─┘


윈도우 함수

Kim  | 10 | 팀 총점 60
Lee  | 20 | 팀 총점 60
Park | 30 | 팀 총점 60
```

| 구분 | `GROUP BY` | 윈도우 함수 |
|---|---|---|
| 원본 행 | 여러 행을 하나로 압축 | 그대로 유지 |
| 그룹 통계 | 가능 | 가능 |
| 개별 데이터 확인 | 어려움 | 가능 |
| `SUM`, `AVG`, `COUNT` | 사용 가능 | `OVER()`와 함께 사용 |
| 사용 목적 | 그룹별 요약 | 개별 데이터 + 그룹 통계 |

```text
그룹별 결과만 필요
→ GROUP BY

각 행과 그룹 통계를 동시에 확인
→ Window Function
```

# **4. 순위 윈도우 함수**

윈도우 함수는 순위를 계산할 때도 많이 사용.

대표적인 순위 함수.

| 함수 | 특징 |
|---|---|
| `ROW_NUMBER()` | 무조건 `1, 2, 3, 4 ...` 순서 부여 |
| `RANK()` | 동점은 같은 순위, 다음 순위 건너뜀 |
| `DENSE_RANK()` | 동점은 같은 순위, 다음 순위는 연속 |
| `NTILE(n)` | 데이터를 `n`개의 그룹으로 분할 |


<br>


> ## **4-1 ) ROW_NUMBER()**

각 팀에서 득점이 높은 선수부터 번호 부여.

### [ sql : code ] "팀별 선수 득점 순서에 연속 번호 부여"

```sql
SELECT
    team_id,
    player_name,
    score,
    ROW_NUMBER() OVER (
        PARTITION BY team_id
        ORDER BY score DESC
    ) AS score_order
FROM player_stats
ORDER BY team_id, score_order;
```

### [ Result ]

```text
team_id | player_name | score | score_order
--------|-------------|-------|------------
1       | Park        | 30    | 1
1       | Lee         | 20    | 2
1       | Kim         | 10    | 3
2       | Han         | 60    | 1
2       | Jung        | 50    | 2
2       | Choi        | 40    | 3
```

```text
PARTITION BY team_id
→ 팀별로 번호를 다시 1부터 시작

ORDER BY score DESC
→ 점수가 높은 선수부터 정렬

ROW_NUMBER()
→ 각 행에 1, 2, 3 ... 번호 부여
```


<br>


> ## **4-2 ) RANK()**

`RANK()`는 동점자가 있는 경우 같은 순위를 부여.

예시 데이터.

| player_name | score |
|---|---:|
| Kim | 30 |
| Lee | 30 |
| Park | 25 |
| Choi | 20 |

### [ sql : code ] "동점자를 같은 순위로 처리하는 선수 순위 계산"

```sql
SELECT
    player_name,
    score,
    RANK() OVER (
        ORDER BY score DESC
    ) AS score_rank
FROM player_stats
ORDER BY score_rank;
```

### [ Result ]

```text
player_name | score | score_rank
------------|-------|-----------
Kim         | 30    | 1
Lee         | 30    | 1
Park        | 25    | 3
Choi        | 20    | 4
```

`30점`을 기록한 선수가 2명이므로 둘 다 `1위`.

다음 순위는 `2위`를 건너뛰고 `3위`.


<br>


> ## **4-3 ) RANK와 DENSE_RANK 차이**

### [ sql : code ] "RANK와 DENSE_RANK 순위 방식 비교"

```sql
SELECT
    player_name,
    score,
    RANK() OVER (
        ORDER BY score DESC
    ) AS rank_result,
    DENSE_RANK() OVER (
        ORDER BY score DESC
    ) AS dense_rank_result
FROM player_stats;
```

### [ Result ]

```text
player_name | score | rank_result | dense_rank_result
------------|-------|-------------|------------------
Kim         | 30    | 1           | 1
Lee         | 30    | 1           | 1
Park        | 25    | 3           | 2
Choi        | 20    | 4           | 3
```

| 함수 | 결과 | 특징 |
|---|---|---|
| `ROW_NUMBER()` | `1, 2, 3, 4` | 동점이어도 다른 번호 |
| `RANK()` | `1, 1, 3, 4` | 동점 수만큼 다음 순위 건너뜀 |
| `DENSE_RANK()` | `1, 1, 2, 3` | 동점 이후에도 순위 연속 |

# **5. 윈도우 함수의 종류**

윈도우 함수는 크게 **순위 함수, 집계 함수, 분석 함수**로 구분.

| 분류 | 대표 함수 | 사용 목적 |
|---|---|---|
| 순위 함수 | `RANK()`, `DENSE_RANK()`, `ROW_NUMBER()`, `NTILE()` | 그룹 내 순위 계산 |
| 집계 함수 | `SUM()`, `AVG()`, `COUNT()`, `MIN()`, `MAX()` | 행을 유지하면서 그룹 통계 계산 |
| 분석 함수 | `LAG()`, `LEAD()`, `FIRST_VALUE()`, `LAST_VALUE()` | 이전·다음 행 또는 특정 위치 값 확인 |


<br>


> ## **5-1 ) LAG() - 이전 행 값 확인**

`LAG()`는 현재 행을 기준으로 **이전 행의 값**을 가져올 때 사용.

선수의 현재 경기 득점과 이전 경기 득점을 비교.

### [ sql : code ] "선수별 이전 경기 득점 확인"

```sql
SELECT
    player_name,
    game_id,
    score,
    LAG(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
    ) AS previous_score
FROM game_stats
ORDER BY player_name, game_id;
```

### [ Result ]

```text
player_name | game_id | score | previous_score
------------|---------|-------|---------------
Kim         | 1       | 10    | NULL
Kim         | 2       | 20    | 10
Kim         | 3       | 15    | 20
Kim         | 4       | 30    | 15
```

### 코드 흐름

```text
현재 경기
    ↓
LAG(score)
    ↓
같은 선수의 경기 중
바로 이전 경기 확인
    ↓
previous_score에 저장
```

첫 번째 경기는 이전 경기가 없으므로 `NULL`.


<br>


> ## **5-2 ) LEAD() - 다음 행 값 확인**

`LEAD()`는 현재 행을 기준으로 **다음 행의 값**을 가져올 때 사용.

### [ sql : code ] "선수별 다음 경기 득점 확인"

```sql
SELECT
    player_name,
    game_id,
    score,
    LEAD(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
    ) AS next_score
FROM game_stats
ORDER BY player_name, game_id;
```

### [ Result ]

```text
player_name | game_id | score | next_score
------------|---------|-------|-----------
Kim         | 1       | 10    | 20
Kim         | 2       | 20    | 15
Kim         | 3       | 15    | 30
Kim         | 4       | 30    | NULL
```

| 함수 | 확인하는 값 |
|---|---|
| `LAG()` | 이전 행 |
| `LEAD()` | 다음 행 |

# **6. 윈도우 함수는 왜 WHERE에서 바로 사용할 수 없을까?**

윈도우 함수는 SQL의 논리적 실행 순서상 `WHERE`보다 나중에 계산.

간단하게 보면 다음과 같은 흐름.

```text
FROM / JOIN
    ↓
WHERE
    ↓
GROUP BY
    ↓
HAVING
    ↓
윈도우 함수
    ↓
SELECT 결과 생성
    ↓
ORDER BY
```

따라서 `WHERE`가 실행되는 시점에는 아직 `RANK()`, `ROW_NUMBER()` 등의 결과가 만들어지지 않은 상태.

다음처럼 윈도우 함수의 별칭을 `WHERE`에서 바로 사용할 수 없음.

### [ sql : code ] "윈도우 함수 결과를 WHERE에서 바로 사용한 잘못된 예"

```sql
SELECT
    player_name,
    score,
    RANK() OVER (
        ORDER BY score DESC
    ) AS score_rank
FROM player_stats
WHERE score_rank <= 3;
```

### [ Result ]

```text
ERROR

WHERE가 실행되는 시점에는
score_rank가 아직 계산되지 않음
```


<br>


> ## **6-1 ) 서브쿼리를 이용한 해결**

먼저 안쪽 쿼리에서 순위를 만든 뒤 바깥쪽 쿼리에서 필터링.

### [ sql : code ] "서브쿼리로 상위 3명의 선수 조회"

```sql
SELECT
    player_name,
    score,
    score_rank
FROM (
    SELECT
        player_name,
        score,
        RANK() OVER (
            ORDER BY score DESC
        ) AS score_rank
    FROM player_stats
) ranked
WHERE score_rank <= 3;
```

### [ Result ]

```text
player_name | score | score_rank
------------|-------|-----------
Kim         | 30    | 1
Lee         | 28    | 2
Park        | 25    | 3
```

### 코드 흐름

```text
player_stats
      ↓
안쪽 SELECT 실행
      ↓
RANK() 계산
      ↓
score_rank 생성
      ↓
바깥 SELECT 실행
      ↓
WHERE score_rank <= 3
      ↓
상위 3명의 선수 조회
```


<br>


> ## **6-2 ) CTE를 이용한 해결**

CTE를 사용하면 복잡한 쿼리를 단계별로 분리 가능.

### [ sql : code ] "CTE를 이용해 상위 3명의 선수 조회"

```sql
WITH ranked_players AS (
    SELECT
        player_name,
        score,
        RANK() OVER (
            ORDER BY score DESC
        ) AS score_rank
    FROM player_stats
)
SELECT
    player_name,
    score,
    score_rank
FROM ranked_players
WHERE score_rank <= 3;
```

### [ Result ]

```text
player_name | score | score_rank
------------|-------|-----------
Kim         | 30    | 1
Lee         | 28    | 2
Park        | 25    | 3
```

```text
윈도우 함수 결과로 필터링
        ↓
서브쿼리 또는 CTE에서 먼저 계산
        ↓
바깥 WHERE에서 조건 적용
```

# **7. 윈도우 함수와 실행계획**

윈도우 함수는 `PARTITION BY`와 `ORDER BY`를 사용하기 때문에 데이터 정렬 작업이 발생할 수 있음.

PostgreSQL에서는 `EXPLAIN`을 이용해 실행계획 확인 가능.


<br>


> ## **7-1 ) 팀별 득점 순위 실행계획 확인**

### [ sql : code ] "팀별 선수 순위 쿼리의 실행계획 확인"

```sql
EXPLAIN
SELECT
    team_id,
    player_name,
    score,
    RANK() OVER (
        PARTITION BY team_id
        ORDER BY score DESC
    ) AS score_rank
FROM player_stats;
```

### [ Result ]

실제 비용과 행 수는 데이터 크기나 DB 환경에 따라 다르지만 다음과 같은 형태로 확인 가능.

```text
WindowAgg
  -> Sort
       Sort Key: team_id, score DESC
       -> Seq Scan on player_stats
```

실행계획은 일반적으로 **아래에서 위로** 확인.


<br>


> ## **7-2 ) Seq Scan - 데이터 읽기**

```text
Seq Scan on player_stats
```

`Seq Scan`은 테이블 데이터를 처음부터 순차적으로 읽는 작업.

```text
player_stats
      ↓
전체 데이터 읽기
      ↓
다음 단계로 전달
```


<br>


> ## **7-3 ) Sort - 계산에 필요한 순서로 정렬**

```text
Sort
Sort Key: team_id, score DESC
```

윈도우 함수를 계산하기 위해 필요한 순서로 데이터 정렬.

SQL에서 작성한 부분.

```sql
PARTITION BY team_id
ORDER BY score DESC
```

실행 과정.

```text
팀 1
  높은 점수
      ↓
  낮은 점수

팀 2
  높은 점수
      ↓
  낮은 점수
```

따라서 실행계획에서 다음처럼 나타날 수 있음.

```text
Sort Key: team_id, score DESC
```


<br>


> ## **7-4 ) WindowAgg - 윈도우 함수 계산**

정렬된 데이터를 이용해 실제 윈도우 함수 계산.

```text
WindowAgg
```

예시.

```text
정렬된 데이터

팀 1 | Kim  | 30
팀 1 | Lee  | 25
팀 1 | Park | 20
        ↓
    WindowAgg
        ↓
팀 1 | Kim  | 30 | 1
팀 1 | Lee  | 25 | 2
팀 1 | Park | 20 | 3
```


<br>


> ## **7-5 ) 실행 흐름 한 번에 보기**

```text
Seq Scan
player_stats 데이터 읽기
        ↓
Sort
team_id + score DESC 기준 정렬
        ↓
WindowAgg
RANK() 계산
        ↓
팀별 선수 득점 순위
```

SQL과 실행계획을 연결하면 다음과 같음.

| SQL 요소 | 실행계획에서 하는 일 |
|---|---|
| `FROM player_stats` | `Seq Scan` 등으로 데이터 읽기 |
| `PARTITION BY team_id` | 같은 팀끼리 계산할 수 있도록 데이터 준비 |
| `ORDER BY score DESC` | `Sort`를 통해 계산 순서 준비 가능 |
| `RANK()` | `WindowAgg`에서 순위 계산 |

# **8. 윈도우 함수 사용 시 성능 고려사항**

윈도우 함수 자체가 항상 느린 것은 아니지만 `ORDER BY`가 포함되면 많은 데이터를 정렬해야 할 수 있음.

특히 다음과 같은 구조.

### [ sql : code ] "팀별 득점 순위를 위한 윈도우 정렬"

```sql
RANK() OVER (
    PARTITION BY team_id
    ORDER BY score DESC
)
```

데이터베이스는 윈도우 함수를 계산하기 위해 `team_id`, `score` 기준으로 데이터를 정렬할 수 있음.

데이터가 많다면 `Sort` 비용 증가 가능.

실제 실행 시간까지 확인하려면 `EXPLAIN ANALYZE` 사용.

### [ sql : code ] "윈도우 함수의 실제 실행 시간과 실행계획 확인"

```sql
EXPLAIN ANALYZE
SELECT
    team_id,
    player_name,
    score,
    RANK() OVER (
        PARTITION BY team_id
        ORDER BY score DESC
    ) AS score_rank
FROM player_stats;
```

### [ Result ]

```text
WindowAgg
  -> Sort
       Sort Key: team_id, score DESC
       -> Seq Scan on player_stats

Planning Time: ...
Execution Time: ...
```

실행계획에서 확인할 요소.

| 확인 요소 | 의미 |
|---|---|
| `WindowAgg` | 윈도우 함수 계산 |
| `Sort` | 정렬 작업 |
| `Sort Key` | 정렬에 사용된 컬럼 |
| `Seq Scan` | 테이블 전체를 순차 탐색 |
| `Index Scan` | 인덱스를 이용한 데이터 탐색 |
| `actual time` | 실제 실행에 걸린 시간 |

`PARTITION BY`, `ORDER BY`에 사용하는 컬럼에 적절한 인덱스가 있으면 일부 쿼리에서 성능에 도움이 될 수 있음.

하지만 **인덱스를 만든다고 항상 `Sort`가 사라지는 것은 아님**.

따라서 실제 성능은 `EXPLAIN ANALYZE`로 확인하는 것이 중요.

> ## **9-3 ) 선수별 누적 득점**

`UNBOUNDED PRECEDING`을 사용하면 파티션의 첫 번째 행부터 현재 행까지 계산 가능.

### [ sql : code ] "선수별 첫 경기부터 현재 경기까지 누적 득점 계산"

```sql
SELECT
    player_name,
    game_id,
    score,
    SUM(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_score
FROM game_stats
ORDER BY player_name, game_id;
```

```text
player_name | game_id | score | cumulative_score
------------|---------|-------|-----------------

Kim         | 2       | 20    | 30
Kim         | 3       | 15    | 45
Kim         | 4       | 30    | 75
```

`UNBOUNDED PRECEDING`

```text
파티션의 첫 번째 행부터
```

`CURRENT ROW`

```text
현재 행까지
```

따라서,

```text
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

→ 첫 경기부터 현재 경기까지
→ 누적합 계산
```

# **10. Advanced 추가 학습**

> ## **10-1 ) 윈도우 프레임**

윈도우 함수가 실제 계산에 사용할 행의 범위를 `Frame`이라고 함.

| 문법 | 의미 |
|---|---|
| `UNBOUNDED PRECEDING` | 파티션의 처음부터 |
| `2 PRECEDING` | 현재 행보다 앞의 2개 행 |
| `CURRENT ROW` | 현재 행 |
| `1 FOLLOWING` | 현재 행 다음 1개 행 |
| `UNBOUNDED FOLLOWING` | 파티션의 마지막까지 |

예를 들어,

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

```text
이전 2행 + 현재 행
```

반면,

```sql
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

```text
첫 번째 행부터 현재 행까지
→ 누적합 등에 활용
```


<br>


> ## **10-2 ) LAG를 이용한 경기별 증감 계산**

`LAG()`를 이용하면 이전 경기와 현재 경기의 득점 차이도 계산 가능.

### [ sql : code ] "현재 경기와 이전 경기의 득점 차이 계산"

```sql
SELECT
    player_name,
    game_id,
    score,
    score - LAG(score) OVER (
        PARTITION BY player_name
        ORDER BY game_id
    ) AS score_change
FROM game_stats
ORDER BY player_name, game_id;
```

### [ Result ]

```text
player_name | game_id | score | score_change
------------|---------|-------|-------------
Kim         | 1       | 10    | NULL
Kim         | 2       | 20    | 10
Kim         | 3       | 15    | -5
Kim         | 4       | 30    | 15
```

### 결과 해석

```text
score_change > 0
→ 이전 경기보다 득점 증가

score_change < 0
→ 이전 경기보다 득점 감소

score_change = 0
→ 이전 경기와 같은 득점

NULL
→ 비교할 이전 경기가 없음
```

# **11. 핵심정리**

- 윈도우 함수는 **원본 행을 유지하면서 여러 행을 참고하여 계산**하는 함수.
- `OVER()`는 일반 집계 함수가 윈도우 함수로 동작하도록 만드는 핵심 문법.
- `PARTITION BY`는 **누구끼리 계산할지** 결정.
- `ORDER BY`는 **어떤 순서로 계산할지** 결정.
- `ROWS` / `RANGE`는 **실제로 어디까지 계산할지** 결정.
- `GROUP BY`는 여러 행을 하나의 결과로 압축.
- 윈도우 함수는 **기존 행을 유지하면서 그룹 통계를 추가**.
- `ROW_NUMBER()`는 동점과 관계없이 연속 번호 부여.
- `RANK()`는 동점 이후 순위를 건너뜀.
- `DENSE_RANK()`는 동점 이후에도 순위를 연속해서 부여.
- `LAG()`는 이전 행을 확인할 때 사용.
- `LEAD()`는 다음 행을 확인할 때 사용.
- 윈도우 함수 결과는 `WHERE`에서 바로 사용할 수 없으므로 **서브쿼리나 CTE에서 먼저 계산한 뒤 필터링**.
- PostgreSQL 실행계획에서는 윈도우 함수 계산이 `WindowAgg`로 나타날 수 있음.
- `PARTITION BY`와 `ORDER BY` 때문에 필요한 경우 `Sort` 발생 가능.
- 실행계획은 일반적으로 **아래에서 위로** 읽으면서 데이터 처리 흐름 확인.
- 대용량 데이터에서는 `Sort` 비용이 커질 수 있으므로 `EXPLAIN ANALYZE`로 실제 성능 확인.

```text
윈도우 함수 이해 순서

OVER()
→ 행을 유지하면서 계산

        ↓

PARTITION BY
→ 누구끼리 계산?

        ↓

ORDER BY
→ 어떤 순서로 계산?

        ↓

ROWS / RANGE
→ 어디까지 계산?

        ↓

SUM / AVG / RANK / LAG ...
→ 무엇을 계산?
```

> **핵심**
>
> `GROUP BY`
> → 데이터를 **요약해서 줄이는 것**
>
> `Window Function`
> → 데이터를 **유지하면서 계산 결과를 옆에 붙이는 것**
