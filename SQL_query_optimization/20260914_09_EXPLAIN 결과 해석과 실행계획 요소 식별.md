# **1. EXPLAIN과 실행계획이 중요한 이유**

SQL에서 원하는 결과를 얻는 것만으로는 실제 서비스의 성능을 보장할 수 없다.

같은 결과를 반환하는 SQL이라도 PostgreSQL이 데이터를 읽고, 조인하고, 정렬하는 방식에 따라 실행 속도가 크게 달라질 수 있다.

이때 PostgreSQL이 SQL을 어떤 순서와 방법으로 처리할지 보여주는 것이 **실행계획(Execution Plan)** 이고, 이를 확인하는 명령어가 `EXPLAIN`이다.

```text
SQL 작성
   ↓
EXPLAIN으로 실행계획 확인
   ↓
Scan / Join / Sort 등 확인
   ↓
비용이 큰 작업 확인
   ↓
병목 원인 추정
   ↓
인덱스 / 조인 / 정렬 / 쿼리 구조 개선
```

즉, SQL 튜닝은 무작정 인덱스를 생성하는 것이 아니라 **실행계획에서 문제가 발생하는 위치를 먼저 확인하는 것**부터 시작한다.

<br>

> ## **1-1 ) EXPLAIN과 EXPLAIN ANALYZE**

`EXPLAIN`과 `EXPLAIN ANALYZE`는 비슷하지만 확인할 수 있는 정보에 차이가 있다.

| 구분 | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| 실제 SQL 실행 | X | O |
| 예상 실행계획 | O | O |
| `cost` | O | O |
| 예상 `rows` | O | O |
| 실제 `rows` | X | O |
| `actual time` | X | O |
| 전체 실행시간 | X | O |
| 주요 목적 | 예상 실행 방식 확인 | 실제 병목 확인 |

특히 `EXPLAIN ANALYZE`는 SQL을 **실제로 실행한다.**

따라서 `SELECT`에서는 비교적 부담 없이 사용할 수 있지만 `UPDATE`, `DELETE`, `INSERT` 등에 사용할 경우 실제 데이터가 변경될 수 있으므로 주의해야 한다.

# **2. 복합 쿼리의 EXPLAIN 결과 구조**

> ## **2-1 ) 실행계획은 트리 구조로 나타난다**

`JOIN`, 서브쿼리, 윈도우 함수 등이 포함된 복합 SQL은 실행계획 역시 여러 단계의 **트리(Tree) 구조**로 나타난다.

예를 들어 다음과 같은 SQL 처리 과정이 있다고 가정할 수 있다.

```text
데이터 읽기
    ↓
조건에 맞는 데이터 필터링
    ↓
테이블 조인
    ↓
필요한 순서로 정렬
    ↓
윈도우 함수 계산
    ↓
최종 결과 반환
```

실행계획에서는 보통 다음과 같은 노드가 나타난다.

| 실행계획 노드 | 의미 |
|---|---|
| `Seq Scan` | 테이블 전체를 순차적으로 읽음 |
| `Index Scan` | 인덱스를 이용하여 데이터를 읽음 |
| `Bitmap Index Scan` | 인덱스를 이용해 필요한 행의 위치를 찾음 |
| `Bitmap Heap Scan` | 찾은 위치를 이용해 실제 테이블의 행을 가져옴 |
| `Sort` | 데이터를 특정 기준으로 정렬 |
| `Nested Loop` | 한쪽 결과를 기준으로 다른 테이블을 반복 탐색 |
| `Hash Join` | 조인 키의 해시 테이블을 생성하여 조인 |
| `Merge Join` | 정렬된 두 데이터 집합을 비교하며 조인 |
| `Aggregate` | `SUM`, `AVG`, `COUNT` 등의 집계 수행 |
| `WindowAgg` | 윈도우 함수 계산 |
| `SubPlan` | 서브쿼리 실행 |

<br>

> ## **2-2 ) 실행계획은 아래쪽부터 위쪽으로 읽는다**

실행계획은 일반적으로 **가장 안쪽 또는 아래쪽 노드부터 실행**된다.

예를 들어 다음 실행계획이 있다고 하자.

```text
Sort
  ↓
Hash Join
  ├─ Seq Scan on match_stats
  └─ Seq Scan on players
```

실제 데이터 처리 흐름은 다음과 같다.

```text
match_stats 데이터 읽기 ─┐
                         ├→ Hash Join
players 데이터 읽기 ─────┘
                            ↓
                           Sort
                            ↓
                         최종 결과
```

따라서 실행계획을 처음 볼 때는 가장 위에 있는 노드부터 읽기보다는 **아래쪽의 `Scan` 노드부터 위쪽으로 따라가는 방식**이 이해하기 쉽다.

<br>

> ## **2-3 ) 복합 쿼리 실행계획 예제**

[ sql : code ] "축구 선수 정보와 경기 기록을 조인한 뒤 경기 날짜순으로 정렬하는 쿼리의 실행계획 확인"

```sql
EXPLAIN
SELECT
    p.player_id,
    p.player_name,
    m.match_id,
    m.match_date
FROM players p
JOIN match_stats m
    ON p.player_id = m.player_id
ORDER BY m.match_date;
```

[ Result ]

※ 실제 실행계획은 데이터 크기, 통계 정보, 인덱스 등에 따라 달라질 수 있다.

```text
Sort
  Sort Key: m.match_date
  -> Hash Join
       Hash Cond: (m.player_id = p.player_id)
       -> Seq Scan on match_stats m
       -> Hash
            -> Seq Scan on players p
```

### 실행 흐름 해석

```text
players 전체 읽기
        ↓
Hash 생성
        │
        ├────────────┐
        │            ↓
match_stats 읽기 → Hash Join
                      ↓
              match_date 기준 Sort
                      ↓
                   최종 결과
```

1. `players` 테이블을 읽는다.
2. `player_id`를 기준으로 해시 구조를 생성한다.
3. `match_stats` 데이터를 읽는다.
4. 두 데이터를 `player_id`로 조인한다.
5. 최종 결과를 `match_date` 기준으로 정렬한다.

# **3. 실행계획의 주요 요소 확인하기**

> ## **3-1 ) Scan : 데이터를 어떻게 읽는가**

`Scan`은 PostgreSQL이 테이블에서 데이터를 읽는 방식을 의미한다.

대표적인 방식은 `Seq Scan`, `Index Scan`, `Bitmap Scan`이다.

| 방식 | 의미 | 특징 |
|---|---|---|
| `Seq Scan` | 테이블 전체를 순차적으로 읽음 | 많은 데이터를 조회할 때 유리할 수 있음 |
| `Index Scan` | 인덱스를 따라 필요한 행 조회 | 소수의 데이터를 찾을 때 유리 |
| `Bitmap Index Scan` | 인덱스로 필요한 위치를 먼저 수집 | 여러 행을 조회할 때 사용될 수 있음 |
| `Bitmap Heap Scan` | 수집된 위치의 실제 행 조회 | `Bitmap Index Scan`과 함께 나타나는 경우가 많음 |

`Seq Scan`이 나타났다고 해서 반드시 문제가 있는 것은 아니다.

예를 들어 전체 선수의 80~90%를 조회해야 한다면 인덱스를 따라가는 것보다 테이블 전체를 읽는 것이 더 효율적일 수 있다.

즉,

```text
Seq Scan = 무조건 느림 X
Index Scan = 무조건 빠름 X
```

PostgreSQL은 데이터의 크기와 조회 비율 등을 고려하여 실행 방식을 선택한다.

<br>

> ## **3-2 ) Join : 두 데이터 집합을 어떻게 연결하는가**

실행계획에서는 여러 종류의 조인 알고리즘이 나타날 수 있다.

| 조인 방식 | 특징 | 주로 확인할 부분 |
|---|---|---|
| `Nested Loop` | 한 행씩 다른 테이블을 반복 조회 | 반복 횟수가 너무 많지 않은지 |
| `Hash Join` | 조인 키를 해시 구조로 만들어 연결 | 처리하는 행이 지나치게 많지 않은지 |
| `Merge Join` | 정렬된 데이터를 순서대로 비교 | 정렬 비용이 추가되는지 |

조인 방식 자체를 외우는 것보다 **얼마나 많은 데이터가 조인되는지**를 함께 확인하는 것이 중요하다.

<br>

> ## **3-3 ) Sort : 정렬이 발생하는가**

`ORDER BY`, 일부 윈도우 함수, `GROUP BY` 등의 처리 과정에서는 `Sort`가 발생할 수 있다.

정렬 대상 데이터가 적으면 문제가 되지 않지만 수십만~수백만 행을 정렬하면 비용이 크게 증가할 수 있다.

특히 다음과 같은 결과가 나타나면 확인이 필요하다.

```text
Sort Method: external merge
Disk: 16248kB
```

이는 메모리 안에서 정렬을 끝내지 못하고 **디스크를 사용하여 정렬했다는 의미**이다.

반면 다음과 같은 경우는 메모리에서 정렬이 수행되었다.

```text
Sort Method: quicksort
Memory: 25kB
```

| 정렬 방식 예시 | 의미 |
|---|---|
| `quicksort` | 메모리에서 정렬 |
| `external merge` | 디스크까지 사용하여 정렬 |
| `Memory` | 정렬에 사용된 메모리 |
| `Disk` | 정렬에 사용된 디스크 공간 |

<br>

> ## **3-4 ) WindowAgg : 윈도우 함수 계산**

`RANK()`, `ROW_NUMBER()`, `LAG()`, `LEAD()`, `SUM() OVER()` 등의 윈도우 함수가 사용되면 실행계획에서 `WindowAgg`가 나타날 수 있다.

[ sql : code ] "농구 선수의 득점 순위를 윈도우 함수로 계산하고 실행계획 확인"

```sql
EXPLAIN
SELECT
    player_id,
    points,
    RANK() OVER (ORDER BY points DESC) AS scoring_rank
FROM basketball_stats;
```

[ Result ]

```text
WindowAgg
  -> Sort
       Sort Key: points DESC
       -> Seq Scan on basketball_stats
```

### 실행 흐름

```text
basketball_stats 데이터 읽기
            ↓
      points DESC 정렬
            ↓
       RANK() 계산
            ↓
         최종 결과
```

`RANK()`를 계산하려면 먼저 점수 순서를 알아야 하기 때문에 `Sort` 이후 `WindowAgg`가 수행되는 것을 확인할 수 있다.

# **4. cost와 rows 읽는 방법**

> ## **4-1 ) cost란 무엇인가**

실행계획에는 다음과 같은 값이 나타난다.

```text
Seq Scan on match_stats
(cost=0.00..1840.00 rows=50000 width=32)
```

`cost`는 PostgreSQL 옵티마이저가 여러 실행계획을 비교하기 위해 사용하는 **상대적인 예상 비용 값**이다.

```text
cost=시작비용..총비용
```

예를 들어,

```text
cost=0.00..1840.00
```

이라면

- 시작 비용 : `0.00`
- 해당 노드의 예상 총 비용 : `1840.00`

이라는 의미이다.

중요한 점은 다음과 같다.

```text
cost = 실행시간(ms) X
```

`cost`는 실제 밀리초가 아니라 PostgreSQL 내부에서 사용하는 상대적인 비용 단위이다.

<br>

> ## **4-2 ) rows란 무엇인가**

```text
rows=50000
```

`rows`는 해당 노드가 반환할 것이라고 PostgreSQL이 **예상한 행 수**이다.

`EXPLAIN ANALYZE`에서는 예상값과 실제값을 함께 비교할 수 있다.

```text
rows=1000
actual rows=50000
```

이처럼 예상은 `1,000행`인데 실제로는 `50,000행`이 처리되었다면 옵티마이저의 예상과 실제 데이터 사이에 큰 차이가 존재한다.

이러한 차이는 잘못된 실행계획 선택으로 이어질 수 있기 때문에 확인할 필요가 있다.

<br>

> ## **4-3 ) actual time과 loops**

`EXPLAIN ANALYZE`에서는 다음과 같은 정보도 확인할 수 있다.

```text
(actual time=0.019..74.576 rows=400205 loops=1)
```

| 항목 | 의미 |
|---|---|
| `actual time=0.019..74.576` | 실제 시작 시간과 종료 시간 |
| `rows=400205` | 실제 반환된 행 수 |
| `loops=1` | 해당 노드가 실행된 횟수 |

특히 `Nested Loop`처럼 동일한 노드가 반복 실행되는 경우에는 `loops`도 함께 확인해야 한다.

```text
actual time만 확인 X
actual time + rows + loops 함께 확인 O
```

# **5. EXPLAIN ANALYZE로 실제 병목 찾기**

> ## **5-1 ) 실제 실행 시간 확인**

[ sql : code ] "마라톤 기록을 경기 날짜순으로 정렬하는 SQL의 실제 실행시간 확인"

```sql
EXPLAIN ANALYZE
SELECT *
FROM marathon_records
WHERE race_date >= '2026-01-01'
ORDER BY race_date DESC;
```

[ Result ]

※ 아래 결과는 구조를 이해하기 위한 예시이다.

```text
Sort
  (cost=28399.54..28816.20 rows=166667 width=32)
  (actual time=256.411..327.851 rows=400205 loops=1)

  Sort Key: race_date DESC
  Sort Method: external merge
  Disk: 16248kB

  -> Seq Scan on marathon_records
       (actual time=0.019..74.576 rows=400205 loops=1)
       Filter: (race_date >= '2026-01-01'::date)
       Rows Removed by Filter: 99795

Planning Time: 0.196 ms
Execution Time: 350.346 ms
```

### 결과 해석

먼저 데이터 조회 부분을 확인한다.

```text
Seq Scan on marathon_records
actual time=0.019..74.576
rows=400205
```

약 `400,205행`이 조회되었고 스캔 과정이 약 `74.576ms`까지 수행되었다.

다음으로 정렬을 확인한다.

```text
Sort
actual time=256.411..327.851

Sort Method: external merge
Disk: 16248kB
```

정렬 과정에서는 디스크까지 사용되고 있다.

전체 실행 시간은 다음과 같다.

```text
Execution Time: 350.346 ms
```

따라서 이 실행계획에서는 단순히 데이터 조회뿐 아니라 **많은 행을 정렬하는 과정도 성능에 큰 영향을 주고 있음**을 의심할 수 있다.

### 실행 흐름

```text
marathon_records 전체 확인
          ↓
race_date 조건 필터링
          ↓
약 400,205행 반환
          ↓
race_date DESC 정렬
          ↓
메모리 부족 → 디스크 정렬
          ↓
최종 결과 반환
```

<br>

> ## **5-2 ) 병목 구간 찾는 순서**

실행계획에서 병목을 찾을 때는 하나의 숫자만 보는 것보다 다음 순서로 확인하는 것이 좋다.

```text
1. 전체 Execution Time 확인
        ↓
2. 데이터 Scan 방식 확인
        ↓
3. 각 노드의 rows 확인
        ↓
4. actual time 확인
        ↓
5. loops 확인
        ↓
6. Sort / Join / SubPlan 등 비용 큰 작업 확인
        ↓
7. 예상 rows와 actual rows 비교
        ↓
8. 개선 가능성 검토
```

### 1단계. 최상위 노드 확인 (총 비용)

전체 쿼리가 어떤 작업을 마지막으로 수행하는지 확인한다.

### 2단계. 하위 노드 확인

큰 `cost`, 많은 `rows`, 긴 `actual time`이 나타나는 노드를 찾는다.

### 3단계. 예상 행 수와 실제 행 수 비교

```text
예상 rows ≈ actual rows
→ 통계 예측이 비교적 잘 맞음

예상 rows << actual rows
→ PostgreSQL이 실제 데이터량을 과소평가했을 가능성

예상 rows >> actual rows
→ PostgreSQL이 실제 데이터량을 과대평가했을 가능성
```

### 4단계. 디스크 사용 여부 확인

```text
Sort Method: external merge
Disk: ...
```

와 같은 결과가 있다면 정렬 과정에서 디스크 I/O가 발생하고 있는지도 확인한다.

# **6. 인덱스가 실제로 사용되는지 확인하기**

> ## **6-1 ) 인덱스를 생성했다고 항상 사용하는 것은 아니다**

인덱스를 생성해도 PostgreSQL이 반드시 해당 인덱스를 사용하는 것은 아니다.

PostgreSQL은 비용을 계산한 뒤 더 효율적이라고 판단한 실행계획을 선택한다.

따라서 중요한 것은

```text
인덱스를 생성했다
```

가 아니라

```text
실행계획에서 인덱스가 실제 사용되고 있는가?
```

# **7. 실행계획 요소별 개선 방법**

> ## **7-1 ) 병목 신호와 개선 힌트**

실행계획에서 특정 노드가 보인다고 바로 문제라고 판단하면 안 된다.

**많은 데이터 처리 + 긴 실행시간 + 높은 반복 횟수 + 디스크 사용 여부** 등을 함께 확인한 뒤 개선 방향을 결정해야 한다.

| 실행계획 요소 | 확인해야 할 병목 신호 | 개선 힌트 |
|---|---|---|
| `Seq Scan` | 큰 테이블 전체를 읽는데 실제로 필요한 행은 매우 적음 | `WHERE` 조건 컬럼 인덱스 검토 |
| `Index Scan` | 매우 많은 행을 인덱스로 반복 접근 | 오히려 `Seq Scan`이 나은 상황인지 확인 |
| `Nested Loop` | 큰 데이터에 대해 반복 횟수가 매우 많음 | 조인 컬럼 인덱스, 통계 정보 확인 |
| `Hash Join` | 해시 대상 데이터가 매우 큼 | 조인 전 필터링 가능 여부 확인 |
| `Sort` | 정렬 행이 많고 디스크까지 사용 | 정렬 대상 데이터 축소, 인덱스 검토 |
| `WindowAgg` | 매우 많은 데이터를 먼저 정렬 | 윈도우 함수 대상 행을 사전에 줄일 수 있는지 확인 |
| `SubPlan` | 각 행마다 서브쿼리가 반복 실행됨 | `JOIN`, CTE, 윈도우 함수 등으로 재작성 검토 |
| 예상/실제 `rows` 큰 차이 | 옵티마이저가 데이터 규모를 잘못 예측 | `ANALYZE`, 통계 정보 확인 |

<br>

> ## **7-2 ) Seq Scan이 나타났을 때**

다음과 같이 큰 테이블에서 특정 선수만 조회한다고 가정한다.

```sql
SELECT *
FROM athlete_measurements
WHERE athlete_id = 500;
```

실행계획이 다음과 같다면

```text
Seq Scan on athlete_measurements
```

`athlete_id`로 전체 테이블을 읽고 있는 것이다.

데이터가 매우 크고 `athlete_id = 500`에 해당하는 데이터가 적다면 다음과 같은 인덱스를 검토할 수 있다.

[ sql : code ] "선수 번호를 이용한 조회 성능 개선을 위해 인덱스 생성"

```sql
CREATE INDEX idx_athlete_measurements_athlete_id
ON athlete_measurements(athlete_id);
```

인덱스 생성 후 다시 실행계획을 확인한다.

```sql
EXPLAIN ANALYZE
SELECT *
FROM athlete_measurements
WHERE athlete_id = 500;
```

[ Result ]

예를 들어 다음과 같이 바뀔 수 있다.

```text
Index Scan using idx_athlete_measurements_athlete_id
on athlete_measurements

Index Cond: (athlete_id = 500)
```

단, 인덱스를 만들었다고 해서 반드시 `Index Scan`으로 변경되는 것은 아니다.

<br>

> ## **7-3 ) Sort가 병목일 때**

다음 쿼리를 생각해보자.

```sql
SELECT *
FROM running_records
ORDER BY record_time;
```

수백만 행을 모두 정렬해야 한다면 `Sort` 비용이 매우 커질 수 있다.

개선 방법으로는 다음과 같은 방법을 검토할 수 있다.

```text
전체 데이터 정렬
        ↓
정말 전체 데이터가 필요한가?
        ↓
WHERE로 데이터 범위 축소
        ↓
LIMIT 적용 가능 여부 확인
        ↓
정렬 컬럼 인덱스 검토
```

예를 들어 최근 기록 100개만 필요하다면

```sql
SELECT *
FROM running_records
ORDER BY record_time DESC
LIMIT 100;
```

처럼 불필요한 대량 결과 반환을 줄일 수 있다.

<br>

> ## **7-4 ) SubPlan이 반복될 때**

선수마다 평균 기록을 계산하는 상관 서브쿼리가 있다고 가정한다.

[ sql : code ] "선수마다 서브쿼리를 반복 실행하는 예제"

```sql
SELECT
    p.player_id,
    p.player_name,
    (
        SELECT AVG(m.distance_km)
        FROM match_stats m
        WHERE m.player_id = p.player_id
    ) AS avg_distance
FROM players p;
```

실행계획에서 `SubPlan`이 선수마다 반복 수행되면 데이터가 많을수록 비용이 커질 수 있다.

경우에 따라 다음처럼 미리 집계한 후 조인하는 구조를 검토할 수 있다.

[ sql : code ] "경기 기록을 먼저 집계한 뒤 선수 테이블과 조인하는 방식"

```sql
SELECT
    p.player_id,
    p.player_name,
    m.avg_distance
FROM players p
LEFT JOIN (
    SELECT
        player_id,
        AVG(distance_km) AS avg_distance
    FROM match_stats
    GROUP BY player_id
) m
    ON p.player_id = m.player_id;
```

### 두 방식 비교

| 방식 | 처리 특징 |
|---|---|
| 상관 서브쿼리 | 선수마다 서브쿼리가 반복될 가능성 |
| 집계 후 `JOIN` | 경기 데이터를 한 번 집계한 뒤 선수와 연결 |

항상 두 번째 방식이 빠르다고 단정할 수는 없으므로 최종 판단은 `EXPLAIN ANALYZE` 결과를 비교해야 한다.

# **8. EXPLAIN 분석 실전 순서**

> ## **8-1 ) 처음 보는 실행계획에서 확인할 순서**

실행계획을 처음부터 모든 숫자까지 분석하려고 하면 복잡해진다.

다음 순서로 확인하면 비교적 쉽게 접근할 수 있다.

```text
① Scan
어떻게 데이터를 읽는가?
        ↓
② rows
몇 행을 읽거나 반환하는가?
        ↓
③ Filter
불필요한 데이터를 많이 읽고 버리고 있지는 않은가?
        ↓
④ Join
어떤 방식으로 테이블을 연결하는가?
        ↓
⑤ Sort
대량 정렬이 발생하는가?
        ↓
⑥ actual time
실제로 어느 작업에서 시간이 사용되는가?
        ↓
⑦ loops
같은 작업이 지나치게 반복되는가?
        ↓
⑧ 예상 rows ↔ actual rows
옵티마이저 예측이 실제와 크게 다른가?
        ↓
⑨ Execution Time
전체 SQL 실행시간은 얼마인가?
```

<br>

> ## **8-2 ) 데이터 사이언티스트가 우선 확인할 항목**

DBA 수준으로 모든 실행계획 노드를 깊게 이해할 필요는 없다.

데이터 분석 업무에서는 우선 다음 정도를 확인할 수 있으면 충분하다.

| 질문 | 확인 항목 |
|---|---|
| 데이터를 어떻게 읽는가? | `Seq Scan`, `Index Scan` |
| 너무 많은 데이터를 읽고 있는가? | `rows`, `actual rows` |
| 테이블 연결이 어떻게 이루어지는가? | `Nested Loop`, `Hash Join`, `Merge Join` |
| 정렬이 발생하는가? | `Sort` |
| 정렬이 디스크까지 사용하는가? | `Sort Method`, `Disk` |
| 윈도우 함수 연산이 있는가? | `WindowAgg` |
| 반복되는 서브쿼리가 있는가? | `SubPlan`, `loops` |
| 어떤 작업에서 실제 시간이 많이 사용되는가? | `actual time` |
| 전체 실행시간은 얼마인가? | `Execution Time` |

# **9. Advanced 추가 학습**

> ## **9-1 ) ANALYZE와 통계 정보**

PostgreSQL은 데이터의 분포를 기반으로 실행계획을 결정한다.

데이터가 크게 변경되었는데 통계 정보가 오래된 경우 옵티마이저가 `rows`를 잘못 예상할 수 있다.

이때 `ANALYZE`를 통해 통계 정보를 갱신할 수 있다.

```sql
ANALYZE match_stats;
```

쉽게 말하면 PostgreSQL에게

```text
"현재 데이터가 어떻게 분포되어 있는지 다시 조사해."
```

라고 요청하는 작업이다.

<br>

> ## **9-2 ) 복합 인덱스**

조건과 정렬이 함께 사용되는 SQL에서는 하나의 컬럼만 사용하는 인덱스뿐 아니라 **복합 인덱스**를 검토할 수도 있다.

예를 들어

```sql
WHERE player_id = 100
ORDER BY match_date DESC
```

가 자주 사용된다면 다음과 같은 구조를 검토할 수 있다.

```sql
CREATE INDEX idx_player_match_date
ON match_stats(player_id, match_date DESC);
```

하지만 인덱스가 많아질수록 저장 공간과 데이터 입력·수정 비용도 증가하므로 필요한 SQL 패턴을 기준으로 설계해야 한다.

<br>

> ## **9-3 ) BUFFERS 옵션**

조금 더 깊게 분석하려면 다음과 같이 `BUFFERS` 옵션을 사용할 수 있다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM match_stats
WHERE player_id = 100;
```

이를 통해 실행시간뿐 아니라 PostgreSQL이 데이터를 읽을 때 **메모리와 디스크를 얼마나 사용했는지**도 추가로 확인할 수 있다.

처음에는 `EXPLAIN ANALYZE`에 익숙해진 후 학습하면 된다.

# **10. 핵심정리**

- `EXPLAIN`은 PostgreSQL이 선택한 **예상 실행계획**을 확인하는 명령어이다.
- `EXPLAIN ANALYZE`는 SQL을 실제로 실행하여 `actual time`, `actual rows`, `loops`, `Execution Time` 등을 확인할 수 있다.
- 실행계획은 **트리 구조**이며 일반적으로 아래쪽의 데이터 조회 작업부터 위쪽으로 따라가면 이해하기 쉽다.
- `Scan`은 데이터를 읽는 작업이며 대표적으로 `Seq Scan`, `Index Scan`, `Bitmap Scan` 등이 있다.
- `Seq Scan`이 나타났다고 무조건 성능 문제가 있는 것은 아니며 데이터 조회 비율과 테이블 크기를 함께 확인해야 한다.
- `Join`에서는 `Nested Loop`, `Hash Join`, `Merge Join` 등의 방식이 사용될 수 있으며 조인 방식뿐 아니라 처리 행 수도 함께 확인한다.
- `Sort` 대상 데이터가 많으면 비용이 증가할 수 있으며 `external merge`와 `Disk`가 나타난다면 디스크 정렬이 발생한 것이다.
- `WindowAgg`는 `RANK()`, `ROW_NUMBER()` 등의 윈도우 함수 처리 과정에서 나타날 수 있다.
- `cost`는 PostgreSQL의 **예상 상대 비용**이며 실제 실행시간을 의미하지 않는다.
- `rows`는 예상 행 수이고 `actual rows`는 실제 처리된 행 수이다.
- 예상 `rows`와 `actual rows`의 차이가 매우 크다면 PostgreSQL의 데이터 통계나 선택도 예측을 확인할 필요가 있다.
- 병목은 하나의 `cost` 값만으로 결정하기보다 `actual time`, `rows`, `loops`, 정렬 방식, 디스크 사용 등을 함께 확인한다.
- 인덱스를 생성했다고 PostgreSQL이 반드시 사용하는 것은 아니므로 `EXPLAIN` 또는 `EXPLAIN ANALYZE`에서 실제 사용 여부를 확인해야 한다.
- `Index Cond`를 통해 어떤 조건에 인덱스가 적용되었는지 확인할 수 있다.
- `Seq Scan`이 실제 병목이라면 조건 컬럼의 인덱스를 검토할 수 있다.
- `Sort`가 병목이라면 조회 범위 축소, `LIMIT`, 정렬 컬럼 인덱스 등을 검토할 수 있다.
- `SubPlan`이 많은 행에 대해 반복된다면 `JOIN`, 사전 집계, 윈도우 함수 등 다른 SQL 구조를 검토할 수 있다.
- SQL 튜닝의 핵심 흐름은 **실행계획 확인 → 병목 위치 파악 → 개선 → 다시 EXPLAIN ANALYZE로 비교**이다.

```text
SQL 실행이 느림
      ↓
EXPLAIN ANALYZE
      ↓
Scan / Join / Sort 확인
      ↓
rows / actual rows 확인
      ↓
actual time / loops 확인
      ↓
병목 구간 발견
      ↓
인덱스 / 필터링 / 조인 / 정렬 개선
      ↓
다시 EXPLAIN ANALYZE
      ↓
개선 전후 성능 비교
```
