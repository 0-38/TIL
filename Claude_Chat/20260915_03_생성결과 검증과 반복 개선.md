# **1. 생성형 AI 결과는 반드시 검증해야 한다**

Claude와 같은 생성형 AI는 자연스러운 문장, 코드, 분석 결과를 빠르게 생성할 수 있다.

하지만 결과가 자연스럽고 그럴듯하게 보인다고 해서 반드시 정확한 것은 아니다.

생성형 AI는 다음과 같은 문제를 포함한 결과를 생성할 수 있다.

```text
사실과 다른 설명
잘못된 코드
요구사항과 다른 계산
부적절한 분석 방법
과도한 결과 해석
일부 요구사항 누락
```

따라서 다음 원칙을 기억해야 한다.

```text
결과가 생성되었다
≠
결과가 검증되었다
```

<br>

> ## **1-1 ) 자연스러운 답변이 항상 정확한 것은 아니다**

예를 들어 운동역학 딥러닝 프로젝트에서 다음과 같이 질문했다고 가정한다.

[Prompt : code] "LSTM 모델의 성능에 대한 질문"

```text
LSTM Layer를 많이 쌓으면
무릎 관절각 예측 성능이 항상 좋아지는 거지?
```

Claude가 다음과 같이 답변했다고 가정해보자.

[ Result ]

```text
네.

LSTM Layer를 많이 쌓을수록
더 복잡한 특징을 학습할 수 있기 때문에
모델의 성능은 계속 좋아집니다.

따라서 가능한 한 많은 LSTM Layer를 사용하는 것이 좋습니다.
```

문장 자체는 자연스럽지만 내용에는 문제가 있다.

LSTM Layer를 증가시키면 모델의 표현력이 높아질 수 있지만 모델이 지나치게 복잡해져 다음 문제가 발생할 수 있다.

```text
과적합
학습 시간 증가
Gradient 문제
불필요한 모델 복잡도 증가
Validation 성능 저하
```

따라서 Layer를 많이 사용한다고 항상 성능이 좋아지는 것은 아니다.

올바른 설명은 다음과 같다.

```text
LSTM Layer 증가
        ↓
모델 복잡도 증가
        ↓
복잡한 패턴 학습 가능

하지만

모델 복잡도 증가
        ↓
학습 데이터에 과도하게 적합
        ↓
Overfitting 가능성 증가
        ↓
새로운 데이터 예측 성능 저하 가능
```

즉, `Training Loss`만 확인할 것이 아니라 `Validation Loss`와 `Test 성능`까지 함께 확인해야 한다.

<br>

> ## **1-2 ) 생성형 AI에서 발생할 수 있는 주요 오류**

| 오류 유형 | 설명 | 운동역학 딥러닝 예시 |
|---|---|---|
| 사실과 다른 내용 | 모델이나 개념을 잘못 설명 | LSTM Layer가 많을수록 항상 좋다고 설명 |
| 맥락 오해 | 사용자의 데이터나 목적을 잘못 이해 | 무릎 각도를 예측해야 하는데 분류 문제로 처리 |
| 잘못된 코드 | 실행되지 않거나 잘못 동작 | 존재하지 않는 `knee_flexion` 컬럼 사용 |
| 잘못된 계산 | 실행되지만 원하는 계산과 다름 | MAE 요청에 MSE 계산 |
| 잘못된 분석 | 부적절한 분석 방법 적용 | 시계열 순서를 무시하고 무작위 데이터 처리 |
| 잘못된 해석 | 결과보다 지나친 결론 | 높은 상관관계를 인과관계로 해석 |
| 요구사항 누락 | 일부 조건을 반영하지 않음 | Subject 단위 데이터 분할 조건 누락 |

특히 다음 두 상황을 구분해야 한다.

```text
실행 자체가 안 되는 코드
→ 비교적 쉽게 발견 가능

실행은 되지만 계산이 틀린 코드
→ 발견하기 어려움
```

두 번째 상황이 더 위험할 수 있다.

<br>

> ## **1-3 ) Claude에게 자기 검토를 요청할 수도 있다**

Claude가 생성한 결과를 다시 검토하도록 요청할 수도 있다.

[Prompt : code] "생성 결과 자기 검토 요청"

```text
방금 작성한 운동역학 딥러닝 분석 내용을 다시 검토해줘.

- 사실과 다른 설명이 있는지
- 내가 요청한 조건을 누락한 부분이 있는지
```

# **2. 생성된 코드를 검증하는 방법**

Claude가 Python 코드를 생성했다고 해서 바로 실제 분석에 사용하는 것은 위험하다.

코드를 검증할 때는 단순히 실행 여부뿐만 아니라 **요구한 작업과 실제 코드가 일치하는지** 확인해야 한다.

> ## **2-1 ) 실행되는 코드가 항상 올바른 것은 아니다**

예를 들어 보행 예측모델의 성능을 `MAE`로 평가해달라고 요청했다고 가정한다.

Claude가 다음 코드를 작성했다.

[Python : code] "잘못된 모델 평가 코드"

```python
from sklearn.metrics import mean_squared_error

score = mean_squared_error(
    y_test,
    y_pred
)

print(score)
```

[ Result ]

```text
12.84
```

코드는 정상적으로 실행될 수 있다.

하지만 사용자가 요구한 것은 `MAE`이고 코드에서는 `MSE`를 계산하고 있다.

즉,

```text
코드 실행 성공
≠
요구사항 수행 성공
```

이다.

<br>

> ## **2-2 ) 올바르게 수정한 코드**

[Python : code] "무릎 관절각 예측 MAE 계산"

```python
from sklearn.metrics import mean_absolute_error

mae = mean_absolute_error(
    y_test,
    y_pred
)

print(round(mae, 2))
```

[ Result ]

```text
2.41
```

결과는 다음과 같이 해석할 수 있다.

```text
MAE = 2.41
```

예측값과 실제 무릎 관절각의 차이가 평균적으로 약 `2.41°`라고 해석할 수 있다.

단, 실제로 결과가 좋은지 나쁜지는 다음 요소와 함께 판단해야 한다.

```text
측정 장비의 오차
타깃 관절각의 범위
기존 연구 성능
Baseline Model
실제 연구 목적
```

<br>

> ## **2-3 ) 코드 검증 순서**

Claude가 생성한 코드는 다음 순서로 검증할 수 있다.

```text
1. 코드를 직접 실행
        ↓
2. 오류 발생 여부 확인
        ↓
3. 사용 컬럼 확인
        ↓
4. 함수와 계산 방법 확인
        ↓
5. 입력 데이터 확인
        ↓
6. 출력 데이터 확인
        ↓
7. 요구사항과 비교
        ↓
8. 결과값의 범위 확인
```

확인해야 하는 내용을 표로 정리하면 다음과 같다.

| 확인 항목 | 확인 내용 |
|---|---|
| 실행 여부 | Syntax Error 등의 오류가 없는가? |
| 컬럼 | 실제 존재하는 컬럼인가? |
| 함수 | 목적에 맞는 함수를 사용했는가? |
| 입력 | 올바른 데이터를 입력했는가? |
| 출력 | 원하는 결과가 출력되는가? |
| 계산 방식 | 요청한 계산 방식과 일치하는가? |
| 결과 범위 | 비정상적으로 큰 값이나 작은 값이 아닌가? |

<br>

> ## **2-4 ) 예측모델에서 특히 확인할 코드**

운동역학 딥러닝 모델에서는 다음 부분을 특히 확인해야 한다.

```text
Train / Validation / Test 분할

Scaling

Window 생성

Input Shape

Target 생성

Loss Function

Evaluation Metric
```

예를 들어 다음과 같은 오류가 발생할 수 있다.

```text
전체 데이터 Scaling
        ↓
Train / Test Split
```

이 과정은 Test 데이터의 정보가 학습 과정에 반영될 가능성이 있기 때문에 데이터 누수가 발생할 수 있다.

보다 안전한 흐름은 다음과 같다.

```text
Train / Test Split
        ↓
Train 데이터로 Scaler 학습
        ↓
Train Transform
        ↓
Test Transform
```

예를 들어 다음과 같이 작성할 수 있다.

[Python : code] "Train 데이터만 이용한 StandardScaler 학습"

```python
from sklearn.preprocessing import StandardScaler

scaler = StandardScaler()

X_train_scaled = scaler.fit_transform(X_train)

X_test_scaled = scaler.transform(X_test)
```

여기서 중요한 차이는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `fit_transform(X_train)` | Train 데이터로 기준을 학습하고 변환 |
| `transform(X_test)` | Train에서 학습한 기준만 사용하여 Test 변환 |

# **3. 분석 결과를 검증하는 방법**

코드가 올바르게 실행되더라도 분석 결과의 해석이 잘못될 수 있다.

따라서 코드와 결과 해석은 별도로 검증해야 한다.

> ## **3-1 ) 상관관계와 인과관계 구분**

예를 들어 보행 데이터에서 다음 결과가 나왔다고 가정한다.

```text
보행 속도와 무릎 최대 굴곡각의
상관계수 = 0.78
```

Claude가 다음과 같이 해석했다고 가정한다.

```text
보행 속도가 증가하면
무릎 최대 굴곡각이 증가합니다.

따라서 무릎 굴곡각을 증가시키기 위해서는
보행 속도를 증가시키는 것이 좋습니다.
```

이 해석에는 문제가 있다.

상관관계가 높다는 것은 두 변수가 함께 변화하는 경향이 있다는 의미이지 하나가 다른 하나의 원인이라는 것을 의미하지 않는다.

```text
상관관계

보행 속도 ↑
무릎 굴곡각 ↑

→ 두 변수가 함께 변화하는 경향
```

하지만 이것만으로 다음을 증명할 수는 없다.

```text
보행 속도 증가
        ↓
무릎 굴곡각 증가
```

즉,

```text
Correlation
≠
Causation
```

이다.

<br>

> ## **3-2 ) 모델 결과 역시 지나치게 해석하면 안 된다**

예를 들어 LSTM 모델에서 다음 결과가 나왔다고 가정한다.

```text
MAE = 2.3°
RMSE = 3.1°
```

이 결과만 보고 다음과 같이 결론을 내리면 안 된다.

```text
LSTM이 무릎 관절각을 정확하게 예측하므로
실제 임상 환경에서도 사용할 수 있다.
```

추가적으로 확인해야 할 내용이 많다.

```text
Test 데이터가 완전히 독립적인가?

여러 피험자를 대상으로 검증했는가?

특정 피험자에게만 잘 맞는 것은 아닌가?

측정 장비의 오차는 어느 정도인가?

Baseline보다 실제로 성능이 좋은가?

다른 속도나 조건에서도 성능이 유지되는가?
```

따라서 보다 적절한 해석은 다음과 같다.

```text
현재 Test 데이터에서
LSTM 모델의 무릎 관절각 예측 오차는

MAE = 2.3°
RMSE = 3.1°

로 나타났다.

다만 일반화 성능을 판단하기 위해서는
독립적인 피험자와 다양한 보행 조건에서
추가적인 검증이 필요하다.
```

<br>

> ## **3-3 ) 분석 결과 검증 흐름**

```text
사용한 데이터 확인
       ↓
분석 방법 확인
       ↓
계산 과정 확인
       ↓
결과값 확인
       ↓
해석 확인
       ↓
과도한 결론 여부 확인
```

분석 결과에서는 다음 내용을 확인해야 한다.

| 항목 | 검증 질문 |
|---|---|
| 데이터 | 분석에 적절한 데이터를 사용했는가? |
| 계산 | 계산 방법이 올바른가? |
| 모델 | 문제에 적합한 모델인가? |
| 평가 | 평가 지표가 적절한가? |
| 해석 | 결과가 올바르게 해석되었는가? |
| 결론 | 결과 이상의 주장을 하고 있지 않은가? |

# **4. 운동역학 딥러닝 모델 결과 검증 예시**

> ## **4-1 ) 잘못된 성능 비교 예시**

다음과 같은 모델 결과가 있다고 가정한다.

```text
LSTM

Train MAE = 0.8°
Validation MAE = 1.1°
Test MAE = 8.5°
```

Claude가 다음과 같이 해석했다.

```text
Train MAE가 0.8°로 매우 낮으므로
모델의 예측 성능이 매우 좋습니다.
```

이 해석은 적절하지 않다.

모델의 실제 일반화 성능은 `Train`이 아니라 `Validation` 및 특히 독립적인 `Test` 데이터 성능을 함께 확인해야 한다.

현재 결과는 다음과 같다.

```text
Train MAE
0.8°

Validation MAE
1.1°

Test MAE
8.5°
```

Test 성능이 크게 나빠졌기 때문에 다음 문제를 의심할 수 있다.

```text
Overfitting

Train / Test 데이터 분포 차이

피험자 차이

전처리 문제

데이터 누수 여부

Test 환경 차이
```

<br>

> ## **4-2 ) Train과 Validation Loss 확인**

[Python : code] "LSTM 학습 과정에서 과적합 확인"

```python
history = model.fit(
    X_train,
    y_train,
    validation_data=(X_val, y_val),
    epochs=50,
    batch_size=32
)

train_loss = history.history["loss"]
val_loss = history.history["val_loss"]

print("Train Loss:", round(train_loss[-1], 3))
print("Validation Loss:", round(val_loss[-1], 3))
```

[ Result ]

```text
Train Loss: 1.124
Validation Loss: 6.842
```

Train Loss보다 Validation Loss가 훨씬 높게 나타난다면 과적합 가능성을 확인해야 한다.

```text
Epoch 증가
      ↓
Train Loss 계속 감소

하지만

Validation Loss 증가
      ↓
새로운 데이터에 대한 성능 저하
      ↓
Overfitting 가능성
```

이 경우 다음 방법을 검토할 수 있다.

```text
Early Stopping
Dropout
모델 구조 단순화
데이터 증가
Regularization
학습 Epoch 조절
```

하지만 이 방법 역시 무조건 적용하는 것이 아니라 실제 원인을 먼저 확인해야 한다.

# **5. 피드백을 이용한 결과 개선**

Claude가 생성한 결과에서 문제가 발견되었다면 처음부터 다시 요청할 필요는 없다.

문제가 무엇인지와 원하는 수정 방향을 구체적으로 전달하면 된다.

> ## **5-1 ) 좋지 않은 피드백**

```text
틀렸어.

다시 해줘.
```

이러한 요청은 무엇이 잘못되었는지 명확하지 않다.

# **11. 핵심정리**

1. 생성형 AI가 만든 결과는 자연스럽고 그럴듯해 보여도 반드시 정확하다고 볼 수 없다.

2. 생성형 AI에서는 `사실 오류`, `맥락 오해`, `잘못된 코드`, `잘못된 분석`, `요구사항 누락`, `잘못된 해석` 등이 발생할 수 있다.

3. 중요한 원칙은 `결과가 생성되었다 ≠ 결과가 검증되었다`이다.

4. 코드 검증에서는 단순히 실행되는지만 확인하는 것이 아니라 **요구사항대로 동작하는지, 올바른 함수와 계산 방법을 사용했는지** 확인해야 한다.

5. 실행 가능한 코드라도 `mean()` 대신 `sum()`을 사용하거나 `MAE` 대신 `MSE`를 계산하는 등 논리적인 오류가 있을 수 있다.

6. 딥러닝 예측모델에서는 `Train / Validation / Test 분할`, `Scaling`, `Window 생성`, `Input Shape`, `Loss Function`, `Evaluation Metric`을 특히 확인해야 한다.

7. 운동역학 데이터에서는 같은 피험자의 데이터가 Train과 Test에 섞이지 않았는지 확인하여 **데이터 누수와 과대평가 가능성**을 검토해야 한다.

8. 분석 결과는 데이터와 계산 방법뿐 아니라 **결과의 해석이 적절한지**도 검증해야 한다.

9. 높은 상관관계가 있다고 해서 하나의 변수가 다른 변수의 원인이라고 판단할 수 없으므로 `상관관계 ≠ 인과관계`를 기억해야 한다.

10. 낮은 Training Loss만으로 좋은 모델이라고 판단하지 말고 `Validation`과 독립적인 `Test` 데이터의 성능을 확인해야 한다.

11. 문제가 발견되었을 때 `다시 해줘`라고 요청하기보다 **현재 문제, 문제가 되는 이유, 원하는 수정 방향**을 구체적으로 전달하는 것이 좋다.

12. 수정된 결과 역시 다시 검증해야 하며 생성형 AI와의 작업은 `생성 → 검증 → 피드백 → 수정 → 재검증`의 반복 과정으로 이루어진다.

13. Claude가 생성한 결과는 최종 정답이라기보다 **사람이 검토하고 개선해야 하는 초안**으로 활용하는 것이 중요하다.
