# PostgreSQL Index

# **[ 1. B-Tree 인덱스 ]**

> B-Tree   
= 데이터를 **정렬된 트리 구조**로 관리하고,    
검색 범위를 단계적으로 줄여 원하는 값을 빠르게 찾는 인덱스 구조.

PostgreSQL에서 일반적으로 사용하는 기본 인덱스 방식.

### B-Tree 탐색 원리

인덱스가 없으면 조건에 맞는 데이터를 찾기 위해 테이블의 많은 행을 직접 확인하는 `Seq Scan`이 발생할 수 있음.

[ sql : code ] **인덱스 생성 코드**
```sql
-- orders 테이블의 customer_id에 인덱스가 있다고 가정

CREATE INDEX idx_orders_customer_id
ON orders (customer_id);


EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 300;
```

[ Result ]
```text
Bitmap Heap Scan on orders  (cost=4.47..27.82 rows=6 width=32)
  Recheck Cond: (customer_id = 300)
  ->  Bitmap Index Scan on idx_orders_customer_id  (cost=0.00..4.47 rows=6 width=0)
        Index Cond: (customer_id = 300)
```

```text
[10] → [20] → [30] → [40] → ... → [300]
             하나씩 확인
```

### **[ 인덱스 동작 구조 ]**
B-Tree 인덱스가 있으면 정렬된 구조를 따라 **검색 범위를 좁혀감**.

```text
전체 데이터
    │
    ├── 200보다 작음
    │
    ├── 200 ~ 500
    │       │
    │       └── 300 발견
    │
    └── 500보다 큼
```

즉, 전체 데이터를 하나씩 확인하는 대신 값의 범위를 단계적으로 좁혀 원하는 데이터를 빠르게 찾는다.

# **[ 2. 인덱스 생성 ]**

```sql
CREATE INDEX 인덱스명
ON 테이블명 (컬럼명);
```

예시:

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);

-- oreders 테이블에 customer_id에 인덱스를 만든다.
```

검색:

```sql
SELECT *
FROM orders
WHERE customer_id = 300;
```

> 만약 `CREATE INDEX` 후에 새로운 데이터를 추가해야한다면,    
현재 존재하는 INDEX와 관련된 INDEX에도 새로운 키를 반영해야한다.

예시)
```sql
-- 1. 인덱스 생성
CREATE INDEX idx_products_name
ON products (product_name);

CREATE INDEX idx_products_category
ON products (category_id);

-- 2. 데이터 추가
INSERT INTO products (
    product_id,
    product_name,
    category_id
)
VALUES (
    1001,
    '무선 키보드',
    3
) ;

---------------------
products 테이블
    ↓ 새 상품 저장

idx_products_name
    ↓ 인덱스 갱신

idx_products_category
    ↓ 인덱스 갱신

idx_products_price
    ↓ 인덱스 갱신
```

#### 1. [ 인덱스 장점 ]
- 검색 속도 향상 가능
- `WHERE` 조건 검색에 유리
- 범위 검색에 유리
- 정렬이나 `JOIN`에서도 활용될 수 있음
- 데이터가 많을수록 효과가 커질 수 있음

<br>

####  2. [ 인덱스의 단점 ]

인덱스는 조회 성능을 높일 수 있지만 추가 비용이 발생.

#### **INSERT**

새로운 데이터가 추가되면 인덱스에도 새로운 값을 추가해야 함.

```text
테이블 INSERT
      ↓
인덱스에도 데이터 추가
```

#### **UPDATE**

인덱스가 걸린 컬럼의 값이 변경되면 인덱스도 갱신해야 함.

#### **DELETE**

데이터가 삭제되면 인덱스에서도 해당 항목을 제거해야 함.

따라서 인덱스가 많아질수록:

```text
INSERT
UPDATE
DELETE
```

같은 쓰기 작업의 비용이 증가할 수 있음.

<br>

#### 3. 인덱스는 많을수록 좋은가?

아님.

인덱스를 많이 만들면 조회 성능에는 도움이 될 수 있지만:

- 저장 공간 증가
- INSERT 성능 저하
- UPDATE 성능 저하
- DELETE 성능 저하
- 인덱스 관리 비용 증가

등의 문제가 발생할 수 있음.

따라서 **자주 조회하는 컬럼을 중심으로 필요한 인덱스만 생성**하는 것이 중요.

# **[ 3. 인덱스 실행계획 ]**

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 300;
```

실행계획 예시:

```text
Bitmap Heap Scan on orders
  Recheck Cond: (customer_id = 300)
  -> Bitmap Index Scan on idx_orders_customer_id
       Index Cond: (customer_id = 300)
```

### 실행계획 해석

| Scan 방식 | 설명 |
|---|---|
| `Seq Scan` | 테이블을 순차적으로 탐색 |
| `Index Scan` | 인덱스를 이용해 필요한 행을 탐색 |
| `Bitmap Index Scan` | 인덱스를 이용해 조건에 맞는 행의 위치를 먼저 수집 |
| `Bitmap Heap Scan` | 수집한 위치를 이용해 실제 테이블 데이터 조회 |

# **[ 4. B-Tree가 잘 활용되는 조건 ]**

B-Tree는 정렬된 구조를 사용하기 때문에 비교 연산과 범위 검색에 적합.

```sql
-- 같은 값 검색
WHERE customer_id = 300

-- 범위 검색
WHERE price >= 100

WHERE price BETWEEN 100 AND 200

-- 크기 비교
WHERE age > 30

WHERE age < 50
```

대표적으로 다음 연산에서 활용 가능.

```text
=
<
>
<=
>=
BETWEEN
```

# **[ 7. Index Scan vs Bitmap Index Scan ]**

PostgreSQL은 항상 `Index Scan`만 사용하는 것은 아님.

> ## 7-1 ) Index Scan

조건에 맞는 데이터가 적을 때 주로 유리.

```text
Index
  ↓
행 위치 확인
  ↓
Table
```

<br>

> ## 7-2 ) Bitmap Index Scan

조건에 맞는 데이터가 어느 정도 많을 때 여러 행의 위치를 먼저 모아 접근.

```text
Index
  ↓
조건에 맞는 위치 수집
  ↓
Bitmap 생성
  ↓
Table 접근
```

<br><br>

---


# **[ 8. 인덱스가 있어도 Seq Scan을 사용할 수 있음 ]**

인덱스가 있다고 해서 PostgreSQL이 항상 인덱스를 사용하는 것은 아님.

옵티마이저가 실행 비용을 비교해서 더 효율적이라고 판단하는 방법을 선택.

예를 들어 전체 데이터 중 대부분을 조회하는 경우:

```sql
SELECT *
FROM products
WHERE price > 1;
```

대부분의 행이 조건을 만족한다면 인덱스를 여러 번 탐색하는 것보다 전체 테이블을 읽는 `Seq Scan`이 더 빠를 수 있음.

즉,

```text
인덱스 존재 = 무조건 Index Scan
```

이 아님.

# **[ 9. 선택도 Selectivity ]**

> 선택도   
> : 조건을 통해 전체 데이터 중 얼마나 **적은** 데이터를 선택하는지를 의미.

예:

```text
전체 100,000행
조건 결과 10행
```

→ 선택도가 높음.

```text
전체 100,000행
조건 결과 90,000행
```

→ 선택도가 낮음.

일반적으로 조건에 맞는 데이터가 적을수록 인덱스 사용이 유리해질 가능성이 높음.

# **[ 10. 복합 인덱스 ]**

여러 컬럼을 하나의 인덱스로 만들 수도 있음.

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);
```

예:

```sql
SELECT *
FROM orders
WHERE customer_id = 300
  AND order_date >= '2026-01-01';
```

복합 인덱스에서는 **컬럼 순서가 중요**함.

```text
(customer_id, order_date)
```

인덱스라면 일반적으로 `customer_id` 조건부터 사용하는 쿼리에 더 적합.

# **[ 11. 인덱스 적용 전후 비교 ]**

인덱스 효과를 확인할 때는 `EXPLAIN ANALYZE` 사용.

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 300;
```

```text
Gather  (cost=1000.00..7374.39 rows=6 width=32) (actual time=7.095..69.705 rows=7.00 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared read=3731
  ->  Parallel Seq Scan on orders  (cost=0.00..6373.79 rows=2 width=32) (actual time=2.177..18.589 rows=2.33 loops=3)
        Filter: (customer_id = 300)
        Rows Removed by Filter: 166664
        Buffers: shared read=3731
Planning:
  Buffers: shared hit=45 read=2
Planning Time: 3.150 ms
Execution Time: 69.758 ms
```


비교할 항목:

| 항목 | 의미 |
|---|---|
| Scan 방식 | Seq Scan / Index Scan / Bitmap Scan |
| `cost` | 옵티마이저의 예상 비용 |
| `rows` | 예상 반환 행 수 |
| `actual rows` | 실제 반환 행 수 |
| `actual time` | 각 단계의 실제 수행 시간 |
| `Execution Time` | 전체 쿼리 실행 시간 |

인덱스 생성 전과 생성 후의 실행계획을 비교하면 인덱스가 실제로 사용되었는지 확인 가능.

# **[ 12. 선택도와 카디널리티 ]**

> ## 12-1 ) 카디널리티 (Cardinality)

- 정의 : 컬럼에 **서로 다른 값이 얼마나 많이 존재하는지**를 의미.

예:

| 컬럼 | 카디널리티 |
|---|---|
| `user_id` | 매우 높음 |
| `email` | 높음 |
| `country` | 낮음 |
| `status` | 매우 낮음 |

예를 들어 `user_id`처럼 거의 모든 값이 다르면 카디널리티가 높음.

```text
user_id
1
2
3
4
5
...
```

반대로 `status`처럼 값의 종류가 적으면 카디널리티가 낮음.

```text
status
ACTIVE
INACTIVE
```

<br>

> ## 12-2 ) 선택도 (Selectivity)

정의 : 특정 조건을 적용했을 때 **전체 데이터 중 조건을 만족하는 행의 비율**.

```text
선택도 = 조건을 만족하는 행 수 / 전체 행 수
```

예:

```text
전체 데이터      1,000,000건
조건 만족 데이터          3건

선택도 = 3 / 1,000,000
```

→ 선택도가 매우 낮음.

반대로:

```text
전체 데이터      1,000,000건
조건 만족 데이터    800,000건
```

→ 선택도가 높음.

---

### 인덱스와 선택도

일반적으로:

```text
카디널리티 높음
        +
선택도 낮음
        ↓
인덱스 사용에 유리
```

예:

```sql
SELECT *
FROM orders
WHERE customer_id = 12345;
```

특정 고객의 주문이 전체 데이터에서 몇 건밖에 없다면 인덱스를 이용해 필요한 행만 찾는 것이 효율적.

반대로:

```sql
SELECT *
FROM orders
WHERE payment_status = '결제완료';
```

전체 주문의 대부분이 `결제완료`라면 많은 행을 읽어야 하므로 `Seq Scan`이 더 효율적일 수 있음.

# **[ 13. 카디널리티와 선택도에 따른 인덱스 효과 ]**

| 컬럼 예시 | 카디널리티 | 선택도 | 인덱스 효과 |
|---|---|---|---|
| `user_id` | 매우 높음 | 매우 낮음 | 매우 효과적 |
| `email` | 높음 | 낮음 | 효과적 |
| `country` | 낮음 | 비교적 높음 | 상황에 따라 다름 |
| `status` | 낮음 | 높음 | 효과가 작을 수 있음 |
| `gender` | 매우 낮음 | 매우 높음 | 효과가 거의 없을 수 있음 |

즉, 값의 종류가 적고 조건을 걸어도 많은 행이 남는 컬럼은 인덱스 효과가 낮을 가능성이 큼.

# **[ 14. 인덱스가 비효율적인 경우 ]**

다음과 같은 경우에는 인덱스가 있어도 효과가 작거나 사용되지 않을 수 있음.

> ### 1. 선택도가 높은 경우

- 조건을 걸어도 대부분의 행이 남는 경우.

```sql
WHERE status = 'ACTIVE'
```

- 전체 데이터 대부분이 `ACTIVE`라면 인덱스 효과가 작을 수 있음.

> ### 2. 테이블이 작은 경우

- 수백 건 정도의 작은 테이블은 전체를 읽는 비용 자체가 작음.

```text
작은 테이블
→ Seq Scan 비용 자체가 낮음
```

> ### 3. 쓰기 작업이 많은 경우

```text
INSERT
UPDATE
DELETE
```

가 자주 발생하면 인덱스 유지 비용이 증가.

- 따라서 조회 성능 이득보다 쓰기 비용이 더 클 수도 있음.

# **[ 15. WHERE 절과 인덱스 활용 ]**

인덱스가 걸린 컬럼은 가능하면 **가공하지 않고 그대로 비교**하는 것이 좋음.

예:

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

### 인덱스를 활용하기 좋은 조건

```sql
SELECT *
FROM orders
WHERE customer_id = 5000;
```

### 인덱스를 활용하기 어려울 수 있는 조건

```sql
SELECT *
FROM orders
WHERE customer_id + 1 = 5001;
```

일반적인 B-Tree 인덱스는 원래 `customer_id` 값을 기준으로 정렬되어 있기 때문에 컬럼에 연산이나 함수가 적용되면 기존 인덱스를 직접 활용하기 어려울 수 있음.

따라서:

```text
WHERE customer_id = 5000
```

처럼 인덱스 컬럼을 직접 비교하는 것이 좋음.

# **[ 16. 함수나 연산이 적용된 컬럼 ]**

아래처럼 인덱스 컬럼에 함수를 적용하는 경우에도 일반 인덱스를 활용하지 못할 수 있음.

```sql
WHERE LOWER(email) = 'test@email.com'
```

이 경우 필요하다면 **표현식 인덱스 Expression Index**를 만들 수 있음.

```sql
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));
```

그러면 다음 조건에서 활용 가능.

```sql
SELECT *
FROM users
WHERE LOWER(email) = 'test@email.com';
```

# **[ 17. 복합 인덱스와 컬럼 순서 ]**

여러 컬럼을 하나의 인덱스로 만들 수 있음.

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);
```

복합 인덱스에서는 **컬럼 순서가 중요**.

```text
(customer_id, order_date)
```

인덱스라면 일반적으로 다음 조건에 활용하기 좋음.

```sql
WHERE customer_id = 100
```

또는:

```sql
WHERE customer_id = 100
  AND order_date >= '2026-01-01'
```

반면 앞쪽 컬럼인 `customer_id` 없이 `order_date`만 사용하는 경우에는 인덱스의 효율이 떨어질 수 있음.

```sql
WHERE order_date >= '2026-01-01'
```

# **[ 18. 복합 인덱스의 기본 원칙 ]**

예:

```text
INDEX (A, B, C)
```

일반적으로 다음과 같은 조건에서 활용하기 쉬움.

```text
A
A + B
A + B + C
```

예:

```sql
CREATE INDEX idx_users_country_age
ON users (country, age);
```

활용하기 좋은 예:

```sql
WHERE country = 'KR'
```

```sql
WHERE country = 'KR'
  AND age >= 30
```

다만 실제 인덱스 사용 여부는 데이터 분포와 비용 계산에 따라 달라질 수 있음.

## [ 19. 인덱스 추가 판단 체크리스트 ]

새로운 인덱스를 만들기 전 다음 항목을 확인.

| 판단 기준 | 확인 내용 |

| 카디널리티 | 서로 다른 값이 충분히 많은가 |
| 선택도 | 조건을 걸었을 때 적은 행만 남는가 |
| 테이블 크기 | 인덱스를 사용할 만큼 데이터가 충분히 많은가 |
| 조회 빈도 | 해당 조건의 조회가 자주 발생하는가 |
| 쓰기 빈도 | INSERT / UPDATE / DELETE가 너무 자주 발생하지 않는가 |
| 실행계획 | 실제로 인덱스가 사용되는가 |

<br><br>

## [ 20. 인덱스를 만들기 좋은 예 ]

상품 데이터가 200만 건 있고 `product_code`가 거의 고유한 값이라고 가정.

```sql
SELECT *
FROM products
WHERE product_code = 'BK-2026-001923';
```

특징:

```text
카디널리티    높음
선택도        매우 낮음
테이블 규모   큼
조회 빈도     높음
```

이 경우 인덱스 추가를 우선 검토할 수 있음.

```sql
CREATE INDEX idx_products_product_code
ON products (product_code);
```

## [ 21. 인덱스를 만들기 애매한 예 ]

```text
employees 테이블
전체 행: 400

status
재직: 370
퇴사: 30
```

다음 조건:

```sql
SELECT *
FROM employees
WHERE status = '재직';
```

`재직` 데이터가 전체의 대부분이기 때문에 선택도가 높음.

또한 테이블 자체도 작기 때문에 PostgreSQL이:

```text
Seq Scan
```

을 선택할 가능성이 있음.

## [ 22. 옵티마이저는 어떻게 Scan 방식을 결정할까? ]

PostgreSQL 옵티마이저는 테이블의 통계정보를 이용하여 예상 비용을 계산.

대표적으로 비교하는 실행 방식:

| Scan 방식 | 설명 |
|---|---|
| `Seq Scan` | 테이블 전체를 순차적으로 탐색 |
| `Index Scan` | 인덱스를 이용해 필요한 행을 직접 탐색 |
| `Bitmap Index Scan` | 조건에 맞는 행 위치를 인덱스에서 먼저 수집 |
| `Bitmap Heap Scan` | 수집한 위치를 이용해 실제 테이블 데이터 조회 |

옵티마이저는 각 방식의 예상 `cost`를 비교해서 가장 저렴하다고 판단한 실행계획을 선택.

<br><br>

## [ 23. 통계정보와 ANALYZE ]

PostgreSQL 옵티마이저는 테이블의 통계정보를 이용하여:

```text
예상 rows
선택도
데이터 분포
```

등을 추정.

통계정보는 `ANALYZE`를 통해 갱신할 수 있음.

```sql
ANALYZE orders;
```

테이블 데이터가 크게 변경되었는데 통계가 오래된 경우:

```text
예상 rows
≠
actual rows
```

차이가 커질 수 있음.

이 경우 옵티마이저가 비효율적인 실행계획을 선택할 가능성도 있음.

<br><br>

## [ 24. 예상 rows와 actual rows 비교 ]

`EXPLAIN ANALYZE`를 사용하면 옵티마이저의 예상값과 실제 결과를 비교할 수 있음.

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 100;
```

예:

```text
rows=60
actual rows=48
```

의미:

```text
예상 반환 행 수 = 60
실제 반환 행 수 = 48
```

두 값이 비슷하다면 옵티마이저가 데이터 분포를 비교적 정확하게 추정한 것.

차이가 매우 크다면 통계정보나 데이터 분포 등을 확인해볼 필요가 있음.

<br><br>

## [ 25. 인덱스 성능은 EXPLAIN ANALYZE로 확인 ]

인덱스를 만들었다고 성능이 좋아졌다고 바로 판단하면 안 됨.

### 인덱스 생성 전

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 100;
```

### 인덱스 생성

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

### 인덱스 생성 후

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 100;
```

비교할 항목:

| 항목 | 확인 내용 |
|---|---|
| Scan 방식 | `Seq Scan` → `Index Scan` 등으로 변경되었는지 |
| `cost` | 옵티마이저 예상 비용 |
| `rows` | 예상 반환 행 수 |
| `actual rows` | 실제 반환 행 수 |
| `Buffers` | 읽은 데이터 블록 |
| `Execution Time` | 실제 전체 실행 시간 |

## [ 26. 선택도와 카디널리티 핵심 관계 ]

```text
카디널리티 높음
        ↓
서로 다른 값이 많음
        ↓
특정 값 조회 시 적은 행 반환
        ↓
선택도 낮아질 가능성
        ↓
인덱스 활용에 유리
```

하지만 카디널리티가 높다고 항상 인덱스가 효과적인 것은 아님.

실제 인덱스 사용 여부는:

```text
카디널리티
선택도
테이블 크기
데이터 분포
조회 패턴
쓰기 빈도
옵티마이저 비용
```

등을 종합해서 결정.
