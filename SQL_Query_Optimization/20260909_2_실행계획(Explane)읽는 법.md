# **[ 1. EXPLAIN / EXPLAIN ANALYZE 차이 ]**

## 1-1 ) EXPLAIN

- 쿼리를 어떻게 실행할지 계획만 확인

#### [ sql ] **EXPLAIN**
```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 100;
```

#### [Result]
```text
Gather  (cost=1000.00..7374.39 rows=6 width=32)
  Workers Planned: 2
  ->  Parallel Seq Scan on orders  (cost=0.00..6373.79 rows=2 width=32)
        Filter: (customer_id = 100)
```

<br>

## 1-2 )  EXPLAIN ANALYZE

- 쿼리를 실제로 실행하고 실제 결과까지 확인

#### [ sql ] **EXPLAIN ANALYZE** 

```sql
EXPLAIN ANALYZE 
SELECT *
FROM orders
WHERE customer_id = 100;
```

#### [Result]
```text
Gather  (cost=1000.00..7374.39 rows=6 width=32) (actual time=70.576..362.337 rows=6.00 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared hit=2048 read=1683 dirtied=3677
  ->  Parallel Seq Scan on orders  (cost=0.00..6373.79 rows=2 width=32) (actual time=104.996..311.427 rows=2.00 loops=3)
        Filter: (customer_id = 100)
        Rows Removed by Filter: 166665
        Buffers: shared hit=2048 read=1683 dirtied=3677
Planning Time: 0.141 ms
Execution Time: 362.376 ms
```

- `actual time`과 `actualrows`가 추가되어 실제 실행 결과와 옵티마이저의 예상을 비교할 수 있다.

- `cost` : 실제 실행시간(ms)이 아닌 옵티마이저의 상대적인 비용 값이다.




#### [ EXPLAIN / EXPLAIN ANALYZE 차이 ]
||EXPLAIN|EXPLAIN ANALYZE|
|---|---|---|
|실제 실행 여부|X|O|
|실행 결과|옵티마이저가 세운 계획|예상치, 실제소요시간, 실제 처리된 행 수|

# **[ 2. 스캔 방식 읽기: Full Scan, Index Scan, Index Only Scan ]**

> ## 2-1 ) Seq_Scan

- 조건에 대한 결과를 찾기 위해 모든 데이터를 확인하며 데이터를 읽는 방식

- 테이블을 순차적으로 읽으면서 조건에 맞는 데이터를 찾는다.

```text
Seq Scan on customers  (cost=0.00..4192.00 rows=1 width=102)
  Filter: (customer_id = 100)
```

- 결과값에 Seq Scan이 표시됨

<br>

> ## 2-2 ) Index Scan

-  인덱스를 참고해 필요한 행 위치를 찾은 뒤 해당 행을 읽는 방식

```text
Index Scan using idx_customers_customer_id on customers
  (cost=0.29..8.31 rows=1 width=80)
  Index Cond: (customer_id = 100)
```
- 결과값에 Index Scan이 표시됨

<br>

> ## 2-3 ) Index Only Scan

- 필요한 컬럼이 모두 인덱스에 포함되어 있고 SQL이 테이블을 추가로 확인할 필요가 없을때 선택될 수 있다.

- 인덱스에 포함된 정보만으로 결과를 낼 수 있어 테이블에 접근하지 않고 인덱스만 읽는 효율적인 방식

> **주의**   
> 인덱스가 있다고 해서 항상 `Index Scan`이 선택되는 것은 아니다.   
> 전체 데이터 중 많은 행을 조회해야 한다면 옵티마이저가 오히려 `Seq Scan`이 더 효율적이라고 판단할 수도 있다.

#### [ Scan 방식 차이 ]
|스캔 방식|	데이터 접근 범위|	유리한 상황|
|---|---|---|
|`Seq Scan`<br>(Full Scan)|	테이블 전체|	조회 대상 행이 전체의 상당 비율을 차지할 때|
|`Index Scan`|	인덱스로 위치를 찾은 후 테이블 접근|	조회 대상 행이 소수 (확인 필요한 행)이고 인덱스가 있을 때
|`Index Only Scan`|	필요한 데이터를 주로 인덱스에서 조회|	필요한 컬럼이 모두 인덱스에 포함되어 있을 때

# **[ 3. 비용(cost)과 예상 행 수(rows) 읽는 법 ]**

```text
Gather  (cost=1000.00..7374.39 rows=6 width=32) (actual time=70.576..362.337 rows=6.00 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared hit=2048 read=1683 dirtied=3677
  ->  Parallel Seq Scan on orders  (cost=0.00..6373.79 rows=2 width=32) (actual time=104.996..311.427 rows=2.00 loops=3)
        Filter: (customer_id = 100)
        Rows Removed by Filter: 166665
        Buffers: shared hit=2048 read=1683 dirtied=3677
Planning Time: 0.141 ms
Execution Time: 362.376 ms
```

#### [ EXPLAIN ANALYZE 해석 ]

| 반환 결과 | 설명 |
|---|---|
| `cost=시작비용..총비용` | 옵티마이저가 예상한 상대적인 실행 비용 |
| `rows` | 옵티마이저가 예상한 반환 행 수 |
| `width` | 한 행의 예상 평균 크기(Byte) |
| `actual time=시작시간..종료시간` | 해당 실행 단계가 실제로 시작되고 결과를 반환하기까지 걸린 시간(ms) |
| `actual rows` | 실제로 해당 실행 단계에서 반환된 행 수 |
| `loops` | 해당 실행 단계가 반복 수행된 횟수 |
| `Rows Removed by Filter` | `WHERE` 등의 필터 조건을 만족하지 못해 제거된 행 수 |
| `Filter` | 데이터에 적용된 필터 조건 |
| `Index Cond` | 인덱스를 이용해 데이터를 찾을 때 사용한 조건 |
| `Buffers: shared hit` | 메모리의 공유 버퍼에서 읽은 블록 수 |
| `Buffers: shared read` | 디스크에서 실제로 읽어 공유 버퍼에 올린 블록 수 |
| `Planning Time` | 옵티마이저가 실행 계획을 만드는 데 걸린 시간 |
| `Execution Time` | 쿼리 전체가 실제로 실행되는 데 걸린 총 시간 |
| `Workers Planned` | 옵티마이저가 계획한 병렬 Worker 수 |
| `Workers Launched` | 실제 실행에 사용된 병렬 Worker 수 |

- rows와 actual rows가 다르면 통계정보가 현재 데이터의 분포를 충분히 확인하는지 확인해볼 수 있다.

# [ 4. 실행계획 트리 읽는 순서 ]


#### [ sql : code ]
```sql
-- 영업팀과 고객관리팀의 데이터를 이용해 하나의 보고서를 만든다.
-- 먼저 각 부서의 데이터를 가져온 뒤, 두 데이터의 고객 번호를 기준으로 연결해야한다.

EXPLAIN
SELECT
    o.order_id,
    c.first_name,
    c.last_name
FROM orders o
JOIN customers c
    ON o.customer_id = c.customer_id;
```

#### [Result]
```text
Hash Join  (cost=5192.00..20859.92 rows=503744 width=18)
  Hash Cond: (o.customer_id = c.customer_id)
  ->  Seq Scan on orders o  (cost=0.00..8741.44 rows=503744 width=8)
  ->  Hash  (cost=3942.00..3942.00 rows=100000 width=18)
        ->  Seq Scan on customers c  (cost=0.00..3942.00 rows=100000 width=18)
```

- 위에서부터 해석하면 실제 데이터 처리 흐름을 이해하기 어렵다.

- 가장 안쪽부터 해석해야한다.

### **해석 순서 흐름**
> 1. Seq Scan on customers c
  - `customers` 테이블을 순차적으로 읽는다.

> 2. Hash
  - `customer_id`를 기준으로 조인에 사용할 해시 구조를 만든다.

> 3. Seq Scan on orders o
  -  다른쪽에서는 `orders` 테이블을 순차적으로 읽는다.

> 4.  Hash Join   
      Hash Cond: (o.customer_id = c.customer_id)
  - 마지막으로 `orders`의 `customer_id`와 `customers`의 `customer_id`를 비교하여 두 테이블의 데이터를 연결한다.

```
  간단하게 표현하면  
  
  customers → Seq Scan → Hash ──┐  
                                ├─→ Hash Join  
  orders    → Seq Scan ─────────┘

  와 같다.
```

- 실행계획에서는 아래쪽의 스캔 작업부터 확인한 뒤, 그 결과가 어떤 상위 노드로 전달되는지 따라가며 읽으면 된다.
