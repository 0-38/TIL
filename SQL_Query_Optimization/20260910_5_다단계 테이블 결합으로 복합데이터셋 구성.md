# **3개 이상 테이블 다단계 JOIN**

# **1. 다단계 JOIN이란?**

> **3개 이상의 테이블을 관계에 따라 연결하여 하나의 결과를 만드는 것**.

예:

```text
customers
    ↓ customer_id
orders
    ↓ order_id
order_items
    ↓ product_id
products
```

각 테이블에 필요한 정보가 나누어져 있기 때문에 연결 Key를 따라 JOIN.

```sql
SELECT
    o.order_id,
    c.first_name,
    c.last_name,
    p.product_name,
    oi.quantity
FROM orders o
JOIN customers c
    ON c.customer_id = o.customer_id
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id;
```

<br><br>

---

# **2. 다단계 JOIN 설계 순서**

여러 테이블을 바로 JOIN하지 말고 다음 순서로 설계.

```text
1. 최종 결과의 기준 단위 결정
        ↓
2. 필요한 컬럼 확인
        ↓
3. 컬럼이 있는 테이블 확인
        ↓
4. 테이블 간 관계 확인
        ↓
5. JOIN Key 확인
        ↓
6. INNER / LEFT JOIN 선택
        ↓
7. 필터 조건 배치
        ↓
8. 결과 검증
```

### 결과의 기준 단위 `Grain`

먼저 **결과 한 행이 무엇을 의미하는지** 결정.

예:

```text
주문 1건당 한 행
상품 1개당 한 행
고객 1명당 한 행
주문 상품 1개당 한 행
```

이 기준을 `Grain`이라고 볼 수 있음.

다단계 JOIN에서 매우 중요한 개념.

# **3. 필요한 컬럼과 테이블 확인**

예:

| 필요한 정보 | 테이블 |
|---|---|
| 주문 번호 | `orders` |
| 고객 이름 | `customers` |
| 상품 수량 | `order_items` |
| 상품명 | `products` |

JOIN을 작성하기 전에 **어떤 정보가 어느 테이블에 있는지 먼저 확인**.

<br><br>

# **4. JOIN Key 확인**

테이블 사이를 연결하는 Key 확인.

| 기준 테이블 | 연결 테이블 | JOIN Key |
|---|---|---|
| `customers` | `orders` | `customer_id` |
| `orders` | `order_items` | `order_id` |
| `orders` | `staffs` | `staff_id` |
| `order_items` | `products` | `product_id` |
| `products` | `stocks` | `product_id` |

보통 `PK`와 `FK` 관계를 따라 JOIN.

# **5. 테이블 관계 이해하기**

JOIN 전에는 테이블 관계를 확인해야 함.

### 1:1 관계

한 행이 상대 테이블의 한 행과 연결.

```text
A (1) ───── (1) B
```

### 1:N 관계

한 행이 상대 테이블의 여러 행과 연결.

```text
customers (1) ───── (N) orders
```

예:

```text
고객 A
 ├── 주문 1
 ├── 주문 2
 └── 주문 3
```

JOIN하면 고객 A가 3행으로 나타날 수 있음.

### N:M 관계

양쪽 데이터가 서로 여러 행과 연결.

일반적으로 중간 테이블 사용.

```text
orders
   ↓
order_items
   ↓
products
```

`order_items`가 주문과 상품을 연결하는 중간 테이블 역할.

<br><br>

# **6. JOIN 후 행이 증가하는 이유**

JOIN 후 행이 많아졌다고 해서 무조건 중복 오류는 아님.

예:

```text
orders

order_id
--------
1
```

해당 주문에 상품이 3개라면:

```text
order_items

order_id | product_id
---------|-----------
1        | 10
1        | 20
1        | 30
```

JOIN 결과:

```text
order_id | product_id
---------|-----------
1        | 10
1        | 20
1        | 30
```

즉:

```text
주문 1행
   ↓ 1:N JOIN
주문 상품 3행
```

정상적인 행 증가.

# **7. INNER JOIN**

`INNER JOIN`은 **양쪽 테이블에서 JOIN 조건을 만족하는 데이터만 반환**.

```sql
SELECT
    o.order_id,
    c.first_name
FROM orders o
JOIN customers c
    ON c.customer_id = o.customer_id;
```

구조:

```text
customers      orders
    A  ───────  A
    B  ───────  B
    C           X

결과
A
B
```

매칭되지 않는 데이터는 제외.

<br><br>

---

# **8. LEFT JOIN**

`LEFT JOIN`은 **왼쪽 테이블의 모든 데이터를 유지**.

```sql
SELECT
    c.customer_id,
    c.first_name,
    o.order_id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id;
```

주문이 없는 고객:

```text
customer_id | order_id
------------|---------
1           | 100
2           | 101
3           | NULL
```

오른쪽 테이블에 매칭 데이터가 없으면 `NULL`.

### 사용 예

```text
전체 고객 유지
전체 상품 유지
전체 직원 유지
```

하면서 연결된 정보가 있을 때만 추가하고 싶은 경우.

<br><br>

---

# **9. JOIN 종류 비교**

| JOIN | 설명 |
|---|---|
| `INNER JOIN` | 양쪽에 모두 존재하는 데이터만 반환 |
| `LEFT JOIN` | 왼쪽 데이터를 모두 유지 |
| `RIGHT JOIN` | 오른쪽 데이터를 모두 유지 |
| `FULL JOIN` | 양쪽 데이터를 모두 유지 |

실무에서는 `INNER JOIN`, `LEFT JOIN`을 자주 사용.

# **10. ON과 WHERE의 차이**

### ON

```text
어떤 데이터를 연결할 것인가?
```

### WHERE

```text
JOIN이 끝난 결과에서 어떤 행을 남길 것인가?
```

특히 `LEFT JOIN`에서는 조건 위치가 중요.

<br><br>

---

# **11. LEFT JOIN에서 WHERE 조건**

```sql
SELECT
    c.customer_id,
    o.order_id,
    o.store_id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
WHERE o.store_id = 1;
```

과정:

```text
모든 고객 LEFT JOIN
        ↓
JOIN 결과 생성
        ↓
WHERE store_id = 1
        ↓
NULL 데이터 제거
```

결과적으로 **1번 매장 주문이 있는 고객만 남음**.

`LEFT JOIN`을 사용했어도 오른쪽 테이블 조건을 `WHERE`에 작성하면 매칭되지 않은 행이 제거될 수 있음.

<br><br>

---

# **12. LEFT JOIN에서 ON 조건**

```sql
SELECT
    c.customer_id,
    o.order_id,
    o.store_id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
   AND o.store_id = 1;
```

과정:

```text
모든 고객 유지
        ↓
1번 매장 주문만 연결
        ↓
1번 매장 주문 없음 → NULL
```

1번 매장 주문이 없는 고객도 결과에 유지.

<br><br>

---

# **13. ON vs WHERE 핵심 비교**

| 조건 위치 | 의미 |
|---|---|
| `ON` | 어떤 행끼리 연결할지 결정 |
| `WHERE` | JOIN 후 어떤 행을 남길지 결정 |

특히:

```text
LEFT JOIN + 오른쪽 테이블 조건
```

에서는 주의.

```text
ON
→ 왼쪽 데이터 유지

WHERE
→ NULL 행이 제거될 수 있음
```

<br><br>

---

# **14. 매칭되지 않는 데이터 찾기**

`LEFT JOIN + IS NULL`을 이용하면 상대 테이블과 연결되지 않는 데이터 확인 가능.

예: 주문이 없는 고객 찾기.

```sql
SELECT
    c.customer_id,
    c.first_name,
    c.last_name
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

의미:

```text
customers에는 존재
        +
orders에는 존재하지 않음
```

이런 형태를 **Anti Join 패턴**이라고 볼 수 있음.

# **15. JOIN 결과 행 수 검증**

다단계 JOIN 후에는 결과를 바로 믿기보다 행 수 확인.

### JOIN 전

```sql
SELECT COUNT(*)
FROM orders;
```

### JOIN 후

```sql
SELECT COUNT(*)
FROM orders o
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id;
```

예:

```text
JOIN 전       500,000행
JOIN 후     1,539,911행
```

행이 증가했다면 테이블 관계 확인.

```text
orders 1
   ↓
order_items N
```

1:N 관계라면 정상적인 증가일 수 있음.

<br><br>

# **16. 특정 Key의 중복 확인**

```sql
SELECT
    o.order_id,
    COUNT(*) AS row_count
FROM orders o
JOIN order_items oi
    ON oi.order_id = o.order_id
GROUP BY o.order_id
HAVING COUNT(*) > 1
ORDER BY row_count DESC;
```

`HAVING COUNT(*) > 1`을 이용하면 JOIN 후 한 Key가 여러 행으로 확장되었는지 확인 가능.

하지만 여러 행이 나온다고 무조건 오류는 아님.

```text
1:N 관계
→ 정상적인 행 증가 가능
```

# **17. 잘못된 JOIN 조건**

관계없는 컬럼을 JOIN하면 잘못된 결과가 발생할 수 있음.

잘못된 예:

```sql
SELECT *
FROM orders o
JOIN order_items oi
    ON o.customer_id = oi.product_id;
```

올바른 예:

```sql
SELECT *
FROM orders o
JOIN order_items oi
    ON o.order_id = oi.order_id;
```

JOIN 전 반드시:

```text
PK
FK
테이블 관계
```

확인.

# **18. Cartesian Product**

테이블 사이의 올바른 연결 조건이 없으면 행 수가 크게 증가할 수 있음.

```sql
SELECT *
FROM customers
CROSS JOIN orders;
```

예:

```text
customers = 100행
orders    = 1,000행

100 × 1,000
= 100,000행
```

예상보다 결과 행이 지나치게 많다면 JOIN 조건부터 확인.

<br><br>

---

# **19. N:M JOIN의 행 증가**

두 테이블에 JOIN Key가 각각 여러 번 존재하면 행 수가 곱해질 수 있음.

A:

```text
id
--
1
1
1
```

B:

```text
id
--
1
1
```

JOIN:

```sql
SELECT *
FROM A
JOIN B
    ON A.id = B.id;
```

결과:

```text
3 × 2 = 6행
```

N:M 관계에서는 예상보다 많은 행이 생성될 수 있으므로 주의.

# **20. JOIN 전 중복 Key 확인**

JOIN 결과가 예상보다 많다면 각 테이블의 Key 중복 확인.

```sql
SELECT
    customer_id,
    COUNT(*)
FROM customers
GROUP BY customer_id
HAVING COUNT(*) > 1;
```

```sql
SELECT
    order_id,
    COUNT(*)
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

PK라고 생각한 컬럼에 실제 중복이 있는지도 확인.

# **21. JOIN 전에 집계하기**

상세 데이터를 그대로 JOIN하면 행이 크게 증가할 수 있음.

주문별 총 수량만 필요하다면 먼저 집계.

```sql
SELECT
    o.order_id,
    oi.total_quantity
FROM orders o
JOIN (
    SELECT
        order_id,
        SUM(quantity) AS total_quantity
    FROM order_items
    GROUP BY order_id
) oi
    ON oi.order_id = o.order_id;
```

과정:

```text
order_items 상세 데이터
        ↓
order_id 기준 집계
        ↓
주문당 1행
        ↓
orders와 JOIN
```

불필요한 행 증가를 줄일 수 있음.

<br><br>

# **22. COUNT(*)와 COUNT(column)**

`LEFT JOIN` 결과를 집계할 때 주의.

```sql
SELECT
    c.customer_id,
    COUNT(*) AS cnt
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
GROUP BY c.customer_id;
```

`COUNT(*)`는 결과 행 자체를 계산.

따라서 주문이 없는 고객도 한 행이 존재하므로 `1`이 될 수 있음.

주문 수를 세려면:

```sql
SELECT
    c.customer_id,
    COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
GROUP BY c.customer_id;
```

차이:

```text
COUNT(*)          → 결과 행 수 계산
COUNT(column)     → NULL을 제외하고 계산
```

# **23. JOIN과 NULL 처리**

`LEFT JOIN`에서는 매칭되지 않은 오른쪽 데이터가 `NULL`.

```text
customer_id | order_id
------------|---------
1           | 100
2           | NULL
```

필요하면 `COALESCE()`를 이용해 다른 값으로 변경 가능.

```sql
SELECT
    c.customer_id,
    COALESCE(o.order_id::text, '주문 없음') AS order_info
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.customer_id;
```

# **24. EXISTS**

상대 테이블의 데이터를 가져올 필요 없이 **존재 여부만 확인**하려면 `EXISTS` 사용 가능.

예: 주문 경험이 있는 고객.

```sql
SELECT
    c.customer_id,
    c.first_name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

의미:

```text
해당 고객의 주문이 하나라도 존재하는가?
```

JOIN처럼 주문 개수만큼 고객 행이 증가하지 않음.

<br><br>

---

# **25. NOT EXISTS**

연결된 데이터가 없는 행 검색.

예: 주문이 없는 고객.

```sql
SELECT
    c.customer_id,
    c.first_name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);
```

다음과 비슷한 목적:

```sql
LEFT JOIN orders o
    ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

# **26. JOIN Key와 인덱스**

큰 테이블을 자주 JOIN한다면 JOIN Key의 인덱스도 고려.

```sql
SELECT *
FROM orders o
JOIN order_items oi
    ON oi.order_id = o.order_id;
```

`order_items.order_id`를 자주 사용한다면:

```sql
CREATE INDEX idx_order_items_order_id
ON order_items (order_id);
```

인덱스는 JOIN 탐색 성능에 도움을 줄 수 있음.

하지만:

```text
인덱스 존재
≠
무조건 인덱스 사용
```

옵티마이저가 비용을 비교해 결정.

> PostgreSQL에서는 `PRIMARY KEY`, `UNIQUE`에는 인덱스가 생성되지만 외래키 컬럼에는 자동으로 인덱스가 생성되지 않음.

자주 JOIN되는 FK 컬럼은 인덱스 필요 여부를 따로 검토.

# **27. JOIN 실행계획 확인**

JOIN 성능은 `EXPLAIN ANALYZE`로 확인.

```sql
EXPLAIN ANALYZE
SELECT
    o.order_id,
    p.product_name
FROM orders o
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id;
```

PostgreSQL의 대표적인 JOIN 방식:

| JOIN 방식 | 특징 |
|---|---|
| `Nested Loop` | 한 테이블의 각 행에 대해 다른 테이블 탐색 |
| `Hash Join` | Hash 구조를 만들어 JOIN Key 비교 |
| `Merge Join` | 정렬된 두 데이터를 순서대로 비교 |

<br><br>

---

# **28. Nested Loop**

개념:

```text
Table A
  ↓
A의 한 행
  ↓
Table B에서 매칭 데이터 검색
  ↓
다음 A 행
```

한쪽 결과가 작거나 다른 테이블에서 인덱스를 효율적으로 사용할 수 있을 때 유리할 수 있음.

실행계획 예:

```text
Nested Loop
    ↓
Index Scan
```

<br><br>

# **29. Hash Join**

JOIN Key를 기준으로 Hash 구조를 만들어 비교.

```text
Table A
   ↓
Hash 생성

Table B
   ↓
Hash 값 비교
   ↓
JOIN
```

많은 데이터를 `=` 조건으로 JOIN할 때 사용될 수 있음.

```sql
ON a.customer_id = b.customer_id
```

실행계획 예:

```text
Hash Join
  Hash Cond: (...)
```

<br><br>

# **30. Merge Join**

두 입력이 JOIN Key 기준으로 정렬되어 있을 때 순서대로 비교.

```text
A : 1 2 3 4 5
B : 1 2 4 5 7
        ↓
   순서대로 비교
```

정렬된 대량 데이터를 처리할 때 사용될 수 있음.

```text
Merge Join
  Merge Cond: (...)
```

# **31. SQL의 JOIN 순서와 실제 실행 순서**

SQL을 다음처럼 작성해도:

```sql
FROM A
JOIN B
JOIN C
JOIN D
```

PostgreSQL이 반드시:

```text
A → B → C → D
```

순서대로 처리하는 것은 아님.

옵티마이저가 비용을 계산하여 더 효율적인 JOIN 순서를 선택할 수 있음.

```text
SQL 작성 순서
≠
실제 실행 순서
```

실제 순서는 `EXPLAIN`, `EXPLAIN ANALYZE`로 확인.

# **32. SELECT * 사용 주의**

다단계 JOIN에서는 여러 테이블의 컬럼이 합쳐지므로 `SELECT *` 사용 시 불필요한 데이터가 많아질 수 있음.

```sql
SELECT *
FROM orders o
JOIN customers c
    ON c.customer_id = o.customer_id
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id;
```

필요한 컬럼만 조회하는 것이 좋음.

```sql
SELECT
    o.order_id,
    c.customer_id,
    p.product_name,
    oi.quantity
FROM orders o
JOIN customers c
    ON c.customer_id = o.customer_id
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id;
```

장점:

```text
불필요한 데이터 감소
가독성 향상
컬럼 이름 충돌 방지
결과 확인 용이
```

# **33. Alias 사용**

여러 테이블 JOIN 시 Alias를 사용하면 SQL이 간결해짐.

```sql
FROM customers c
JOIN orders o
    ON o.customer_id = c.customer_id
JOIN order_items oi
    ON oi.order_id = o.order_id
JOIN products p
    ON p.product_id = oi.product_id
```

예:

```text
customers   → c
orders      → o
order_items → oi
products    → p
staffs      → s
stocks      → st
```

# **34. 다단계 JOIN 검증 체크리스트**

| 확인 항목 | 내용 |
|---|---|
| 결과 기준 | 한 행이 무엇을 의미하는가 |
| JOIN Key | 올바른 PK/FK를 연결했는가 |
| 관계 | 1:1 / 1:N / N:M 중 무엇인가 |
| JOIN 종류 | INNER / LEFT가 요구사항에 맞는가 |
| 행 수 | JOIN 전후 행 수가 예상과 맞는가 |
| 중복 | 정상적인 1:N 증가인지 잘못된 중복인지 |
| NULL | 매칭되지 않은 데이터가 정상적인가 |
| 필터 위치 | `ON`과 `WHERE` 위치가 맞는가 |
| 인덱스 | JOIN Key에 필요한 인덱스가 있는가 |
| 실행계획 | `EXPLAIN ANALYZE` 결과가 적절한가 |

<br><br>

# **35. 다단계 JOIN 작성 흐름**

```text
① 결과 한 행의 기준은 무엇인가?
        ↓
② 어떤 컬럼이 필요한가?
        ↓
③ 각 컬럼은 어느 테이블에 있는가?
        ↓
④ 테이블은 어떤 Key로 연결되는가?
        ↓
⑤ 1:1 / 1:N / N:M 중 어떤 관계인가?
        ↓
⑥ 데이터가 없어도 기준 행을 유지해야 하는가?
        ↓
   YES → LEFT JOIN
   NO  → INNER JOIN
        ↓
⑦ 필터를 ON에 둘지 WHERE에 둘지 결정
        ↓
⑧ COUNT로 행 수 확인
        ↓
⑨ 중복 및 NULL 검증
        ↓
⑩ EXPLAIN ANALYZE로 성능 확인
```

# 핵심 정리

- 다단계 JOIN은 **필요한 컬럼 → 테이블 → 관계 → JOIN Key** 순서로 설계.
- 가장 먼저 **결과 한 행의 기준(Grain)** 을 정하는 것이 중요.
- JOIN은 정확한 `PK`, `FK` 관계를 이용.
- `1:N` 관계에서는 JOIN 후 행이 증가하는 것이 정상일 수 있음.
- `N:M` 관계에서는 행 수가 곱해져 크게 증가할 수 있음.
- `INNER JOIN`은 양쪽에서 매칭되는 데이터만 반환.
- `LEFT JOIN`은 왼쪽 데이터를 모두 유지하고 매칭되지 않으면 `NULL`.
- `ON`은 **어떤 데이터를 연결할지**, `WHERE`는 **JOIN 후 어떤 데이터를 남길지** 결정.
- `LEFT JOIN`에서 오른쪽 테이블 조건을 `WHERE`에 작성하면 `NULL` 행이 제거될 수 있음.
- `LEFT JOIN + IS NULL` 또는 `NOT EXISTS`로 매칭되지 않는 데이터를 찾을 수 있음.
- 존재 여부만 확인하려면 `EXISTS` 사용 가능.
- 상세 데이터가 필요하지 않다면 먼저 `GROUP BY`로 집계한 후 JOIN하는 방법도 고려.
- `LEFT JOIN` 집계에서는 `COUNT(*)`와 `COUNT(column)` 차이에 주의.
- 큰 테이블을 자주 JOIN한다면 JOIN Key의 인덱스를 검토.
- PostgreSQL의 주요 JOIN 방식은 `Nested Loop`, `Hash Join`, `Merge Join`.
- SQL에 작성한 JOIN 순서와 실제 실행 순서는 다를 수 있음.
- JOIN 결과는 반드시 **행 수, 중복, NULL, 실행계획**을 확인하여 검증.
